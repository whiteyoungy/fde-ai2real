# 第 5 章 · 中国现场的三个硬约束

> **档位：5.1 全档必读 · 5.2／5.3 重档**
> 5.1 节讲协议不兼容——**这一节不分档位，谁想接国产模型都会撞上。**
> 5.2、5.3 节讲内网和国产操作系统上的坑，没有这类现场可以跳过。

## 配了一下午没配通的 base_url

某团队接了个政务项目，要求用国产大模型。
他们看到 Codex 支持自定义 `model_providers`，觉得这事很简单：
把 `base_url` 指向国产模型的 OpenAI 兼容端点就行了。

配了一下午没通。报错信息里写着一句：

> `` `wire_api = "chat"` is no longer supported. ``
> `` How to fix: set `wire_api = "responses"` in your provider config. ``

改成 `responses` 之后，端点那边返回 404——因为对方根本没有 `/v1/responses` 这个路径。

**这不是配置错误，是协议不兼容。** 这一章讲三个这类硬约束，
以及每一个的现实出路。

## 5.1 第一个约束：协议对不上（最大的坑）

### 事实

Codex 的模型提供方配置长这样 [14]：

```toml
[model_providers.my_provider]
base_url = "https://api.example.com/v1"
env_key  = "MY_API_KEY"
wire_api = "responses"
```

`wire_api` 现在**只有 `responses` 一个合法值**。
源码里对 `chat` 的处理是直接报错并给出迁移提示 [9]：

```rust
const CHAT_WIRE_API_REMOVED_ERROR: &str =
    "`wire_api = \"chat\"` is no longer supported.\n\
     How to fix: set `wire_api = \"responses\"` in your provider config.";
```

### 为什么这在中国是个大问题

国产大模型对外提供的“OpenAI 兼容接口”，
绝大多数指的是 **Chat Completions**（`POST /v1/chat/completions`）。
Responses 是 OpenAI 后来推出的另一套协议，请求体和事件流都不一样。

也就是说：**“OpenAI 兼容”这四个字在这里不成立。**

这一条最好在第 2 关定界阶段就摆到桌面上。它属于最典型的那类定界失守：
**甲方以为兼容，乙方以为兼容，双方都没验，直到进场那天。**

### 三条出路

**出路一：加一层协议转换代理。**

自己起一个服务，对外说 Responses，对内翻译成 Chat Completions。
工作量不大（主要是流式事件的映射），但要自己维护，
而且模型能力对不齐的地方（工具调用格式、推理内容字段）要逐个填。

Codex 自己带了一个协议代理的样板可以参考——
`codex-responses-api-proxy`，它做的是严格转发：
只放行 `POST /v1/responses`，其余一律 `403`，并注入鉴权头 [7]。

```toml
# 你的转换代理跑起来之后，Codex 这边这么配
[model_providers.gateway]
name     = "内网模型网关"
base_url = "http://10.0.0.8:8080/v1"
wire_api = "responses"

[profiles.内网]
model_provider = "gateway"
```

```bash
codex -p 内网
```

> `codex-responses-api-proxy` 还有一个设计值得学：
> **它由特权用户启动、从 stdin 读密钥**，
> 这样非特权用户既看不到也改不了这个密钥 [7]：
>
> ```shell
> printenv OPENAI_API_KEY | env -u OPENAI_API_KEY \
>   codex-responses-api-proxy --http-shutdown --server-info /tmp/server-info.json
> ```
>
> 在多人共用一台跳板机的现场，这个模式可以直接抄。

**出路二：用本地模型。**

Codex 内置了 `ollama` 和 `lmstudio` 两个提供方 [9]，
交互模式下有 `--oss` 开关走这条路。

但要注意：**内置的这两个提供方同样走 Responses 协议** [9]。
所以本地模型服务也得能说 Responses，不是随便起个 Ollama 就行。
**上线前必须实测，不要按文档推断。**

**出路三：不用它做模型接入，只用它做 harness。**

这是**中国现场最现实的一条**。

第 2、3、4 章讲的东西——沙箱、命令白名单、网络策略、
管理员强制配置、钩子、事件留痕——**没有一样依赖具体用哪个模型**。

也就是说，你完全可以：

- 模型接入用你自己的网关 / 客户已有的模型平台
- 只把 Codex 当成“能被审计、能被关笼子”的执行环境

甚至更进一步：**Codex 是 Apache-2.0 的，
你可以只 fork 出 `execpolicy`、`linux-sandbox`、`network-proxy` 这几个 crate，
接到自己的 agent 上。** 这是开源许可证给你的自由，
也是它相对闭源工具最实在的价值。

## 5.2 第二个约束：登录要外网

Codex 的两种登录方式（ChatGPT 账号 / API key）都要能连外网 [10][14]。

物理隔离网现场，两条都不成立。

这跟 5.1 是同一个问题的两面：**5.1 是数据面走不通，5.2 是控制面走不通。**
出路也是同一条——把模型接入这一层整个换掉。

如果走出路一（自建网关），鉴权就变成你自己网关的事，
`env_key` 指向你自己发的密钥即可，不需要 OpenAI 账号。

> 上册第 12 章讲国企、银行、政务交付时列过一张“进场前必问清单”。
> 建议在那张表上补两行：
>
> - **模型服务的协议是 Chat Completions 还是 Responses？**（当场让对方发一份接口文档）
> - **工具本身的登录/激活需不需要外网？**（当场断网试一次）

## 5.3 第三个约束：沙箱在国产 OS 上不一定跑得起来

### 事实

Linux 上的文件系统沙箱默认用 bubblewrap（`bwrap`）[5]。
行为是：

- 优先用 `PATH` 里找到的 `bwrap`
- 找不到就退回 Codex 自带的那份，并打一条**启动警告**
- 如果 bubblewrap **建不了 user namespace**，同样只打警告
- **WSL1 不支持**，需要沙箱的命令会被直接拒绝
- 老版本 `bwrap`（不支持 `--argv0`）走兼容路径
- 还留了一条 Landlock + mount 的老路径，
  用 `features.use_legacy_landlock = true` 强制启用 [5]

### 为什么这一条要现场验

麒麟、统信这类国产操作系统，
以及很多金融、政务客户的**安全加固基线**，
经常会关掉 unprivileged user namespace（`kernel.unprivileged_userns_clone = 0`
或者 `user.max_user_namespaces = 0`）。

**关掉之后，Codex 只会给你一条警告，不会崩。**
你以为沙箱开着，其实没开——这比直接报错危险得多。

### 进场当天就该跑的三条命令

```bash
# 1. user namespace 能不能建？输出 0 就是被关了
cat /proc/sys/user/max_user_namespaces
sysctl kernel.unprivileged_userns_clone 2>/dev/null   # 有的发行版才有这个键

# 2. bwrap 在不在，什么版本
command -v bwrap && bwrap --version

# 3. 直接试一次真的隔离
bwrap --unshare-all --ro-bind / / --dev /dev echo ok
```

第三条打不出 `ok`，就说明**这台机器上的沙箱是形同虚设的**。

Codex 自己也带了体检命令 [1]：

```bash
codex doctor    # 检查本地安装、配置、鉴权和运行时状态
```

跑一遍，把输出留档。

### 跑不起来怎么办

三个选择，从好到差：

1. **让客户放开 user namespace。** 走变更流程，多半批不下来，但要问。
2. **整体跑在容器里。** 外层用容器做隔离，内层 Codex 用
   `danger-full-access`——注意这时候 `requirements.toml` 里
   要允许这一档，等于把 2.4 节的锁开了一个口子，
   **必须在方案里写清楚“隔离边界从进程级上移到了容器级”**。
3. **降到 `read-only`。** 让它只读只建议，改动由人来做。
   慢，但在高敏感环境里这经常是唯一能过审的方案。

## 5.4 一张决策表

进场前把这张表填了，能省掉很多返工：

| 现场条件 | 能不能用 Codex | 怎么用 |
|---|---|---|
| 能连外网 + 允许用境外模型 | 能，开箱即用 | 照第 2–4 章配 |
| 能连外网 + 只许用国产模型 | 能，要加一层 | 自建 Responses 转换代理 |
| 内网 + 有自建模型平台 | 能，只当 harness 用 | 模型接入自己做，用它的沙箱和留痕 |
| 内网 + 沙箱跑不起来 | 降级用 | 容器隔离，或降到 `read-only` |
| 信创清单里没有它 | **不能** | 但可以 fork 出组件自己编译 |

最后一行值得单独说：**信创清单是白名单制的**。
“开源可自编译”在很多单位是能走特批流程的理由，
但**这条路要在项目立项阶段就走，不能等到交付阶段**。
这正是上册第 13 章那句结论的意思：
**“合规不是上线前的检查项，是立项前的约束条件。等审批卡住才补课，返工的是整个技术方案。”**
