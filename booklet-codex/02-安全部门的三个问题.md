直到甲方信息安全部的人开口，一共问了三个问题：

> “它有没有可能删掉不该删的文件？”

>
> “它执行的每一条命令，谁批的，事后查得到吗？”

## 2.1 第一问：会不会乱删文件

### 答案：沙箱三档，选一档，写进配置

Codex 的沙箱有三种模式 [11]：

| `sandbox_mode` | 它能干什么 | 什么场景用 |
|---|---|---|
| `read-only` | 只能看，不能改，不能跑命令 | 代码审计、方案评估、演示 |
| `workspace-write` | 能改工作区里的文件、能跑本地命令 | **默认，也是绝大多数场景该用的** |
| `danger-full-access` | 没有任何限制 | 一次性容器里，别的地方都不要用 |

配置写在 `~/.codex/config.toml`：

```toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false        # 工具通道默认不联网；显式写出来给评审看
```

也可以在命令行上临时指定：

```bash
codex --sandbox read-only
```

### 它靠什么强制执行

这一条要能说清楚，否则甲方会认为只是“程序自己承诺不乱来” [5][11]：

| 平台 | 强制机制 | 说给甲方听 |
|---|---|---|
| macOS | Apple Seatbelt | 操作系统级沙箱，不是应用层自律 |
| Linux / WSL2 | bubblewrap（命令名 `bwrap`），旧路径用 Landlock + seccomp | 内核级隔离，用的是容器同一套机制 |
| Windows | 原生 Windows Sandbox | 系统自带 |

表里三个名字都是**操作系统自带的隔离机制**，不用你去装：
Seatbelt 是 macOS 的，Landlock 和 seccomp 是 Linux 内核的，
bubblewrap 是 Linux 上一个很小的沙箱工具（Flatpak 这类软件也在用它）。

**关键区别**：这是操作系统在拦，不是 Codex 自己在拦。
即使模型“想”越界，系统调用直接失败。

> **信创现场必查**：Linux 沙箱依赖 `bwrap` 能创建 **user namespace**——
> 这是 Linux 内核的一个功能，让普通用户能建出一个“看起来自己是 root、
> 但实际上碰不到系统”的隔离环境。容器就是靠它。
> 麒麟、统信这类国产 OS 上，这个能力有可能被安全基线关掉。
> Codex 找不到 `bwrap` 时会退回自带的版本并打一条启动警告 [5]；
> 如果是 user namespace 被禁，同样只给警告。
> **这条必须在第 2 关定界阶段现场验，不是上线前才发现。**
> 第 5 章给具体的验证命令。
>
> 另外：WSL1 不支持，Codex 会直接拒绝需要沙箱的命令 [5]。

## 2.2 第二问：会不会往外传数据

### 答案：先分清模型通道和工具通道

“会不会往外传”不能只用一个开关回答。Codex 至少有两个网络平面：

| 网络平面 | 传什么 | 由什么控制 |
|---|---|---|
| 模型通道 | 提示、选入上下文的代码与文件内容、工具结果 | 模型提供方、部署位置、组织数据策略 |
| 工具通道 | shell 命令、包管理器、测试程序主动发起的连接 | 沙箱 `network_access`、网络策略代理与审批 |

`workspace-write` 沙箱默认不给**工具通道**网络访问。要开，得显式开：

```toml
[sandbox_workspace_write]
network_access = true
```

这个设置不会让 Codex 变成本地模型，也不会阻断模型通道。使用外部模型服务时，
上下文仍需发往该服务；全内网交付必须在第 2 关阶段另行确认模型部署与数据边界。

工具通道需要精细放行时，可以使用 Codex 的**网络策略代理**
（`codex-network-proxy`）[4]。它跑一个本地 HTTP 代理（默认 `127.0.0.1:3128`）
和一个 SOCKS5 代理（默认 `127.0.0.1:8081`。SOCKS5 是一种通用代理协议，
HTTP 代理只能转 HTTP，它什么流量都能转），所有出网流量走这里，
按允许/拒绝清单放行。

```toml
default_permissions = "workspace"

[permissions.workspace.network]
enabled = true
proxy_url = "http://127.0.0.1:3128"
enable_socks5 = true
socks_url = "http://127.0.0.1:8081"
mode = "limited"                          # limited = 只读网络访问
allow_upstream_proxy = true               # 尊重企业的 HTTP(S)_PROXY
dangerously_allow_non_loopback_proxy = false   # 不要改成 true
```

两个细节值得单独讲给安全部门：

- `mode = "limited"` 是**只读网络**模式——能拉，不能推。
  这一档很适合“允许查文档、不允许上传代码”的场景。
- `mode = "limited"` 或者配了 MITM 钩子时（MITM 即“中间人”，
  指代理把 HTTPS 拆开看一眼内容再转发，企业上网行为审计普遍这么做），
  代理会自动启用 HTTPS 中间人解密，**CA 私钥只留在代理进程内存里**，
  子进程通过 `$CODEX_HOME/proxy/` 下的只读公开文件拿到 CA 包 [4]。
  也就是说：出网内容是可以被策略检查的，不是黑盒。

> **说给甲方听的版本**：
> “所有出网流量强制经过本地策略代理，可配置白名单，
> 可开启只读模式，HTTPS 内容可检查。代理是开源的，
> 贵方可以自行编译并审计。”

## 2.3 第三问：谁批准它跑这条命令

### 答案：Starlark 写的命令白名单，而且能单元测试

这是三个问题里最容易被糊弄过去的，也是最容易做扎实的。

Codex 有一套独立的执行策略引擎（`execpolicy`），
规则文件用 Starlark 语法（一个不能读写文件、不能联网的 Python 子集）[2][17]。

规则文件放在配置层旁边的 `rules/` 目录里：

- 用户级：`~/.codex/rules/default.rules`
- 项目级：`<仓库>/.codex/rules/*.rules`（项目需被标记为可信）

一条规则长这样 [2]：

```starlark
prefix_rule(
    pattern = ["git", ["status", "log", "diff"]],   # 列表元素表示"任选其一"
    decision = "allow",
    justification = "只读的 git 操作，不改变仓库状态",
    match = ["git status", "git log --oneline"],     # 必须命中这条规则
    not_match = ["git push"],                        # 必须不命中
)

prefix_rule(
    pattern = ["git", "push"],
    decision = "prompt",
    justification = "推送到远端要人工确认",
    match = ["git push origin main"],
)

prefix_rule(
    pattern = [["rm", "shred"], "-rf"],
    decision = "forbidden",
    justification = "禁止递归强删。需要清理请用 `git clean -n` 先预览。",
    match = ["rm -rf build"],
)
```

三个 `decision` 取值：`allow`（放行）、`prompt`（问人）、`forbidden`（禁止）。
多条规则同时命中时，**最严的那条赢**：`forbidden` > `prompt` > `allow` [17]。

### 三件事让这套东西比“写在文档里的规范”强

**第一，规则自带单元测试。** `match` / `not_match` 里的例子在加载规则时就会验证 [2]。
写错的规则加载不进去，不会等到出事才发现。

**第二，可以离线验证。** 交付前把规则文件和一批命令跑一遍：

```bash
codex execpolicy check --rules .codex/rules/project.rules -- git push origin main
```

输出是 JSON，可以直接接进 CI，作为交付验收的一项。

**第三，`justification` 字段会被显示出来。** 被拒绝的时候，
使用者看到的不是“操作被禁止”，而是你写的那句
“禁止递归强删。需要清理请用 `git clean -n` 先预览。”

> 这两件事——**判据要能自动跑，拒绝的理由要写给人看**——
> 正是上册第 8 章第 4 关验收在强调的。这套规则文件两条都占了。

### 复合命令怎么处理

`a && b`、`a | b`、`a; b` 这类简单串联，
只要里面没有变量、通配符、重定向、命令替换，
Codex 会拆开逐条判 [17]。有重定向或替换的复杂脚本，整条当成一次调用来判。

**这意味着**：不要指望用一条规则拦住所有包了一层 `bash -c` 的东西。
真正的兜底是沙箱（2.1），不是白名单。白名单是第二道，不是第一道。

## 2.4 把三个答案锁死：管理员强制配置

前面三节的配置，用户自己都能改回去。
真正能写进方案、能过审计的，是**管理员强制层** [15]。

Codex 有两个管理员控制的文件：

| 文件 | 作用 | 用户能不能覆盖 |
|---|---|---|
| `requirements.toml` | **硬约束** | **不能** |
| `managed_config.toml` | 默认值 | 能，但下次启动会重新应用 |

路径 [15]：

```
Linux / macOS：   /etc/codex/requirements.toml
                  /etc/codex/managed_config.toml
Windows：         %ProgramData%\OpenAI\Codex\requirements.toml
macOS MDM：       com.openai.codex:requirements_toml_base64
                  （MDM = 移动设备管理，公司统一给员工电脑下发配置的那套系统）
```

一份可以直接抄的 `requirements.toml`：

```toml
# 只允许这两档沙箱，禁掉 danger-full-access
allowed_sandbox_modes = ["read-only", "workspace-write"]

# 只允许"按需审批"，禁掉 never（也就是禁止无人值守免审批）
allowed_approval_policies = ["on-request"]

[rules]
prefix_rules = [
  # 任何直接调 shell 的命令都要人工确认
  { pattern = [{ any_of = ["bash", "sh", "zsh"] }], decision = "prompt" },
]
```

`requirements.toml` 能约束的范围包括 [15]：审批策略、审批人、
自动审查策略、沙箱模式、权限档、联网搜索模式、托管钩子、
用户可以启用哪些 MCP 服务、可以添加哪些插件市场源。

还有一条只在 `requirements.toml` 里生效的开关 [14]：

```toml
allow_managed_hooks_only = true    # 忽略用户/项目/会话级钩子，只跑管理员下发的
```

写在 `config.toml` 里是**无效**的。这条容易踩。

### 配置层的优先级

从高到低 [14]：

```
1. 命令行 --config 覆盖
2. 项目配置  .codex/config.toml（从仓库根往下，越近越优先）
3. 配置档    ~/.codex/<名字>.config.toml
4. 用户配置  ~/.codex/config.toml
5. 系统配置  /etc/codex/config.toml
6. 内置默认值
———— 以上全部再被 requirements.toml 收口 ————
```

另外一条安全设计值得知道：**把项目标记为不可信之后，
Codex 会跳过整个项目级 `.codex/` 层，包括项目配置、钩子和规则** [14]。
拿到一份来路不明的仓库时，这是默认的自我保护。

## 2.5 三个问题的成套答案

评审会上要交的东西，就是这三份文件加一段话：

| 甲方的问题 | 你交什么 | 一句话说明 |
|---|---|---|
| 会不会乱删文件 | `requirements.toml` 的 `allowed_sandbox_modes` | 操作系统级沙箱，管理员锁死，用户改不了 |
| 会不会往外传 | 模型通道的数据说明 + 工具通道的网络配置与代理白名单 | 模型数据边界单独说明；命令出网按策略放行、留痕 |
| 谁批准的命令 | `.rules` 文件 + `codex execpolicy check` 的 CI 结果 | 白名单带单元测试，交付前离线验证过 |

**这三份文件应该跟着方案一起交，不是等着被问。**

上册第 13 章的结论是：**“合规不是上线前的检查项，是立项前的约束条件。”**
这三份配置就是你从立项那天起该攒的东西。
