# 第 1 章 · 它是什么，不是什么

> **档位：轻档起 · 所有人都该读**
> 这一章不需要任何前置条件，10 分钟读完。它决定你后面该读哪几章。

## 一次差点签错的合同

某次投标，甲方在技术要求里写了一条：
“所使用的 AI 辅助工具须开源可审计，不得存在不可控的外部数据传输。”

投标方看到 Codex 是 Apache-2.0 开源，直接写进了方案。
进场部署那天才发现：开源的是**壳**，模型还在外面，
默认要用 ChatGPT 账号或者 API key 登录才能干活，而现场是物理隔离网。

整个方案作废，重新走一遍变更流程，工期多了三周。

这一章要把这件事说清楚：**Codex 到底哪部分是开源的，哪部分不是。**

> **不做投标的读者**：上面这个场景换个说法你也会遇到——
> 你在自己电脑上跑得好好的，换到公司的内网机器上就登不上；
> 或者你想用国产模型省点钱，配了半天配不通。
> **根因是同一个：开源的是壳，模型不在里面。**

## 1.1 harness 这个词，用人话说

模型是发动机，harness 是车。

方向盘、刹车、仪表盘、安全带、后视镜——这些不产生动力，
但没有它们，发动机再强也不能上路。

具体到 AI 干活这件事：

| 你担心的事 | harness 里对应的零件 |
|---|---|
| 它把我文件删了 | 沙箱（文件系统隔离） |
| 它执行命令时把代码传出去了 | 工具网络策略（默认不允许沙箱内命令联网） |
| 它跑了一条我没批准的命令 | 命令白名单 + 审批 |
| 出事了查不到是哪一步 | 事件流 + 日志留痕 |
| 每个人配的不一样 | 管理员强制配置 |

模型自己不会停下来问“这条命令能不能跑”。**harness 会。**

这里必须区分两条网络：**模型通道**把提示、上下文和工具结果发给模型服务；
**工具通道**是 `git`、`curl`、包管理器以及程序运行时主动访问外网。
沙箱里的 `network_access = false` 管的是第二条，不会把第一条变成离线推理。
如果客户问“代码会不会离开现场”，不能只拿工具断网配置作答，还要单独说明模型提供方、
数据处理位置和发送给模型的上下文范围。第 2 章会按这两个平面拆开。

下册第 8 章叫《部署护栏与可观测性》，讲的是同一件事，只是那里的对象是服务，这里是 agent。

**还有一点很多人没意识到：这层壳跟“写代码”没有绑定关系。**
OpenAI 自己把它定位成通用的 agent 执行层——
harness 负责跑 agent 循环、管沙箱和审批，
界面、业务上下文、业务工具、审批流由你的应用自己掌控 [20][21]。
第 6 章 6.0 节展开讲这条分界线，它决定了你能不能把 Codex 当成交付物的一部分。

## 1.2 开源的是什么

`openai/codex` 仓库里，用 Rust 写的核心部分（`codex-rs/`）包含 [1]：

| 目录 | 干什么的 | 对应本书哪一关 |
|---|---|---|
| `linux-sandbox/` `windows-sandbox-rs/` | 文件系统沙箱 | 第 5 关 上线 |
| `execpolicy/` | 命令白名单引擎 | 第 5 关 上线 |
| `network-proxy/` | 网络策略代理 | 第 5 关 上线 |
| `hooks/` | 生命周期钩子 | 第 4 关 验收 |
| `otel/` | OpenTelemetry 上报 | 第 6 关 采用 |
| `app-server/` | 对外的 JSON-RPC 接口 | 可交付组件 |
| `skills/` | 可复用任务包 | 第 3 关 切片 |
| `exec/` | 非交互执行 | 进流水线 |
| `mcp-server/` | 把 Codex 暴露成 MCP 服务 | 企业集成 |

> **两个词先解释一下**：
> **MCP** 是一套让 AI 工具互相调用的开放协议，可以理解成“AI 版的 USB 接口”——
> 插上就能用，不用为每个系统写一遍对接代码（下册第 4 章讲得更细）。
> **crate** 是 Rust 里的“模块／包”，相当于 Python 的一个 package。
> 上表每一行就是一个 crate，可以单独拿走用。

许可证 Apache-2.0，可以自己 fork、自己编译、自己审计、自己改。
**这是它相对闭源工具的全部优势所在。**

## 1.3 不开源的是什么

**模型。** Codex 默认连 OpenAI 的服务。

登录方式两种 [10][14]：

- ChatGPT 账号（Plus / Pro / Business / Edu / Enterprise）
- API key（环境变量 `CODEX_API_KEY` 或 `OPENAI_API_KEY`）

两种都要外网。

配置文件里可以换模型提供方（`model_providers`），
但有一条硬约束卡在那儿——第 5 章专门讲。

> **说给甲方听的版本**：
> “工具本身开源可审计，代码可以交给贵方安全部门review；
> 但模型推理默认在外部，如果贵方要求全内网，
> 需要额外做模型接入层的适配，这部分工作量要单独评估。”
>
> 这句话最好出现在**投标文件**里，不是进场之后。
> 上册第 5 章讲的第 2 关 定界，卡的就是这种条件。

## 1.4 一张对照表：六道关卡 × Codex 的哪个部件

这是这本别册的骨架。后面每一章展开表里的一行。

| 关卡 | 你在这一关要解决的问题 | Codex 的部件 | 落地形态 | 本册章节 |
|---|---|---|---|---|
| **第 2 关 定界** | 边界写下来，人和 AI 看同一份 | `AGENTS.md` | 仓库里的层叠指令文件 | 第 3 章 |
| **第 3 关 切片** | 每片活儿有明确的交付物 | Skills（`.agents/skills/`） | 可复用的任务包 | 第 3 章 |
| **第 4 关 验收** | 判据必须机器可执行 | Hooks / `--output-schema` | 不过就退回，不是提醒 | 第 3 章 |
| **第 5 关 上线** | 甲方安全部门的三个问题 | 沙箱 / execpolicy / 网络代理 / `requirements.toml` | 管理员强制，用户改不了 | 第 2 章 |
| **第 6 关 采用** | 留痕、可审计、接客户监控 | `--json` 事件流 / OTel | 上报到客户的监控系统 | 第 4 章 |

注意第 1 关选题不在表里——**工具解决不了选题问题**。

## 1.5 它和下册第 3 章那三套工具的关系

下册第 3 章比较了 Spec Kit、OpenSpec、Superpowers。补上 Codex 是四栏：

| | Spec Kit | OpenSpec | Superpowers | **Codex** |
|---|---|---|---|---|
| **定位** | 规格流水线 | 变更提案制 | 工程纪律层 | **执行环境层** |
| **回答什么问题** | 这个新功能要做成什么样 | 这次改了系统哪些行为 | AI 干活按什么规矩来 | **AI 干活时能碰什么、留什么痕** |
| **核心产物** | `specs/` 下的规格文件 | `openspec/specs/` + `changes/` | 行为约束 | **配置文件 + 事件流** |
| **谁最关心** | 产品、架构 | 维护者 | 开发者 | **甲方安全部门、运维** |

**四者不在同一层，可以同时用。**

一个完整的现场配置可能长这样：

```
项目根目录/
├── AGENTS.md                    ← 边界和约定（Codex 读）
├── .agents/skills/              ← 可复用任务包（Codex 读）
├── .codex/
│   ├── config.toml              ← 项目级配置
│   ├── rules/project.rules      ← 命令白名单
│   └── hooks/                   ← 验收钩子
├── openspec/                    ← 变更提案（人读，也给 AI 读）
└── specs/                       ← 功能规格（人读，也给 AI 读）
```

规格文件是给“要做什么”用的，Codex 的配置是给“能怎么做”用的。
一个管方向，一个管刹车。
