# 第 6 章 · 把它当成可交付的组件

> **档位：6.0–6.2 中档 · 6.3 及以后重档**
> 6.1 节（进 CI）是团队用 Codex 的常规动作。6.3 节之后讲的是“把 Codex 交付给客户”，
> 不做交付的读者可以只看 6.0 那张责任分界表，它解释了这套东西到底是什么。

## “我们不想每个人都装一个终端工具”

某制造业客户的 IT 负责人在评审会上说了一句：

> “你们工程师用什么工具我不管。但你们说的这套能力，
> 我们的人不会去开终端敲命令。能不能做到我们自己的系统里？”

这个要求很常见，而且合理。**FDE 的交付物不应该是“一个要求客户改变工作习惯的工具”。**

这一章讲四种把 Codex 塞进别的系统里的方式，从轻到重。

## 6.0 先纠正一个印象：它不只是编程工具

绝大多数人把 Codex 理解成“AI 写代码的”。OpenAI 自己的定位不是这样——
2026 年 8 月它发了一篇讲“Codex 作为平台”的文章，
里面把这套东西明确定位成**通用的 agent 执行层** [20]：

> 与其要求每个团队把工作搬到一个通用的编程助手里，
> 不如把 agent 搬进那个为这份工作本身设计的软件里。

同一时间 OpenAI 官方账号的说法更直接 [21]：

> 各团队正在用开源的 Codex harness，把 agent 带进他们已经在用的工具里——
> 从内部应用到运维看板。**应用这一侧掌控界面、上下文、工具和审批，
> harness 负责跑 agent 循环。**

### 责任分界：谁管什么

这张分界表是这一章最重要的东西 [20]：

| harness（Codex）管 | 你的应用管 |
|---|---|
| 对话状态 | 界面与看板 |
| 工具调用 | 业务上下文与业务工具 |
| 沙箱与审批策略的执行 | 操作边界与访问策略 |
| 跨轮次推进任务 | 审批流本身 |
| 流式执行与事件 | 系统记录与数据集成 |

**左边那一列是通用的、难写对的、写错了会出事的**——沙箱、审批、
事件流、跨轮状态。右边那一列是**只有你懂客户业务才写得出来的**。

对 FDE 来说，这条分界线的意义很实在：
**你不需要从零造一个 agent 框架，你需要的是把客户的业务语义接上去。**
上册第 2 章讲“这个岗位在解决什么问题”，答案是“把客户的问题变成可重复的解决方案”——
不是“重新发明执行引擎”。

### 一个非编程的例子

那篇文章里列的落地案例中，有一个和写代码完全无关：
两家公司用它做**报税**，试点处理了 7000 份报税表，
把准备时间压掉约三分之一 [20][21]。

> **可信度说明**：这个数字来自 OpenAI 官方博客，属于**厂商发布的单个试点数据**，
> 不是经过第三方核验的行业基准。它能说明“这套东西可以用在非编程场景”，
> **不能拿来支撑“所以你们上了也能省三分之一”**。
> 这跟第 7 章那个“一百万行”是同一类数字，用法要一样克制。

真正值得学的不是数字，是**它的形态**：
用户面对的是一个报税软件，不是一个终端。
agent 在后面跑，界面、上下文、审批全在应用这一侧。

**这就是本章开头那位 IT 负责人要的东西。**

## 6.1 最轻：`codex exec` 进流水线

非交互模式就是一条普通命令，可以放进任何 CI [10]：

```bash
codex exec "根据本次 diff 生成变更说明，写到 CHANGELOG 草稿里"
```

几个进流水线必备的开关 [10]：

```bash
--sandbox read-only          # CI 里默认只读
--ask-for-approval never     # 无人值守，不能停下来问人
--json                       # 留痕
--output-schema ./s.json     # 结构化结果给下游判断
--skip-git-repo-check        # 不在 git 仓库里时
```

还能从管道吃输入，这个用法在排障时很顺手 [10]：

```bash
make test 2>&1 | codex exec "总结失败原因，给出最小修复方案"
tail -n 200 app.log | codex exec "定位根因，列出下一步排查动作"
```

或者整段提示词都从管道来：

```bash
cat prompt.txt | codex exec -
```

### CI 里的密钥怎么处理

官方给的做法是**分两个 job** [10]：

1. 第一个 job 权限只读，跑 Codex，产出补丁
2. 第二个 job 有写权限，应用补丁

这样密钥永远不会暴露给可能来自外部 PR 的代码。

GitHub Actions 有官方 action [10]：

```yaml
- name: Run Codex
  uses: openai/codex-action@v1
  with:
    openai-api-key: ${{ secrets.OPENAI_API_KEY }}
    prompt: "Run tests and fix failures"
```

> **不要**把 `CODEX_API_KEY` 或 `OPENAI_API_KEY` 设成整个 job 的环境变量，
> 只在调用那一步注入 [10]。
> 这跟本书 Lab-06 里那条约定是同一条：
> **密钥只从环境变量读，永远不落盘、不进日志、不写进任何文件。**

## 6.2 中等：SDK 嵌进客户的内部平台

有 TypeScript 和 Python 两套 SDK [1][8]。
TypeScript 的用法：

```typescript
import { Codex } from "@openai/codex-sdk";

const codex = new Codex();
const thread = codex.startThread({
  workingDirectory: "/srv/客户项目",
  skipGitRepoCheck: true,
});

const turn = await thread.run("诊断这次构建失败，给出修复方案");
console.log(turn.finalResponse);
```

SDK 本质上是**包了一层 CLI**：它启动 `codex` 进程，
通过标准输入输出交换 JSONL 事件 [8]。
这意味着第 2 章那些沙箱和策略配置**照样生效**，
不会因为换了调用方式就绕过去。

要看中间过程（工具调用、文件变更）用流式 [8]：

```typescript
const { events } = await thread.runStreamed("诊断构建失败");
for await (const event of events) {
  if (event.type === "item.completed") console.log("步骤", event.item);
  if (event.type === "turn.completed") console.log("用量", event.usage);
}
```

结构化输出、会话恢复（`codex.resumeThread(id)`）、
附图片，都在 SDK 里 [8]。

还有一个对交付很重要的能力——**完全控制子进程环境** [8]：

```typescript
const codex = new Codex({
  env: { PATH: "/usr/local/bin" },        // 只给这些环境变量
  config: {
    sandbox_workspace_write: { network_access: false },
  },
});
```

在客户的内网平台里跑，能把环境变量收到最小集合，
这是能过安全评审的关键细节。

## 6.3 重一点：把 Codex 暴露成 MCP 服务

```bash
codex mcp-server        # 以 MCP server 身份启动（stdio）
```

这条命令的意思是：**Codex 变成被调用方。**

客户如果已经有自己的 agent 平台（现在国内大企业里越来越常见），
它可以直接把 Codex 当成一个 MCP 工具挂上去，
而不需要用户去开终端。

反过来，Codex 也能当 MCP 客户端，挂载外部 MCP 服务 [14]：

```toml
[mcp_servers.客户ERP]
command = "python3"
args    = ["-m", "erp_mcp_server"]
env     = { ERP_ENDPOINT = "http://10.0.0.5:8080" }
enabled = true
enabled_tools  = ["查询订单", "查询库存"]   # 白名单
disabled_tools = ["修改订单"]               # 黑名单
```

`enabled_tools` / `disabled_tools` 这两个字段值得注意——
**可以只暴露只读工具**。下册第 6 章把直连遗留系统的四种方式和各自的代价讲透了，
结论之一是只读路径的风险显著低于读写。**第一版只开读，是有现成开关的。**

而且 `requirements.toml` 能限制**用户可以启用哪些 MCP 服务** [15]，
所以这个白名单是能被管理员锁死的。

> 下册第 14 章那个“用 MCP 盘活遗留大型机”的案例，
> 桥接层的位置就是这里。区别只是那个案例里 agent 是自己写的，
> 这里换成了 Codex。

## 6.4 最重：app-server，做自己的前端

如果客户要的是“我们自己的界面”，那就用 app-server [3]。

这是 Codex 用来支撑 VS Code 插件那套东西的接口：
**JSON-RPC 2.0 双向通信**，和 MCP 类似的思路 [3]。

> **JSON-RPC** 是一种很轻的远程调用约定：一方发一个 JSON 说“调这个方法、
> 参数是这些”，另一方回一个 JSON。“双向”是指两边都能主动发起——
> 这一点很关键，因为 agent 需要在干活干到一半时反过来问你“这条命令批不批”。

支持的传输方式 [3]：

| 方式 | 启动参数 | 说明 |
|---|---|---|
| stdio | `--stdio`（默认） | 按行分隔的 JSON |
| unix socket | `--listen unix://` | 本地控制面，走 HTTP Upgrade 握手 |
| websocket | `--listen ws://IP:PORT` | **实验性，官方明说不要用于生产** |
| 关闭 | `--listen off` | 不暴露本地传输 |

**接口定义可以自动导出**，这一条对做集成的人很重要 [3]：

```bash
codex app-server generate-ts             # 导出 TypeScript 类型定义
codex app-server generate-json-schema    # 导出 JSON Schema
```

导出的结果**和你手上这个版本的 Codex 严格对应** [3]，
不用担心文档和实现对不上。

几个工程细节，做集成时会用到 [3]：

- websocket 模式下自带健康探针：`GET /readyz`、`GET /healthz`
- 内部用有界队列，过载时返回 JSON-RPC 错误码 `-32001`，
  消息是 `"Server overloaded; retry later."`——**客户端要做指数退避重试**
- `RUST_LOG` 控制日志级别，`LOG_FORMAT=json` 让日志按 JSON 输出到 stderr

最后这一条配合第 4 章的 OTel，日志链路就齐了。

## 6.5 四种方式怎么选

官方文档给三种接入方式的定位是 [20]：`codex exec` 适合“有明确边界的”
脚本和后台任务，SDK 适合程序化地“发起、恢复、流式获取”任务，
app-server 适合“需要持久会话、流式事件和审批处理”的场景。
下面这张表按客户提需求的方式重新组织了一遍，多列了一种 MCP：

| 客户的诉求 | 用哪种 | 工作量 |
|---|---|---|
| “能不能在我们 CI 里自动跑” | `codex exec` | 小时级 |
| “我们的内部平台想加个 AI 功能” | SDK | 天级 |
| “我们已经有 agent 平台了” | `codex mcp-server` | 天级 |
| “我们要自己的界面” | app-server | 周级 |

**从上往下选，能用轻的就别用重的。**
上册第 12 章讲第 3 关切片的结论是：**“竖着切一刀，穿过所有层，哪怕只覆盖一小块业务。”**

照这个切法，大多数项目的第一片应该是 `codex exec` 进 CI，不是自己做界面。

## 本章清单

- [ ] CI 里的调用带了 `--sandbox read-only` 和 `--ask-for-approval never`
- [ ] 密钥只在调用那一步注入，不是整个 job 的环境变量
- [ ] 需要写权限的动作拆成了单独的 job
- [ ] 挂 MCP 服务时第一版只开了只读工具
- [ ] 如果做集成，接口定义是用 `generate-ts` 导出的，不是手抄的
- [ ] 客户端对 `-32001` 过载错误做了退避重试
- [ ] 第一片选的是四种方式里最轻的那一种
