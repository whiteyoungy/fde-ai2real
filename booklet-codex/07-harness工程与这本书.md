# 第 7 章 · harness 工程：这套方法论和本书是同一件事

> **档位：轻档起 · 所有人都该读**
> 这一章讲的是方法论，不含任何配置和命令。可以当成全册的收尾，也可以先读。

## 一个容易被误读的数字

2026 年初，OpenAI 发了一篇讲 harness engineering 的文章，
里面有一组很容易被拿来当标题的数字：

> 一个三人团队，从 2025 年 8 月底的空仓库开始，五个月，
> 一百万行生产代码，1500 个合并的 PR，团队成员**没有手写一行代码**。

先说清楚这个数字该怎么用，再说这套方法论该怎么用。

> **可信度说明**：本节内容为**二手转述**。
> OpenAI 官网对本书写作时使用的抓取方式返回 403，
> 未能逐字核对原文；以下内容依据多个二手来源交叉整理 [18][19]。
> 引号里的表述是转述者的措辞，不是原文引文。

## 7.1 先说这个数字不能怎么用

**它不是行业基准。** 理由三条：

1. **样本 n = 1。** 一个团队，一个项目。
2. **发布方是利益相关方。** OpenAI 用自己的产品做的自己的项目。
3. **团队构成极端不典型。** 造这个工具的人用这个工具，
   踩到坑当场改工具——绝大多数团队没有这个条件。

而且，**一百万行不等于一百万行有价值的代码**。
代码量从来不是产出的度量，AI 生成的代码量更不是。

> 本书上册第 3 章列过一批“不该引用的数字”——
> 那个流传甚广的 RAND 80% 项目失败率、MIT 的 95% 试点失败率，
> 都是被反复转载、原始口径早已模糊的例子。
> **这个一百万行属于同一类。**
> 它可以当成一个有意思的案例讲，
> **不能当成“所以你们团队也应该这样”的论据。**

那这一章为什么还要写？因为**方法论部分是有价值的，和数字无关。**

## 7.2 harness 工程说的是什么

一句话：**工程师的主要工作，从“写代码”变成“造让 agent 能可靠干活的环境”** [18][19]。

具体是——设计环境、明确意图、建反馈回路。
工程师的时间花在更好的地图、更好的检查器、更好的评估器上。

**读到这里应该觉得眼熟。** 这正是本书从第一页开始讲的事——
用一句话概括本书的主张：**FDE 的产出不是代码，
是让客户的问题可重复地被解决的那套东西。**

只不过本书讲的对象是**客户现场**，harness 工程讲的对象是 **agent**。
两者是同构的：

| | FDE 在客户现场 | harness 工程对 agent |
|---|---|---|
| 交付物 | 可重复的解决方案 | 可靠的执行环境 |
| 最难的部分 | 边界和判据 | 边界和判据 |
| 失败模式 | 没人用 | 结果全看运气 |
| 度量 | 采用率 | 一次通过率 |

## 7.3 五条原则，对回六道关卡

二手来源整理出的五条原则如下 [19]，
每条后面是它对应到本书的哪一关：

### 一、agent 看不见的东西，就等于不存在

决策要落进仓库里成为文本，不能只存在于人的脑子里或者聊天记录里。

**对应第 2 关 定界。** 上册第 5 章讲的是同一件事——
只是那一章的读者是甲方和团队，这里多了一个读者是 agent。
**没落到纸上的边界，对谁都不算数。**

落地位置：第 3 章讲的 `AGENTS.md`。

### 二、问“缺什么能力”，不要问“为什么失败了”

agent 干砸了的时候，第一反应不该是改提示词，
而是问：**它缺哪个工具？缺哪个信息？环境里少了什么？**

**对应第 3 关 切片。** 上册第 6 章的切法是“竖着切一刀，穿过所有层”，
判断标准是这一刀下去能不能拿出个能验证的东西——
同样是在问“还缺什么”，而不是“为什么没做好”。

### 三、机器强制，不要靠文档约定

规则用检查器强制，违反就直接构建失败，不要写在文档里指望人记得。
**这些检查器本身也是 agent 写的。**

**对应第 4 关 验收。** 下册第 9 章整章都在讲这件事：
**判据不挂进持续集成，就只是一份没人跑的文件。**

落地位置：第 2 章的 `.rules`、第 3 章的 Hooks。

### 四、给 agent 眼睛

把浏览器调试协议、可观测性工具接给 agent，
让它能自己看到 DOM 快照、指标、日志，而不是靠人复述。

**对应第 5 关上线和第 6 关 采用。** 下册第 8 章讲的可观测性三件套（日志、指标、链路）
是为了让人能看见系统。**对 agent 要做的是同一件事，只是接收端换了。**

落地位置：第 4 章的事件流和 OTel，第 6 章的 MCP 挂载。

### 五、给一张地图，不是一本手册

给简要的架构总览，不要给面面俱到的文档。
而且——**架构约束经常表现为“这里不应该存在某个东西”**，
这种“负面事实”必须显式写出来，因为它没法从代码里读出来。

**对应第 2 关 定界。** 第 3 章那个例子——
在有历史包袱的目录下放一份 `AGENTS.md` 写明“这里的丑是有原因的”——
就是一条负面事实。

## 7.4 对 FDE 最有用的一句话

把五条原则压成一句：

> **你的交付物不再只是代码，是“让活儿能被可靠地干成”的那套环境。**

这句话对 FDE 意味着什么？

**意味着你在客户现场造的那些东西，本来就是 harness。**

想想你在项目里实际花时间做的事：

- 搞清楚客户的数据长什么样，写进文档 → **地图**
- 定验收标准，写成能跑的测试 → **机器强制**
- 搭监控，让运维能看见 → **给眼睛**
- 把边界写进合同和方案 → **看不见就不存在**
- 交接时把排障流程整理成手册 → **可复用的能力**

**FDE 一直在做 harness 工程，只是以前的服务对象是人。**

现在多了一个服务对象，方法没变。
这是这本别册最想说的一句话。

再往前走一步，harness 不是“多装几道安全开关”，而是把项目里的**决定权**做成可执行配置：

| 决定 | 不能只靠什么 | harness 里的落点 |
|---|---|---|
| 哪些文件可以看、可以改 | 口头说“别碰生产目录” | 沙箱与文件权限 |
| 哪些命令可以直接执行 | 每次临场判断 | `.rules` 与审批策略 |
| 哪些网络目的地可以访问 | 笼统说“允许联网” | 工具网络策略与代理 |
| 什么结果才算完成 | 模型自己说“已完成” | Hooks、结构化输出与 CI 门禁 |
| 出事后谁能还原过程 | 聊天截图和个人记忆 | 事件流与遥测 |

所以 harness 更接近一份**能执行的责任分界表**。它不保证模型永远正确，
但能保证模型出错时仍在预先划定的爆炸半径内，关键动作有人或策略批准，结果有证据可查。
这也是它和“写一个更长的提示词”的根本区别：提示词主要影响模型想怎么做，
harness 决定系统实际上允许它做到哪里。

这套分界也补全了上册第 14 章提出的三类交付结果：评估和事件流提供**证据**，
沙箱、规则与审批提供**控制**，版本化配置、技能和运维材料帮助客户**接管**。
缺其中任何一类，都只能算 agent 在某台机器上跑起来了，不能算一个组织接住了它。

### 还有一层：这套环境本身可以是交付物

第 6 章 6.0 节那张责任分界表值得再看一眼：
**通用的、难写对的那一半（沙箱、审批、事件流、跨轮状态）Codex 已经写好了，
而且是 Apache-2.0 的；只有你懂客户业务才写得出来的那一半，才是你的活。**

这对 FDE 的报价方式也有影响：
你卖的不再是“帮客户接一个大模型”，
而是**一个装着 agent、界面和审批都长在客户业务里的系统**——
后者更难被比价，也更难被替换。

## 7.5 什么时候不该用 Codex

诚实地列一遍：

| 情况 | 判断 | 替代 |
|---|---|---|
| 信创清单白名单里没有，且特批走不通 | **不能用** | 用国产工具链，或只 fork 组件自己编译 |
| 客户要求全内网且没有自建模型平台 | **不能用** | 先解决模型接入，这是前置条件 |
| 你缺的是“规格产物格式统一” | 不对症 | Spec Kit（下册第 3 章） |
| 你缺的是“变更轨迹” | 不对症 | OpenSpec（下册第 3 章） |
| 你缺的是“AI 干活的规矩” | 不对症 | Superpowers（下册第 3 章） |
| 你缺的是“沙箱 + 策略 + 留痕” | **对症** | 就是它 |
| 团队只有两三个人，没有合规压力 | 过重 | 直接用，别配那么多 |

最后一行要单独说。**第 2 章那一整套配置是给有合规压力的现场准备的。**
如果你是三个人的团队做内部工具，
把 `requirements.toml`、`.rules`、Hooks 全配一遍是在给自己找麻烦。

下册第 2 章讲过按改动大小分档（A/B/C/D）。**工具配置也该分档**——
这正是导读里那三条读法的由来，附录 A 也按这三档拆成了三段：

| 档 | 配到哪一步 | 谁 |
|---|---|---|
| **轻档** | `AGENTS.md` + 沙箱三行 + 一个拦密钥的钩子 + 技能包 | 个人、小团队 |
| **中档** | 再加命令白名单、留痕归档、进 CI | 团队协作、有 CI |
| **重档** | 再加 `requirements.toml` 锁死、网络策略代理、监控上报 | 客户现场、要过评审 |

**大部分团队在轻档和中档就够了。重档是给银行、政务、军工那类现场的。**
按客户的合规压力选档，不是按“配得越全越专业”选——
**配了但没人维护的护栏，比没配更危险，因为它给人一种已经防住了的错觉。**

## 自检问题

1. 你上一次 agent 干砸活儿，你改的是提示词，还是环境？
2. 你项目里有哪些“负面事实”（这里不应该有某个东西）？它们写在哪儿了？
3. 你现在配的档位，和客户的合规压力匹配吗？还是在为了配而配？
4. 你项目里哪些决定仍只存在于口头约定？它们应该进入指令、规则、审批还是 CI 门禁？为什么？
