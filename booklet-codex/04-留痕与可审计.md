# 第 4 章 · 留痕：让每一步都查得到

> **档位：4.1 中档 · 4.2 及以后重档**

## 那封查不出结果的邮件

项目上线后第九天，客户运维发来一封邮件：
“上周三下午，测试库的一张表被清空了，请说明原因。”

团队翻了三天：git 记录里没有相关提交，
CI 日志只记了构建结果，本地终端历史早就滚没了。
最后给出的答复是“疑似为环境清理脚本误触，已加强管理”。

客户信息安全部把这件事记进了风险台账。第二期招标时，
技术要求里多了一条：“AI 辅助工具须提供完整的操作审计日志。”

**这一条要求，是上一家供应商用一封查不出结果的邮件换来的。**

## 4.1 事件流：`--json`

Codex 的非交互模式可以把整个执行过程按 **JSON Lines** 吐出来 [10]——
就是“一行一个 JSON 对象”的纯文本格式，常见扩展名 `.jsonl`，
好处是可以边写边读，也可以直接 `grep`：

```bash
codex exec --json "把 legacy 模块的单测补到 80% 覆盖率"
```

进度信息走 `stderr`，只有最终回答走 `stdout`，所以可以直接重定向 [10]：

```bash
codex exec --json "……" > run.jsonl
```

事件长这样 [10]：

```json
{"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
{"type":"turn.started"}
{"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}
{"type":"turn.completed","usage":{"input_tokens":24763,"cached_input_tokens":24448,"output_tokens":122}}
```

事件类型包括 `thread.started`、`turn.started`、`turn.completed`、
`turn.failed`，以及各种 `item.*` [10]。

### 这份日志能回答什么

回到开头那封邮件。有了 `run.jsonl`，你能答的是：

- **哪个会话**（`thread_id`）
- **执行了哪条命令**（`item.type = command_execution` 的 `command` 字段）
- **什么时候开始、什么时候结束**
- **用了多少 token**（`usage`，顺便还能算成本）

一个最小的审计导出脚本：

下面这个脚本用到 `jq`——处理 JSON 的命令行工具，
各系统包管理器里都有（`apt install jq` / `brew install jq`）：

```bash
#!/usr/bin/env bash
# 从事件流里抽出所有实际执行过的命令，生成交付审计附件。
# 交付时这份文件跟代码一起给客户，比"我们会注意的"有说服力得多。
jq -r 'select(.type == "item.started")
       | select(.item.type == "command_execution")
       | [.item.id, .item.command] | @tsv' run.jsonl
```

> **交付建议**：把 `run.jsonl` 按天归档，和构建产物一起进制品库。
> 按上册第 13 章的说法，合规是立项前的约束条件——
> **审计能力同理，不是等着被审计的那天才建。**

### 几个和留痕相关的开关

```bash
codex exec --ephemeral        # 不落盘会话文件（跑在客户机器上、不想留东西时用）
codex exec --ignore-user-config  # 忽略 ~/.codex/config.toml，保证可复现
codex exec --ignore-rules        # 忽略用户和项目的规则文件
```

`--ephemeral` 和审计是一对矛盾：**在客户机器上跑要不要留痕，
是第 2 关定界阶段就该谈清楚的事**，不要现场临时决定。

历史记录本身也可以配 [14]：

```toml
[history]
persistence = "save-all"    # 或 "none"
max_bytes   = 104857600     # 超了从最老的开始丢
```

## 4.2 接进客户的监控：OpenTelemetry

`--json` 是给人和脚本看的。要接进客户已有的监控体系，走 **OTel**。

> **先解释三个缩写**：**OpenTelemetry（简称 OTel）** 是一套业界通用的
> “程序怎么上报自己在干什么”的标准；**OTLP** 是它的传输协议；
> **APM** 是“应用性能监控”系统的统称——SkyWalking、Prometheus + Grafana、
> 各家商业监控产品都算。一句话：**按 OTel 的格式报，客户已有的监控就能收。**

Codex 有一个专门的 OpenTelemetry 集成（`codex-otel`），
支持日志、链路（trace）、指标三类导出，
以及会话级的业务事件上报 [6]。

导出走标准的 OTLP over HTTP，可以配端点、请求头和 TLS [6]：

```rust
// 摘自 codex-otel 的用法示例，说明它导出的是标准 OTLP，
// 不是自定义格式——这一点是接客户 APM 的前提。
let settings = OtelSettings {
    environment: "prod".to_string(),
    service_name: "codex-cli".to_string(),
    exporter: OtelExporter::OtlpHttp {
        endpoint: "https://otlp.内网地址/v1/logs".to_string(),
        headers: HashMap::new(),
        protocol: OtelHttpProtocol::Binary,
        tls: None,
    },
    // ……
};
```

**为什么这一条对 FDE 很关键**：

客户的运维体系已经存在了。可能是 SkyWalking、可能是 Prometheus + Grafana、
可能是商业 APM。你交付的东西如果不能接进去，
运维就得为你这一个组件单独看一块屏——**这是采用率杀手**。

上册第 10 章第 6 关采用讲的那种失败——**“验收单签了字、系统也上线了，
六个月后一线还在导 Excel 手工核对”**——运维侧也有对应的版本：
系统上线了，但没人把它纳入值班。能上报 OTLP，这一关就过了一大半。

下册第 8 章讲的可观测性三件套（日志、指标、链路），
在这里是现成的。

## 4.3 会话可恢复、可分叉

事故复盘还有一种需求：**“当时到底是怎么走到那一步的？”**

Codex 的会话持久化在 `~/.codex/sessions` [8]，支持：

```bash
codex exec resume --last "接着修你刚才发现的竞态"
codex exec resume <SESSION_ID>
```

交互模式下还有 `codex resume`（选择器）、`codex fork`（从某个会话分叉）、
`codex archive` / `codex unarchive`（归档）[1]。

`fork` 在排障时特别有用：**从出问题的那一步分叉出去试不同的修法，
原始会话不动**，事后两条路径可以对比。

## 4.4 把留痕做成交付物

把这一章的东西凑起来，交付包里可以多出三样：

| 交付物 | 怎么产生 | 客户拿它干什么 |
|---|---|---|
| `audit/*.jsonl` | `codex exec --json` 归档 | 事后追溯每一条命令 |
| OTLP 上报配置 | `codex-otel` 配置 | 接进现有 APM，进值班流程 |
| `sessions/` 归档 | 会话持久化 | 复盘时能回放当时的上下文 |

这三样加上第 2 章那三份配置（`requirements.toml`、网络策略、`.rules`），
就是一份完整的“AI 工具合规使用”证据包。

**这份证据包本身是有商务价值的**——这是笔者的判断，不是引自任何调研数据。
理由很朴素：上册第 12 章讲清楚了国企、银行、政务这三类客户的共同点是
内部流程极重。**帮客户少开一次会、少补一次材料，是能被记住的。**
