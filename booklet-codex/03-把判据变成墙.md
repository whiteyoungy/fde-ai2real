# 第 3 章 · 把验收判据变成一堵墙

> **档位：轻档 · 全册收益最高的一章**
> 三样东西立刻能用，不需要 root、不需要写策略脚本、不需要动 CI。
> 只读一章的话，读这一章。

## 写了没人看的那份规范

某项目交付前一周，团队发现 AI 生成的代码里有十几处直接读了 `.env` 文件。
翻聊天记录，规范里写得清清楚楚：“禁止在代码中直接读取环境配置文件”。

问题是——规范写在 Confluence 上，AI 没看过，人也没每次都看。

这一章讲三件事，从软到硬：

1. **`AGENTS.md`**——把约定放进 Codex 会加载的指令上下文（软，但必要）
2. **Skills**——把重复的活儿打包成可复用的任务包
3. **Hooks**——把判据变成撞上去会被弹回来的墙（硬）

三件事对应本书的第 2 关 定界、第 3 关 切片、第 4 关 验收。

## 3.1 AGENTS.md：Codex 会加载的那份约定

### 它怎么被找到

Codex 找指令文件的顺序 [12]：

1. **全局**：`~/.codex/AGENTS.override.md`，然后 `~/.codex/AGENTS.md`
2. **项目**：从 git 仓库根目录往下，一直到当前目录，
   每一层依次找 `AGENTS.override.md` → `AGENTS.md` → 后备文件名

然后**从根往下拼接**，中间用空行连起来。
**越靠近当前目录的文件排在越后面，因此会覆盖前面的说法** [12]。

每一层最多取一个文件。总大小超过 `project_doc_max_bytes`（默认 32 KiB）就停。
这里的“加载”不等于“百分之百照做”：`AGENTS.md` 进入指令上下文，仍属于模型需要遵循的软约束。
凡是涉及删除、外联、密钥和发布的硬边界，必须继续用沙箱、`.rules`、Hooks 或 CI 门禁强制，
不能因为文件名叫 `AGENTS.md` 就把它当成访问控制系统。

### 这个层叠规则怎么用

对 FDE 来说，这个“根往下拼、近的覆盖远的”规则正好对上多子系统交付：

```
仓库根/
├── AGENTS.md                 ← 全项目通用：代码风格、提交规范、测试要求
├── services/
│   ├── billing/
│   │   └── AGENTS.md         ← 计费服务特有：金额一律用整数分，禁止浮点
│   └── report/
│       └── AGENTS.md         ← 报表服务特有：查询必须走只读副本
└── legacy-bridge/
    └── AGENTS.md             ← 遗留桥接：这里的代码不要"顺手重构"
```

**最后那一条特别值钱。** 每个做过遗留系统改造的人都见过这一幕：
一段看起来很丑、其实在兜二十年历史包袱的代码，被“顺手优化”掉了。
在那个目录下放一份 `AGENTS.md` 写清楚“这里的丑是有原因的，
改动前先问人”，比在总规范里写一百条都管用。

### 里面该写什么

写**约束**和**这个项目特有的事实**，不要写通用知识。

```markdown
# 项目约定

## 环境
- Python 3.9（客户环境锁死，不要用 3.10+ 的语法）
- 不能联网装包，依赖全部在 `vendor/` 目录里

## 硬约束
- 所有金额用整数分表示，禁止 float
- 数据库连接串只从环境变量读，禁止写进任何文件
- 对外接口的报文编码是 GBK，不是 UTF-8（客户系统限制，不要"修正"）

## 干活方式
- 改代码前先跑 `make test`，确认基线是绿的
- 提交信息用中文，格式：`模块: 做了什么`
```

三条建议：

- **写“不要做什么”比写“要做什么”更有效。**
  架构约束经常是“这里不应该存在某个东西”，这种话必须显式写。
- **写客户环境的怪癖。** GBK 编码、Python 3.9、内网无 pip——
  这些是 AI 猜不到的，也是最容易出事的。
- **别超过 32 KiB。** 超了就拆到子目录去，靠层叠规则组装。

## 3.2 Skills：把重复的活儿打包

Skills 是可复用的任务包，遵循开放的 agent skills 标准 [13]。
目录结构：

```
my-skill/
├── SKILL.md          ← 必需
├── scripts/          ← 可选，脚本
├── references/       ← 可选，参考资料
└── assets/           ← 可选
```

`SKILL.md` 的头部：

```yaml
---
name: 交付前检查
description: 在向客户交付之前跑一遍完整检查。当用户说"要交付了""打包""出版本"时使用。
---
```

**`description` 是最重要的一行**——它决定这个 skill 什么时候会被自动挑中 [13]。

存放位置和优先级 [13]：

| 范围 | 路径 | 用途 |
|---|---|---|
| 仓库（就近） | `.agents/skills` | 某个目录专用 |
| 仓库（根） | `$REPO_ROOT/.agents/skills` | 整个项目共用 |
| 用户 | `$HOME/.agents/skills` | 跨项目的个人技能 |
| 管理员 | `/etc/codex/skills` | 组织统一下发 |

调用方式两种：显式（在 Codex 里打 `$技能名`）或隐式（按 `description` 自动匹配）[13]。

### 对 FDE 的意义

**每个交付项目应该有一个 `.agents/skills/` 目录，跟着代码一起交给客户。**

值得打包成 skill 的东西：

- 交付前检查（跑测试、查密钥泄漏、生成变更清单）
- 客户现场的环境搭建步骤
- 那套只有你们团队知道的排障流程
- 对接客户老系统时的报文构造方法

上册第 6 章讲经验资产化，说的就是这件事——
**只不过现在这份资产不只是给人看的文档，是能被 AI 直接执行的包。**

而且格式是开放标准，跟 Superpowers 的技能是同源的（下册第 3 章）。

## 3.3 Hooks：把判据变成墙

前两节都是“告诉 AI 该怎么做”。这一节是“AI 做错了直接拦下来”。

Codex 的生命周期钩子事件 [16]：

| 事件 | 什么时候触发 | 能干什么 |
|---|---|---|
| `SessionStart` | 会话开始 | 注入上下文 |
| `UserPromptSubmit` | 用户提交提示词 | 检查、补充 |
| `PreToolUse` | **工具调用前** | **拒绝或改写这次调用** |
| `PermissionRequest` | 请求审批时 | 自动批准/拒绝 |
| `PostToolUse` | 工具调用后 | 带反馈拦回去 |
| `PreCompact` / `PostCompact` | 上下文压缩前后 | 保住关键信息 |
| `SubagentStart` / `SubagentStop` | 子 agent 起止 | 追踪 |
| `Stop` | 回合结束 | 收尾校验 |
| `SessionEnd` | 会话结束 | 归档 |

配置写在 `config.toml` 里 [16]：

```toml
[[hooks.PreToolUse]]
matcher = "^Bash$"

[[hooks.PreToolUse.hooks]]
type = "command"
command = 'python3 .codex/hooks/check_secrets.py'
timeout = 30
statusMessage = "检查是否触碰敏感文件"
```

钩子从标准输入拿到一个 JSON，里面有 `session_id`、`cwd`、
`hook_event_name`、`model`、`turn_id`，以及事件相关的字段
（比如 `PreToolUse` 会有 `tool_name`）[16]。

拦截的方式两种 [16]：

- 返回 `{"permissionDecision": "deny", "permissionDecisionReason": "……"}`
- 或者直接**以退出码 2 退出**，把理由写到 stderr

一个能直接用的例子——不许碰凭据文件：

```python
#!/usr/bin/env python3
# .codex/hooks/check_secrets.py
# 交付项目里最常见的一类事故：AI 为了"看看配置"读了 .env，
# 然后把里面的连接串写进了它生成的代码或者日志里。
import json, sys, re

BANNED = re.compile(r'\.env|id_rsa|\.pem$|credentials|secrets\.ya?ml')

event = json.load(sys.stdin)
cmd = str(event.get("tool_input", {}).get("command", ""))

if BANNED.search(cmd):
    # 退出码 2 = 拦下来，stderr 的内容会回给模型，让它换个做法
    print("禁止读取凭据文件。需要配置项请读 config.example.toml，"
          "或者告诉我你需要哪个键，我给你脱敏后的值。", file=sys.stderr)
    sys.exit(2)
```

注意最后那句提示的写法：**不是“禁止”两个字，是“禁止 + 你应该改用什么”。**
这跟 2.3 节 `justification` 的道理一样——
拦住之后如果不给出路，模型会换个花样再试一次。

### 为什么这比写在文档里强

回到开头那个 `.env` 的事故。三种做法的区别：

| 做法 | 什么时候发现问题 | 成本 |
|---|---|---|
| 写在 Confluence 规范里 | 交付前一周 review 时 | 返工一周 |
| 写在 `AGENTS.md` 里 | 大部分时候不会发生，但不保证 | 偶尔漏 |
| 写成 `PreToolUse` 钩子 | **发生的那一秒** | 零 |

下册第 8 章开篇那句话点得很准：**“上册第 13 章给的是判据，
这一章给的是让判据能自动跑起来的代码。”** Hooks 就是让判据能自动跑的地方之一。

三层配合：`AGENTS.md` 说明意图（为什么），
`.rules` 拦命令（能不能跑），Hooks 拦语义（这次调用对不对）。

## 3.4 结构化输出：让判据的结果可以被程序读

还有一种“判据”是要拿结果去做下一步的。
Codex 支持按 JSON Schema 约束输出 [10]：

```bash
codex exec "检查这个仓库的交付就绪度" \
  --output-schema ./schema.json \
  -o ./readiness.json
```

`schema.json` 就是普通的 JSON Schema：

```json
{
  "type": "object",
  "properties": {
    "ready":   { "type": "boolean" },
    "blockers": { "type": "array", "items": { "type": "string" } },
    "risk":    { "type": "string", "enum": ["low", "medium", "high"] }
  },
  "required": ["ready", "blockers", "risk"],
  "additionalProperties": false
}
```

这样下游脚本可以直接读 `ready` 字段决定卡不卡流水线，
而不是去正则匹配一段自然语言。

> 下册第 8 章的结论是：**“门禁不挂进持续集成，评估集就只是一份没人跑的文件。”**
> 而要挂进持续集成，结果就得是程序能读的。`--output-schema` 解决的正是这一步。
