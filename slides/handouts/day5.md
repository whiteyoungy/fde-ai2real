## 二、上机任务书 · 开源组件进场评估

### 两条路径，按教室的网络条件选

| | A 路径 · 有网有 key | B 路径 · 断网 |
|---|---|---|
| 做什么 | 装起来、接端点、跑配置树输出、看强制力等级、发一条消息看日志 | 只读官方文档和仓库结构 |
| 产出 | 同一张评估表，每行有实测依据 | 同一张评估表，每行注明依据出处 ＋ “这一条我没验证过” |

**B 路径不是 A 路径的降级版。** 真实项目里，绝大多数进场评估都是在拿不到环境的
情况下做的——能把“我没验证过”这几个字明明白白写进评估表，本身就是一项能力。

### A 路径开跑之前

```
□ 先确认运行时版本    —— 前置条件，上不去就直接走 B 路径
□ 准备一个模型端点    —— 接不上就按七步顺序排查，这本身就是第 3 行的内容
□ 先跑配置树输出      —— 在改任何东西之前跑一次，存下来，这是基线
□ 看一次强制力等级    —— 拿到“部分”不是失败，是第 4 行的答案
```

**整个上机过程中，每做一步就填一行表。不要等做完再回忆着填。**

## 三、开源组件进场评估表

每一行填三样：**结论**、**依据**、**证据等级**（实测 / 读文档 / 未验证）。

| # | 问题 | 骨架层 | 结论 | 依据 | 证据等级 |
|---|---|---|---|---|---|
| 1 | 它归谁维护？合同期和它的版本节奏哪个更长？ | 公理 | | | |
| 2 | 它能帮你过哪几关？哪几关它帮不上？ | 过程 | | | |
| 3 | 接得上吗？端点、协议、凭据三件事各自的结论是什么？ | 过程 | | | |
| 4 | 它的护栏能不能自报强制力？失败时是拒绝还是放行？ | 控制 | | | |
| 5 | 它默认往外发什么？能不能关？关法写进物料清单了吗？ | 控制 | | | |
| 6 | 它留下的痕迹够不够回答“当时它看到了什么”？ | 证据 | | | |
| 7 | 痕迹是持久的还是进程内的？重启之后还在吗？ | 证据 | | | |
| 8 | 它帮你攒下了什么模型换了也不用重建的东西？ | 资产 | | | |
| 9 | 许可证是什么？客户的软件清单接受吗？ | 风险 | | | |
| 10 | 拆／改／嵌之后，上游升级的验证面有多大？ | 风险 | | | |

### 一行填完长什么样

| 列 | 示范 |
|---|---|
| 结论 | 护栏能自报强制力，本机为“部分” |
| 依据 | 运行时返回的强制力字段；内核版本 X |
| 证据等级 | 实测（日期、机器） |

**反例**：结论写“护栏很完善”，依据写“官方文档”，证据等级空着。三处都不合格。

### 最后 20 分钟：两组交换

按这个顺序问对方那张表：

1. 哪一行的“依据”那一列写的是感觉，不是出处？
2. 哪一行的证据等级标的是“实测”，但其实只是看到了文档里这么写？
3. 第 1 行答出来了吗？“归谁维护”这个问题，答案里有具体的人或团队吗？
4. 第 8 行答出来了吗？答不出来的话，用它到底为你留下了什么？

**一张全是“实测”的评估表，通常是一张没认真做的评估表。**

## 四、七个模块的清单合集（现场速查）

### 4.1 可配置 vs 可替换

| | 可配置 | 可替换 |
|---|---|---|
| 你能说的话 | 已配置为不允许任何域名 | 树里没有这个工具 |
| 证明方式 | 展示配置文件当前的值 | 展示配置树，那一项不在里面 |
| 出错时 | 配置读取失败可能回落到默认值 | 没有的东西不会因为读取失败而出现 |

**一个被配置关掉的能力，仍然在进程里。**

### 4.2 接不上的七步排查

```
① 网络可达      在目标机器上直接发一次请求，不在自己笔记本上试
② 凭据          环境变量名、值有没有被引号包进去、前后空格
③ 协议形状      这个端点到底是哪种协议
④ 两个开关      推理模型单独失败 → 角色开关；整个请求被拒 → 字段名开关
⑤ 模型目录声明  分清是发送前被拒还是发送后被拒
⑥ 网关自己的限制 并发上限、单请求体积上限、超时
⑦ 再回头看日志  前六步都排除了，才值得逐字读模型请求的组装结果
```

**进场之前先查两件在会议室里问不出来的事**：目标机器的运行时版本；
有没有一个能用的模型端点。

### 4.3 交付材料里关于护栏的六行

```
□ 本机实际强制力等级、内核版本、记录日期——三样一起写
□ 沙箱管什么、不管什么——主动写明网络与进程可见性不在其范围内
□ 每个旋钮的实际取值，不是预设名
□ 审批在无人值守时的行为：拒绝还是放行？验证过吗？
□ 每条护栏配一条验证命令 ＋ 一段预期的拒绝输出，成对写
□ 写状态描述时用“每一次执行按会话解析”，不用“整个进程运行在某模式下”
```

### 4.4 从故障采回归用例的四步

```
第一步  故障还热着的时候先记会话 id
        在群里回“我看一下”的同时把 id 贴出来

第二步  修完之后从那个会话里取三样
        当时的输入、当时的上下文投影、当时的工具调用与返回
        注意：要“按当时的投影”，不是“全部日志”

第三步  写判据，不写期望输出
        回归集守的是行为的边界，不是文本的相等

第四步  挂进能自动跑的地方
```

**最短判据**：如果把代码回滚到修复之前，这条用例会不会失败？不失败就是没抓住。

**三条边界条件**：会话日志里有客户业务数据，脱敏之后才能进你的仓库；
环境相关的故障要标注清楚，不要当成不稳定用例删掉；回归集单调增长但 CI 有时长预算，
分层跑、全量定期跑。

## 六、五天收束

### 如果只带走三句话

**一、客户买的是风险转移，不是代码。**
所以计价方式决定了这句话有没有牙齿——系统没人用你会少收多少钱，
答案是“一分不少”的话，责任其实还在客户那边。

**二、顺序被关卡锁死。**
证据攒在第 2–4 关，控制攒在第 5 关，接管只能在第 6 关。
没有证据就上线，控制保护的是一个没人验证过的东西。

**三、留下的东西必须反锁定。**
在“成果全部归甲方”这类条款下，任何以锁住客户为目的的资产都谈不下来。
唯一立得住的，是明确增强客户自主权的那一样。
