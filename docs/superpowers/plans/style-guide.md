## 1. 语气

**工程师对工程师。直给结论，先说做法再说原因。**

第 1 章开篇是标准示范：

> 前线部署工程师（Forward Deployed Engineer, FDE）这个词不是哪个咨询公司发明的营销概念，
> 它有明确的出生证明：Palantir。

**禁止**：
- 「随着人工智能的飞速发展」「在当今数字化浪潮下」「众所周知」这类开场
- 「本节将介绍……」这类元叙述，直接讲内容
- 「非常重要」「至关重要」这类强调词——重要性由内容本身体现
- 正确的废话（「要重视需求调研」「建立清晰的沟通机制」）

**要做**：
- 第一句就进正题
- 有争议的地方摆出争议（第 1 章引了 a16z 对 FDE 岗位的批评「title arbitrage」并表示认同）
- 该说「我们没查到」的时候就说

## 1.5 文风红线：既不要 AI 味，也不要口水话

目标是**一个有十年经验的工程师在写技术书**。不是论文，不是公众号推文，不是博客。
终校（Task 50）要逐章按这一节清理。

### A. AI 味的九种典型症状（见到就删或改写）

| 症状 | 例子 | 改法 |
|---|---|---|
| 万能开场 | 「随着人工智能的飞速发展」「在当今数字化转型的浪潮下」 | 删掉，第一句直接进正题 |
| 空洞强调 | 「至关重要」「不容忽视」「值得注意的是」「显而易见」 | 删。重要性由内容本身体现，不靠形容词 |
| 强行排比 | 「不仅……而且……更重要的是……」 | 拆成陈述句 |
| 升维套话 | 「这不仅仅是技术问题，更是……」 | 删。除非真的要讲第二层，且第二层有内容 |
| 凑数分点 | 明明两条，非要硬凑成三条 | 有几条写几条 |
| 每段总结 | 段末都来一句「综上所述」「总而言之」 | 删。段落自己会结束 |
| 预告过渡 | 「接下来我们将探讨……」「下面让我们看看……」 | 删。直接写下一节 |
| 抽象名词堆砌 | 「赋能」「抓手」「闭环」「链路」被滥用成万金油 | 换成具体动词：「让 X 能做 Y」 |
| 结尾升华 | 「让我们一起拥抱……」「未来已来」 | 删。技术书不需要号召 |

### B. 口水话的六种症状（矫枉过正的另一头）

| 症状 | 例子 | 改法 |
|---|---|---|
| 语气词泛滥 | 「其实吧」「说白了」「你懂的」「emmm」 | 删 |
| 过度自问自答 | 每隔两段就「那么问题来了？」 | 一章最多一两次，且问题要真值得问 |
| 段落碎成短句 | 连续五六行都是十来字的短句 | 该长的句子就写长，逻辑连贯优先 |
| 表情与感叹号 | 😊 「太强了！」 | 删。⚠️ 只用于合成案例警示标注 |
| 第二人称过腻 | 「亲爱的读者朋友，你一定会想……」 | 用「你」可以，但当工程师之间讲话，不是导购 |
| 网络梗与流行语 | 「YYDS」「一整个大无语」 | 删。三年后没人看得懂 |

### C. 判定标准

改完之后自问三句：

1. **这句话删掉，读者会损失什么？** 答不上来就删。
2. **这话像不像一个人对另一个人说的？** 不像就重写。
3. **五年后重读，会不会觉得当年的文风很尴尬？** 会就重写。

### D. 保留什么

**不要为了去 AI 味把书改成大白话。** 以下都要保留：
- 完整的长句——技术论证本来就需要从句和限定
- 书面语的连接词（「因此」「但」「换言之」）
- 精确的术语，包括英文原文
- 「笔者归纳」「未逐字核对」这类限定语——那是可信度分层的一部分，不是啰嗦（**但只在 A9 规定的三类地方用，见文末 A9**）
- 表格、清单、决策树等结构化表达

**已确认的三个样板**（`book/01-`、`book/07-`、`book/17-`）就是文风基准。
拿不准时对照它们。

## 2. 可信度分层（★贯彻全书）

**这是本书区别于市面同类内容的核心，不得省略。**

调研阶段做了 530 处引文的全量审计，修正 87 处（失败率 16.4%），
包括杜撰的法条、错配的公司名、编造的验收标准示例。**这套严格性必须在正文里可见。**

### 分层标准
| 层级 | 例子 | 引用方式 |
|---|---|---|
| 一手可验证 | 官方 JD、法条原文、官方模型卡、arXiv 论文全文 | 直接引用，带 URL 与检索日期 |
| 多源交叉印证 | 同一数字在两个独立信源出现且量级吻合 | 可引用，注明「多源交叉」 |
| 二手推测 | 招聘中介博客的薪酬估算 | 引用时**必须**标注「未经官方验证」 |
| 笼统说法 | 「年薪可达百万级别」，无区间无分位数 | **不采信**，可对照着说明为什么不用 |

### 硬性做法
- **溯不到源的说法直接放弃**，不要模糊化处理后偷偷用上。
  第 1 章的示范：「四周现场冲刺解锁百万合同」这类说法读起来像销售话术，经不起追问：
  哪四周？谁的合同？本书没有找到能验证的公开一手数据，不编造，直接跳过。
- **抓取失败要写出来**：「Levels.fyi 与 Glassdoor 页面核实时分别返回 404 和 403，
  本书拿到的数字是经搜索引擎摘要间接获取的，没有逐字核对原始页面」
- **口径不同的数字不能并列比较**，要说明为什么不能比

### 禁用清单
见实施计划 Global Constraint #13。写作前必读，涉及：
源 PDF 的薪酬四档表（编造）、「Operating Loop」（自造术语）、「80% 自治率」（无来源）、
「RAND 80% 失败率」（实为供应商 CEO 采访发言）、「70% 变革失败率」（僵尸数字）、
John Deere「70%」（须限定为峰值，官方年均 59%/2024、约 50%/2025）。

## 3. 章节固定结构

```markdown
# 第 N 章 · 标题

（案例章：章首 ⚠️ 教学合成案例标注，见第 6 节）

## 本章目标
（3–5 条。写「读完能做到什么」，不是「了解 XX」。
 样板：「用『介入时机 + 成功指标 + 谁背什么锅』三个维度，快速判断一份 JD 写的
 到底是 FDE 还是 SE / CE / BA-PO，不被头衔忽悠」）

## N.1 …
## N.2 …

## 本章要点回顾
（5–7 条，每条是一个可独立成立的判断，不是章节目录的复述）

## 自检问题
（5–8 题。**给判断标准，不给完整答案。**见第 5 节）

## 参考来源
（编号 + 标题 + Markdown 链接 + 检索日期。低质量来源要在括号里标明性质）
```

**章末要有向下一章的过渡句**，说明本章结论如何被下一章使用。

## 4. 篇幅

- 计划里每章的页数是**下限不是上限**
- 1 页 A4 ≈ 800 中文字符（正文），代码块按 40 行 ≈ 1 页折算
- 校验用 `len(re.findall(r'[一-鿿]', text))`，只数中文字符
- **允许超出，禁止注水**

### ★ 关于「篇幅不够怎么办」

**不要编新事实或引文来填。** 这是有实测教训的：02 号调研笔记为达标做过一次大规模扩写
（8000 → 38000 字），引文失败率从 5% 飙到 22%，其中包括 4 个完全虚构的验收标准示例。

**大规模扩写是伪造引文的高发期。**

篇幅不够时的正确做法：
1. 把已有素材讲出层次（机制 → 判据 → 边界条件 → 反例）
2. 补充「什么情况下这个做法不适用」——这类内容最容易被略过，也最有价值
3. 实在不够就写短，并在报告里说明素材缺口

## 5. 自检问题

**给判断标准，不给完整答案。** 目的是让读者自查思路，不是背答案。

样板（第 1 章第 3 题）：

> **Anthropic Applied AI Architect 的薪酬区间（$240K–$315K）不低于 Applied AI Engineer
> （$200K–$320K），这条数据能得出什么结论、不能得出什么结论？**
>
> 参考答案要点：能得出——市场对「售前技术说服力」的定价不低于「工程实现能力」。
> 不能得出——不能推广为「所有公司的售前岗位都比工程岗位赚得多」，
> 这只是 Anthropic 一家公司的内部定价，样本量为 1。

注意这题同时在教**统计谦逊**。好的自检题应该有这种额外收益。

题型建议：判断类（这个岗位是 FDE 还是 SE）、辨伪类（看到这个数字该怎么核查）、
权衡类（这两个方案在什么条件下各自更优）、反例类（这个结论在什么情况下不成立）。

## 6. 案例章专用

### 七段式模板（第 17 章定型，六个案例章沿用）

1. **客户背景** —— 场景、规模、现有流程
2. **真实冲突** —— 具体的技术与业务矛盾，不写「面临挑战」这种废话
3. **被否决的方案** —— **至少两个，写清否决原因**。★这一段是案例章的价值核心，
   只讲最终方案是产品手册，讲清为什么否决了另外两个才是工程复盘
4. **最终架构决策** —— 怎么选的、判据是什么
5. **关键代码骨架** —— 片段即可；有对应 Lab 就指向 Lab，没有就标明「示意，未实测」
6. **踩过的坑** —— 统一用「**当时以为** X，**实际** Y」格式
7. **复盘与可迁移经验** —— 分「可迁移」与「不可直接迁移」两块写

### 合成案例标注

章首用引用块，格式：

```markdown
> ⚠️ **教学合成案例**：本章的项目叙事、架构决策过程与踩坑细节为基于行业常态构建的
> 教学案例，非特定客户的真实项目。文中标注了来源的具名企业数据（<具体列出>）
> 为可查证的真实信息，已注明出处。
```

**行文中合成部分与可查证部分要能分辨**，不要让读者以为整章都是真事。
案例档位见 `docs/research/07-cases.md`（可查证 / 部分可查证 / 无来源）。

## 10. 提交协议（并行写作时）

### ★ 只用这一条命令提交，不要拆成两步

```bash
git commit -m "docs: 第 N 章 xxx" -- book/NN-xxx.md
```

**⚠️ 参数顺序不能反。** `git commit -- <path> -m "..."` 会把 `-m` 和消息本身
当成路径参数，报 `pathspec '-m' did not match any file(s)`。
`-m` 必须在 `--` 之前。

**⚠️ 新文件的第一次提交要多一步。** `git commit -- <path>` 的路径匹配**只认已被索引的文件**，
全新未跟踪的文件会报 `pathspec ... did not match any file(s)`。所以每章的**第一次**提交要写成：

```bash
git add -- book/NN-xxx.md
git commit -m "docs: 第 N 章 骨架" -- book/NN-xxx.md
```

**只有第一次需要这样**，文件被跟踪之后的所有增量提交都用一步式。
这一步的 `git add` 明确指定了路径，不会卷入其他 agent 的文件。

**不要写成 `git add <file>` + `git commit`。** 这两步之间存在时间窗，
并发的其他 agent 可能在这个窗口里把它的文件暂存进共享 index，
你的 commit 会把它一起提交走。

**这不是理论风险，实测发生过**：第 3 章的 agent 用了两步式，
把第 8 章写到一半的文件卷进了自己的提交，事后要用 `git rm --cached` 撤出来
（`git rm --cached` 是正确的补救方式——只取消跟踪，不碰工作区文件）。

- **禁止 `git add -A` / `git add .`**

### ★★ 每写完一个 `##` 小节就立刻提交

**不允许连续写两个小节而不提交。** 这是机械规则，不是建议。

**实测教训**：一轮并行写作中，六个 agent 在同一时刻因会话额度耗尽中断，
凡是没落盘的全部丢失——**包括一章已经写完 10584 字、只差最后提交的**。
那一章之所以保住，纯粹是因为文件已经写到磁盘上，控制者手动捡回来的；
另外五章从零开始重写。

**攒着不提交 = 随时可能白干。** 中断可能来自额度耗尽、进程退出、终端断开，
这些都不可预测，而且往往同时命中所有并行 agent。

做法：
- 写完 `## N.1` → 提交 → 写 `## N.2` → 提交 → …
- 提交信息用 `docs: 第 N 章 N.X 小节标题`，最后一次用 `docs: 第 N 章 完稿`
- **允许提交不完整的章节。** 仓库里有一个写到一半的章节，
  远好过有一个丢光的章节
- **篇幅校验只在最后一次提交前跑**，中途不用管字数
- 骨架先提交一次，之后分节提交，**不要攒到最后**（进程崩过一次，丢过 4 个 agent 的成果）
- 撞 `index.lock` 等几秒重试

# 附 · 2026-08-20 两册重构追加约定

> 以下七条在原有约定之上叠加，**优先级高于前文任何与之冲突的条目**。
> 重构背景与两册目录见 `2026-08-20-两册重构方案.md`。

## A1. 英文长引文一律转中文

正文不出现连续三行以上的英文原文。需要保留原话的，**中文转述放正文，英文原文放章末参考来源**。

反例（原第 1 章）：连续三段 Palantir 官方博客英文原文块。中国读者会直接跳过，
跳过之后后面的论证就断了。

正例：「官方博客把这条分界线概括成一句话：一边是一个能力服务很多客户，
另一边是一个客户需要很多能力。」

## A2. 弱化外国人名

公司名保留（Palantir、OpenAI、Anthropic 这类无法替代）。
**具体外国员工的姓名、职称、所在城市一律删除**，改成职能描述。

| 改前 | 改后 |
|---|---|
| 纽约的 Delta Elisa 说…… | 官方博客里几位一线工程师的说法归纳起来是…… |
| 阿布扎比的 Dyon 和圣保罗的 G.M. 补充 | （合并进上一句，不单列） |
| Marty Cagan 提出的四类产品风险框架 | 产品管理领域一个流传很广的四类风险框架 |

人名进章末参考来源，正文不出现。判据很简单：**这个名字删掉，读者会损失什么？**
答不上来就删。

## A3. 术语首次出现给一句人话

在首次出现处就地加括号解释，不要让读者去翻术语表。

- 向量检索（把文字变成一串数字，再找数字最接近的那几段）
- override 率（人工改写模型结果的比例）
- 灰度发布（先放一小部分流量进来，出事只影响这一小部分）

## A4. 引用链接一条不删

章末「参考来源」保留完整 URL 与检索日期。这是本书可信度的基础，也是读者验证的入口。
**任何「篇幅原因略去部分引用」的做法都不允许。**

## A5. 每章开头换成场景

现在多数章第一句是定义或分类，读起来像教材。改成一个具体现场，120–250 字，
让读者先反应过来「这不就是我上周碰到的事」。

场景要有细节：什么客户、卡在哪、当时怎么办的。不要写「随着 AI 的发展」，
不要写「本章将介绍」。

## A6. 「要点回顾」改成「本章清单」

要点回顾是复述知识，清单是布置动作。条目一律写成动作句：

| 改前 | 改后 |
|---|---|
| 退出标准必须可判定 | [ ] 把手上项目的退出标准逐条读一遍，凡是不能用「是/否」回答的，当场重写 |
| 评估集要覆盖真实失败案例 | [ ] 数一下评估集里有多少条来自真实历史工单，低于 20 条就补到 20 条 |

## A7. 统一的章节模板

```markdown
# 第 N 章 · 标题

> **一句话结论**：（不超过 40 字）

## （一个具体场景的小标题）
```

## A9. 可信度限定语只用在三类地方（2026-08-21 追加，优先级高于第 2 节）

第 2 节的可信度分层**继续有效**，但**表达方式**收紧。读者反馈正文晦涩，
实测下来限定语是长句的主要成因之一。规则：

**按顺序问三个问题：**

1. **不说这句限定，读者会不会照着一个错的东西去做事？** 会 → 留在正文，而且要显眼。
   典型：反常识的结论、会被拿去写方案/谈薪/做决策的具体数字、法规条款。
2. **这句是在说“信息本身多可靠”，还是在说“我是怎么查的”？** 后者 → **删。**
   调研过程不是读者的事。
3. **剩下的（官方／二手／博客这类出处属性）** → 下沉到章末参考来源，正文一个字不留。

**两条硬规则：**

- **一个数字如果不可信到不能用，就别在正文出现。** 不要“引一个数字 + 说它不可信”，
  那是两头不讨好：占了篇幅，又没给出可用信息。要么删掉数字只留方向性结论，
  要么留数字并写清楚怎么用。
- **内部调研笔记编号、抓取工具名一律不进正文**（“06 号调研笔记”“本轮检索”
  “WebFetch 抓取时”“本笔记”）。这些是写给自己的话。

**表达形式**：留下来的限定语，从句子里拿出来单独成块或成短句，不要塞进主句里当从句——

```markdown
> **可信度说明**：本节内容为二手转述，未能逐字核对原文。
```

## A8. 关卡编号是硬约定

六道关卡：第 1 关 选题 / 第 2 关 定界 / 第 3 关 切片 / 第 4 关 验收 / 第 5 关 上线 / 第 6 关 采用，
两册共用同一套编号。

**不再使用 G1–G6 这套字母编号**（G 取自 Gate，对中文读者太晦涩）。全书已统一替换，
新写的内容一律用「第 N 关」。空格规则：作为标签时保留空格（「第 2 关 定界」，
用于标题、表格、图示），行文中不留（「卡在第 3 关」「在第 4 关爆炸」）。

- 讲到某个问题时，标出它属于哪一关（「这类问题死在第 2 关」）
- 跨册引用写成「上册第 8 章 / 下册第 9 章，同属第 4 关」
- **不要新造平行的阶段名**。「六阶段」「作业闭环」这些旧称呼全部替换为「六道关卡」

## A10. 方法论用词约束（2026-08-25 追加，优先级高于第 2 节）

本书有一批自造概念。**给自造概念硬找祖先，是本书最容易犯、也最难被读者发现的错。**
下表逐条规定怎么说、怎么不能说。**新写和改写一律照此表。**

| 本书概念 | 该怎么说 | 不该怎么说 |
|---|---|---|
| 六道关卡 | 本书综合 Stage-Gate、精益实验与高可靠治理提出的证据门控框架 | 六道关卡源于 Stage-Gate |
| 证据—控制—接管 | 本书对质量管理、社会—技术治理与吸收能力的三段式综合 | 管理学已有的标准模型 |
| spec coding | 以 BDD/ATDD、可执行规格和精益反馈为谱系的 AI 原生开发方式 | 精益方法论直接提出了 spec coding |
| thin slice | 精益小批量、敏捷频繁交付在工作流层面的应用 | 就是做一个功能少的 MVP |
| Customer Zero | 领先用户创新与组织吸收能力在内部场景的组合应用 | 内部用了就证明外部客户会用 |
| champion network | 以创新实施氛围、同伴扩散和实践共同体为依据的采用机制 | 找几个关系好、愿意宣传的人 |
| 模型中立 | 基于交易成本、退出权和韧性的治理主张 | 所有模型随时无成本替换 |
| 现场嵌入 | 边界跨越与隐性知识发现的组织机制 | 驻场越久，客户价值越高 |
| 四层骨架 | 本书提出的教学结构，每一层各有独立理论支撑 | 行业通用的分层模型 |

**三档措辞，按证据强度选：**

| 档 | 什么时候用 | 措辞 |
|---|---|---|
| 直接出处 | 理论与动作有清晰、可核验的概念对应 | 「依据」「源于」「可由……解释」 |
| 组合推导 | 多个成熟理论被重新组合到 AI 交付情境 | 「可综合为」「本书据此推导」 |
| 本书原创 | 为教学和实践提出的新名称、新结构 | **「本书提出」「本书将其定义为」** |

**和 A2 的关系**：学术出处按 A2 处理——**正文只出现概念名，人名与年份进章末参考来源。**
正文写「组织研究里有一个边界跨越者的概念」，不写「Tushman 和 Scanlan 提出……」。
