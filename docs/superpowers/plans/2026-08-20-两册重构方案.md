## 1. 拆分方案

### 1.1 为什么不按「方法论 / 技术」直接切

按「方法论归上册、技术归下册」切，会立刻撞上三个麻烦：

- **案例章无处安放。** 七个案例每一个都同时含决策线和工程线，整章丢给任何一册都会让另一册变干。
- **中国落地五章横跨两边。** 甲乙方关系、国企银行政务、合规备案是决策层的事；国产模型选型、信创适配是工程层的事。捆在一起没法分。
- **评估与护栏（原第 7 章，3.2 万字）本身就是骑墙的。** 「验收标准怎么定」是高管要听的，「LLM-as-Judge 的提示词怎么写、CI 门禁怎么挂」是工程师要看的。

### 1.2 实际采用的切法：一副骨架，两个视角

两册共用同一副骨架（§2 的六道关卡），区别只在回答的问题不同：

- **上册回答「这一关该怎么设、谁签字、什么条件下叫停」** —— 判据、产出物、责任人。
- **下册回答「这一关怎么用代码过」** —— 实现、验收脚本、Lab。

好处是两册可以**按关卡号互相索引**：上册读到「关卡四·验收」，脚注直接指向下册对应章；下册工程师想知道某个门禁值为什么定在那儿，回上册看判据。培训时也能分开卖：上册两天高管班，下册三到五天技术班加 Lab。

## 2. 六道关卡：全书骨架

这是本次重构最核心的改动，用来回应「更系统化，要有层级、有骨架」。

```
第 1 关 选题 ──→ 第 2 关 定界 ──→ 第 3 关 切片 ──→ 第 4 关 验收 ──→ 第 5 关 上线 ──→ 第 6 关 采用
   ↑                                                              │
   └──────────────── 反哺：把这次的经验变成下次的默认值 ←──────────┘
```

每一关在两册里都用同一张四栏表描述，栏目固定：

| 栏目 | 含义 |
|---|---|
| **进入条件** | 上一关交付了什么，才允许进这一关 |
| **产出物** | 这一关结束时手上必须有的东西（文档、代码、数据、签字） |
| **通过标准** | 什么情况下算过。必须是可验的，不能是「大家觉得差不多了」 |
| **失守的后果** | 这一关没守住，通常在哪一关爆炸、爆炸的样子是什么 |

上册讲前三栏，下册讲第二、三栏的工程实现。第 3 章（死法）和第 14 章（复盘）都按关卡号归因，读者读完能形成一张「问题 → 关卡」的对照表。

### 2.1 统一的章节模板

两册所有章统一改成这个结构，替换现在的「本章目标 → N 个小节 → 要点回顾 → 自检 → 参考来源」：

```markdown
# 第 N 章 · 标题

> 一句话结论：（这一章最想让你记住的那一句，不超过 40 字）

## 开头：一个具体场景
（120–250 字。真实到有细节：什么客户、卡在哪、当时怎么办的。
 不写「随着 AI 的发展」，不写「本章将介绍」。）

## 读完这章你能做什么
（3–5 条，每条是一个动作，不是一个知识点。）

## N.1 ... N.x 正文
（每节开头先给结论，再给理由。术语首次出现给一句大白话解释。）

## 本章清单
（可以直接照着做的动作项，带勾选框。区别于原来的「要点回顾」——
 要点回顾是复述知识，清单是布置动作。）

## 自检问题
（保留。3–6 题，带参考答案要点。）

## 参考来源
（保留全部链接与检索日期，一条不删。英文原文引用放这里，正文只出中文转述。）
```

## 3. 文风改造七条

在现有 `style-guide.md` 之上追加。原文件的「AI 味九症状」「口水话六症状」继续有效。

1. **英文长引文一律转中文。** 正文不出现连续三行以上的英文原文；需要保留原话的，中文转述在正文，英文原文进章末「参考来源」的注里。示例：原第 1 章那三段 Palantir 官方博客英文引文全部改写。
2. **弱化外国人名。** 公司名保留（Palantir、OpenAI、Anthropic 等无法替代）；具体外国员工姓名、职称、所在城市一律删除，改成「官方博客里几位一线工程师的说法归纳起来是……」。中国读者不认识这些人，写出来只增加阅读成本。
3. **术语首次出现给一句人话。** 例：「向量检索（把文字变成一串数字，再找数字最接近的那几段）」。全书统一在首次出现处加，不在术语表里等读者去查。
4. **不省略引用链接。** 章末「参考来源」保留完整 URL 与检索日期。这是本书的可信度基础，也是读者验证的入口。
5. **每章开头换成场景。** 现在多数章第一句就是定义或分类，读起来像教材。改成一个具体现场，200 字以内，让读者先「这不就是我上周遇到的事」。
6. **可执行优先于可理解。** 每章末的「要点回顾」改成「本章清单」，条目一律写成动作句（「把 X 写进 Y」「上线前跑一遍 Z」），不写陈述句。
7. **降低预设门槛，但不降低密度。** 假设读者写过代码、用过大模型 API，但没做过客户现场交付；不假设读者读过论文、了解 Palantir 组织史、熟悉英文 JD 的行文习惯。删掉的是背景知识门槛，不是内容深度。

- 3.2 组合用法：宪法用 Spec Kit 立，日常增量用 OpenSpec 提案，执行纪律用 Superpowers 兜
- 3.3 Git 协作规范（分支、Conventional Commits、PR 对照宪法评审、密钥绝不入库）
- 3.4 团队一致性：constitution 是共享契约，不是某个人的偏好
- 3.5 常见翻车与对策（取自 FAQ）
- 3.6 这套东西和本书 12 个 Lab 的 `verify.sh` 是同一件事的两个层次

## 5. 这本书凭什么算经典

三条护城河，改写全程不许削弱：

1. **可信度分层。** 530 处引文全量审计、87 处修正的记录继续留在书里。「未逐字核对」「笔者归纳」这类限定语是特征不是瑕疵。
2. **代码可跑。** 12 个 Lab 全部实现并通过 `verify.sh`，正文代码标注来源。全书仅剩的 3 处「未实测代码」逐处写明缺什么条件。
3. **骨架可用。** 六道关卡不只是目录结构，是读者第二天上班就能拿去用的检查表。上册附录 A 的一页纸自查表是这条的落点。
