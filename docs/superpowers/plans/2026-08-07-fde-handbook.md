# 《AI 前线部署工程师（FDE）实战教程》实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 产出一本 250–280 页 A4 的中文 FDE 实战教材（29 章 + 4 附录 + 12 个可运行 Lab），读者学完可独立承担 AI FDE 岗位。

**Architecture:** 分章 Markdown 源文件 + 独立 Lab 代码仓 + Pandoc/XeLaTeX 构建脚本合并出可打印 PDF。写作顺序为「调研补料 → 风格样板定稿 → 分部批量撰写 → Lab 实现与实测 → 合并排版校对」。

**Tech Stack:** Markdown · Mermaid · Pandoc + XeLaTeX · Python 3.11 · LangGraph · Qdrant · vLLM · Langfuse · Docker Compose

**设计文档:** `docs/superpowers/specs/2026-08-07-fde-handbook-design.md`（章节大纲、页数预算、Lab 清单的唯一真源）

## Global Constraints

以下约束适用于每一个 task，不再逐条重复：

1. **语言**：简体中文。技术术语首次出现给英文原文，如「检索增强生成（Retrieval-Augmented Generation, RAG）」。
2. **篇幅**：spec 中每章标注的页数是**下限**。1 页 A4 ≈ 800 中文字符（正文），代码块按实际行数折算（40 行代码 ≈ 1 页）。允许超出下限，**禁止为凑页数注水**。
3. **章节结构**：每章必须包含 `## 本章目标` → 正文 → `## 本章要点回顾` → `## 自检问题`（5–8 题，附参考答案要点）→ `## 参考来源`。
4. **事实标注**：薪酬数据、市场数据、法规条文、框架 API 四类内容必须来自 `docs/research/` 下的调研笔记，正文带角标，章末列来源 URL 与检索日期。
5. **案例真实性**：非公开可查证的案例，必须在章首用引用块标注 `> ⚠️ 教学合成案例：基于行业常态构建，非特定客户真实项目。`
6. **代码**：长代码放 Lab，正文只放关键片段并给出 Lab 路径。因阶段三（章节）先于阶段四（Lab），章节中尚未经 Lab 验证的代码块必须在块前一行标注 `<!-- UNVERIFIED: Lab-NN -->`，对应 Lab task 完成后**必须**执行回填：以 Lab 中实测通过的代码为准修正正文，并删除该标注。Task 50 终校会扫描残留的 `UNVERIFIED` 标注，有残留即判不通过。
7. **图表**：架构图与流程图用 Mermaid 源码内嵌；决策/对比用 Markdown 表格。不做装饰性配图。
8. **语气**：工程师对工程师。直给结论，先说做法再说原因，不写「随着人工智能的飞速发展」这类开场白。
9. **文件命名**：`book/NN-章节短名.md`，NN 为两位数章号（00–28）。
10. **提交**：每个 task 结束提交一次，message 前缀 `docs:`（章节）/ `feat:`（Lab 代码）/ `chore:`（构建脚本）/ `research:`（调研笔记）。

11. **并行 agent 的提交协议**（一次会话崩溃丢掉 4 个 agent 成果后加的）：

    教训：为避免 git 竞争而禁止并行 agent 提交，结果进程退出时 4 个 agent 的成果全部
    丢失（只在内存里，未落盘）。**未提交 = 未完成**。

    并行 agent **必须自己提交**，但：
    - **必须用 `git commit -- <自己的文件路径>` 这种 partial commit 形式**，一步完成暂存+提交。
      只用 `git add <file>` 再 `git commit` **不够**——并发下别的 agent 可能已经把它的文件
      暂存进了共享 index，你的提交会把它一起卷进去。实测发生过：一个 agent 的提交里
      混进了另一个 agent 的 `02-methodology.md`（内容没丢，但提交信息与内容对不上）
    - **禁止 `git add -A` / `git add .`**
    - 提交前不必检查其他文件的状态，只管自己那一个
    - 撞 `index.lock` 就退避重试，不要放弃提交
    - 长任务应**分阶段提交**（例如调研笔记先落一版骨架再逐节补），不要攒到最后一次性提交

12. **引文保真度强制流程**（阶段一三次踩坑后加的硬约束，所有调研与撰写任务适用）：

    问题模式：agent 在想让论述更有力时，会把转述、改写、拼接的内容加上引号，并声称
    "已抓取逐字核对"。01 号笔记出现 4 处，02 号扩充又出现 3 处（其中 Docusign SOW
    四句条款整段编造——原页面根本没有那些句子）。**声称核对过本身不可信。**

    因此每一条带引号的内容必须满足全部三项，缺一不可：
    - **原文可复现**：给出抓取方式（WebFetch / curl / r.jina.ai 代理）与页面上用于定位
      该句的锚点（前后文关键词）。写"经核对"而不给锚点视同未核对
    - **不得跨句拼接**：两个不同句子不许合并成一个引号短语。要引两句就分别引，各自标出处
    - **不确定即降级**：抓不到、被墙、被 CAPTCHA 拦、只找到二手转述——一律移出
      「一手引文摘录」，改为不带引号的概括并注明「系笔者归纳」，同时写进「存疑与待核实」

    审查任务必须**逐条**核对引文，不许抽样。抽样通过 ≠ 该文件通过。

    **抓取方式有优先级，WebFetch 排最后。** Task 4 审查中实测：核对 vLLM 量化支持表时
    WebFetch 的 AI 摘要给出了与原文相反的结论（误报 AWQ 在 x86 CPU 上不支持），
    用 `curl` 拉 GitHub 原始 Markdown 后才发现摘要错了。**WebFetch 会对页面做二次转述，
    转述本身可能出错**——用它核对引文等于用一个可能出错的工具去查另一个可能出错的结论。
    因此核对引文时：
    1. **首选原始文本**：`curl -sL <URL>` 拿 HTML/Markdown 源码；GitHub 上的文档直接取 raw 链接；
       arXiv 取 HTML 版或 PDF 全文；PyPI/GitHub 版本号走 JSON API
    2. 次选 `https://r.jina.ai/<原URL>` 代理（返回的是页面正文纯文本，不做摘要）
    3. **WebFetch 仅用于初步定位**，不得作为"逐字核对通过"的唯一依据

    **WebSearch 的摘要同样会编造。** Task 7b 实测：检索"交付沉淀为产品能力"的案例时，
    WebSearch 返回了一个带具体数字（90% / 18 个月）的 Mailchimp 产品化案例，
    去直接抓它标注的来源核实——**该案例根本不存在**。
    两个检索工具都已被实测抓到会引入幻觉。因此：
    **凡是从 WebSearch / WebFetch 摘要里得到的事实、数字、案例，都必须再去原始页面确认存在，
    确认不了的一律不用。** 检索工具只负责"告诉你去哪找"，不负责"告诉你那里有什么"。

13. **源 PDF 已证伪内容的禁用清单**（阶段一调研的溯源结果，任何章节不得违反）：
    - **薪酬**：源 PDF 的四档表（$100K–130K / $130K–180K / $180K–250K+ / $250K–500K+）与 $210K 中位数**系编造**，其标注出处 sundeepteki.org 全文只有一句 `$135K–$600K` 笼统区间。第 1、27 章一律改用 `01-role-and-market.md` 中 Palantir / Databricks / Scale AI / Anthropic 官方 JD 逐条披露的真实区间。
    - **「Operating Loop / 作业闭环」不是业界既有术语**，检索无任何独立信源，系源 PDF 自造。第 2 章框架保留，但措辞必须降级为「本书归纳的作业闭环」，并在章首明示这是本书的整理框架而非行业标准术语。全书不得出现「业界称之为 Operating Loop」这类表述。
    - **「80% 自治率」（案例 B / 第 15 章）经多轮检索无任何信源**，判定为疑似编造。必须标注为合成案例的设定值，不得作为行业实测数据引用。
    - **「降低除草剂喷洒量 70%」（案例 D / 第 17 章）情况更微妙，不是简单证伪**：OpenAI 官网确有 "up to 70%" 的表述（一手来源存在），但 John Deere 自己披露的**年度平均值是 43%–59%**。
      `up to 70%` 是最优条件下的峰值，源 PDF 把它当成普遍效果无限定引用。
      **Deere 官方可核实的年度数字是 59%（2024 年官方新闻稿）与约 50%（2025 年）。**
      注意：早前笔记里写的"43%–59%"区间经全量审计**溯不到源，已删除**——不要再用这个区间。
      本书引用时必须写成"最优条件下最高可降低 70%，Deere 官方披露 2024 年为 59%、
      2025 年约 50%"，**不得只写 70%**。这个案例本身正好可以用来教读者一件事：厂商宣传的峰值数字与真实年度均值之间是什么关系——这是 FDE 在客户现场天天要面对的期望管理问题。
    - **源 PDF 的 arXiv 引用有两种隐蔽失真**（5 篇经 arXiv export API 逐篇核实，论文本身都真实存在，
      问题出在转述）：
      ① **把论文的抽象论点自行"具体化"成论文里不存在的术语**——如 `2604.02640`，源 PDF 替它编造了
      "精确匹配 / 余弦相似度 / k 折交叉验证"这些原文没有的具体名词，读起来更专业但是假的；
      ② **悬空引用**——`2506.00054` 与 `2410.12812` **两篇都是**，列在参考文献里却从未被正文实际引用，是凑数堆砌。
      （`2410.12812` 起初被判为"转述位置不精确"，04 号笔记的全量审计通过文本提取 + 将源 PDF
      第 7 页渲染成图片做视觉核对，确认脚注 23 在正文中从未出现、只存在于参考文献，
      **与 2506.00054 属同一类失真**。）
      引用这 5 篇时一律以原文为准，`docs/research/04-rag-and-evals.md` 有逐篇的「原文实际结论 vs
      源 PDF 转述」对照。转述最准的是 `2602.23374`（Higress-RAG），可放心引用。
    - **AI 项目失败率数字**：「RAND 称 80% AI 项目失败」不可用——溯源到 RAND 报告脚注引用的 2022 年 *Fortune* 文章，该数字实为一位 AI 供应商 CEO 的采访发言，非 RAND 研究结论。「70% 变革失败率」是已被证伪的僵尸数字（Hughes 2011）。唯一可引用的是 MIT NANDA 的「95% 零回报」，但其口径是**投资回报**而非「项目失败」，引用时必须写明口径，不得混用。

- [ ] **Step 3: 写构建脚本**

`build/build.sh`:
```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."

OUT="build/FDE实战教程.pdf"
CHAPTERS=$(ls book/*.md | sort)

echo "合并章节："
for f in $CHAPTERS; do echo "  - $f"; done

pandoc $CHAPTERS \
  --metadata-file=build/metadata.yaml \
  --pdf-engine=xelatex \
  --highlight-style=tango \
  --top-level-division=chapter \
  -o "$OUT"

echo "已生成 $OUT"
pdfinfo "$OUT" | grep -E '^(Pages|File size)'
```

- [ ] **Step 4: 写占位章节并验证构建**

`book/00-导读.md` 先写一个最小可编译内容（含一个标题、一段文字、一个表格、一段代码块、一个 Mermaid 块），用于验证中文字体、代码高亮、表格渲染都正常。

Run:
```bash
chmod +x build/build.sh && ./build/build.sh
```
Expected: 输出 `已生成 build/FDE实战教程.pdf` 且 `Pages: 1` 或 2。

- [ ] **Step 5: 处理 Mermaid**

Pandoc 原生不渲染 Mermaid。在 `build/build.sh` 的 pandoc 调用前增加预处理：用 `mermaid-cli`（`npm i -g @mermaid-js/mermaid-cli`）把 ```` ```mermaid ```` 块导出为 `book/assets/*.svg` 并替换为图片引用。若 mmdc 不可用，降级为保留代码块原样渲染（PDF 中显示为源码），并在 `build/build.sh` 中打印警告。

### ⚠️ 实测环境约束（2026-08-08 勘查，Lab 设计必须遵守）

| 项 | 实测结果 | 对 Lab 的影响 |
|---|---|---|
| Docker + Compose | ✅ 29.5.2 / v5.1.4 | 可跑 Qdrant / Kafka / Langfuse |
| **GPU** | ❌ **无**（无 nvidia-smi） | Lab-06 只能走 vLLM CPU 档或 llama.cpp/Ollama |
| CPU | **2 核** | 多容器同时起会吃力 |
| 内存 | **3G** | **并行度必须降到 2–3 个 Lab**，且错开需容器的 |
| 磁盘 | 16G 可用（已清理） | 够拉镜像，但不宜同时缓存多个大镜像 |

**因此阶段四不能像阶段三那样 6 个并行。** 需容器的 Lab（01/03/04/05/06/08/10）
必须串行或最多 2 个并行；纯文档型 Lab（11/12）可与之并行。

### 模型接入：双路径（已实测就位）

| 路径 | 配置 | 用途 |

import os
if os.getenv("DEEPSEEK_API_KEY"):
