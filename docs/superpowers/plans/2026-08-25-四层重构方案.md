## 1. 四层结构怎么落到两册

四层是**书级**的，但两册各自要能单独读（上册"不需要会写代码"的承诺不能破）。
因此采取：**层级显性化为「部」，两册的分界不动。**

```
上册 · 交付方法论          下册 · 系统工程实现
├ 第一部 骨架               ├ 第三部 实践（工程实现）
└ 第二部 细化方法论          └ 第四部 例子（案例 + Labs）
                            └ 别册一/二/三（不进目录）
```

上册内部仍按 骨架 → 细化 → 约束下的实践 → 复盘 走完一遍，
下册按 工程骨架 → 工程细化 → 例子 走完一遍。**四层是主线，不是硬隔断。**

## 4. 两章本体论的提纲

### 4.1 上册第 6 章 · 最小可执行业务模型

```
场景：客户说「你先把我们的业务理清楚」，你不知道理到什么粒度算完
6.1  Palantir 本体论是什么          简介，2–3 页
6.2  为什么不能照搬                  供应可得性 + 方法两层
6.3  七要素                          对象 状态 关系 动作 判据 权限 证据
6.4  它和六道关卡怎么接              插在第 3 关与第 4 关之间
6.5  本体属于客户，平台只是一种运行方式
```

**6.1 的分量控制**：用户原话是"简单介绍一下"，这一节按 2–3 页写，
讲清 Ontology 是什么、它为什么被称为企业操作系统、FDE 在其中的位置。
**不逐个介绍 Foundry 的产品模块。**

**6.2 必须写实的两层**（调研已给一手出处）：
- 现实层：Palantir 2025 年 Form 10-K 明确不在中国托管平台、限制从中国访问。
  **这不是产品选型问题，是供应可得性问题。**
- 方法层：统一平台路线需要强数据治理和高水平团队同时成立；
  中国多数项目是多部门、多厂商、多套遗留系统、项目制采购、分阶段验收。
  直接复制**容易把本体做成新一代数据中台**。

**6.3 七要素表**（直接取自调研）：

| 内容 | 回答的问题 |
|---|---|
| 对象 | 业务操作的东西是什么 |
| 状态 | 对象现在处于什么阶段 |
| 关系 | 它与哪些对象相关 |
| 动作 | 用户或 Agent 可以做什么 |
| 判据 | 什么条件下允许执行 |
| 权限 | 谁能看、谁能批、谁能执行 |
| 证据 | 执行后留下什么可审计结果 |

**第七要素「证据」正好接骨架的证据层**——这是骨架承重的最好示范，要写明。

### 4.2 下册第 7 章 · 本体的工程实现

```
场景：七要素定完了，落到什么技术栈上
6.1  可替换优先的技术选型            开放 Schema / 关系层 / 动作层 / 权限层 / 事件层
6.2  Agent 通过工具接口调动作，不直连数据库
6.3  元数据要能导出、版本化、差异审查
6.4  参照实现：semantica              ontology / provenance / reasoning / evals / change_management
6.5  什么时候不该用它
```

**semantica 的写法照别册二的规矩**：钉在一个提交上，
逐条标明哪些是官方文档、哪些是本书推论，诚实写限制（0.6.x 版本）。
仓库：`semantica-agi/semantica`，MIT，Python，`v0.6.6`。

## 6. 骨架下沉：机械动作

这是修复 0.1 的核心，**每一章都要做，不能挑**。

**每个关卡章**（上册 03/04/05/07/08/09）在「本章清单」之前加一节：

```markdown
### 这一关攒的是什么

- **证据**：……（这一关产出的、能拿给业务看的东西）
- **控制**：……（这一关立起的、能拿给安全看的边界）
- **接管**：……（这一关留下的、客户能自己接手的部分）
- **攒不够的样子**：……（失守时长什么样，接原第 3 章那条死法）
```

**每个下册工程章**在导言里加一句定位：这一章做的是骨架的哪一层。

**验收标准**：重构完成后，`grep -c 接管 <每一章>` 全部 > 0。
现在是 26 章零命中，这条脚本化校验必须过。

## 7. 交叉引用迁移

上一次 G1–G6 改名的教训：**机械替换会留下空格与顺序伪影，必须逐条校验。**

```
1. 先 git mv 全部改名的章节文件（build.sh 按文件名排序，编号前缀决定顺序）
2. 正则迁移：上册第 N 章 / 下册第 N 章 / §N.M
   —— 必须用「旧号→新号」映射表，不能用偏移量（有新增章，偏移不均匀）
3. 校验脚本（复用别册二那套）：
   - 章存在性：所有「上册第 N 章」「下册第 N 章」指向真实标题
   - 节存在性：所有 §N.M 指向真实小节
   - 骨架覆盖：每章「接管」命中 > 0
   - 引号配对、直角引号、ASCII 引号
   - 列表编号连续性
   - 全量构建 + 缺字检查 + Overfull hbox 计数
4. tools/final_check.sh 里硬编码的 FILES 列表要跟着改
5. 别册一/二正文里引用上下册章号的地方要一起改（别册二有 12 处）
```

**新增：迁移前先跑一次基线**，把当前所有交叉引用导出成清单，迁移后逐条对照。

## 9. 不做什么

- **不动两册分界。** 上册"不需要会写代码"的承诺、下册的工程定位都不变。
- **不把竞品调研写进正文。** 那是办培训的情报，不是教材。
- **不把 Palantir 的具体数字（NDR、转化率、客单价）写进书。** 全是第三方解读，非财报口径。
- **不重写案例章的内容**，只改编号与骨架挂载。
- **不重写代码，不重跑已经跑过的东西。**（2026-08-25 用户追加的硬约束）
  - Lab-01 至 Lab-12 的**代码与编号一律不动**，`verify.sh` 不重跑——它们跑过且通过了。
  - 正文里的代码片段只在**章号变动导致引用失效**时改，不做风格性重写。
  - semantica 章按别册二的做法写：**读仓库和官方文档，不跑它的代码**，
    未实测的地方逐条标注。
  - 构建只在**内容真的变了**的册上跑，不做全量重建凑完整。
- **不合并别册。** 三本别册继续独立，不进目录。
