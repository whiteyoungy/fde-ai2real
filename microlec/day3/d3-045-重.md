### 一、这条微课要讲的例子

这正是 Lab-02 验收标准里“证书轮换过程中零失败请求”要考察的能力——40 并发跨轮换窗口，failures=0。另外一条建议：长期有效的静态密钥应尽量替换为短生命周期的动态凭据，把泄露的影响窗口从“直到下次人工轮换”压缩到密钥本身的有效期之内。

### 三、这一页在论证什么

**这一页的主张**：核心原则是重叠窗口，不是一刀切替换

**这一页的其他内容**：无论轮换的是 TLS 证书、OAuth2 客户端密钥还是长期 API Key，都不应该“签发新的、同时立即吊销旧的”。；① / 先签发新凭据 / 新旧并存，两套都能验证通过。；② / 确认已在所有消费方生效 / 分批灰度轮换，把爆炸半径控制在可回滚的范围内。；③ / 再吊销旧凭据 / 确认全部切换完成之后才动这一步。；硬切换的那一刻，必然有一部分尚未完成配置刷新的调用方会被拒绝。

## 要求

**时长**：6–8 分钟　**正文字数**：900–1200 字

这一条是**重档**：例子本身带完整案例、可查证数字或官方原文，值得单独成课。脚本要把来龙去脉讲完整——事情怎么发生的、当时可以怎么判断、判错了代价是什么。

写作时守住四条：

1. **从例子进，不从定义进。** 开头三十秒之内要出现这个例子的具体场景，
   不要先讲一段概念再举例。学员点开这条微课，是因为它的标题写着一个具体的事。
2. **把判据说清楚。** 微课的落点不是“记住这个故事”，是“下次遇到同类情况，
   用哪一句话做判断”。脚本结尾要能提炼出一句可以直接用的判据。
3. **来源怎么说就怎么说。** 上面“来源”那一栏里如果写了“实测”“官方”“原文”，
   脚本里可以说得肯定；如果写了“归纳”“推导”“教学示例”“未核实”“合成案例”，
   脚本里必须照实说明，不能升级成确定结论。
4. **不要新编案例。** 需要补充例证时，只能用这门课已有的材料
   （六道关卡、12 个 Lab 的实测数字、四个案例章、两个决策复盘）。
