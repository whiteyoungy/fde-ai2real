## 材料

### 一、这条微课要讲的例子

很多工程师习惯一上来就怀疑认证配置，因为认证报错信息最显眼。实际上认证层的问题必须建立在前三层都已经排除的前提下才有意义排查，否则很容易在错误的层级里打转。走 VPN 分离隧道导致的 DNS 问题，报错通常是“连接超时”而不是“域名解析失败”。

**来源**：下册 §6.4

### 三、这一页在论证什么

**这一页的主张**：把“连不上”拆成四层逐层定位

**这一页的其他内容**：① / DNS / 解析到的是哪个地址？内网可能做了分离视界解析，同一域名内外结果不同。；② / TCP / 端口通不通？防火墙白名单申请周期以周计，技术方案定稿当天就要提。；③ / TLS / 证书链完整吗？内网自签 CA 的根证书要手动导入每一个消费方的信任库。；④ / 应用层认证 / 凭据对不对？这一层必须建立在前三层都排除的前提下才有意义排查。；这棵树的价值不在于覆盖所有情况，而在于排查顺序本身。

## 要求

**时长**：3–4 分钟　**正文字数**：450–650 字

这一条是**中档**：例子有实质内容但不够撑满一节完整微课。脚本走精简结构——场景、判据、一句总结，不铺陈背景。

写作时守住四条：

1. **从例子进，不从定义进。** 开头三十秒之内要出现这个例子的具体场景，
   不要先讲一段概念再举例。学员点开这条微课，是因为它的标题写着一个具体的事。
2. **把判据说清楚。** 微课的落点不是“记住这个故事”，是“下次遇到同类情况，
   用哪一句话做判断”。脚本结尾要能提炼出一句可以直接用的判据。
3. **来源怎么说就怎么说。** 上面“来源”那一栏里如果写了“实测”“官方”“原文”，
   脚本里可以说得肯定；如果写了“归纳”“推导”“教学示例”“未核实”“合成案例”，
   脚本里必须照实说明，不能升级成确定结论。
4. **不要新编案例。** 需要补充例证时，只能用这门课已有的材料
   （六道关卡、12 个 Lab 的实测数字、四个案例章、两个决策复盘）。
