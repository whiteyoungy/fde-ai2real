## 材料

### 一、这条微课要讲的例子

一份合同的假设条款第一条不是“数据要可得”这类具体前提，而是：本协议的任何变更都将使用项目变更请求表记录。它提前告诉客户——我们现在写的假设，一旦不成立，走的是那张表，不是一场争吵。

**来源**：上册 §5.3

### 三、这一页在论证什么

**这一页的主张**：依赖条款要点名到具体主体，不能写“客户配合”

**这一页的其他内容**：守不住 / · “依赖客户配合提供数据。” / · “不含系统集成。” / · “由各方协商。”；点名到主体和动作 / · “依赖客户方 IT 部门在【具体时限】内开通【具体系统】的只读访问权限。” / · “老旧数据库的驱动适配、字符集与时区差异处理，责任主体为总包或甲方科技部门。” / · 写明由谁发起、谁批、批不下来时本方排期怎么顺延。；“由各方协商”这五个字，在总分包结构里等于“由最没有话语权的那一方兜底”。依赖条款里出现这五个字，基本可以判定这一条守不住。

### 四、前后文

- **前一页**：范围外条款怎么写才不空洞
- **后一页**：比条款写得详细更重要的：让客户书面确认

## 要求

**时长**：3–4 分钟　**正文字数**：450–650 字

这一条是**中档**：例子有实质内容但不够撑满一节完整微课。脚本走精简结构——场景、判据、一句总结，不铺陈背景。

写作时守住四条：

1. **从例子进，不从定义进。** 开头三十秒之内要出现这个例子的具体场景，
   不要先讲一段概念再举例。学员点开这条微课，是因为它的标题写着一个具体的事。
2. **把判据说清楚。** 微课的落点不是“记住这个故事”，是“下次遇到同类情况，
   用哪一句话做判断”。脚本结尾要能提炼出一句可以直接用的判据。
3. **来源怎么说就怎么说。** 上面“来源”那一栏里如果写了“实测”“官方”“原文”，
   脚本里可以说得肯定；如果写了“归纳”“推导”“教学示例”“未核实”“合成案例”，
   脚本里必须照实说明，不能升级成确定结论。
4. **不要新编案例。** 需要补充例证时，只能用这门课已有的材料
   （六道关卡、12 个 Lab 的实测数字、四个案例章、两个决策复盘）。
