# 第 3 章 · 护栏会自报强制力

> **一句话结论**：护栏最危险的状态不是没配，是配了、没完全生效、而且没人知道。

## 那台内核有点旧的机器

客户给的机器是一台国产发行版，内核版本比你手上开发机低两个大版本。
你把沙箱配成只读模式，跑了一遍冒烟用例，agent 想写文件的时候被拦住了，
截图存进交付材料，这一项算过了。

三周后出了一次事故：agent 改掉了一个它本不该碰到的文件。
你回去看配置，配置没错。看日志，那条命令确实是在只读模式下执行的。

问题出在中间那层：**那个内核版本的 Landlock 只能管住一部分文件效果，
剩下的它管不了。** 你的冒烟用例恰好落在它管得住的那一半里。

这不是配置错误，也不是实现 bug。**这是强制力不完整，而你没有去问它完不完整。**

## 读完这章你能做什么

1. 一句话说清这套沙箱管什么、不管什么，并在安全评审上答对“它能不能断网”。
2. 分辨“完全强制”和“部分强制”，并知道后者在什么平台、什么内核上会出现。
3. 说明这套东西在护栏失效时为什么会拒绝执行而不是放行，以及这句话的三处落点。
4. 在评审材料里写对一句话：受约束的是**每一次调用**，不是整个进程。

## 3.1 先划清楚：沙箱只管文件效果

`SandboxMode` 有三档 [1]：

| 模式 | 允许什么 |
|---|---|
| `read-only` | 只允许必需的写出口，比如 POSIX 运行器给 shell 的 `/dev/null` |
| `workspace-write` | 再加上工作区根目录，以及后端自己承诺的临时区 |
| `danger-full-access` | 绕过隔离 |

然后是本节真正要说的那句，官方文档写得很直白 [1]：

> **网络与进程可见性不在此处的定义范围内。**

**这句话你要能在会议室里主动说出来。**

安全评审上被问“它能不能上网”，最差的回答是“我们配了沙箱”。
这个回答同时做到了两件坏事：它没回答问题，而且它让对方以为你回答了。
等到有人发现沙箱模式和网络无关，你之前所有关于边界的陈述都会被重新审视一遍。

正确的答法是分开说：

- **文件边界**由沙箱管，模式有三档，我们配的是哪一档。
- **网络边界**不在沙箱里，要靠别的手段——出口代理、网络命名空间、
  主机防火墙，这三样归客户的网络组，不归这个工具。
- **模型通道是第三件事。** 就算命令一条都出不去，模型推理请求本身仍然要出网，
  除非模型部署在本地。**这是数据边界，别混进网络边界里讲。**

别册一导读里已经说过这层区分，本册再说一遍，因为**这是最常被压缩成一句话的地方，
而压缩之后那句话是错的**。

## 3.2 它会告诉你自己有没有完全生效

这一节是本章的核心，也是这套 harness 最值得学的一处设计。

后端执行完约束之后，会报告一个事实 [1]：

```text
enforcement: 'full' | 'partial'
```

`full` 表示后端管住了这个模式承诺的所有文件效果。
`partial` 表示**活跃后端或者较旧的内核 ABI 只管住了其中一个子集** [1]。

然后是最要紧的一句约定 [1]：

> 要求绝对保证的消费方**必须拒绝，或者向上暴露这一区别**。

官方文档还点了名，当前哪些情形会报 `partial` [1]：

- **较旧的 Landlock ABI**——就是开头那台机器。
- **Windows ACL 运行器**的 Everyone 与硬链接边界；
  这个运行器还有一条：只读模式下**不授予任何显式可写根目录** [1]。

### 为什么这个设计值得单独讲

把大多数工具在这个位置的做法摆出来对比一下：

| | 常见做法 | 这里的做法 |
|---|---|---|
| 内核不支持全部特性 | 尽量启用，能管多少管多少 | 启用，**并报告只管住了一部分** |
| 调用方知不知道 | 不知道 | 知道，是返回值的一部分 |
| 你在评审会上能说什么 | “我们启用了沙箱” | “本机强制力为 full／partial，依据如下” |
| 出事之后回头看 | 配置是对的，没法解释 | 当时就记录了强制力等级 |

**静默降级是护栏工程里最贵的一类缺陷**，因为它把“没防住”伪装成“已防住”。
下册第 8 章讲护栏时那句话在这里落到了实处：
**配了但没生效的护栏，比没配更危险，因为它给人一种已经防住了的错觉。**

这套东西把那个错觉变成了一个可读的字段。

### 落到动作上

**进场第一天，把这台机器的强制力等级记下来，写进交付材料。**

它属于本书四层骨架里的**证据**层，不是控制层——
控制是“我配了只读”，证据是“在这台机器上，只读的强制力等级是 full”。
**前者是你的意图，后者才是事实。** 上册第 2 章那句判断在这儿正好用得上：
没有证据，业务不该信。

如果拿到的是 `partial`，有三条路，按代价从低到高：

1. **换机器或升内核。** 最干净，但在客户现场往往最难谈。
2. **在这个边界之外再加一层。** 比如容器或 microVM——
   官方文档明说这类是完整能力 seam 的同级实现，不是 `ctx.sandbox` 的提供方 [1]，
   也就是说它们是另一条路，不是这条路的补丁。
3. **接受它，但写进风险登记，并把受影响的目录范围缩到最小。**
   这条要客户签字，不能自己默默接受。

## 3.3 失败时拒绝，不是失败时放行

“fail-closed”这个词很多工具都说，区别在于它是实现习惯还是接口契约。这里是后者。

**沙箱这一侧** [1]：`ctx.sandbox.confine()` 要么返回一个真正施加约束的 argv，
要么在没有可用后端时抛 `SandboxUnavailableError`（错误码 `SANDBOX_UNAVAILABLE`）。
官方文档的原话是：

> 对于受限策略，**静默的无隔离透传永远不合法。**

**审批这一侧** [2]：结果只有四个值，而且是闭合的——
`allowed-once`、`rejected`、`cancelled`、`unavailable`。

> **只有 `allowed-once` 是授权，而且只授权所问的那一个操作。**
> 调用方对 `rejected`、`cancelled`、`unavailable` 一律拒绝。

关键在最后那个值怎么产生的 [2]：

> 缺失、不负责该请求、抛异常，或者返回了不合规值的应答者，
> 产生的是 `unavailable`，**而不是放行**。

把这三种情况分开看，就知道这条约定挡住了什么：

| 情况 | 松散实现的常见后果 | 这里 |
|---|---|---|
| 没有任何应答者（比如无人值守跑批） | 超时后默认继续 | 拒绝 |
| 应答者代码抛异常 | 异常被吞，继续 | 拒绝 |
| 应答者返回了个奇怪的值 | 真值判断，可能当成允许 | 归一化成 `unavailable`，拒绝 |

第三行是我最喜欢的一条。**“不合规的返回值被归一化为不可用”**，
这是把一个本来会在某天变成事故的模糊地带，提前钉成了确定行为。

## 3.4 `never` 策略在分发之前生效

每个会话有一个审批策略，两个值 [2]：

- `ask`——委托给应答者链；一个应答者都没有的时候，链会落到 `unavailable`，也就是拒绝。
- `never`——**每一次询问都确定性地返回 `rejected`，不分发任何应答者。**

`never` 是给 CI 和无人值守跑批用的，是那个“不问也知道结果”的策略 [2]。

但真正要记住的是它的**执行位置** [2]：

> `never` 在服务内部、waterfall 分发之前强制执行，
> 因此**即使后来以 `prepend` 注册的应答者也无法绕过它**。

这句话的分量，要从反面看才清楚。

假设 `never` 是作为链上第一个应答者实现的。那么任何一个后来注册、
而且插在链首的插件，都能抢在它前面回答“允许”。
这不是假想的攻击，这是插件系统的日常——**一个足够可扩展的系统，
它的策略如果也只是一个可扩展点，那这个策略就不是策略。**

把它放在分发之前，意味着它不参与那场竞争。

**这条对 FDE 的意义**：你可以在评审材料里写一句能站得住的话——
在这个部署里，无人值守的会话不会有任何操作被批准，**而且这不取决于加载了哪些插件**。
上册第 5 章讲第 2 关定界时说，写不下来的边界等于不存在；
这条边界不但写得下来，还写在一个插件够不着的地方。

## 3.5 权限预设是给人看的，强制在旋钮上

`dsh` 把沙箱模式和审批策略这两个**相互独立**的旋钮捆成具名预设，
让客户端可以只提供一个权限选择器 [3]。默认表里有两项：

| 预设 | 沙箱 | 审批 |
|---|---|---|
| `workspace-write` | `workspace-write` | `ask` |
| `danger-full-access` | `danger-full-access` | `never` |

**但这一层不拥有任何强制执行。** 官方文档写得很明确：
执行、提示词叙述与回放仍然读取各自旋钮的折叠结果，
预设切换只记录意图，并通过每个旋钮各自的规范 setter 写入 [3]。

还有一个派生状态叫 `custom`：如果两个旋钮的当前值不匹配任何一个预设，
`current()` 返回 `custom`。**它只是派生值——客户端可以显示它，
但它绝不是切换目标，也绝不出现在事件负载里** [3]。

### 一条评审用的规矩

**看旋钮，不要看预设名。**

预设是 UI 的方便，两个不同的预设完全可能捆着同一组旋钮值。
你在交付材料里要写的是沙箱模式是哪一档、审批策略是哪一个，
**不是“我们选了标准安全预设”**——后者对下一个接手的人没有任何信息量。

这条规矩超出这个工具本身。**凡是把多个开关打包成一个名字的界面，
评审时都要拆回开关看。** 名字会变，名字的含义也会变，开关的值不会。

## 3.6 受约束的是每一次调用，不是整个进程

最后一条，因为它最容易在方案里写错。

策略是**按每次能力调用**解析并携带的，不是钉在提供方上 [1]。
官方文档举的例子很具体：同一时刻，bash 可能跑在只读模式下，
而一个受限的子 agent 需要它的状态目录可写；**已批准的提权重试是一次新的调用，
带着一个更宽的策略** [1]。

所以下面这句话是错的：

> **（错）** 这个进程整体运行在只读模式下。

正确的说法是：

> **（对）** 每一次执行按会话解析策略；当前部署的默认模式是只读，
> 会话可以在日志里记录覆盖值，被批准的提权是一次单独记录在案的调用。

**这两句话的差别，在事故复盘会上就是全部差别。** 第一句会在有人翻出
一条以更宽策略执行的记录时当场崩掉，连带你其他所有陈述的可信度。
第二句从一开始就把提权路径讲清楚了，翻出那条记录反而是它的证明。

工作区根目录的解析也值得记一笔：普通工具调用从**调用会话不可变的 cwd**
派生工作区根，而且**先按文件系统语义规范化再做词法规范化**，
所以一个包含 `symlink/..` 的 cwd 标识的是进程实际运行的目录 [1]。
这条是防符号链接绕过的，评审时问得到。

## 3.7 三档模式怎么选

| 场景 | 选哪档 | 理由 |
|---|---|---|
| 只让 agent 读代码、做分析、出报告 | `read-only` | 它不需要写，就别给写 |
| agent 要改代码、跑测试 | `workspace-write` | 边界就是工作区，够用 |
| 任何客户现场 | **不要用** `danger-full-access` | 它绕过隔离，而且默认捆着 `never` 审批 |
| 你自己的机器上做实验 | 随便 | 但别把这台机器的配置带进现场 |

最后一行是认真的。**开发机的配置漂进交付环境，是这类工具最常见的事故来源。**
第 6 章讲交付形态时会给一个具体做法：让现场配置和开发配置来自两份不同的 patch，
而不是靠人记得改回来。

## 本章清单

- [ ] 在目标机器上记录沙箱强制力等级（`full`／`partial`），写进交付材料并注明日期和内核版本
- [ ] 拿到 `partial` 时，走完那三条路的判断，**并让客户在风险登记上签字**
- [ ] 交付材料里把文件边界、网络边界、模型通道分三段写，不合并成一句
- [ ] 无人值守的部署确认审批策略是 `never`，并在材料里注明它不受插件加载顺序影响
- [ ] 评审材料写旋钮的值，不写预设的名字
- [ ] 检查方案里有没有“整个进程运行在只读模式下”这类说法，有就改掉
- [ ] 确认 `danger-full-access` 没有出现在任何一份会进客户环境的配置里

## 自检问题

1. 客户问“这个 agent 能不能访问互联网”，你的完整回答分几段？
   参考答案要点：至少三段——工具通道、进程网络、模型推理通道。
   **合并成一句的回答一定漏了其中一条。**
2. `partial` 这个返回值，为什么说它属于证据层而不是控制层？
   参考答案要点：控制是你施加的意图，证据是可被第三方核验的事实。
   同一份配置在两台机器上可以给出不同的强制力等级，**能区分这件事的只有事实那一侧**。
3. 如果 `never` 策略是作为应答者链的第一环实现的，会出什么问题？
   参考答案要点：任何插在链首的插件都能抢答；一个可扩展系统的策略如果本身是扩展点，
   它就不是策略。
4. 你手上的项目里，有没有哪条护栏你只验证过“它拦住了我故意触发的那一次”？
   你怎么知道它拦得住你没想到的那些？
5. “我们选了标准安全预设”这句话，在三年后接手的人眼里值多少信息量？
