# 第 1 章 · 一棵可以拆开的树

> **一句话结论**：可配置和可替换不是一回事，而这个区别决定了你的交付物是一份操作手册还是一份文件。

## 会议室里那个改不动的开关

某银行的评审会，安全部门提了一条：这个 agent 工具不许有联网能力，
连读网页都不行——**理由不是怕它下载什么，是怕它把行内的代码贴出去。**

这条要求本身很合理。麻烦在于你手上那个工具的联网能力是内置的，
配置项里只有“允许的域名列表”，没有“整个关掉”。
你能做的是把列表配成空，然后在方案里写一句“已配置为不允许任何域名”。

安全部门的人问了第二句：**“配置能被谁改回来？”**

这一问就到底了。**配置项是厂商留给你的活动余地，它的边界不是你划的。**
真要那条能力不存在，你需要的不是一个开关，是把那个零件拿掉的能力。

## 读完这章你能做什么

1. 说清楚 `dsh` 启动时那棵插件树是怎么叠出来的，以及你能在哪一层插手。
2. 用 `--dump-config` 打出实际生效的配置树，并指出其中任何一条的替换方式。
3. 判断一项能力是“配置得掉”还是“拆得掉”，并知道在评审会上这两句话的分量差多少。
4. 把一次现场定制写成一份 patch 文件，而不是一份操作步骤文档。

## 1.1 一切皆插件，没有特权内核

`dsh` 底下是一个叫 Cordis 的插件框架 [1][2]。它的规则只有两条，
但这两条决定了后面所有事情：

**第一条，产品的每一部分都是插件。** 模型适配器是插件，工具注册表是插件，
会话日志是插件，**连 agent 循环本身也是插件** [2]。所以每一部分都能从配置里换掉。

**第二条，扩展的方式是并排挂载，不是打补丁。** 官方文档的原话是：
不存在需要打补丁的特权内核。各项注册都是副作用，**插件卸载时会撤销** [2]。

第二条比第一条重要，而且容易被读过去。展开说：

大多数“可扩展”的系统是这样的——有一个核心，核心留了若干挂钩，
你的扩展挂在钩子上。核心本身你碰不到。所以扩展能做什么，取决于核心留了几个钩子，
**而钩子是别人按自己想象中的用法留的。**

这套东西不是。**它没有那个碰不到的核心。** agent 循环是 `core/agent-loop` 这个包
提供的一个默认驱动器，它实现 `core/agent` 定义的接口 [2]——
既然是实现接口的一个提供方，那就换得掉。

对 FDE 来说，这句话可以翻译成一句现场用得上的：

> **你不需要说服供应商给你留一个开关。**

## 1.2 seam：能力是三个角色，不是一个模块

`dsh` 把可替换的能力叫 **seam**（接缝）。一条 seam 有三个角色 [2]：

| 角色 | 干什么 | 举例 |
|---|---|---|
| Service Definition | 声明接口 | `dsh-sandbox`：沙箱能力长什么样 |
| Service Provider | 实现接口 | `dsh-sandbox-local`：用 bwrap／Landlock／Seatbelt／Windows ACL 实现 |
| Consumer | 用这个接口 | `dsh-bash-sandbox`：执行 bash 前先把命令包起来 |

一个包可以同时担几个角色，但**单独一个角色本身不算一条 seam**——
加一项能力意味着三样一起设计 [2]。

这个划法有个直接后果，官方文档举了一个很好的例子：
文件系统提供方和进程提供方**共享同一个执行世界**。
所以把这两个提供方指向一个远程沙箱，就等于**把 Bash、PTY 和 LSP 一并搬了过去**，
不需要为每个消费方各写一个分支 [2]。

停下来想一下这个例子对交付意味着什么。

“把 agent 的执行搬到一台隔离机器上”这件事，在别的架构里通常是一个项目：
命令执行要改、终端要改、语言服务要改，每一处都要单独适配，
而且每加一个新工具就要再适配一次。在这里它是**换两个提供方**。

**能力的边界画在正确的位置上，改造成本会差一个数量级。**
这不是这个工具特有的道理，是本书上册第 5 章讲第 2 关定界时反复说的同一句话——
只不过那一章讲的是划业务边界，这里划的是能力边界。

## 1.3 profile、组合包、patch：交付形态藏在这里

跑起来的 `dsh` 是一棵插件树，由启动时按序叠加的几层拼出来 [2]。

**组合包（bundle）** 是分发单位，里面是一组 Cordis 配置条目和挂载它们的代码。
随发行版给了三个：

- `dsh-base`——每个 profile 的第一层：模型适配器、工具、持久化、
  **沙箱与审批策略**、设置、凭据、遥测 [2]。
- `dsh-web-app`——在 base 上加浏览器应用。
- `dsh-headless`——在 base 上加一次性运行器，**完全不带服务器** [2]。第 6 章会用到它。

**profile** 是一份具名组装，它列出自己要叠哪些组合包，
存放自己装的树外插件，并保存用户自己的 `cordis.patch.yml` [2]。

叠加顺序是固定的，从空条目列表开始 [2]：

```text
1. 按 profile 列出的顺序，逐个应用组合包
2. profile 自己的 cordis.patch.yml
3. Harness home 级的那份 cordis.patch.yml
4. 命令行 --patch 传进来的 overlay
```

**越靠后越晚生效，也就越有话语权。** 一条 patch 按 id 定位某个条目，
替换它的整个 config，或者插入一个新条目 [2]。

> ⚠️ **替换的是整个 config，不是逐字段合并。** 这一点官方文档写得很直白，
> 但很容易在写第一份 patch 的时候踩到：你想改一个字段，
> 结果把同一条目下其他字段的默认值全丢了。
> 做法是先把那条目现在的完整 config 打出来，改完再整条写回去。

打出来用这条命令 [2]：

```sh
dsh --profile web --dump-config
```

**它打印出的任何条目，都可以由你自己的 patch 替换。** 这是官方文档的原话，
也是本章标题那句话的出处。

### 这条命令值得当成一个动作固定下来

**每次进现场前先跑一次 `--dump-config`，把输出存进项目仓库。** 三个理由：

1. **它是评审材料。** 安全部门问“这东西加载了什么”，你给的不是一段描述，
   是一份逐条列出的清单。
2. **它是差异基准。** 三个月后有人说“它行为变了”，你 diff 一下就知道是配置变了
   还是版本变了。
3. **它是接管材料。** 客户运维接手时，最需要的就是这份“现在实际跑的是什么”。

上册第 14 章讲经验资产化时有一条：**能被自动生成的文档，就不要手写。**
这条命令的输出正好是这类东西。

## 1.4 “可配置”和“可替换”，在评审会上差多少

回到开头那个会议室。

同样一件事——“这个 agent 不能联网”——两种系统给你的答案是不一样的：

| | 可配置的系统 | 可替换的系统 |
|---|---|---|
| 你做的动作 | 把域名白名单配成空 | 不挂载联网工具那个插件 |
| 你能说的话 | 已配置为不允许任何域名 | **树里没有这个工具** |
| 对方能追问的 | 谁能改回来？改了谁知道？ | （追问的是别的事了） |
| 证明方式 | 展示配置文件当前的值 | 展示配置树，那一项不在里面 |
| 出错时会怎样 | 配置读取失败可能回落到默认值 | 没有的东西不会因为读取失败而出现 |

**最后一行是要害。** 一个被配置关掉的能力，仍然在进程里；
它靠一个值保持关闭状态，而值有默认值、有回落路径、有被覆盖的可能。
一个没被挂载的能力，是不在的。

这个区别本书讲过一遍，只是当时讲的是别的事——上册第 5 章说
**谈判桌上写不下来的边界等于不存在**。这里是它的工程版本：
**靠一个值维持的边界，和靠结构维持的边界，抗压能力不一样。**

### 别把这条推得太远

诚实地补两句，免得读者拿着这一节去过度承诺：

**第一，拆掉零件是有代价的。** 你拆掉的每一个插件，都意味着上游升级时
你要重新确认这条 patch 还成不成立。**一份 patch 是一份需要长期维护的资产**，
不是一次性动作。第 7 章会把这笔账算清楚。

**第二，不挂载不等于沙箱。** 不挂载联网工具，意味着模型没有那个工具可调；
它不阻止模型通过 `bash` 工具执行一条 `curl`。真要断网，
你要动的是第 3 章讲的沙箱和执行策略，**而那一层的能力边界和这一层不是一回事**。
别册一导读里那句话在这里同样成立：沙箱能阻断命令主动联网，
却不能把外部模型调用变成本地推理。**能力通道和模型通道要分开算。**

## 本章清单

- [ ] 跑一次 `dsh --profile web --dump-config`，把输出存进项目仓库，注明版本和日期
- [ ] 从输出里挑一条，写一份 patch 把它换掉，跑通——**先在自己机器上做，不要在客户环境第一次做**
- [ ] 写 patch 前先把目标条目的完整 config 抄下来，避免只改一个字段却丢掉其余默认值
- [ ] 把项目里“客户要求不能有的能力”列出来，逐条判断是配置得掉还是拆得掉
- [ ] 对每一条拆掉的能力，检查一遍 `bash` 工具能不能绕过去

## 自检问题

1. 你手上正在用的 AI 工具，有哪一项能力是你想去掉但只能配置成关闭的？
   如果安全部门追问“谁能改回来”，你现在能答上来吗？
2. `--dump-config` 的输出属于上册第 14 章说的哪一类资产？为什么它比手写的架构说明更可靠？
   参考答案要点：属于自动生成、随代码同步、不会腐坏的那一类；手写说明会在配置变了之后继续保持正确的样子。
3. “不挂载联网工具”和“沙箱禁止出网”分别挡住了什么？两者都做了之后，
   还有哪条通道是敞开的？
   参考答案要点：前者挡工具调用，后者挡进程发起的连接；模型推理请求本身仍然要出网，
   除非模型也在本地——**这是数据边界，不是网络边界**。
4. 你项目里有几处定制现在是靠“操作手册第 3 步”维持的？它们里面有几处能改写成一份 patch 文件？
