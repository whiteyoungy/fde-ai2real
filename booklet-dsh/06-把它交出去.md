# 第 6 章 · 把它交出去

> **一句话结论**：交付物是一份能评审、能回滚、能被别人执行的文件，不是一份写着“第 3 步：修改配置”的操作手册。

## 周六凌晨两点，敲键盘的不是你

客户的变更窗口是周六凌晨两点到四点，两个小时。
按他们的规定，生产环境的命令由他们的运维执行，你在旁边看着，通过堡垒机。
堡垒机全程录屏。

你准备的材料是一份十四页的部署文档。第 6 页第 3 步写着：
“修改 `settings.yaml`，将 `sandbox` 段的 `mode` 改为 `read-only`。”

凌晨两点二十，那位运维打开文件，问你：“哪个 `sandbox` 段？我这儿有三处。”

你凑过去看屏幕。**你不能碰键盘。** 你只能念坐标。

**窗口的价值密度极高，而你正在用它做一件本该在办公室里做完的事。**

## 读完这章你能做什么

1. 把一次现场定制交付成一份文件，而不是一段需要人照着敲的步骤。
2. 用无头模式把 agent 挂进持续集成和变更窗口脚本，拿到可判定的退出码。
3. 判断该把 harness 交成一个工具，还是嵌进客户已有的业务系统。
4. 说清楚兼容既有钩子的价值边界——它在迁移期值钱，长期不值钱。

## 6.1 交付物是文件，不是步骤

第 1 章讲过，这棵插件树的每一层都能被 patch 替换，而且顺序是固定的。
这一节讲这件事在交付上的用法。

把两种交付形态摆在一起：

| | 操作手册 | 一份 patch 文件 |
|---|---|---|
| 谁执行 | 人，照着念 | 机器，加载 |
| 出错的地方 | 找不到位置、改错行、少改一处 | 语法错会当场失败 |
| 能不能评审 | 只能评审文字 | **能 diff，能进代码评审** |
| 能不能回滚 | 靠另一份手册反着来 | 删掉这份 overlay |
| 三个月后有人问“为什么这么配” | 靠记忆 | git log |
| 在变更窗口里花多久 | 逐步执行加确认 | 放文件、重启、验证 |

**第三行是本节的重点。** 一份配置补丁能走客户的代码评审流程，
而一份 Word 文档只能走一个“已阅”。前者会被人逐行看，后者不会。

### 具体做法

**一、现场配置和开发配置来自两份不同的 patch。**

不要靠人记得在进现场前把某几行改回去。第 3 章末尾提过这条，这里给做法：
仓库里放 `patch/dev.cordis.patch.yml` 和 `patch/site-<客户>.cordis.patch.yml`，
启动时用 `--patch` 指定哪一份。**哪一份被加载了，是命令行上看得见的事实。**

**二、每一份现场 patch 配一份 `--dump-config` 的输出。**

第 1 章说过这条。这里补一句用法：**把补丁前后的两份 dump 一起放进交付材料，
diff 就是这次改了什么。** 这是评审会上最省事的一张材料——
你不需要解释你改了什么，你把差异摆出来。

**三、按下册第 8 章那套四件套准备变更窗口。**

下册第 8 章讲“命令不由你来敲的时候”，给了四件套：
编号执行脚本（可单独重跑无副作用）、每步验证命令与期望输出、回滚脚本、预检脚本。
**这一章讲的 patch 正好是第一件的内容。** 剩下三件照那一章做。

还有一条从那一章直接继承过来的：**堡垒机会留档，别在命令行参数里带密钥，
别把配置文件 `echo` 到屏幕上。** 第 2 章讲过这套东西的密钥只以环境变量名的形式
出现在配置里——**这个设计正好让你的配置文件可以放心地在录屏里被打开。**

## 6.2 无头模式：一条命令，一个退出码

`dsh-headless` 是随发行版给的一个组合包。它在 `dsh-base` 之上叠加，
**不挂载任何 Host、HTTP 服务器、Web 运行时或浏览器插件** [1]。

它的行为是这样的 [1]：

```text
dsh --profile headless "任务文本"
```

- 创建一个全新的持久化 agent，把任务作为普通用户消息提交，等待完全停稳。
- **把最后一条非空 assistant 文本写到 stdout。**
- **退出码：最终轮次正常结束为 0，否则为 1。**
- 结束原因是 `error` 时，把错误码和消息写到 stderr；**成功运行时 stderr 是空的。**
- **进程不打开监听端口。**

这五条合起来，正好是一个能被脚本调用的东西该有的样子。

### 为什么这几条对交付场景要紧

**不开监听端口**，意味着它在一台不允许开放端口的机器上也能跑。
在客户现场，“这个进程监听了哪个端口”是安全扫描必查项，答案是“没有”最省事。

**退出码可判定**，意味着它能挂进持续集成，也能挂进变更窗口的执行脚本。
第 5 章那条回归用例最后要落到的地方就是这里。

**成功时 stderr 为空**，意味着你的脚本可以用“stderr 非空即告警”这条最简单的规则。
听起来是小事，但**一个总是往 stderr 打日志的程序，会让告警规则退化成没有告警规则**。

### 两条已知限制，官方自己列的

**一、只提交一个任务。** 它没有交互式后续输入的界面 [1]。所以它适合
“跑一件事、看结果”，不适合需要中途追问的流程。

**二、`ctx.appExit` 由启动器持有。** 在 `dsh` 启动器之外启动 headless profile，
会在激活时明确报错，直到宿主提供那个退出请求 [1]。

第二条是那种**你只会踩一次但会浪费半天**的坑：你想把 headless 嵌进自己的程序，
发现它不肯起来，而报错信息指向的是一个你从没听说过的服务名。
**记住这一条，比记住它的原理有用。**

## 6.3 SDK：装进客户已经在用的系统里

还有一条路：不给客户一个工具，而是把 agent 装进他们已经在用的系统里。

官方给了 Python SDK [2]：

```python
from deepseek_harness import DeepSeekHarness

with DeepSeekHarness(
    provider="deepseek-official",
    model="deepseek-v4-flash",
    cwd="/absolute/path/to/workspace",
    session_root="/absolute/path/to/sessions",
    cordis="/path/to/your.cordis.yml",
) as harness:
    result = harness.run("……", session_id="example-001")
print(result.final_response)
```

三个参数值得注意，它们正好对上前面几章：

| 参数 | 对应 |
|---|---|
| `cwd` | 工作区根，也就是第 3 章那个 `workspace-write` 的边界 |
| `session_root` | 会话日志落在哪里——第 4 章的账本，第 5 章的原料 |
| `cordis` | 你那份 patch 过的配置树，第 1 章 |

**会话目录会收到 JSONL 日志，里面包含组装后的模型请求和工具调用** [2]。
也就是说，走 SDK 这条路，第 4 章那套留痕一样不少。

还有一条对内网部署很关键的：**安装后的运行时不需要系统提供 Node.js** [2]。
在一台连装 Node 都要走审批的机器上，这一条能省掉一整轮流程。
但平台限制要一起记住——第 2 章 2.6 节列过：Python 3.10 以上，
Linux x64、Linux arm64，或 macOS 14 以上的 arm64 [2]。

### 这条路对 FDE 意味着什么

别册一第 6 章讲过同一件事，结论在这里同样成立，而且更具体：

> **你交付给客户的可以是一个装着 agent 的业务系统，
> 而不是一个要求客户学着开终端的工具。**

这个区别在第 6 关 采用上是决定性的。上册第 10 章讲采用率崩塌的常见死法，
第一条就是**要求用户改变工作方式**。一个要人打开终端、记住命令、
理解什么是工作区的工具，在大多数客户组织里的采用率上限很低——
不是因为难，是因为它不在任何人的工作流里。

**装进他们已经每天在用的系统里，这个问题就不存在了。**

## 6.4 兼容既有钩子：迁移期的价值

`dsh` 提供两个桥接插件，能跑用户现有的 Claude Code 或 Codex 钩子配置里
受支持的那部分命令钩子 [3][4]。

```yaml
- dsh-hooks-claude-code:
    configPath: ./.claude/hooks.json
    projectDir: .
```

对一个已经在用这些工具的团队，这条路让迁移成本降了一大截：
你现有那些拦密钥、拦危险命令的钩子脚本，不用重写。

**但这一节要说的主要是它的边界**，因为官方文档自己把话说得很清楚 [3]：

> 原生 Cordis 插件可以完成此桥接的所有工作，功能更强，且具有类型化返回，
> 没有序列化边界。**该桥接只是已映射命令钩子子集的兼容路径。**

具体缺什么，逐条列出来：

| 限制 | 细节 |
|---|---|
| Codex 桥接只覆盖一部分钩子点 | 十个里的五个：`PreToolUse`、`PostToolUse`、`SessionStart`、`UserPromptSubmit`、`Stop` [4] |
| 只跑 shell 形式的命令钩子 | `http`／`mcp_tool`／`prompt`／`agent` 类型会被解析后跳过，**只记一条警告** [3] |
| Codex 桥接没有工具前审批或改写路径 | 钩子可以阻塞，但桥接不会预审批或替换工具输入 [4] |
| 配置是进程级的 | `configPath` 在加载时解析**一次**，相对路径按进程启动目录算；按会话发现尚未实现 [3] |
| 读取失败不会崩，但也不会拦 | 路径拼错时桥接记警告、不注册任何东西 [3] |

**第二行和最后一行合起来是一个真实的风险。**
你以为你的钩子在拦，实际上它被跳过了，而证据只是一条日志里的警告。
**这正是第 3 章讲的静默降级，只不过换了个位置。**

所以给一条规矩：

> **迁移期用桥接，稳定后换原生插件。**
> 而且不管用哪条路，**每一条护栏都要有一次故意触发的验证**——
> 看到它真的拦住了，再写进交付材料。

这条规矩的后半句适用于任何工具，别册一附录 A 里也是这么写的：
**每条护栏都给验证命令，验过才算配好。**

## 6.5 子 agent：把别的产品也接进来

`dsh` 的子 agent 是一条能力 seam，而且和别的 seam 不一样——
**同一个上下文里可以并存多个提供方实现**，按名字注册 [5]。
随仓库给了六个提供方，其中包括把一轮工作委派给 Claude Code 或 Codex 的那两个 [5]。

这条能力本身怎么用，不是本册的重点。**要记的是它那条约定** [5]：

> 提供方通过静态描述符公布启动时的能力，服务会在任何一次运行存在之前就检查；
> 如果请求依赖提供方不具备的能力，会被**明确拒绝**（`UNSUPPORTED_CAPABILITY`），
> **绝不会被接受后静默忽略。**

这是第 3 章那条“失败时拒绝”在另一个位置的同一条设计。
**看到第三处出现同一条原则的时候，它就不是巧合了，是这个项目的性格。**
你在评审会上可以把它当成一条整体判断来讲，而不是逐个特性讲。

### 一条要说给客户听的

Claude Code 那个提供方有一个性质，**在客户机器上部署时必须主动说明** [6]：
它故意不设 SDK 的设置来源选项，因此官方 SDK 会相对于父会话的工作目录，
**读取宿主机上常规的用户、项目和本地 Claude 设置，包括原生账户状态与产品配置**。
提供方既不复制也不过滤这些文件，也不会创建或修改登录状态 [6]。

翻译成评审会上的话：**这条路径会读到那台机器上已经存在的配置。**
在自己开发机上这是方便；在客户的机器上，这是一件必须写进数据流向说明里的事。

## 6.6 交出去之前要留下什么

上册第 2 章说，第 6 关 采用是三类结果里**接管**唯一能攒出来的地方，
前面五关做得再漂亮，没有人接手，它仍然是你的私人系统。

对着这套东西，接管要留下的是这几样：

| 留什么 | 长什么样 |
|---|---|
| 现在实际跑的是什么 | `--dump-config` 的输出，带版本和日期 |
| 这次改了什么、为什么 | 现场 patch 文件，进客户的版本库，带提交信息 |
| 怎么验证它还好着 | 一条无头模式命令，退出码即结论 |
| 出事怎么退回去 | 回滚脚本，以及删掉哪一份 overlay |
| 判据在哪 | 第 5 章那份验收集，存在客户环境里 |
| 谁维护 | **一个具体的人名，不是一个部门名** |

最后一行是上册第 10 章反复说的那件事。**“交给运维部”不是接管，是弃养。**

## 本章清单

- [ ] 把这次现场定制写成 patch 文件，进客户的版本库，走一次他们的代码评审
- [ ] 现场配置和开发配置分成两份 patch，靠 `--patch` 参数区分，不靠人记得改
- [ ] 交付材料里放补丁前后两份 `--dump-config` 的 diff
- [ ] 用无头模式给这套部署写一条冒烟命令，退出码即结论，挂进定时任务
- [ ] 评估一次：交成工具还是嵌进客户已有系统——**按第 6 关采用的口径评估，不按工作量**
- [ ] 用了钩子桥接的，逐条确认哪些钩子类型被静默跳过了
- [ ] 每条护栏做一次故意触发的验证，验过再写进材料
- [ ] 用了 Claude Code 子 agent 提供方的，把“会读宿主机现有设置”写进数据流向说明
- [ ] 接管人写成人名，不是部门名

## 自检问题

1. 你上一次交付的现场定制，现在还能 diff 出来吗？如果不能，接手的人怎么知道你改了什么？
2. “进程不打开监听端口”这条性质，在客户现场值多少钱？
   参考答案要点：省掉一整轮端口审批和安全扫描的解释；在有些单位这是几周的时间差。
3. 钩子桥接会把不支持的钩子类型解析后跳过，只记一条警告。
   这个行为属于第 3 章讲的哪一类问题？你打算怎么防？
   参考答案要点：静默降级；防法只有一个——**每条护栏做一次故意触发的验证**。
4. “交给运维部”和“交给张工”，在半年后的差别是什么？
5. 你手上的项目如果改成嵌进客户已有系统，工作量会增加多少？采用率会变化多少？
   这两个数你现在都答不上来的话，缺的是哪一样？
