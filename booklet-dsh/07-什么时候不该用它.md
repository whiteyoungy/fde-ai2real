# 第 7 章 · 什么时候不该用它

> **一句话结论**：一个明说自己会破坏兼容的组件，能不能写进合同，取决于合同期和它的版本节奏哪个更长。

## “那我们下个项目就用它了？”

读完前六章，有人会得出这个结论。这一章是来拦这句话的。

前六章讲的每一条设计都是真的：护栏自报强制力、失败时拒绝、模型可见即已记录、
一切皆插件。这些都不是营销话术，是能在源码和文档里逐条对上的东西。

**但“设计得好”和“该用在你这个项目上”之间，隔着一整章的距离。**

上册第 3 章讲过一个判断：技术选型的失败，很少是因为选了个坏东西，
多半是因为**把一个好东西用在了它不适配的约束下**。这一章就是那些约束。

## 读完这章你能做什么

1. 把“开发者预览”这四个字算成一笔具体的成本，而不是一个模糊的顾虑。
2. 拿一张表判断你手上这个项目现在该不该用它。
3. 说清楚两本别册各自适用什么场景，不把它们讲成竞品对比。

## 7.1 “会有破坏性变更”要算成多少钱

仓库首页写着：目前处于开发者预览阶段，**未来将出现破坏性变更** [1]。
本册写作时的版本是 `0.1.1-rc.2`。

这句声明是加分项——**一个提前说清楚的风险，比一个没说的风险好管理得多。**
但它要被算进成本，不能只当成一句免责声明读过去。

成本落在三处：

**一、你那些 patch 的维护成本。**

第 1 章说过，patch 是一份需要长期维护的资产。上游改了配置结构，
你按 id 定位的那个条目可能就不在了，或者 config 的形状变了。
**这个成本和你写了多少条 patch 成正比**，而写 patch 又正是这套东西最吸引人的地方。

有一条能压住它：**patch 越少越好，能靠不挂载解决的就不要靠替换解决。**
删掉一个条目比替换一个条目稳定得多，因为前者不依赖那个条目的内部结构。

**二、接口变更传导到你自己代码的成本。**

如果你只是配置它，这块成本近似为零。如果你写了原生插件、或者用 SDK 嵌进了产品，
每次上游的接口调整都要你跟一次。

**三、客户侧升级要走的流程。**

这条最容易被低估。在一个生产环境的版本变更要走变更评审的单位，
**升级不是技术动作，是一次流程**。一年升四次和一年升一次，对客户运维是完全不同的负担，
而这个负担最后会算到你头上。

### 所以判断是这样的

> **合同的运维期，和它的版本节奏，哪个更长？**

- **运维期短、或者你自己就是运维方**（内部项目、验证性项目、你们长期驻场）
  → 风险可控，可以用。
- **运维期长、交付后就撤场、客户自己维护**
  → **要么锁死版本并在合同里写明升级不在服务范围内，要么不用。**

**关于它的版本节奏，本册给不出数据。** 只有一个 `0.1.1-rc.2` 和一句声明，
没有足够长的发布历史可以看出规律。**这件事你要自己去它的发布记录里看**，
在你做决定的那个时间点看，而不是信一本写于 2026 年 8 月的册子。

> **可信度说明**：本节关于成本结构的分析是**本书的判断**，
> 不是对该项目的实测结论。**本册没有经历过一次它的破坏性升级。**

## 7.2 什么情况下不该用

| 情况 | 判断 | 怎么办 |
|---|---|---|
| 目标机器的 Node 版本上不去，且升级走不通 | **不能用** | 先解决 Node，这是前置条件，不是可以绕的 |
| 客户要求全内网，且没有可用的模型端点 | **不能用** | 先解决模型接入，第 2 章讲的是接得上之后的事 |
| 合同运维期三年，交付后你就撤场 | **谨慎** | 锁版本 + 合同里写明升级不在服务范围，或换成熟方案 |
| 客户的软件清单要求组件有商业支持 | **不能用** | MIT 开源件通常过不了这一关，先问清楚清单口径 |
| 走 Python SDK，但目标机是 Windows | **不能用这条路** | 用 Node 侧，或换部署形态 |
| 团队里没人会读 TypeScript | 可以用，但别写插件 | 只做配置和 patch，能力边界要在项目计划里写清楚 |
| 你缺的是“规格产物格式统一” | 不对症 | Spec Kit（下册第 3 章） |
| 你缺的是“变更轨迹” | 不对症 | OpenSpec（下册第 3 章） |
| 你缺的是“AI 干活的规矩” | 不对症 | Superpowers（下册第 3 章） |
| 你缺的是“沙箱 + 审批 + 留痕”，而且要成熟 | 不对症 | **别册一那套**，见下节 |
| 你缺的是“能拆开、能改造、能嵌进自己产品” | **对症** | 就是它 |
| 内部工具、验证性项目、你自己维护 | **对症，且风险最低** | 直接用 |

**倒数第三行要认真读。** 如果你要的是一个配好就不用管、
有大量现成实践可抄、生态成熟的执行层，**这一册讲的不是你要的东西**。

## 7.3 两本别册怎么分工

用户会问“到底该看哪本”。给一张能直接用的表：

| 你的处境 | 看哪本 |
|---|---|
| 甲方安全部门要正式过审，你需要成熟答案 | **别册一** |
| 你要接国产模型，卡在协议上 | **别册二第 2 章** |
| 你要把一项能力从系统里彻底拿掉 | **别册二第 1 章** |
| 你要向客户证明护栏真的生效了 | **别册二第 3 章** |
| 你要回答“它当时看到了什么” | **别册二第 4 章** |
| 你要在项目里攒下一份能留住的东西 | **别册二第 5 章** |
| 你要把 agent 嵌进客户已有的业务系统 | **两本都有，别册一第 6 章 + 别册二第 6 章** |
| 你只想快点把工具用顺手 | **别册一，轻档五步** |

**两本别册在方法论上是同一件事，只是拿了两个不同的对象来讲。**
这也是它们都不进上下册目录的原因：上下册讲“该做成什么样”，
别册讲“拿一个具体的东西怎么做到那样”，**而具体的东西会过期，该做成什么样不会。**

## 7.4 三个和工具无关的停止信号

最后给三条通用的。这三条不管你用哪个 harness 都成立，
而且它们比前面所有技术判断都更能预测项目的死法。

**一、配了但没人维护的护栏，比没配更危险。**

下册第 8 章说过，别册一也说过。**这里再说一遍是因为这套东西的可配置程度更高，
所以这个坑更深。** 你能配出一套非常漂亮的策略树，然后没有人看得懂它，
六个月后有人为了让某个功能跑通，把其中一条注释掉了。

判断很简单：**这套配置，除了你之外还有几个人能改？** 答案是零的话，
先别加新的护栏，先解决那个零。

**二、你配的档位要匹配客户的合规压力，不是匹配你的技术审美。**

三个人的团队做内部工具，把沙箱、审批、遥测、不变量全配一遍，是在给自己找麻烦。
别册一那张轻/中/重的分档表在这里同样适用。

**三、能力集中在一个人身上，这个项目就没被接住。**

上册第 10 章讲第 6 关 采用讲的就是这件事。第 2 章末尾提过一次：
如果团队里只有你会改 `settings.yaml`，其他人只会点设置页面，
**那么第 2 章那两个开关就是一个单点故障**，和技术无关。

## 7.5 说到底，harness 是什么

别册一第 7 章有一个结论，本册要接着往前走一步。那个结论是：

> **FDE 一直在做 harness 工程，只是以前的服务对象是人。**

这句话是对的。造地图、定判据、搭监控、把边界写进合同、把排障流程整理成手册——
FDE 在客户现场做的这些事，换个服务对象就是 harness 工程。

**本册要补的一步是：harness 也可以是交付物本身。**

不是“我用一个 harness 帮客户干活”，而是**“我在客户那里留下了一套 harness”**。
第 6 章那张接管清单里的每一项——实际跑的配置树、现场 patch、
一条命令的冒烟验证、回滚路径、验收集——合起来就是那套东西。

### 挂回四层骨架

上册第 2 章那四层，在这套具体的工具上是这样落的：

| 层 | 这套东西给了什么 | 谁来做 |
|---|---|---|
| **公理**·风险转移 | 什么都没给 | **只能你来** |
| **过程**·六道关卡 | 什么都没给 | **只能你来** |
| **结果**·证据 | 会话日志、成对审计事件、强制力自报 | 它给形状，你填内容 |
| **结果**·控制 | 沙箱、审批、fail-closed、权限旋钮 | 它给形状，你定档位 |
| **结果**·接管 | patch、无头模式、SDK、既有钩子兼容 | 它给形状，你找人接 |
| **资产**·验收集 | 只给了原料 | **只能你来** |

**看第一、二行和最后一行。**

前两层，任何工具都不会给你——判断这个项目该不该做、边界画在哪、
六道关卡怎么过，这是 FDE 这个岗位存在的理由，不是可以外包给工具的东西。

最后一层，工具只能给你原料。日志在那儿，但把日志变成一份越用越厚的验收集，
是要有人每次故障之后花二十分钟去做的事。**没人做，它就只是一堆日志。**

中间三层，这套东西给得相当好——好到值得写一本册子。但**它给的是形状**。
形状里装什么，还是你的活。

**工具会换，而且这一个明说了自己会变。四层不换。**
这也是为什么两本别册都不进上下册的目录：**保质期不一样的东西，不该装订在一起。**

## 自检问题

1. 你手上这个项目的合同运维期是多久？交付后谁负责升级？
   这两个问题答不上来之前，7.2 那张表用不了。
2. “patch 越少越好”这条建议，和第 1 章说的“可替换比可配置强”矛盾吗？
   参考答案要点：不矛盾。可替换是**能力**，patch 是**行使这个能力的代价**。
   能力值得要，代价要算。**能靠不挂载解决的，就不要靠替换解决**——
   删掉一个条目不依赖它的内部结构，替换一个条目依赖。
3. 四层骨架里，这套工具在哪两层上什么都没给？为什么它给不了？
   参考答案要点：公理和过程。它们是关于**这个项目该不该做、边界在哪**的判断，
   属于人和组织，不属于执行环境。
4. 如果三年后 DeepSeek Harness 不维护了，你在客户那里留下的哪些东西还有效？
   参考答案要点：验收集、判据、边界文档、客户方接手的那个人的能力。
   **失效的是配置和 patch，留下的是第 5 章那一样。**
5. 你读完这两本别册，最想立刻动手的是哪一件事？为什么是它而不是别的？
