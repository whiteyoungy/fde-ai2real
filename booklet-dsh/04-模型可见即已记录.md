# 第 4 章 · 模型可见即已记录

> **一句话结论**：“我们记了日志”不是承诺，“凡是模型看见过的都能从日志重建出来”才是。

## 复盘会上答不上来的那个问题

一次线上事故的复盘会。agent 在生产库上执行了一条它不该执行的语句。
你带了完整的操作记录：谁开的会话、几点几分、调用了哪个工具、参数是什么、返回了什么。

客户的技术负责人问了一个你没准备的问题：

> **“它当时看到了什么？”**

不是它做了什么，是它**看到了什么**。什么系统提示词、什么历史、
哪几条工具返回被放进了上下文、有没有别的东西被注入进去。
因为如果它看到的东西本身是错的，那问题就不在这一条语句上，
而在“为什么会有一条错的信息进到上下文里”，**这是个会重复发生的问题**。

你答不上来。你的日志记的是动作，不是视野。

## 读完这章你能做什么

1. 说清楚这套系统里“进日志”和“进模型上下文”分别是什么，两者为什么不是一回事。
2. 向客户解释一条比“我们记了日志”硬得多的承诺，并说明它由什么保证。
3. 分辨护栏的执行记录和护栏拦下的动作记录，并知道为什么前者也必须留。
4. 在方案里把遥测能保证什么、不能保证什么写对，不写成“一条不丢”。

## 4.1 日志是真源，不是副产品

大多数系统里，日志是**从行为里派生出来的**：程序做一件事，顺手记一条。
所以日志的完整性取决于每一处有没有记得记，漏了不会有人知道。

这里反过来 [1]：

> 会话日志是**模型所见上下文的来源**。`deriveMessages()` 从中投影出模型历史……
> fork、恢复、文本记录、遥测和持久化都派生自该事件流。

也就是说，**不是先做事再记日志，而是先进日志，模型才看得见。**
日志漏一条，模型就少看见一条——**漏记会立刻表现为功能故障，而不是审计缺口。**

这个方向的差别，是本章后面所有内容的地基。审计完整性在这里不是靠自律维持的，
是靠“不完整就跑不起来”维持的。

## 4.2 那条不变量

架构文档里有一句加粗的话 [1]：

> **模型可见即已记录。** 抵达模型请求的一切都必须能从日志重建，
> 并由**一项运行时不变量断言**这一点。因此，新增一项模型可见输入
> 就需要新增一个会话事件：扩展 `SessionEventMap` 并从日志渲染。

三层意思，逐层拆：

**第一层，它是一条承诺。** “凡是模型看见过的，都能从日志重建出来”——
这句话比“我们记了日志”强一个数量级，因为它划的是范围，不是行为。

**第二层，它由运行时检查托着，不是靠约定。** 仓库里有一个专门的不变量服务
（`ctx.invariants`），每个工作区包发布一个配套插件，用自己确切的 npm 包名注册检查；
约定里明写了检查可以断言什么——**权威事件流或可变数据，绝不是某个服务或方法是否存在** [2]。

最后半句值得停一下。“断言方法存在”是一种看起来在检查、实际什么都没检查的写法，
它只能发现拼写错误。这套约定把它排除掉了。**这是一条关于怎么写检查的好规矩，
和这个工具无关，值得抄进自己项目。**

**第三层，它约束了以后的改动。** 想给模型多喂一样东西，
你就得先给它造一个会话事件。**这条约束把“悄悄往上下文里塞点东西”这条路堵死了**——
而这正是复盘会上最难查的那类问题的来源。

### 拿到客户面前怎么说

对比一下两种说法：

| | 常见说法 | 这里能说的 |
|---|---|---|
| 承诺的内容 | 我们记录了所有操作 | 模型看到的全部内容都能从日志重建 |
| 谁保证 | 开发规范 | 运行时不变量，违反了会失败 |
| 漏记的后果 | 审计里少一条，可能没人发现 | 模型少看见一条，功能立刻不对 |
| 能回答开头那个问题吗 | 不能 | 能 |

**第三行是这条设计真正的力量所在**，也是我建议你在评审会上主动讲的一句：
在这套结构里，审计缺口和功能故障是同一件事。

> **可信度说明**：以上均取自官方架构文档与不变量子系统文档的表述 [1][2]。
> **本册没有实测这条不变量在违反时的实际行为。**
> 如果你要把这句话写进给客户的方案，建议先自己构造一次违反场景验证，
> 或者把它写成“官方文档声明”而不是“我们验证过”。

## 4.3 三种事件域，别混着讲

文档把扩展点分成三类，选对事件域是大多数改动的第一个决定 [1]：

| 事件域 | 是什么 | 什么时候用 |
|---|---|---|
| **会话事件** | 追加到日志、通过 `session/event` 广播的**持久事实** | 某个事实必须在重新加载后仍然存在 |
| **Agent 事件**（`agent/*`） | 携带活跃 agent：收件箱、步骤、状态、请求、续跑 | 要观察或拦截**进行中**的工作 |
| **能力事件** | 向某条 seam 附加策略和适配器（`fs/*`、`tools/*`、`telemetry/*`） | 挂策略，且不想引入循环依赖 |

一个轮次的骨架长这样 [1]：

```text
turn/start
  step/start
    agent/pre-step        ← 决定模型看到什么，可以改写也可以直接拒绝
    agent/request → llm/stream → assistant/chunk* → assistant/message
    tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  step/end
  agent/turn-stopping
turn/end
```

其中 `turn/*`、`step/*`、`user/message`、`assistant/*` 和 `tool/*` 是**持久会话事件**，
其余是实时扩展点 [1]。

有一条细节对审计特别要紧 [1]：

> `agent/pre-step` 决定模型看到什么。监听器可以改写已领取的消息，也可以直接拒绝它们；
> 首次领取被拒绝或被改写为空时，**仍会关闭一个不含步骤的持久轮次，因此日志会记录这次尝试。**

**被拒绝的尝试也留痕。** 这是审计设计里的一个常见漏洞——只记录发生了的事，
不记录被挡下的事，于是“护栏拦了多少次”这个问题永远答不出来。这里没有这个漏洞。

## 4.4 护栏自己的执行也留痕，而且是成对的

**审批**留两条事件，靠一个专门的 `ApprovalRequestId` 配对 [3]：

```text
approval/asked    ← 问了
approval/decided  ← 决定是什么
```

那个 id 是每次询问新发一个的品牌类型，**不会和工具调用 id 或者会话 id 互换** [3]。

**钩子**同理，靠 `handlerId` 配对 [4]：

```text
hook/invoked   ← 钩子命令跑了
hook/result    ← 它的结果，含决策和 stderr 摘要
```

两组都有同一条性质，而且这条性质容易被忽略 [3][4]：

> **审计事件仅写入日志，不进入模型的文本记录。**

也就是说，模型不会因为“上次那个操作被拒了”而在上下文里看到这段历史；
模型可见的后果是调用方派生的工具结果和当前运行时上下文快照 [3]。

**为什么这个分离是对的**，值得说一句：审批记录是给人看的，
它进了模型上下文只会有两个后果——占 token，以及给模型提供一条它可能学着绕过去的信息。
留痕的目的是可追溯，不是给模型当参考资料。

### 一条现场用得上的规矩

**分开问两个问题：**

1. 被拦下的动作有没有记录？（大多数系统有）
2. **护栏本身跑没跑，有没有记录？**（大多数系统没有）

第二个问题在事故复盘里才会显出价值。“这条钩子当时执行了吗”——
如果答不上来，你就无法区分“护栏放行了”和“护栏根本没跑”，
而这两种情况的修法完全不同。

有一条边界也要记住：钩子调用／结果记录**必须位于一个尚未结束的轮次内**。
`SessionStart` 在轮次 1 之前运行，所以**它没有 `hook/*` 记录** [4]。
这是个真实的盲区，别在材料里把留痕说成无死角。

## 4.5 遥测能保证什么，不能保证什么

对外上报是一条独立的能力 seam，官方给了一个 OpenTelemetry 后端 [5]。
这一节要说的全是**限制**，因为这些限制会直接决定你在方案里能写什么。

**第一，harness 的职责止于 `emit()`。** 批处理、重试、排队、丢失策略
**都属于上报 SDK**，不属于 harness [5]。这是一条被明确写下来的边界公理。

**第二，投递是尽力而为的。** 游标标记的是“已交接”，不是“已送达”；
记录**可能丢**（崩溃、重载窗口），也**可能重**（无游标的重新接管、SDK 重试）[5]。

**第三，接收端要自己去重。** 对账本类记录按 `(session.id, event.seq)` 去重；
运维类记录（`channel: 'ops'`）刻意不带这类标识——它们是用来告警的信号，
不是用来累加的条目，**重复被容忍而不是被去重** [5]。

**第四，`seq` 有缺口是常态。** 每个 `(轮次, 步骤)` 只发出第一条 `assistant/chunk`，
作为“流已开始”的信号，其余分片在捕获时丢弃。所以
**传输中的 `seq` 缺口是正常的，绝不是数据丢失的信号** [5]。

> ⚠️ 第四条会直接坑到运维。有人看到 `seq` 不连续，报“日志丢了”，
> 然后一整个下午在查一个不存在的故障。**把这句话写进运维手册。**

### 所以方案里该怎么写

错的写法：

> 所有会话事件实时上报至监控平台，确保不丢失。

对的写法：

> 会话事件以尽力而为方式上报至监控平台。可能重复，接收端按会话 id 与事件序号去重；
> 极端情况（进程崩溃、重载）下可能丢失，**因此审计以本地会话日志为准，遥测仅用于告警和观测。**

**最后半句是关键。** 它把两样东西的定位分开了：本地日志是账本，遥测是仪表盘。
一份方案如果把仪表盘当账本用，第一次崩溃就会露馅。

还有一条合规相关的：每个后端都必须通过一个 `sharing` 成员**披露它的部署级共享策略**，
只有在完全没挂载遥测服务时，界面才渲染成“未配置”[5]。
在中国现场，“这个工具会不会把我们的数据发出去”是必问题——
**这个字段是你回答它的依据，而且它是强制披露的，不是可选说明。**

## 4.6 崩溃之后，日志不截断也不伪造

后端重新加载一个在轮次中途崩溃的日志时，会看到一个开着的 `turn/start`
却没有 `turn/end`。它**不会截断日志** [6]：

> 在长周期任务中，单个轮次可能非常庞大（许多步骤、大量工具输出），
> 而这些事件在崩溃前已被持久追加。后端改为用一个合成的
> `turn/end { reason: { kind: 'interrupted' } }` 关闭这个遗留轮次，
> **在不改变其前后任何独立事件的情况下**配平被中断的执行。

而且 `interrupted` 是唯一一个**不由循环发出的**轮次结束原因 [6]。

对审计来说，这个设计做对了两件事：

1. **崩溃不会让已经发生的事情消失。** 已经追加的事件一条不动。
2. **崩溃不会被伪装成正常结束。** 那条合成的结束事件带着一个独有的原因值，
   一眼能看出来它是被补上的。

**这两件事缺一不可。** 只做第一件，日志里会留下一个永远开着的轮次，
后续所有处理都要绕过它；只做第二件，你会丢掉崩溃前的全部工作。

## 4.7 这些日志是可以查的

会话语料是可查询的，而且有一个概念对第 5 章很关键——
每条事件被分成三种“surface”[7]：

| surface | 含义 |
|---|---|
| `current` | 它现在就在模型上下文里 |
| `shadowed` | 它曾经在，后来被替换掉了 |
| `log-only` | 它只在原始日志里，从不进模型上下文 |

**这个三分法是把日志变成资产的入口。** 它让你能精确地问出
“这一轮当时模型实际看见的是哪些”，而不是把整条原始日志端出来。

另外，`dsh` 给模型自己也提供了查会话的工具：`session_search`、`session_trace`、
`session_event_read`、`session_event_search`、`session_event_trace` [8]。
也就是说，**agent 可以检索自己过去的会话。**

这件事有两面，都要说：

- **有用的一面**：排障时它能自己去找上一次同类故障是怎么解决的。
- **要当心的一面**：这意味着历史会话是一个可被读取的数据源。
  **在客户现场，得先想清楚谁的会话能被谁的 agent 检索到**，
  否则这就成了一条绕过权限边界的读取路径。

第 5 章会用这套查询能力做一件本书更在意的事。

## 自检问题

1. “我们记录了所有操作”和“模型看到的全部内容都能从日志重建”，
   这两句话在事故复盘会上分别能回答什么问题？
   参考答案要点：前者回答“它做了什么”，后者还能回答“它为什么会这么做”。
   **只有后者能查出会重复发生的问题。**
2. 为什么审批记录不进模型的文本记录是对的？
   参考答案要点：留痕是给人看的；进上下文既占 token，又给模型提供了一条
   关于护栏怎么工作的信息。
3. 你现在的项目里，如果有人问“上周三下午那条护栏执行了吗”，你多久能答出来？
   答不出来的话，缺的是哪一类记录？
4. 遥测“可能重复”和“可能丢失”，哪一个对审计更致命？为什么？
   参考答案要点：丢失更致命，因为重复可以在接收端去重，丢失无法在接收端补回来。
   **所以审计必须以本地日志为准，这不是保守，是唯一正确的定位。**
5. agent 能检索自己过去的会话——在你手上这个客户那里，这条能力是资产还是风险？
   你打算怎么划这条线？
