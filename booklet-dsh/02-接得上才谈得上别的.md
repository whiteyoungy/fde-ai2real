# 第 2 章 · 接得上，才谈得上别的

> **一句话结论**：国产网关拒绝请求的原因高度集中在两处，而这两处都有现成的开关，只是不在设置页面上。

## 密钥对、地址通、每个请求都被拒

某省属国企的内网项目。模型是他们自己部署的，一台 GPU 机器上跑着推理服务，
前面挂了一层公司网关做统一鉴权和计费。网关对外的说法是“OpenAI 兼容”。

你把地址和密钥填进去，点保存，页面没报错。发第一条消息，报错。
换个模型，还是报错。用 `curl` 直接打那个地址，通的；密钥也是对的，
网关的调用记录里能看到你的请求进来过，然后被它自己拒了。

**这类故障最耗时间的地方在于，它看起来像配置错了，其实是请求的形状不对。**
你反复检查地址和密钥，而那两样从一开始就是对的。

## 读完这章你能做什么

1. 说出国产网关拒绝 OpenAI 形状请求的两个最高频原因，以及各自改哪一行。
2. 在没有设置页面字段的情况下，直接改 `settings.yaml` 把一条模型路由配对。
3. 说清楚密钥存在哪里、什么时候被读、页面上能不能看到明文，并能回答客户安全部门的追问。
4. 在进场之前判断目标机器的 Node 版本和操作系统够不够格，而不是到现场才发现。

## 2.1 “OpenAI 兼容”这四个字，兼容的是一个子集

先把中国现场的模型接入分成三类，因为它们的失败模式不一样：

| 类型 | 长什么样 | 典型失败 |
|---|---|---|
| 公有云国产模型 API | 厂商官方端点 | 少，厂商自己会对齐 |
| **企业网关** | 甲方 IT 搭的统一入口，转发到后端 | **最多**，网关自己实现了一遍协议 |
| 内网自建推理服务 | vLLM 一类的推理框架直接暴露端点 | 中等，取决于框架版本 |

中间那一类是 FDE 最常碰到的，也是最难的，因为**网关是甲方 IT 写的，
他们实现的是自己用得到的那部分**。下册第 6 章讲客户 IT 部门那套黑话时有一句
“这个我们有接口”——网关就是那句话的常见形态。

官方文档对这件事的表述值得原样记住 [1]：

> pi-ai 依据端点的 URL 决定请求的形状——系统提示词由哪个角色承载、
> 输出上限写在哪个字段、思考级别如何传输——而对于它无法识别的地址，
> 会当作 OpenAI 本身来对待。**多数 OpenAI 兼容网关至少会拒绝 OpenAI 所接受的某一样东西。**

最后半句是本章存在的理由。它不是在抱怨网关做得不好，
而是在陈述一个工程事实：**兼容性是按端点声明的，不是猜出来的。**

## 2.2 两个开关

官方文档说，两样占了绝大多数 [1]。逐条拆开：

### 一、系统提示词的角色

声明了推理能力的模型，它的系统提示词会以 `role: "developer"` 发出。
**很多网关直接拒绝这个角色**，因为它们只实现到 `system`／`user`／`assistant`。

改法：

```yaml
llm-pi-ai:
  providers:
    my-gateway:
      compat:
        supportsDeveloperRole: false
```

**故障表现有个特征值得记住**：普通模型能用，只有推理模型失败。
碰到这个组合，八成就是它，不用再往别处查 [1]。

### 二、输出上限写在哪个字段

OpenAI 现在把输出上限写作 `max_completion_tokens`。
**只认老字段 `max_tokens` 的服务端会拒绝整个请求。**

```yaml
llm-pi-ai:
  providers:
    my-gateway:
      compat:
        maxTokensField: max_tokens
```

### 合起来的最小可用配置

```yaml
llm-pi-ai:
  providers:
    my-gateway:
      apiKeyEnv: GATEWAY_API_KEY
      api: openai-completions
      baseURL: https://gateway.example/v1
      compat:
        supportsDeveloperRole: false
        maxTokensField: max_tokens
      models:
        - id: my-model
```

**这四行 `compat` 是本册单位篇幅价值最高的内容**，理由不是它多难，
而是没有它你会花一天时间查一件跟你的配置无关的事。

> **可信度说明**：本节配置片段与故障对应关系取自官方《配置模型》指南 [1]，
> 逐字对照过。**但本册没有在真实网关上实测过这两个开关。**
> 你第一次用的时候，请按 2.5 节那个顺序验证，别直接抄进客户环境。

### 三条需要一起记住的规矩

**第一，设置页面里没有这两个字段。** 表单只有 Provider ID、地址、协议、密钥、模型。
`compat` 只能写在 `$DSH_HOME/settings.yaml` 里 [1]。
**这意味着一个只会点页面的人排不出这个故障**——值班交接时要写清楚。

**第二，开关是断言，不是检查。** 官方原话：开关陈述的是关于你的端点的一个断言，
而不是对它的检查；设置一个网关其实并不需要的开关，只是发出一个不同的请求而已 [1]。
所以**配错了不会报“配错了”，只会换一种方式失败**。

**第三，冒号后面必须给值。** 写成 `supportsDeveloperRole:` 后面留空会被拒绝，
而不是被忽略——因为空值会抹掉已安装目录里已知的信息，却没给出替代 [1]。
这个设计是对的，但第一次踩到会懵。

### 路由和模型两级，模型级逐字段胜出

`compat` 写在路由上是这条路由所有模型的默认值，写在某个模型上则逐字段覆盖 [1]。
所以改正一个模型不需要重述整条路由：

```yaml
      models:
        - id: my-model
        - id: my-reasoner
          compat:
            thinkingFormat: deepseek
```

两级都没设的字段，沿用已安装目录为该模型记录的值；目录也没描述的，
落到 pi-ai 自己的检测 [1]。

全部开关、各自的取值、以及哪些协议接受它们，在自动生成的配置目录里
（`docs/config-catalog.zh.md` 的 `PiAiCompatProfile` 段）。
**那份文档派生自源码**，所以不会落后于适配器实际接受的内容 [1]——
这一点比“文档写得全不全”重要得多，上册第 6 章讲过同一个道理。

## 2.3 模型目录：声明的是你，不是它

自定义提供方下手动录入的模型，**在自己声明之前一律按纯文本对待**，
因为没有任何环节能去问端点接受哪些模态 [1]。所以视觉模型要加一行：

```yaml
      models:
        - id: vision-preview
          input: [text, image]
```

一整条路由都是视觉模型的话，路由上写一次 `defaultInput: [text, image]` 就够。
它是回落值不是覆盖值：在目录提供方上，它只为目录没描述的模型作答，
**不会把目录里本来就有图片能力的模型的这项能力去掉** [1]。

和 `compat` 一样，这两个字段也是断言而不是检查 [1]。所以失败会分成两个方向，
而这两个方向的排查位置完全不同：

| 现象 | 说明 | 改哪儿 |
|---|---|---|
| 图片**在发送前**就被拒，还点了模型的名 | 该模型没声明图片模态 | 给它加 `input: [text, image]` |
| 请求发出去了，**提供方**拒绝 | 声明了端点其实不提供的能力 | 从授予它图片能力的那个列表里去掉 `image` |

> ⚠️ **第二种情况有个尾巴，不处理会一直复发。** 附加的图片会留在会话日志里，
> 所以在会话离开它之前，**同一个请求会不断重复** [1]。
> 改完配置要**开一个新会话**，不是在原会话里重试。

这个坑值得单独记，因为它的表现是“我明明改对了但还在报同一个错”，
而这句话在排障时最容易把人引到错误的方向上。

## 2.4 密钥挡在配置之外

凭据这条 seam 的设计只有一句话：**settings 和配置条目里携带的是引用，不是值** [2]。

具体是这样：

- 一条凭据的“引用”就是一个 POSIX 风格的环境变量名，比如 `GATEWAY_API_KEY` [2]。
- 值归提供方所有；本地提供方把它存在 `$DSH_HOME/.credentials.yaml`，
  settings 里只留引用 [1][2]。
- **密钥字段是只写的。** 保存之后页面只会收到脱敏描述符，**永远不会收到明文** [1]。
- **消费方每次操作重新解析，绝不跨操作缓存。** 模型适配器每次模型请求解析一次，
  所以**轮换后的凭据不用重启，紧接着的下一次请求就生效** [2]。
- 空的存储值在任何地方都视为不存在 [2]。

最后再加一条设计得很克制的细节：如果一条引用当前是由**进程环境**供值的，
本地提供方会把它报告成 `writable: false`。因为那样的写入会**表面成功，
而解析持续返回被遮蔽的旧值**——所以 seam 直接拒绝，界面也提前把它渲染成只读 [2]。

**这一条是本节最值得学的地方，而且和这个工具无关。**
一个会“表面成功但实际无效”的写入路径，比一个明确失败的写入路径危险得多，
因为它会让人相信自己已经改过了。下册第 10 章讲护栏时说过同一句话：
**配了但没生效的护栏，比没配更危险。**

### 对回本书

这一节和本书两处直接咬合：

- **下册第 10 章 7.5 节日志脱敏。** 那一节讲的是别让密钥进日志；
  这里讲的是别让密钥进配置文件。**两条一起做，才叫密钥不落盘。**
- **Lab-06 那条不变量**：key 只从环境变量读，永远不落盘、不进日志、不写进任何文件。
  这套凭据 seam 是同一条不变量的一个工业级实现，可以拿去当参考。

## 2.5 接不上的时候，按这个顺序查

排障最贵的成本是查错方向。按这个顺序走，每一步都能把范围切一半：

```text
1. 密钥能解析吗
   报 MISSING_CREDENTIAL → 走模型页存密钥，或把被引用的环境变量提供上
2. 地址通吗
   用 curl 直接打 baseURL，不通就是网络／代理／证书，别在这里往下查
3. 模型名对吗
   报 UNKNOWN_MODEL → 选一个已配置的模型，或给自定义提供方补上它
4. 能列出模型吗
   “获取可用模型”返回 401 → 密钥问题
   返回 404 → 这个服务没有 GET /models 端点，手动录入模型即可，不是故障
5. 前四步都对，但每个请求都被拒 → 请求形状不对
   先设 compat.supportsDeveloperRole: false 与 compat.maxTokensField: max_tokens
6. 只有推理模型失败 → 就是 developer 角色，单独设那一个开关
7. 某个开关因为没有值被拒 → 冒号后面补上值，或删掉这个键
```

前四条的错误码和现象取自官方排错表 [1]。

**第 2 步值得特别说。** 在中国现场，`curl` 通不通经常不是模型的问题，
是代理、证书链或者内网 DNS 的问题。下册第 6 章那张“客户 IT 黑话”表里
第一行就是“网络是通的”——**每听到一句就追问一层**，在这里同样适用。

## 2.6 进场之前先确认的两件事

这一节是给要去现场的人的。**这两件事在会议室里问不出来，要提前查。**

**第一，Node 版本。** 仓库的 `package.json` 声明 `engines.node` 为
`^22.19.0 || >=24.0.0` [3]。信创操作系统自带的 Node 版本经常达不到，
而在一台不能随便装东西的机器上升级 Node 是一件要走流程的事。
**下册第 13 章讲信创适配时那套“先查清单再谈方案”的做法，在这里就是查这一行。**

**第二，如果走 Python SDK，平台限制更紧。** 官方快速上手页写明的前置要求是
Python 3.10 以上，操作系统为 Linux x64、Linux arm64，或 macOS 14 以上的 arm64 [4]。

> **注意读法**：这条平台清单是 **Python SDK 的**前置要求，
> 不等于整个 `dsh` 只跑在这些平台上——仓库里有 Windows ACL 沙箱后端，
> 说明 Node 侧是支持 Windows 的。**别把这两件事混起来说给客户听。**

Python SDK 有一条对内网部署很友好的性质：**安装后的运行时不需要系统提供 Node.js** [4]。
在一台连 Node 都要走审批才能装的机器上，这一条能省掉一整轮流程。

## 自检问题

1. 你现在项目里的模型密钥存在哪里？如果客户安全部门要求“证明页面上看不到明文”，
   你打算怎么证明？
   参考答案要点：能证明的是机制——存储位置、只写字段、页面收到的是脱敏描述符；
   **口头保证在评审会上的证明力是零**，这一点下册第 1 章讲过。
2. `compat` 开关“是断言不是检查”，这句话为什么会让排障变难？
   参考答案要点：配错不会报配错，只会换一种方式失败，所以你不能靠报错信息定位它，
   只能靠先全开、通了再逐个撤这种减法。
3. 一个团队里只有你会改 `settings.yaml`，其他人只会用设置页面。
   这在本书的六道关卡里属于哪一关的问题？
   参考答案要点：第 6 关 采用。能力集中在一个人身上，这个项目就没被接住——
   上册第 15 章讲的就是这件事。
4. “安装后的运行时不需要系统 Node.js”这一条，在什么样的现场是决定性的？
   在什么样的现场根本无所谓？
