# 第 2 章 · 面试与作品集

> **一句话结论**：系统设计题失分，往往不在技术方案本身，
> 在**没有先确认前提条件**就开始画架构图。

## “端到端 300 毫秒”

面试官抛出一道题：客户要求端到端 300 毫秒内返回，数据在内网数据库，怎么设计？

大多数候选人从这里开始讲选型：用什么向量库、怎么做缓存、模型放哪。

问对了的候选人先问一句：**这 300 毫秒是从哪个节点算到哪个节点？**

包不包括客户端网络？包不包括鉴权？是 P50 还是 P95？这三个问题的答案不同，
架构可以差出一个数量级。

> **在骨架里的位置**：作品集最容易犯的错是只展示证据（我做了什么、指标多少），**不展示控制和接管**。面试官真正在意的那句话是：**你走之后，那套东西还在跑吗、谁在跑。**

## 读完这章你能做什么

1. 面对系统设计题时，**先拆延迟、权限、数据口径这类前提条件**，而不是直接跳去讨论选型。
2. 在非技术面试官面前，把“召回率 85%”“P95 延迟”“灰度发布”翻译成对方能拿去做决策的话。
3. 把 12 个实验组织成一份讲清楚“**为什么否决了另一个方案**”的作品集，而不是一堆仓库链接。
4. 看到“年薪百万”这类说法时，按可信度分层分清哪些是官方披露、哪些是二手推测。

## 2.1 FDE 系统设计题库

这十道题不是刷题库，是从上册第 8、9、10、15 章与下册第 4、5、7、8、9、16 章的真实决策场景里提炼出来的。每题给考察点（面试官到底在看什么）、参考解法要点（不是标准答案，是判断框架）、常见失分点（真实候选人最容易栽的地方）。

**题 1：客户要求端到端 300ms 内返回，数据在内网 Oracle，怎么设计？**

- 考察点：全链路延迟预算拆解能力，是否会先确认“300ms 从哪个节点算到哪个节点”，能否在存储、检索、推理三层之间做取舍，而不是上来就选型。
- 参考解法要点：
  - 先拆预算（网络往返、SQL 查询、检索、模型推理、序列化各占多少）。
  - 内网 Oracle 不可能承受实时全表扫描，考虑只读副本、物化视图或预计算。
  - 检索层如涉及 RAG，用语义缓存（下册第 8 章缓存策略）命中高频重复问题。
  - 推理层用小模型、量化或 vLLM 批处理压缩耗时。
  - 预算实在不够时，提出分诊方案——简单请求走缓存/规则，复杂请求走完整链路，而不是让所有请求走同一条最慢路径。
- 常见失分点：
  - 不问清延迟测量口径就直接讨论“用哪个向量数据库”。
  - 默认可以随意在 Oracle 上加索引或建物化视图，不确认客户 DBA 权限和变更窗口。
  - 把 300ms 当成必须 100% 满足的硬指标，不区分 P50/P95/P99，也没有降级兜底方案。

**题 2：遗留系统只认 mTLS，云端 Agent/SaaS 只会 OAuth2，怎么设计认证桥接？**

- 考察点：是否理解协议桥接的本质是“终结 + 转换”而不是简单透传，能否设计出证书轮换不中断服务的方案。
- 参考解法要点：
  - 网关模式——对外呈现标准 OAuth2 资源服务器，对内维护 mTLS 客户端证书池。
  - 证书轮换要设计新旧证书并存的过渡期，避免单点切换导致请求失败。
  - 两侧的身份要在审计日志里可关联，否则出问题时查不清楚是谁调用的。
- 常见失分点：
  - 把两个协议直接拼接而没有做清晰的“终结”边界划分。
  - 完全没考虑证书轮换期间的过渡策略，方案平时能跑，一到轮换那一刻就炸。

**题 3：Webhook 高可用接收器——客户系统会重复推送、乱序、突发峰值，怎么设计？**

- 考察点：幂等设计、削峰填谷、消息顺序保证之间的取舍能力。
- 参考解法要点：
  - 接收层先快速落一个轻量队列再返回 ACK，避免处理耗时导致客户端重试风暴。
  - 用幂等键（事件 ID + 版本号）去重。
  - 乱序问题先确认业务是否真的要求严格顺序——不要求就并行消费，要求就按聚合键分区顺序消费。
  - 突发峰值靠队列缓冲加消费者水平扩展应对。
- 常见失分点：
  - 想在接收的同一个请求里完成全部业务逻辑，导致接收慢、客户端超时重试、系统雪崩。
  - 没有设计幂等键，重复事件被重复处理产生脏数据。

**题 4：混合检索 RAG 召回率上不去，怎么诊断改进，并向业务方讲清楚？**

- 考察点：检索质量诊断方法论（下册第 5 章三分法）与把技术指标翻译成业务语言的能力，两者缺一不可。
- 参考解法要点：
  - 先定位问题出在检索层、生成层还是数据层。
  - 检索层常见问题是分块策略不当、embedding 模型不匹配领域术语、纯向量检索对精确型号/编号这类查询天然弱，需要 BM25 关键词兜底再做 RRF 融合和 rerank。
  - 给业务方讲解“召回率 85%”时不甩术语，讲后果分布——“每 100 个问题里有 15 个系统压根没找到相关资料，这 15 个集中在哪类场景”。
- 常见失分点：
  - 诊断时不区分检索问题和生成问题，一律“换个更大的模型”了事。
  - 给业务方讲解时堆砌 Recall@5、RRF 这类术语，对方听不懂又不好意思追问，造成“已经沟通过”的假象。

**题 5：该用 RAG、微调还是长上下文，给一个决策框架？**

- 考察点：下册第 7 章微调 vs RAG vs Prompt 决策表的实际应用能力，是否理解三者并非互斥选项。
- 参考解法要点：
  - 看知识更新频率（高频更新用 RAG，静态领域知识可考虑微调）。
  - 看是否要改变模型的“行为风格”而非“知识”（微调更适合格式/语气对齐，RAG 更适合事实性知识注入）。
  - 看上下文窗口是否够装下所需材料且能否接受随之增长的延迟成本。
  - 实践中常是组合拳——长上下文兜底小规模场景，RAG 处理大规模知识库，微调处理输出格式对齐。
- 常见失分点：
  - 把三者当成排他选项、选一个用到底。
  - 忽略“知识更新频率”这个最关键的判据，选了微调结果客户数据一周一变，还要不停重新训练。

**题 6：多智能体编排在生产环境里死循环或超预算，怎么设计护栏？**

- 考察点：下册第 7 章 Agent 可靠性工程的实际落地能力。
- 参考解法要点：
  - 最大轮次、最大 token 预算、单次调用超时这类硬限制必须在框架层强制执行，不能只靠 prompt 里写“请不要重复调用”。
  - 关键决策点加人工确认，或至少检测“连续 N 次相同工具调用则中断并升级”。
  - 每一跳都要有可观测的 trace（对应下册第 8 章可观测性），否则出问题时排查不出死循环发生在哪一层。
- 常见失分点：
  - 只在 prompt 里写“避免重复调用”就当作已解决。
  - 没有设计成本上限，压测时才发现一次异常 session 能把当月 API 预算打光。

**题 7：客户内网完全断网，要交付一套完整 AI 系统离线安装包，怎么设计？**

- 考察点：下册第 8 章自包含离线部署包的实操理解，是否想到 SBOM/签名这类供应链安全环节。
- 参考解法要点：
  - 构建阶段产出全部镜像 tar 包、Helm Chart、依赖清单，离线环境不能临时拉取任何东西。
  - 提供 SBOM（软件物料清单）和签名（如 cosign）供客户安全团队审计——断网客户往往有更严格的合规审查。
  - 安装脚本要有前置环境检查（内核版本、存储空间、端口占用），防止装到一半才发现环境不满足。
- 常见失分点：
  - 方案里出现“如果缺少某依赖会自动下载”这类假设，断网环境下直接导致部署失败。
  - 完全没考虑安全审计环节，只关注“能不能装上”。

**题 8：上线 30 天采用率不到 20%，怎么诊断根因并翻盘？**

- 考察点：上册第 9、10 章采用率崩塌成因分析能力，能否区分技术、流程、政治三类根因。
- 参考解法要点：
  - 先分类——是系统本身有 bug 或慢（技术）、是用户不知道怎么用或流程没嵌入日常工作（流程）、还是有人不希望这个系统成功因为触及既有利益（政治）。
  - 技术类看监控数据（错误率、延迟）。
  - 流程类需要重新做几场影子跟随，观察真实使用场景。
  - 政治类需要找到关键决策人背后的真实顾虑，而不是继续优化技术指标。
- 常见失分点：
  - 不做任何数据诊断就一律归因于“用户培训不够”。
  - 完全忽略政治因素，以为纯技术优化能解决所有采用率问题。

**题 9：怎么设计 CI 门禁防止一次模型/prompt 升级导致生产质量隐性退化？**

- 考察点：下册第 9 章三层评估集 + CI 门禁设计能力。
- 参考解法要点：
  - 黄金集（已知正确答案，做回归检测）、对抗集（边界 case 与攻击性输入）、生产采样回放集三层并行。
  - 评分器覆盖客观指标（格式正确性等可编程判断）和主观指标（LLM-as-Judge，需警惕 judge 本身的偏差）。
  - CI 门禁要有明确阈值和“劣化就阻断”的硬规则，而不是生成一份报告供人工参考了事。
- 常见失分点：
  - 只做人工抽查不做自动化门禁，改动上线后才发现问题。
  - 评估集从不更新，新出现的失败模式一直没被纳入回归集。

**题 10：遗留系统没有 API，只有数据库直连权限，四种集成方式怎么选？**

- 考察点：下册第 4 章遗留系统对接四种方式的选型判断力。
- 参考解法要点：
  - 直连只读副本（最快但耦合最深，客户改 schema 就炸）。
  - 批量 ETL 导出（延迟高但侵入最小）。
  - 触发器/CDC 捕获变更（实时性和侵入性折中）。
  - 由客户方新增一层轻量 API 包装（长期最干净但需要客户配合开发，周期最长）。
  - 选择依据是实时性要求、客户 IT 团队的配合意愿与能力、系统本身的变更频率。
- 常见失分点：
  - 无脑选“最优雅”的方案而不考虑客户实际配合能力和项目周期。
  - 直接读写生产库而不走只读副本，存在拖垮生产系统性能的风险。

## 2.2 现场演练题

系统设计题考察知道什么，现场演练题考察临场怎么表现。很多候选人前者答得很好，一到模拟现场就露怯。

**演练一：需求发现模拟**

找一个人扮演客户业务负责人，给他一份“秘密脚本”：真实瓶颈藏在某个具体环节。他不会主动说出来，只会重复“我们需要一个 AI 系统帮我们提效”这类泛化陈述。你用上册第 4 章的情境访谈技巧，在 20 分钟内挖出真实瓶颈。

评分看三点：

- 有没有问出“现在这件事不做会怎样”这类能暴露真实优先级的问题。
- 有没有被“我们需要一个 AI 系统”这种泛化陈述带偏，一头扎进技术方案讨论。
- 有没有识别出上册第 4 章 §4.7 七种需求错位里的至少一种。

**练这个的重点不是话术熟练度，是能不能在对方说套话时保持怀疑，继续往下追问一层。**

**演练二：技术权衡的非技术表达**

给几个真实场景练习：

- 把召回率 85% 翻译给业务方。
- 解释为什么方案要多花两周做灰度发布，而不是直接全量上线。
- 跟业务方说清楚模型偶尔“一本正经地给错答案”这件事，而不是甩出“这是幻觉问题”就算解释完了。

一个具体示范（对应题 4 的口语化版本）：

> “我们现在测下来，100 个客户问题里，系统能准确找到相关资料再回答的大概有 85 个。剩下 15 个不是系统瞎编，是压根没找到相关资料——这 15 个主要集中在合同条款细节这类问题上。如果现在就上线，这 15% 的用户会拿到不准确甚至误导性的回答，这类场景风险偏高。我们有两个选择：一是先只覆盖能处理好的 85%，查不到就明确告诉用户'没有找到相关信息'而不是瞎猜；二是再花一到两周补齐这 15% 缺失的资料来源。”

这段示范做对了三件事：把抽象指标换成具体数字和场景、讲清楚不作为的后果、给出可选方案而不是只报告问题。

**常见的失败版本是说“我们的 embedding 质量还有提升空间”。这句话没有回避错误，但也没有回答业务方真正关心的问题：这意味着什么后果，现在能不能上线。**

## 2.3 作品集构建

12 个 Lab 直接罗列成一排 GitHub 链接不是作品集，是代码仓库清单。作品集要按下册第 14 章定型的七段式结构包装每一个 Lab：

- 客户背景（可以注明是训练场景）
- 真实冲突
- **被否决的方案（至少写一个，说清楚为什么否决）**
- 最终架构决策
- 关键代码或架构图
- 踩过的坑
- 复盘

被否决的方案这一段是价值核心。全书案例章反复用同一个理由：只讲最终方案是产品手册，讲清楚为什么否决了另外的选项才是工程判断力的证据。

比如 Lab-02 的认证桥接，最初可能考虑过“让客户直接开放 mTLS 白名单给云端 IP”这个更简单的方案，后来因为客户安全团队不接受动态 IP 白名单而否决。这段否决记录比“最后用了网关模式”这句话本身更能说明你的判断过程。

呈现方式建议做一张技能矩阵表：横轴是 Lab-01 到 Lab-12，纵轴是数据处理、企业集成、Agent 编排、评估、部署运维五个能力维度，标出每个 Lab 覆盖了哪些维度。面试官不需要逐个点开代码库就能看出你的能力覆盖面，而不是只覆盖了某一类问题就反复展示。

再补一份 1–2 页的项目摘要文档作为入口，链接到具体 Lab 仓库作为佐证材料，而不是让面试官自己进代码库里找亮点。现场演练题考察的是你能不能讲清楚，作品集考察的是你有没有提前把“讲清楚”这件事准备好。

## 2.4 国内外岗位与薪酬现实

**具体金额在配套手册 C4**，那一页每年复核一次，并合并了上册 §1.2 原来那份重复的表。
这一节只留谈薪时真正用得上的三条判断——**它们不会过期，金额会。**

**第一条，分层引用。** 官方招聘页的 Pay Transparency 披露可以直接引用；
薪酬聚合平台的间接数字必须标注不确定性，因为它们的统计口径经常不一致
（一个可能含期权，一个可能只是基本工资），而且本书核实时那两个平台的页面
**分别返回 404 和 403**。招聘中介博客上的「总包区间」没有官方来源，
**谈薪时不能拿来当对标基准。**

**第二条，偏售前的区间不低于偏工程的。** 这是那张表里唯一不随年份变化的信息：
市场对「把技术讲清楚并对结果负责」的定价，不低于「把技术做出来」。
上册 §1.4 从企业侧论证过为什么——**买的是风险转移，不是代码产出。**

**第三条，识别国内对标岗位靠职责，不靠头衔。** 国内没有统一使用这个头衔，
一手 JD 里最接近的表述是「对模型在业务场景中的效果负责」。
**看到这句话，不管头衔写的是解决方案架构师还是应用开发工程师，
问责机制上就是这个岗位。**

至于「驻场交付工程师年薪可达百万级别」这类国内媒体说法：只有笼统表述，
没有区间也没有分位数，按上册第 1 章的分层标准属于**不采信**那一档。
谈薪时以一手 JD 的区间作现实基准，把百万年薪当作个别头部案例或未经证实的传闻。

## 自检问题

**1. 面对系统设计题时，如果面试官没有主动说明延迟测量的具体口径（比如是否区分 P50/P95），你应该怎么做？**

参考答案要点：主动问，不要假设。第 1 题的常见失分点专门指出，把“300ms”当成必须 100% 满足的硬指标而不区分分位数，是典型的没有先确认前提就开始设计。

**2. 一位候选人在演练二里详细讲解了“什么是向量检索的余弦相似度”，业务方模拟评委反馈“没听懂但也不知道该问什么”，这段表达哪里出了问题？**

参考答案要点：讲解停留在技术原理层面，没有回答业务方真正关心的问题——这意味着什么后果、现在能不能上线、有哪些可选方案。技术翻译的目标是让对方能做决策，不是让对方理解技术细节。

**3. 作品集里某个 Lab 只写了“最终我们用了方案 A，效果很好”，没有提到方案 B、C 为什么被否决，这段介绍缺了什么？**

参考答案要点：缺了判断过程本身，这正是§2.3强调的作品集价值核心。只有结果没有否决记录，看起来像在复述产品手册，而不是展示工程判断力。

**4. 看到“FDE 年薪中位数 21 万美元”这个说法，应该用什么标准判断能不能直接采信？**

参考答案要点：回到上册第 1 章的可信度分层。先确认这个数字是来自官方 JD 披露还是二手聚合平台，如果是聚合平台要看是否核对过原始页面。还要确认统计口径（总包还是基本工资）是否和自己要对比的数字一致，口径不同不能直接并列比较。

**5. 如果面试官问“你觉得自己能拿到多少薪水”，只用国内三条一手 JD 的区间（34–65 万，见配套手册 C4.2）来回答，是否合适？**

参考答案要点：可以作为现实基准之一，但要结合具体公司、地区、经验年限调整，不能不加说明地直接照搬。因为样本只有三家、且三家的业务性质和产品定价能力并不相同，用作参考区间而非精确报价。

**6. 一份国内 JD 用“年薪可达百万级别”这样的措辞吸引应聘者，本章的态度是接受还是否定这个说法？为什么两种简单回答都不够准确？**

参考答案要点：既不是简单接受也不是简单否定。本章的处理方式是把两个数字都摆出来（笼统说法与三条一手 JD 折算区间），说明缺口存在。让读者自己判断这句话更可能描述的是极少数头部案例还是行业普遍水平，这里不替读者下一个非黑即白的结论。
