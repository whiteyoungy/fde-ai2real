# Lab-09 · 国产栈演练

**关联章节**：下册第 8 章（国产模型与平台栈）、下册第 7 章（信创改造与国产化适配）
**预计耗时**：6–8 小时
**前置**：Ollama + `qwen2.5:0.5b`（CPU 可跑）。**不需要 GPU，也不需要昇腾硬件**

## 这个 Lab 要解决什么

国产栈选型看起来是个技术问题，实际上第一道关卡是法务。

下册第 8 章把这条列为全章最需要记住的硬约束：**Qwen2.5-3B-Instruct 用的是 Qwen RESEARCH LICENSE AGREEMENT，仅限研究与评估、不可商用**；而同系列的 72B 用的是允许商用的 Qwen License。**档位相邻不代表授权条款相邻。**

这个坑之所以危险，是因为它和所有技术直觉都反着来：3B 参数最小、显存最省、在资源受限的现场看起来最合适——恰恰是它不能商用。选错的代价不是效果差一点，是项目上线后被法务叫停。

`fixtures/scenarios.json` 里的 `s1` 和 `s2` 是同一套硬件约束，**只差"是否商用"一个条件**，正确答案就换了一档。这是有意设计的。

## 三种缺口，性质不同，不能用同一句话带过

这个 Lab 最特别的地方是它同时包含三类不同性质的路径，附录 A 已把这件事说清楚：

| 路径 | 本书能不能验 | 该怎么写 |
|---|---|---|
| CPU 降级 | **能**，本 Lab 实测跑通 | 给实测数据 |
| GPU 标准路径 | 不能（无 GPU） | 给官方文档流程，标明未实测 |
| 昇腾 / 国产算力 | 不能（无硬件） | 同上，且要说清缺的是硬件不是意愿 |

实施计划对这一条写得很硬：**「CPU 路径必须实测跑通；昇腾路径若无硬件，明确标注为『基于官方文档的流程说明，未实测』，不假装已验证。」**

所以 `verify.sh` 第 7 项**把这条文档要求做成了机器检查**——产出的昇腾说明里必须有明确的未实测标注和依据来源。

**但它同时查了标注不被滥用**：CPU 路径是实测跑通的，不许也顺手标成"未实测"。只查"有没有写未实测"的话，满篇都标未实测也能过——**那是用免责声明替代验证，比不写更坏**。

## 五步判据（下册第 8 章）

**商用授权 → 显存预算 → 上下文需求 → 函数调用 → 中文能力**

顺序不能换。把商用授权放第一步，是因为它是唯一一个"过不了就完全出局、再好的技术指标也没用"的维度。

**五步走完可行集为空，正确做法是回去和客户谈判放松某个维度，不是硬凑一个方案上线。** `s3` 就是这种情况：政务长文档要 128K 上下文，满足的只有 DeepSeek-V3，但它单机放不下。这时候要给客户的不是一个勉强的方案，而是"要么降上下文走分块检索、要么加硬件预算"这样一个选择题。

`verify.sh` 第 4 项因此要求：`s3` 不但要返回空，还要给出谈判建议。**只说"无解"对客户没有价值。**

## 探针 CLI 契约

- `python3 -m src.select --models fixtures/models.json --scenarios fixtures/scenarios.json --out results`
  → 写出 `results/selection.json`，含 `results[].{scenario_id, selected, reason}`；无解场景 `selected` 为 `null` 并给出 `negotiation` 字段
- `python3 -m src.deploy_cpu --backend http://127.0.0.1:11434`
  → 真调本地模型，打印 `backend=ollama model=... tokens=N ok=true`
- `python3 -m src.vram_budget --models fixtures/models.json --out results`
  → 写出 `results/vram_budget.md`
- `python3 -m src.ascend_doc --out results`
  → 写出 `results/ascend_deploy.md`

## 验收标准

跑 `bash verify.sh`，7 项全部 OK 且退出码 0。

1. **夹具与本地模型就位** — 5 个模型、4 个场景、Ollama 可达
2. **选型结果全部正确** — 4 个场景各自选对（含 `s3` 应为空）
3. **商用场景避开研究许可** — 任何 `commercial_use: true` 的场景都不得选中 3B。**一次都不许**
4. **无解时不硬凑** — `s3` 返回空且给出谈判建议
5. **CPU 路径实测跑通** — 真调模型出结果，不接受任何模拟
6. **显存预算表口径清晰** — 每个数字标明"官方给出"还是"按参数量估算"，估算值按 ≥20% 上浮
7. **未实测标注诚实且不滥用** — 昇腾说明有明确未实测标注与依据来源；CPU 路径不得被误标为未实测

第 3 项独立于第 2 项单列，是因为它的性质不同：**选错档位是准确率问题，选中不可商用的是法务问题**，不适用任何通过率口径。

第 6 项的 20% 上浮不是拍脑袋——估算值只算权重、不含 KV Cache，贴着估算值配硬件在真实负载下必然 OOM。下册第 8 章原文要求"不低于 20%"，并且要说明这个比例的依据。

## 可替换组件

| 本 Lab 用的 | 可换成 | 注意 |
|---|---|---|
| Ollama + `qwen2.5:0.5b` | vLLM + 更大模型（有 GPU 时） | 换后所有延迟数字作废，选型判据不变 |
| 静态 `models.json` | 从官方页面实时抓取 | **许可证条款会变**，正式选型前必须重新核对官方 LICENSE 文件。另注意 `context` 取的是 config.json 默认口径，不是 YaRN 扩展后的 128K |
| 规则选型 | 模型辅助选型 | 五步判据是确定性的，用规则更稳；模型的价值在解释和长尾 |

## 关于本 Lab 数据的时效性

`fixtures/models.json` 是写作时的快照。**许可证条款、上下文长度、显存要求都会变**，正式项目里这份表必须从各模型官方仓库的 LICENSE 与 config.json 重新取数，并标注取数日期。

下册第 8 章还提醒了一条容易混淆的：DeepSeek-V3 开源权重版**从初版发布起就是 128K 上下文**，不存在"某个后续版本才扩展到 128K"这回事——那说的是在线聊天产品，与开源模型规格是两回事。

## 故障排查

**第 3 项失败**
选型逻辑把许可证判据放在了后面，或者压根没判。它必须是第一步，且是一票否决。

**第 4 项：`s3` 选出了一个模型**
约束被悄悄放松了。检查是不是把"上下文 ≥128K"写成了"取最大的"。

**第 5 项：`tokens=0`**
没有真调模型。这一项不接受桩实现——实施计划对 CPU 路径的要求是"必须实测跑通"。

**第 7 项：CPU 路径被标成未实测**
免责声明不能当挡箭牌用。能验的就要验，验了就如实写验了。

## 延伸练习

1. 把 `s1` 的显存上限从 40G 改成 **8G**，重跑。可行集会真的清空（7B 估算 14GB，上浮后 16.8GB，24G 仍塞得下，所以改成 24G 是看不出变化的）。此时该给客户什么建议？正好复用 `s3` 那套动作。
2. 给 `models.json` 加一列"是否支持国密算法"，看下册第 7 章讲的信创合规要求会怎样改变选型结果。
3. 故意把昇腾说明里的"未实测"三个字删掉，跑一次第 7 项，确认它真的会失败。**一个不会失败的检查等于没有这个检查。**
