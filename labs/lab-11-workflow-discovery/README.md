# Lab-11 · 工作流发现演练

服务《前线部署工程师（FDE）：把 AI 交付到真实世界》上册第 10 章（G1 选题）与上册第 11 章（G2 定界）。

## 这个 Lab 和其他 Lab 不一样

其他 Lab 大多是"跑代码、看指标"。这个 Lab 不需要模型、不需要容器、不需要写一行生产代码——它是一次**文档型演练**：你会拿到一套虚构但埋了坑的客户材料，读完之后自己产出一份 Scoping 文档，`verify.sh` 只检查这份文档的**结构**是否完整，不检查、也没有能力检查你的判断对不对。

**这一点必须在开始前说清楚**：`verify.sh` 通过，只说明你写了一份"形式合格"的 Scoping 文档；它完全无法判断你有没有识别出材料里埋的需求错位、有没有看穿访谈里的矛盾、有没有把该砍的需求砍掉。真正用来自评的是 `reference-answer.md`——那不是一份"标准答案"，而是一份"判断标准"：材料里埋了哪些坑、正确的识别方式是什么、哪些需求该砍、验收标准该怎么写。跑完 `verify.sh` 之后，请务必回头对照 `reference-answer.md` 逐条自查，这一步不能省。

## 场景

虚构客户：恒信重工装备有限公司（中型制造企业，生产大型工程机械与生产线设备）。该公司希望给"设备故障报修流程"引入 AI 辅助分诊，找到了你（FDE）。

材料包对应上册第 10 章 4.10 节任务书里描述的场景设置：三个角色（车间班长、维修工程师、设备科科长）加一个 IT 角色的访谈记录、一份现有报修系统的字段/系统清单、一份三年前制定且未更新的"标准报修流程"文档、干系人往来邮件（其中至少一处管理层描述与访谈记录矛盾）。

## 怎么做这个 Lab

1. 通读 `materials/` 全部六份材料，建议顺序就是文件编号顺序——`01` 是客户嘴上说的需求，`02` 到 `05` 是让你去交叉验证这个需求是否属实的素材，`06` 是原始数据，用来验证访谈里提到的"数据质量"问题是不是真的。
2. 读的过程中，尝试用上册第 10 章的工具箱标注：哪些是"待验证假设"、哪些是"当场/有证据确认过的事实"；这份需求里踩中了六种需求错位里的哪几种、证据在哪一份材料的哪一句话。
3. 用 `templates/workflow-canvas.md` 把"设备故障报修"这个流程拆一遍——先判断该用服务蓝图还是 Foundry 本体拆解，再动笔。
4. 复制 `templates/scoping-document.md` 到 `submission/scoping-document.md`，逐段填写。**验收标准段落必须写量化指标，不能写"提高效率"这类无法验收的话**（上册第 11 章 5.4 节的反例）；范围外条款至少列 2 条，且要点名到具体材料里的证据，不能泛泛而谈。
5. 跑 `./verify.sh`，看结构校验是否通过。
6. **无论 `verify.sh` 是否通过，都要打开 `reference-answer.md` 做一次内容自评**——这一步是这个 Lab 真正的价值所在，结构校验只是及格线。

## verify.sh 检查什么、不检查什么

**检查（结构性）**：

- `submission/scoping-document.md`（或 `--example` 模式下的 `submission.example/scoping-document.md`）是否存在
- 是否包含全部 7 个必填段落：范围内 / 范围外 / 假设与依赖 / 验收标准 / 里程碑 / 双方职责 / 变更流程
- "验收标准"段落里是否包含至少一条量化指标（正则匹配"数字 + 单位/百分比"，例如 "≤ 2 小时"" 95%"" 4 周"）
- "范围外"段落是否至少列出了 2 条条款
- 全文是否至少识别出 1 处"权限拿不到/审批卡住"的风险（正则匹配"权限/审批/访问"类关键词与"无法/未/待/卡住/风险"类关键词同现）

**不检查（内容判断）**：

- 你写的"范围内/范围外"划分是否合理
- 你识别出的需求错位是不是真的、证据是否站得住
- 你的验收标准数字是否合理、是否真的可执行
- 你砍掉的需求该不该砍

这些判断力相关的问题，`reference-answer.md` 会给出讲师视角的判断依据，请自己对照，`verify.sh` 做不到，也不应该假装能做到。

## 用法

```bash
cd labs/lab-11-workflow-discovery

# 第一次运行前，先创建你自己的答卷
mkdir -p submission
cp templates/scoping-document.md submission/scoping-document.md
# ……填写 submission/scoping-document.md……

./verify.sh              # 校验你自己的答卷
./verify.sh --example    # 校验讲师提供的示范答卷（应始终通过，退出码 0）
```

## 常见故障排查

- **`./verify.sh` 报"找不到 submission/scoping-document.md"**：先执行 `mkdir -p submission && cp templates/scoping-document.md submission/scoping-document.md`，再填写、再跑。
- **"缺少必填段落"报错但我确实写了那一段**：检查段落标题是不是用的 Markdown 标题语法（`#`/`##`/`###` 开头），且标题文字里包含要求的关键词本身（如"三、范围外"包含"范围外"三个字即可，不需要一字不差）；纯加粗文字（`**范围外**`）不会被识别为标题。
- **"验收标准缺少量化指标"报错**：检查是不是只写了"提升效率""让系统更智能"这类表述——参考上册第 11 章 5.4 节的反例/正例表，改写成带数字、单位、时限的句子，例如"上线 4 周内，抽样 200 条分诊结果人工复核，准确率 ≥ 90%"。
- **"未识别出权限风险"报错**：材料包 `03-系统清单.md` 里明确埋了一个"权限拿不到"的系统（MES 生产数据访问），检查你的"假设与依赖"或"范围外"段落有没有提到这件事、有没有用到"权限/审批"和"无法/待批"这类词。
- **`bash: ./verify.sh: Permission denied`**：执行 `chmod +x verify.sh` 后重试。
- **`--example` 模式也失败了**：这说明示范答卷本身和检查脚本不匹配，属于 Lab 本身的 bug，不是你的问题——请检查是不是在错误的目录下执行（必须在 `lab-11-workflow-discovery/` 目录内运行）。

## 延伸练习

1. **反着做一遍**：先不看 `materials/`，只看 `01-需求邮件.md`，直接写一版 Scoping 文档；再读完全部材料后重写一版。对比两版的"范围外"条款差了多少条——这个差值大致就是"不做现场调研直接开工"的隐性成本。
2. **把访谈矛盾做成一张表**：列出 `02-访谈记录.md` 里每一处角色之间的矛盾陈述，逐条判断该信谁、需要什么补充证据（影子跟随/系统日志/书面确认）才能真正分出对错，而不是凭直觉选边站。
3. **给拒绝写脚本**：假设客户在验收前一周提出"顺便把知识库问答机器人也加上"，用上册第 11 章 5.5 节的五句话术之一，写一封回复邮件（不是回复"好的"或"不行"，而是像话术示范那样把决定权交还给客户或升级决策）。
4. **换一个行业重做一遍**：把材料包里的"设备故障报修"换成你熟悉行业的一个真实流程（哪怕是虚构细节），重新走一遍情境访谈标注、需求错位识别、Scoping 文档产出的全过程——这是检验你是不是真的学会方法、而不是记住了这一套材料的最好方式。
