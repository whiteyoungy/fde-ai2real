# Lab-10 · 事件流后台对账智能体

**关联章节**：上册第 14 章第二则（混乱数据摄取与自主对账）、下册第 4 章（企业集成与协议桥接）
**预计耗时**：6–8 小时
**前置**：Docker（跑 Kafka）、约 1GB 磁盘、约 1GB 可用内存

## 这个 Lab 要解决什么

两套系统的账对不上。订单系统说这笔 4580 元结算在 4 月 1 日，财务台账说它在 3 月 31 日。月末结账时，两边月报差了一笔。

传统做法是写个定时脚本比对字段、发一封告警邮件，剩下的交给人。上册第 14 章 16.4 节讲的是另一种做法——**告警里直接带上根因诊断和一份可执行的补偿脚本草案**，人只需要复核和点确认。

差别不在技术含量，在运维成本。一封"T-2001 金额不一致"的告警，收件人要花二十分钟翻两个系统的日志才知道发生了什么；一封"T-2001：B 系统把 UTC 时间当本地时间入库，导致跨月，补偿 SQL 见附件"的告警，复核只要两分钟。

## 智能体的三步（照 16.4 节）

| 步 | 做什么 | 本 Lab 的落点 |
|---|---|---|
| ①隔离 | 把涉事事务标记出来，防止它继续污染下游状态计算 | 写入 `quarantine` 表 |
| ②根因诊断 | 重构该事务在两套系统里的完整执行图（到达顺序、时间戳、状态变更序列），定位到具体原因 | 归类到三种根因之一 |
| ③起草补偿 | 生成可执行的补偿 SQL 草案，连同诊断报告提交人工复核 | 写出 `results/compensation.sql` |

## 这条规矩是硬的：起草 ≠ 执行

16.4 节原文：**"'起草'和'执行'之间必须隔一道人工闸门——财务台账数据的写操作一旦执行错误，回滚成本远高于多等复核的几分钟，这条闸门不能因为省事而省掉。"**

所以 `verify.sh` 第 7 项会检查：智能体跑完之后，`sys_a_txn` 与 `sys_b_txn` **必须一个字节都没变**。它只允许写 `quarantine` 表。

这一项不设比例，改一行也算失败。让智能体"顺手把账平了"在技术上毫不困难，正因为如此才需要一道机器守着的闸门——省掉它的诱惑，恰恰来自它太容易省掉了。

## 三类根因，各一条注入

| 事务 | 根因 | 现象 |
|---|---|---|
| `T-2001` | `timezone` | 金额状态全对，但 A 记 4/1、B 记 3/31。B 把 UTC 值当本地时间入库，**跨了月** |
| `T-2002` | `out_of_order` | `PAID`(10:15) 先于 `CREATED`(10:12) 到达，下游按到达顺序覆盖，终态回退成 `CREATED`，这笔付款在财务侧从未入账 |
| `T-2003` | `model_mismatch` | A 的单位是分，B 接入时当成元又写进了分字段，相差 100 倍 |

**`T-2002` 光比对两张表是判不出根因的**——表上只看得到"状态不一致"，判不出为什么。必须回到事件流里看到达顺序与业务时间的错位。这就是这个 Lab 需要真 Kafka 而不是两张表直接 diff 的原因。

## 对照组才是这份夹具的重点

除了 3 条注入，还有 4 条**看起来可疑、实际完全正常**的事务，外加 40 条普通事务。**一条都不许报**：

| 事务 | 看起来像什么 | 实际 |
|---|---|---|
| `N-3001` | 事件乱序到达 | 下游按事件时间排序处理，终态正确。**乱序 ≠ 不一致** |
| `N-3002` | 金额为负 | 红冲退款，两边都正确记为负。**负数 ≠ 异常** |
| `N-3003` | 发生在 23:58，跨天边缘 | 两边时区处理一致，入账日相同。**跨天 ≠ 时区问题** |
| `N-3004` | 一亿分的整数大额 | 两边一致。**大额 ≠ 单位错** |

没有这组对照，一个"凡是看着奇怪就报异常"的智能体也能拿满分。

而在真实的财务对账里，误报的代价很具体：每一条误报都要一个人去查，查完发现没事。**误报率高的对账系统，最后的结局是没人看它的告警**——那比没有这套系统更糟，因为你以为自己有。

`N-3002` 值得单独一提：Lab-01 里已经因为"金额必须为正"这个假设踩过一次坑，红冲发票的金额本来就是负的。同一个错误假设在对账场景会以"误报"的形式重现。

## 补偿 SQL 怎么验

不验语法，**直接跑**。

`verify.sh` 第 6 项会把 `fixtures/recon.db` 复制一份，在副本上执行智能体产出的 `results/compensation.sql`，然后**重新跑一遍对账**，要求剩余差异为零。

只检查"SQL 语法有效"是没有意义的——`UPDATE sys_b_txn SET amount_cents = 0` 语法完全有效。要验的是它执行完之后账真的平了。

三条注入的补偿方向各不相同，这也是为什么根因诊断必须先做对：

- `timezone` → 修正 B 的 `occurred_at` 与 `book_date`，金额不动
- `out_of_order` → 把 B 的终态推进到 `PAID` 并补上金额
- `model_mismatch` → 把 B 的金额除以 100

诊断错了，补偿方向就错了，第 6 项自然过不去。

## 探针 CLI 契约

- `python3 -m src.publish --bootstrap 127.0.0.1:19092 --events fixtures/events.jsonl`
  → `published=54 topic=txn-events`
- `python3 -m src.agent --bootstrap 127.0.0.1:19092 --db fixtures/recon.db --out results`
  → `consumed=N flagged=3 quarantined=3 executed=0`
  → 写出 `results/report.json`（含每条的 `root_cause` 与诊断说明）与 `results/compensation.sql`

`executed=0` 是自报的，`verify.sh` 不采信——它自己比对业务表有没有被改。

## 验收标准

跑 `bash verify.sh`，7 项全部 OK 且退出码 0。

1. **夹具与 Kafka 就位** — 47 条台账、54 条事件、Kafka 可达
2. **事件流可消费** — 消费者组能读到全部事件，offset 正常推进
3. **不一致全部检出** — 3 条注入一条不漏
4. **零误报** — 4 条对照 + 40 条普通事务，**一条都不许被标记**
5. **根因诊断正确** — 3 条各自归到正确的根因类别
6. **补偿 SQL 执行后账真的平了** — 在库副本上跑完，重新对账剩余差异为 0
7. **人工闸门未被越过** — 智能体跑完后 `sys_a_txn` / `sys_b_txn` 一个字节没变，只写了 `quarantine`

第 3、4 项必须一起看：只看第 3 项，全标记就能过；只看第 4 项，什么都不标记就能过。

## 两档运行

| 档位 | 诊断方式 |
|---|---|
| 有 `DEEPSEEK_API_KEY` | 模型参与诊断报告撰写与交叉复核，**根因仍由规则裁决** |
| 无 key | 规则档：按确定性判据归因并套模板生成 SQL |

无 key 档同样要过全部 7 项——**根因诊断这件事，规则能覆盖的部分就该用规则**。三类根因各有清晰的判据（时间差恰好等于时区偏移、状态发生回退、金额比恰好是 100 的幂），这些用规则判比用模型判更稳、更快、更便宜。

模型的价值在诊断报告的可读性，以及规则没覆盖到的长尾。**别把能用规则解决的问题交给模型**——这本身就是上册第 14 章想让你形成的判断。

## 可替换组件

| 本 Lab 用的 | 可换成 | 注意 |
|---|---|---|
| Apache Kafka（KRaft 模式） | Redpanda / Pulsar / RabbitMQ | KRaft 已不需要 ZooKeeper；Redpanda 更省内存 |
| `kafka-python-ng` | `confluent-kafka` | 后者是 librdkafka 绑定，性能更好但要编译 |
| SQLite | PostgreSQL / MySQL | 补偿 SQL 的方言会变，`datetime()` 函数尤其不通用 |
| 规则归因 | 模型归因 | 见上，三类根因用规则更稳 |

## 故障排查

**Kafka 连不上，但容器日志显示 `Kafka Server started`**
advertised listener 配错了。容器内的 CLI 拿到的地址是给宿主机用的，在容器里连不通——这是 Kafka 最经典的坑。本 Lab 的宿主机客户端连 `127.0.0.1:19092` 是对的。

**第 4 项：对照组被误报**
多半是把"乱序到达"直接当成了异常。`N-3001` 的事件确实乱序，但终态正确。判据应该是终态是否一致，不是事件是否乱序。

**第 5 项：`T-2001` 被判成 `model_mismatch`**
只比了 `book_date` 不同就往下猜。时区问题的判据是**两边 `occurred_at` 的差恰好等于时区偏移**（8 小时），金额完全相同。

**第 6 项：SQL 跑完还有差异**
检查补偿方向。`timezone` 类不该动金额，`model_mismatch` 类不该动时间。

**第 7 项：业务表被改了**
智能体直接执行了补偿 SQL。它只该把 SQL 写进文件。

## 延伸练习

1. 再造一条"两个根因叠加"的事务（既有时区问题又有单位问题），看你的诊断逻辑会输出什么。真实现场里叠加是常态。
2. 把补偿 SQL 的执行做成带审批流的：复核人点确认后才执行，且执行前后各存一次快照。
3. 故意让智能体直接执行补偿 SQL，跑一次第 7 项，确认它真的会失败。**一个不会失败的检查等于没有这个检查。**
4. 本 Lab 的夹具里事务之间没有依赖关系，所以没有落点验证 16.6 节讲的「隔离要级联标记下游依赖事务」。给夹具加一列 `depends_on`，再加一项检查——注意这会和第 4 项的"一条额外的都不许标记"产生张力，你需要先想清楚级联标记出来的事务算不算误报。
