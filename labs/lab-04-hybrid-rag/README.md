# Lab-04 · 混合检索 RAG + 检索质量诊断

**关联章节**：下册第 4 章 §4.6（检索质量三分法诊断）、下册第 5 章（混合检索与 RRF）、下册第 15 章（案例四 · 高并发 RAG 性能手术）
**预计耗时**：8–10 小时
**前置**：Docker（跑 Qdrant）、约 4GB 磁盘（Qdrant 镜像 275MB + embedding 95MB + 重排序模型 1.1GB + CPU 版 venv 约 1.3GB）

## 这个 Lab 要解决什么

客户上线了一套向量检索的知识库问答，用了两周之后来找你："查不准，是不是模型不行？"

这个 Lab 要练的是**不接受这个判断，先去量**。量完你会发现两件事：

1. "混合检索比纯向量好"不是一句放之四海皆准的话。**在很多语料上，纯向量已经接近满分，混合毫无价值，甚至更差。**
2. 混合检索真正成立的前提很窄——**两个检索器的失败集必须不相交**。如果 BM25 只是在向量已经做对的地方也做对，融合不会带来任何提升，反而会把向量做对、BM25 做错的那些拖下来。

### 语料是怎么设计出来的

本 Lab 的语料不是随手凑的。写 Lab 之前先量了三种情形：

| 情形 | 纯向量 Recall@5 |
|---|---|
| A. 120 篇、每篇主题各异 | **100%**（混合毫无价值） |
| B. 40 篇结构相同的维保卡，查询是裸编号 | **40/40**（仍然满分） |
| C. 1200 篇措辞几乎一致、只有编号不同，查询是「一段自然语言里埋着编号」 | **29/40**（终于失手） |

情形 A 和 B 推翻了一个很常见的直觉：「稠密向量分不开 ERR-4012 和 ERR-4021」。实测中裸编码之间的余弦相似度确实高达 0.79，**但只要文档正文各不相同，语义线索就足以把答案送到第一名**。

稠密检索真正失手的是情形 C：文档之间的语义差异趋近于零，唯一的区分信号就是那串编号，而编号在长句里被大量常见词稀释掉了。企业知识库里这类文档——工单、复盘报告、巡检记录、规格书——往往占大头。

所以最终语料同时包含两种性质的文档，评测集也同时包含两种查询。这是混合检索能赢的**必要条件**，不是为了让数字好看。

## 评测集的四类查询

| 类型 | 条数 | 长什么样 | 谁擅长 |
|---|---|---|---|
| `lexical` | 8 | `BX-70 怎么填` | 两者都行 |
| `semantic` | 8 | `报销要等多久才能到账`（文档写「费用核销时限」） | 向量 |
| `buried_id` | 40 | `上次那个对账差异的事件，编号好像是 INC-20777，改进项有哪些` | BM25 |
| `hybrid` | 3 | `存储满了上传失败但下载正常是哪个故障` | 需要两者 |

## 实测基线（写 Lab 时量过，你的实现应当能复现到同一量级）

| | 总 Recall@5 | lexical | semantic | buried_id |
|---|---|---|---|---|
| BM25 only | 92% (54/59) | 8/8 | 3/8 | 40/40 |
| 向量 only | 90% (53/59) | 8/8 | 8/8 | 34/40 |
| **RRF 混合** | **98% (58/59)** | 8/8 | 7/8 | 40/40 |

注意 `semantic` 那一列：混合是 7/8，比纯向量的 8/8 **低**。融合不是免费的，它在某一类上换来的提升，可能在另一类上有代价。总账赢了才叫赢。

## 一个实现上的坑：RRF 要在 top-K 候选上融合

写 Lab 时先按"对两路完整排序做 RRF"实现，结果混合永远夹在两个基线中间，怎么调都超不过更强的那个。原因是完整排序让每一路的头部结果无条件参与打分——一个 BM25 排第 1、向量排第 800 的文档，仍然能靠 BM25 那一项挤掉向量排第 1 的正确答案。

**正确做法是各取 top-K（本 Lab 用 50）截断后再融合**，落在 K 之外的文档不获得任何贡献。改完之后混合才同时超过两个基线。

RRF 公式：`score(d) = Σ 1 / (k + rank_i(d))`，`k` 取 60 是常用默认值。

## Qdrant API 的两个坑（已实测确认，client 1.19.0）

- **`search()` 与 `recommend()` 已被移除**——不是弃用，是调用会直接报 `AttributeError`。必须用 `query_points()`。
- **过滤参数拼写不统一**：`query_points()` 用 `query_filter`，`scroll()` 用 `scroll_filter`。写混了不会报参数名错误，只会静默地不过滤。

三分法 Step 1「知识库里到底有没有这份材料」必须用 `scroll()` 精确扫描，**刻意绕开向量检索**——这一步要确认的是"内容存在与否"这个更底层的事实，不能让检索算法本身的好坏干扰判断。

## 三分法诊断

按下册第 4 章 11.6 节的三步归因实现：

| Step | 判断 | 是 | 否 |
|---|---|---|---|
| 1 | 知识库里有支持材料吗 | 进 Step 2 | `missing_content` |
| 2 | 这份材料出现在检索结果里吗 | 进 Step 3 | `retrieval_failure` |
| 2b | 命中的材料内容本身对吗 | 进 Step 3 | `data_pollution` |
| 3 | 回答忠实于 context 吗 | `answer_actually_correct` | `hallucination` |

`fixtures/diagnose_cases.jsonl` 里 5 条用例覆盖全部四种根因，外加一条本来就正确的——**诊断脚本不能把正常件也报成故障**，这一条是防它乱报的。

`data_pollution` 那条最值得琢磨：知识库里躺着一份 2023 年的旧规（30 个工作日），已被新规（15 个工作日）取代。它内容自洽、措辞专业、检索也能命中，**整条链路每一步看起来都正常**。判据是文档上的 `superseded_by` 字段，不是看模型怎么转述它。

## 验收标准

跑 `bash verify.sh`，7 项全部 OK 且退出码 0。

1. **夹具完整** — 1241 篇文档、59 条查询、5 条诊断用例
2. **Qdrant 索引就绪** — 1241 个向量灌入成功
3. **三路基线可复现** — 脚本自动打印 BM25 / 纯向量 / 混合三个数值
4. **混合显著优于纯向量基线** — RRF 的 Recall@5 至少高出纯向量 5 个百分点，且不低于 BM25
5. **互补性成立** — 分类别报告须显示：`semantic` 类上向量优于 BM25，`buried_id` 类上 BM25 优于向量。这一项防的是"靠单一检索器撑起总分、混合只是搭便车"
6. **Rerank 生效** — 对候选集重排后 MRR 有提升
7. **三分法归因正确** — 5 条注入用例全部判对根因，含那条不该报错的正常件

第 4 项是本 Lab 的核心验收，也是实施计划里写明的那一条。第 5 项是它的护栏——**只看总分会被"BM25 一家独大"蒙混过关**。

## 验收环境（实测数据的产生条件）

本 README 里所有数字都来自下面这套环境，换环境后**数字会变，结论未必变**：

| 项 | 实际值 |
|---|---|
| 硬件 | 无 GPU，2 核 CPU，3GB 内存 |
| Qdrant | 1.19.0（Docker，端口 16333） |
| qdrant-client | 1.19.0 |
| embedding | `BAAI/bge-small-zh-v1.5`，512 维 |
| 重排序 | `BAAI/bge-reranker-base` |
| torch | **CUDA 版**（`pip install sentence-transformers` 的默认行为） |
| 验收结果 | `verify.sh` 7/7，退出码 0 |

**这里有一处落差要说明白**：上面「运行」一节让你装 CPU 版 torch（省约 3.8GB 磁盘），但本 Lab 完成验收时装的是默认的 CUDA 版——因为当时还没意识到它会拉进整套 `nvidia-*` 依赖，是做 Lab-06 时才发现的。

两者在无 GPU 机器上跑的都是 CPU 算子，检索结果预期一致；但**这是推断，不是实测**——我们没有在 CPU 版 torch 下重跑一遍验收。如果你按 README 装 CPU 版后数字对不上，那是一个真实的发现，不是你装错了，欢迎反馈。

之所以不重跑：验收环境已如实记录，而重跑要重新下载约 1.2GB 依赖，在当时只剩 3.8GB 磁盘的机器上代价不划算。**把条件写清楚，比让数字看起来更漂亮重要。**

## 可替换组件

| 本 Lab 用的 | 可换成 | 注意 |
|---|---|---|
| Qdrant | pgvector / Milvus / 纯 numpy 内存索引 | 1241 篇规模用 numpy 完全够；选 Qdrant 是为了贴近生产形态 |
| `BAAI/bge-small-zh-v1.5` | bge-base/large-zh、m3e、text2vec | 换模型后基线数值会变，**必须重新量一遍**，不要沿用本文档的数字 |
| `rank_bm25` | Elasticsearch / OpenSearch | 生产上 BM25 通常已在搜索引擎里现成可用 |
| `jieba` 分词 | HanLP / pkuseg / 字符 n-gram | 本语料上实测**字符 bigram（57/59）反而优于 jieba（54/59）**，不分词只有 10/59。中文 BM25 的关键是切得足够细，不是非用 jieba 不可 |
| RRF | 加权线性融合、learned fusion | RRF 的好处是不需要归一化两路分数 |
| 交叉编码器重排 | 不重排 / LLM 重排 | 重排延迟高，生产上通常只对 top-20 做 |

## 运行

```bash
python3 -m venv .venv && . .venv/bin/activate
# 必须先装 CPU 版 torch，否则 sentence-transformers 会拉进整套 CUDA 依赖，
# venv 从 1.3GB 涨到 5GB 以上。没有 GPU 的机器上这些包一个都用不到。
pip install --index-url https://download.pytorch.org/whl/cpu torch
pip install -r requirements.txt
python3 fixtures/generate.py        # 首次运行需要
bash verify.sh                       # 会自己拉起 Qdrant 容器并在退出时清理
```

首次运行会下载两个模型：embedding 约 95MB，交叉编码器重排序约 1.1GB（第 6 项用）。重排序模型比其余全部依赖加起来还大，网络慢的话这一步最耗时。

测退出码不要放进管道：`bash verify.sh > /tmp/v.log 2>&1; echo $?`

## 故障排查

**`AttributeError: 'QdrantClient' object has no attribute 'search'`**
1.16.0 起已移除，改用 `query_points()`。

**第 4 项：混合没有跑赢纯向量**
先看 RRF 是不是在完整排序上做的。截断到 top-50 再融合。

**第 5 项：互补性不成立**
分类别数值不对，通常是 BM25 那一路的中文没做切分——按空格切的话本语料上只剩 10/59，几乎等于没用。注意「必须用 jieba」是个流传甚广但不准确的说法，见下册第 4 章 11.4 节的实测对比。

**第 7 项：`data_pollution` 被判成了 `answer_actually_correct`**
Step 2b 没做。命中了正确主题的文档不代表文档内容是对的，要检查 `superseded_by`。

**Qdrant 端口冲突**
本 Lab 用 16333，避开默认的 6333。
