## 关于 vLLM：这个 Lab 为什么没跑它

实施计划原文写的是「vLLM 服务 + 量化模型 + 语义缓存层 + 压测脚本」，并预留了一句「**无 GPU 环境降级为 CPU 小模型，验收阈值相应放宽并在 README 说明**」。本书写作的机器就是这种环境：无 GPU、2 核、3GB 内存、磁盘只剩几个 GB。vLLM 的 wheel 本身 303MB，加上 torch 依赖装不下，3GB 内存也起不来。

所以**本 Lab 的推理后端换成了 Ollama**，vLLM 部分只有部署说明、没有实测数据。这一点必须说在前面，因为这本书的规矩是不假装跑过没跑过的东西。

**换掉推理后端不影响这个 Lab 真正要教的内容。** 语义缓存的设计取舍、缓存的误命中风险、压测该量什么、量化档位怎么比——这些和后端是 vLLM 还是 Ollama 无关。真正和 vLLM 强绑定的是 PagedAttention 带来的吞吐量级、连续批处理的调度行为这类数字，而那些数字**本来也不该照抄别人的**，必须在你自己的卡上量。

如果你手上有 GPU，README 末尾的「换成 vLLM」一节给了替换步骤，`verify.sh` 的阈值也留了环境变量入口。

## 这个 Lab 要解决什么

客户嫌贵、嫌慢。你想到的第一个办法通常是加缓存——相同的问题不要重复推理。

问题在于**"相同"怎么定义**。字符串完全相等的缓存命中率低到没有意义（用户不会两次输入一模一样的字）。于是自然想到语义缓存：把问题编码成向量，相似度超过阈值就复用上次的答案。

这个 Lab 要让你亲眼看到这个想法的危险之处：**语义缓存的误命中，是把别人问题的答案，斩钉截铁地回给这个用户。** 它不像检索失败那样表现为"没找到"，而是表现为一个流畅、自信、完全错误的回答，且日志里看起来一切正常——缓存命中率还很好看。

## 核心实测：纯阈值方案无解

`fixtures/cache_pairs.jsonl` 有 22 对问题，10 对应当命中（同义改写），12 对不该命中（似而不同）。用 `bge-small-zh-v1.5` 量出来：

| | 相似度 |
|---|---|
| 应命中的最低 | 0.651 |
| **不该命中的最高** | **0.954**（「合同盖公章找谁」/「合同盖合同章找谁」） |

两组完全重叠。也就是说**不存在任何一个阈值能把它们分开**：

| 阈值 | 命中率 | 误命中 |
|---|---|---|
| 0.85 | 7/10 | **4/12** |
| 0.90 | 5/10 | 2/12 |
| 0.94 | 1/10 | 1/12 |

调到 0.94 时缓存已经基本不工作了（10 条同义改写只认出 1 条），**却仍然有一次误命中**。

这不是模型不好，也不是阈值没调对。是**"语义相似"和"能用同一个答案"本来就是两回事**——「公章」和「合同章」在向量空间里几乎重合，在审批流程里却是两条路。

## 三层缓存

既然单一信号不够，就分层。每一层解决上一层解决不了的那部分：

| 层 | 做什么 | 成本 | 解决什么 |
|---|---|---|---|
| 1. 稠密相似度 | 向量召回候选 | 一次 embedding | 找回改写、同义、语序变化 |
| 2. 标识符护栏 | 问题里的编号必须完全一致 | 免费（正则） | `BX-07`/`BX-70`、`ERR-4021`/`ERR-4012` 这类 |
| 3. 模型裁判 | 判断两问能否共用一个答案 | 一次短推理 | 「公章/合同章」这类纯语义的区分 |

第 2 层实测把误命中从 4 降到 2 而命中率不变——**免费的一层，先加上**。但它降不到零，剩下的 `f01`（试用期是几个月 / 可以延长几个月）和 `f11`（公章 / 合同章）没有编号可比。

这和第 11、12 章混合检索是同一个二元性：**稠密负责找回，词面负责分辨。** 两边都需要。

### 第 3 层的模型选择：实测有下限

| 裁判 | 准确率 | 表现 |
|---|---|---|
| `qwen2.5:0.5b` | 3/6 | **六条全答「是」**，没有任何判别力 |
| `deepseek-chat` | 7/8 | 四条最难的「否」全对 |

0.5B 模型当不了等价性裁判——它不是判错，是根本没在判。这条对下册第 10 章的 LLM-as-Judge 是个补充：**裁判任务有模型尺寸下限，小模型的"判断"可能只是一个恒定输出。**

DeepSeek 唯一的错误是把一对真同义（「试用期多长」/「试用期一般是多久」）判成了「否」。**这个方向的错是安全的**：误判不等价只是多花一次推理，不会返回错答案。裁判就该往这边偏——宁可少命中，不可错命中。

## 两档验收标准（重要）

| 档位 | 条件 | 命中率要求 | 误命中要求 |
|---|---|---|---|
| **有 key** | 有 `DEEPSEEK_API_KEY`，三层全开 | ≥6/10 | **必须为 0** |
| **无 key** | 只有第 1、2 层 | ≥5/10 | ≤2 |

无 key 档的标准是**如实放宽的，不是把夹具改软**。上面的数据已经证明：没有第 3 层，纯 embedding 在这份夹具上任何阈值都做不到零误命中。

**所以无 key 档这个配置是不安全的，只用来跑通链路，不要照搬到生产。** 这句话写在这里，是因为把它藏起来更危险——一个看起来能跑、验收也过了的配置，最容易被直接抄进客户环境。

## 验收标准

跑 `bash verify.sh`，7 项全部 OK 且退出码 0。

1. **夹具与模型就位** — 22 对用例、两个量化档位、Ollama 可达
2. **推理后端可用** — 打印单次基线延迟
3. **缓存命中率达标** — 按上表分档
4. **误命中受控** — 有 key 档必须为 0，无 key 档 ≤2。**这是本 Lab 的核心验收**
5. **对照组证明护栏有效** — 纯阈值方案在同一夹具上的误命中必须严格多于三层方案。这一项防的是"护栏其实没起作用，只是阈值调高了"
6. **压测显示缓存收益** — 缓存开启后 P95 显著下降，且打印 QPS 与命中率
7. **量化档位对比** — q4 与 q8 的延迟、体积、输出对比表

第 5 项值得说明：只看第 4 项的话，把阈值调到 0.99 也能让误命中变 0——但那时缓存等于没有。第 5 项要求**对照组和实验组用同一个阈值**，差别只在护栏，这样才能证明是护栏在起作用。

## 故障排查

**第 4 项：有 key 档误命中不为 0**
第 3 层没接上，或者裁判的 prompt 太宽松。裁判要明确列出"什么情况算不等价"——不同单据编号、不同费用科目、不同假期类型、不同印章、一个问「是什么」另一个问「能不能改」。

**第 5 项：对照组和实验组误命中一样多**
两组用了不同阈值。对照组必须与实验组同阈值，差别只在有没有护栏。

**第 6 项：缓存开了 P95 没降**
压测的请求流里重复率太低。要构造有真实重复模式的流量，不是每条都不一样。

**Ollama 连不上**
`curl http://127.0.0.1:11434/api/version` 确认服务在跑。
