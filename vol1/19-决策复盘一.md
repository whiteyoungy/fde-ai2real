## 为什么复盘要从被否决的方案讲起

方案评审会上被采纳的那个，事后看总是显得理所当然。真正难的是当时摆在桌上的另外三个——
它们各自都有支持者，各自都有说得通的理由，而否决它们的依据往往写在会议纪要之外。

**一年之后，没有人记得为什么否决了方案 B。** 于是下一个项目里，方案 B 又被提了一遍。

本章与下一章各写一则完整复盘，用同一个结构：
客户处境 → 真实冲突 → 被否决的方案及理由 → 最终决策 → 踩过的坑 → 可迁移的部分。

选这两个案例，是因为它们卡在两道不同的关：
**本章这一则卡在第 2 关 定界**——合规边界把技术选型压到了墙角；
**下一章那一则卡在第 1 关 选题与第 2 关 定界之间**——客户以为自己要的是 A，真实痛点是 B。

> **在骨架里的位置**：**读这两则复盘时带一个问题**：每一次被否决的方案，
> 否决它的理由落在三类结果的哪一类上——是攒不出证据、施加不了控制，还是没人能接管。
> **这个分类比“技术上更优”更能解释真实的决策。**

## 读完这章你能做什么

1. 复述这一则里被否决的方案，以及否决的具体依据——不是“不合适”，是具体哪一条不成立。
2. 判断自己手上的项目是不是也被一条合规边界压着，而团队还在比较技术方案。
3. 把“被否决的方案及理由”变成自己项目复盘文档的固定栏目。

## 19.1 客户背景

本章的客户是一家教学合成的精密测控装备制造企业（以下称“衡宇科技”，虚构化名），
主营产品是为军工装备配套的传感器与测控系统。企业本身不直接参与武器系统总体
设计，但产品最终进入涉密供应链，因此其研发网络按涉密信息系统分级保护要求与军工保密资质管理
（涉密系统适用保密行政管理体系的分级保护，不走等保序列——两套体系别混，
非密的办公与生产系统才按等保定级），物理上与办公网、互联网完全隔离，
没有网闸之外的任何连接路径。

工程团队沉淀了二十多年的设计图纸、测试报告、失效分析记录与供应商变更记录，
这些资料散落在不同年代的文档系统里，检索效率很低——一名资深工程师要查一份
十年前的失效分析案例，经常靠“记得是哪个项目”这种口口相传的经验，而不是靠
系统检索。管理层想要的是一个部署在隔离网络内部、面向研发工程师的技术资料
问答系统，把历史设计知识用自然语言检索出来，减少对个别老工程师经验的依赖。

项目立项会上，客户安全办第一句话就把边界划死了：模型、代码、依赖、数据
全部不能离开隔离网络的物理边界，也不能有任何形式的外联——这不是“我们
尽量减少外网依赖”的软性目标，是保密制度的硬性红线。任何技术方案摆上台面，
第一道筛选标准都是“是否需要哪怕一次性的外网连接”，通不过这一条，
后面的架构设计、模型效果都不用再谈。

## 19.2 真实冲突

五个约束叠加在一起，任何单点方案都会先撞上其中一条：

**无外网连接**。研发网与互联网、与企业办公网之间都是物理隔离，除了受严格
审批的单向导入设备之外没有任何连接路径，而单向导入设备本身也要走独立
审批，不是常规运维手段可以调用的通道。这意味着任何“运行时联网校验授权”
“在线更新检查”“云端遥测上报”这类默认行为，都必须先在联网环境里逐一
识别出来并显式关闭，而不能假设它们不存在。

**不能实时拉取依赖**。`pip install`、`npm install`、`docker pull` 在隔离网
内全部无法执行——这正是下册第 1 章 §1.4 讲的“依赖地狱”的极端版本：那一节
处理的是“能连内网但只让走白名单代理”和“能装但版本对不上”两类半隔离
场景，本章处理的是完全没有网络的场景，下册 §1.4 的 wheelhouse 打包思路是
本章离线部署包的雏形，但隔离程度更彻底，容错空间也更小。

**禁遥测与日志回传**。不少推理框架、可观测性 SDK、模型下载工具默认会
上报使用数据或做版本检测请求，而且这类上报调用往往不是统一走一个顶层
开关，是分散在多个子模块里各自发起的——这类“默认打电话回家”的行为，
客户安全办要求逐项识别并阻断，漏掉一个都算不合格，不能靠“关掉能找到
的那个开关”就交差。

**镜像必须过漏洞扫描与合规审查**。进入隔离网络的每一个容器镜像，都要
经过安全办的漏洞扫描、三级等保测评相关流程，以及针对军工保密资质的
专项审查，审查周期以周甚至月计——这不是能靠“加急”缩短的行政流程，
项目排期必须把它当成一个和开发工作量并列的独立里程碑，提前预留出来。

**模型权重传输需审批**。从互联网下载的开源模型权重，要通过介质拷贝
审批（移动硬盘走保密办的登记流程）才能带入隔离网络——不是“scp 一下”
就能解决的事。理论上每一次权重更新（包括微调产出的增量权重）都要走
一次这个流程，这一点直接决定了后面 19.4 节 LoRA 微调这个架构决策的
成因，不是纯技术偏好。

## 19.3 被否决的方案

**方案一：云端 API + 专线**。这是客户 IT 部门最初设想的“折中方案”——
用加密专线把隔离网络和云端大模型 API 连起来，既不用自己维护模型，
延迟也比公网调用低。这个方案在第一次合规评审就被否决，理由不是延迟
或带宽，而是保密制度红线：专线本质上仍然是与外部网络实体的双向连接
路径，涉密网络分级保护的标准不允许隔离网络与任何外部实体存在数据
往返通道，哪怕这条通道是加密的、专用的、低延迟的。更直接的问题是——
调用云端 API 意味着请求内容（可能包含涉密图纸参数、失效分析细节）
必须离开物理边界，这本身就构成保密事件，不是“控制好访问权限”能规避
的问题。这条方案甚至没有进入原型验证阶段，评审当天就被划掉。

**方案二：采购国际厂商的“本地私有化一体机”（闭源黑盒方案）**。市面上
有厂商提供打包好的本地部署一体机，宣传“支持离线部署、无需联网”。
这个方案被否决的原因是合规扫描过不了：闭源二进制无法做代码级漏洞
扫描，也无法生成完整的 SBOM（软件物料清单）——下册第 10 章 §10.2 讲的
syft 生成 SBOM 这一步，前提是能拿到镜像内部的软件成分信息，闭源
黑盒设备连这个前提都不满足，供应链信任链在第一步就断了。更麻烦的
是，这类设备的授权验证和技术支持机制通常依赖联网激活或定期心跳
上报，与“禁遥测”的要求直接冲突，而厂商自己也说不清楚设备内部
到底有没有、有多少个这样的上报点——“说不清楚”本身就是拒绝理由，
不需要等实测抓包坐实。

**方案三：现场从零预训练自有模型**。有人提出“既然不能用别人的模型，
干脆自己训一个，彻底可控”。这个方案在可行性论证阶段就被否决——
预训练需要的数据规模、算力集群、专业人才门槛，客户现场都不具备，
现场项目周期通常以月计，而从零预训练一个可用模型的周期是以年计的，
数量级完全不匹配。这不是“技术上做不到”，是“在项目预算和排期约束
下做不到”，工程决策要把这类现实约束当成硬边界，而不是停留在纸面上
讨论理论可行性。

三个方案被否决后，团队才把选型收敛到“开源权重 + 现场 LoRA 微调 +
完全自包含离线部署”这条路径上。

## 19.4 最终架构决策

判据是三条叠加：**License 是否允许在当前场景下自由部署与修改、模型
参数规模是否匹配客户现场能提供的算力上限、以及每一次迭代产生的变更
是否足够小以便通过审批流程**。据此做出五项决策：

1. **开源权重选型**。综合 License 条款与硬件需求来看，Qwen2.5-7B/14B
   -Instruct（Apache 2.0 协议，单卡消费级 / 入门级数据中心 GPU 即可
   跑起来）与 GLM-4-9B-Chat（glm-4 License，商用需注册但免费，128K
   上下文，单卡 16GB 级即可）是两个能在客户现场有限算力条件下完整
   部署的选项[1][2]。刻意避开了 Qwen2.5-72B 使用的 Qwen License
   （超 1 亿月活需另行申请授权）——虽然客户体量不可能触及这个门槛，
   但合规审查更倾向选择条款最宽松、无需额外申请沟通的协议，能省掉
   一轮审查沟通；DeepSeek-V3、Kimi-K2 这类千亿参数级 MoE 模型则直接
   被参数规模淘汰，它们需要多机多卡集群才能跑起来，客户现场的物理
   机柜与电力预算都不支持[3][4]。
2. **LoRA 微调**。现场用工程团队历史积累的设计文档、失效分析记录做
   微调，选择 LoRA 而不是全参数微调，除了常见的“算力有限、标注数据
   量不足以支撑全参数微调”这个理由之外，还有一条本章场景特有的现实
   考量：LoRA 产出的是体积远小于全量权重的适配器增量文件，而不是
   一整份重新训练出来的完整模型权重——按 §19.2 提到的“模型权重传输
   需审批”这条约束，如果每一次迭代都要把几十 GB 的全量权重重新走
   一次介质审批流程，项目节奏会被行政流程拖垮；LoRA 增量文件小到
   可以合并多次迭代打包成一次审批申请，这是合规约束反过来决定
   技术选型的一个典型例子。
3. **自包含离线部署包**。镜像导出、cosign 签名、syft 生成 SBOM、
   离线依赖打包、离线安装脚本这五步流程，下册第 10 章 §10.2 已经讲
   清楚（对应 Lab-07，Task 42，已实现并通过验收），本章不重复展开，直接复用。
4. **本地向量库硬接线**。检索所需的向量库只能部署在隔离网络内部，
   配置里不允许出现任何可解析到外部地址的连接串——这不只是“记得
   填内网地址”这种操作规范，而是要在配置校验层面做成“物理上不
   可能误配置外部地址”，具体做法见下一节的代码骨架。
5. **合规扫描应对**。在 下册 §10.2 流程基础上加一步“外联地址审计”：
   扫描镜像内所有可执行文件与配置文件里出现的主机名、IP 地址，
   逐条比对内网网段白名单，任何不在白名单内的地址都要在提交安全办
   审查前解释清楚或直接移除，而不是等安全办扫出来才现场解释——
   前者是主动把问题解决在评审之前，后者是被动等着被打回。

```python
# outbound_audit.py —— 外联地址审计骨架（示意，未实测）
import re
from pathlib import Path

# 内网网段与允许的本机地址，按客户实际网络规划替换
INTERNAL_ALLOWLIST = ["10.20.", "127.0.0.1", "localhost"]

HOST_PATTERN = re.compile(
    r"(https?://[a-zA-Z0-9\.\-]+)|(\b(?:\d{1,3}\.){3}\d{1,3}\b)"
)


def scan_file(path: Path) -> list[str]:
    """扫描单个文件里出现的主机名/IP，返回不在白名单内的可疑地址。"""
    text = path.read_text(errors="ignore")
    findings = []
    for match in HOST_PATTERN.finditer(text):
        candidate = match.group(0)
        if not any(candidate.startswith(prefix) for prefix in INTERNAL_ALLOWLIST):
            findings.append(candidate)
    return findings


def audit_directory(root: str) -> dict[str, list[str]]:
    """对解压后的镜像层或配置目录做全量外联地址审计。"""
    report = {}
    for path in Path(root).rglob("*"):
        if path.is_file() and path.suffix in (".py", ".yaml", ".yml", ".json", ".conf"):
            findings = scan_file(path)
            if findings:
                report[str(path)] = findings
    return report
```

## 19.6 踩过的坑

- **当时以为**在联网机器上把要用的 Python 包一次性 `pip download`
  打包好就万事大吉，**实际**按下册第 1 章 §1.4 讲的 `--platform`
  等四个参数虽然对齐了 CPU 架构和 Python 版本，但打包机器和客户
  机器的操作系统发行版底层库版本（如 GLIBC）不一致，个别带 C
  扩展的 wheel 在客户机器上导入时直接报错，才意识到“目标机器
  标签”不只是架构和 Python 版本，操作系统发行版本身也要对齐。
- **当时以为**客户机房的 GPU 驱动是标准安装，装上匹配的 CUDA
  Toolkit 就能跑，**实际**客户机房出于信创审查要求提前预装了一个
  内部审核通过的旧版本 NVIDIA 驱动，与推理框架要求的 CUDA 版本
  不匹配，而驱动升级本身又要走一次新的安全审批，最后是反过来
  选择匹配旧驱动的框架 / CUDA 组合，而不是要求客户升级驱动——
  客户环境的既有基线是约束条件，不是可以随意改动的变量。
- **当时以为**镜像漏洞扫描只是走个流程，**实际**扫描工具报出的
  基础镜像历史 CVE 数量相当可观，其中不少是操作系统基础层的
  已知漏洞、根本不影响实际运行路径，但安全办按数量一刀切打回，
  最后是换用一个更精简的基础镜像把可扫描面积和 CVE 数量本身
  降下来，而不是逐条解释“这个漏洞不影响我们”——解释成本远高于
  换一个更干净的基础镜像。
- **当时以为**模型权重“下载好就能用”，**实际**带入隔离网络的
  每一次权重更新（包括 LoRA 微调产出的增量权重）都要走一次介质
  审批，审批周期以周计，如果没有提前规划好训练迭代节奏、把多次
  小的权重更新攒成一次批量申请，项目进度会被反复的审批流程拖慢。
- **当时以为**关掉一个“网络请求”的顶层开关就等于禁掉了所有遥测，
  **实际**有的 SDK 在多个子模块里各自埋了独立的上报调用，不是
  统一走一个可配置开关，必须逐个审计代码或抓包验证没有任何出站
  流量，才能真正确认遥测已经关闭——这也是 19.5 节那个外联地址
  审计脚本要存在的原因，光靠人工代码审查容易漏。

## 19.7 复盘与可迁移经验

**可迁移的经验**：License 对比这套判据（选条款最宽松、模型规模适配
现场可用硬件的选项）可以搬到任何“不能用云端大模型、只能自己扛”
的场景，不限于军工；LoRA 微调因为增量文件体积小更容易过审批这一点，
是“合规约束反过来决定技术选型”的典型例子，这个思路——先看流程
摩擦成本，再看纯技术最优——可以迁移到很多受严格审计的行业（金融、
医疗、政务）；外联地址审计与本地向量库硬接线这类“把制度要求做成
配置层面物理上不可能违反”的工程化收口手法，也能迁移到所有对数据
出境有硬红线的场景，不只是物理隔离环境。

**不可直接迁移的部分**：具体的漏洞扫描阈值、基础镜像的精简选择、
GPU 驱动与框架版本的匹配组合，是客户当前那套安全基线决定的，换一个
客户环境基本要重新走一遍验证；审批流程的具体周期（以周计还是以月计）、
走哪个审批系统，是客户组织内部流程决定的，不同单位差异很大，
不能假设“上次两周这次也两周”。

**国际对照：政府云隔离与物理隔离不是一回事**。检索范围内能找到的
最贴近本章场景的公开案例，是美国陆军与 Ask Sage 的合作：据 Ask Sage
官方新闻稿（2025 年 6 月 30 日）披露，双方与微软合作，基于 Azure
Government 的 FedRAMP High / IL5（Impact Level 5）授权云环境为
美国陆军部署企业级生成式 AI 环境，接入 Azure AI Foundry 的 GPT-4o
及 o 系列推理模型；同一份新闻稿称“正在积极推进在 IL6（涉密网络）
部署该平台，预计未来数周内推出”[5]。这里有一点容易被读者混淆：
**IL5 依托的是政府云，是“云隔离”而不是“物理隔离 / 空气隙”**，
本章衡宇科技这种研发网与互联网完全物理断开的场景，对应的更接近
新闻稿里提到、但截至发稿仍处于“未来数周内推出”状态的 IL6，
两者不能混为一谈。

另一个常被提及的数字是“400 个用户账号”，但它出自更早的另一份
公告——2024 年 9 月 DefenseScoop 的报道，对应的是陆军 cArmy 云环境
（同样是 IL5）的首次部署阶段，援引 Ask Sage 官方表述“陆军的工具
部署将从 400 个新用户账号开始，目标是扩展到企业级应用”[6]。这个
数字和上面 2025 年 6 月的 IL5 新闻稿是两次不同时间点的公告，不应
拼在一起当成同一次事件的细节——本书写作前的引文审计过程中，
就发现过这类“跨公告拼接”的错误，也发现过“一周内重新分类 30 万份
人员描述文档、节省超过 5 万工时”以及“陆军是首个此规模转型的军种”
这两个说法，在两份新闻稿原文里都找不到出处，判定为无法溯源，
本章不会使用这两个数字。

还有一个信源层级的教学案例值得提一句：多个信源转述美国 Los Alamos
国家实验室（LANL）内部人员表态，称该实验室出于处理受控非密信息、
出口管制信息等原因选择自托管大模型而非依赖云端 API，但这些表态
只在第三方博客里能找到转述引语，没有定位到 LANL 官方新闻室的一手
公告原文。遇到这种情况，正确的处理方式不是因为“听起来很像一个
好案例”就直接引用，而是老实标注“据第三方转述”，把可信度层级如实
呈现给读者——这正是第 2 节讲的可信度分层原则，在案例写作里的
具体落地，不是抽象原则。

MCP 打通遗留系统那一类案例，同样面临“具名企业效果数字查无来源”
的问题，只是表现形式不同——那里缺的是完整效果案例，这里缺的是
被拆开又拼错的运营数字。怎么在缺乏可验证效果数据的情况下，
依然把 MCP 协议本身的公开事实用对地方，下册第 14 章那则完整案例会讲。

## 自检问题

1. 客户 IT 提出“用加密专线把隔离网络连到云端大模型 API，延迟比公网
   低很多，是不是可以考虑”，这个提议站得住脚吗？
   参考答案要点：站不住——问题不在延迟或带宽，专线本质上仍是与
   外部网络实体的双向连接路径，涉密网络分级保护标准不允许这种
   通道存在，且请求内容离开物理边界本身就构成保密事件，这是制度
   红线而不是可以靠工程优化绕开的性能问题。

2. 某国际厂商的本地部署一体机宣传“完全离线、无需联网”，但技术
   细节不公开，能不能作为候选方案进入原型验证？
   参考答案要点：不能直接采信“无需联网”这句宣传语——闭源二进制
   无法做代码级漏洞扫描、生成不了 SBOM，供应链信任链在第一步就
   断了；且这类设备的授权验证和技术支持机制通常依赖联网激活或
   心跳上报，厂商说不清楚内部有没有这类上报点，这本身就是拒绝
   理由，不需要等实测抓包坐实。

3. 为什么本章选择 Qwen2.5-7B/14B-Instruct 或 GLM-4-9B-Chat，而不是
   参数规模更大、榜单分数可能更高的 Qwen2.5-72B 或 DeepSeek-V3？
   参考答案要点：72B 用的 Qwen License 有超 1 亿月活需申请授权的
   条款，虽然客户体量用不到，但更宽松的 Apache 2.0/glm-4 License
   能省掉一轮合规沟通；DeepSeek-V3、Kimi-K2 这类千亿参数级模型
   需要多机多卡集群，客户现场的物理机柜和电力预算根本不支持，
   参数规模是硬约束，不是“选更准的模型”就能绕开的。

4. LoRA 微调在本章里被选中，除了常见的“算力有限”这条理由，还有
   哪条本章场景特有的现实考量？
   参考答案要点：LoRA 产出的增量权重文件体积远小于全量权重，
   而模型权重传输需要走介质审批、周期以周计，体积小的增量文件
   更容易把多次迭代打包成一次审批申请，避免项目节奏被反复的
   审批流程拖慢——这是合规约束反过来决定技术选型的例子。

5. Ask Sage × 美国陆军的 IL5 部署案例，为什么不能直接当作“物理隔离
   AI 部署”的对照案例来用？
   参考答案要点：IL5 依托的是 Azure Government 政府云，是“云隔离”
   而不是“物理隔离/空气隙”，新闻稿里更接近本章场景的 IL6 在披露
   时点仍处于“未来数周内推出”的状态，两者是不同程度的隔离，
   引用时必须明确区分，不能因为都叫“隔离”就等同视之。

6. “400 个用户账号”这个数字能不能和“陆军 IL5 部署”这份 2025 年
   6 月的新闻稿放在一起引用？
   参考答案要点：不能直接放在一起——“400 个账号”出自 2024 年 9 月
   DefenseScoop 报道的 cArmy 部署阶段，是更早的另一次公告，与
   2025 年 6 月的 IL5 新闻稿是两个不同时间点的事件，拼在一起会
   构成跨公告拼接的错误，引用时必须分别标注各自的出处和时间。
