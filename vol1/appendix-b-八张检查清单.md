## B.1 Scoping 检查清单

来源：第 11 章《第 2 关 定界：把“做到哪儿算完”写进合同》。适用时机：客户第一次会议结束后、正式报价之前。任何一项打不了勾，说明 Scoping 还没做完，不要急着进入排期和报价。

**可行性三角（立项前）**

- [ ] 数据轴：数据存在性、可访问性、质量是否已现场抽样核实，而非只听客户口头保证“数据都在系统里”（见第5章 §11.1）
- [ ] 权限轴：谁有最终签字权、正常审批周期多长、审批卡住时有没有不依赖该审批链的绕行方案，三个问题都已问清楚（见第5章 §11.1）
- [ ] 时间轴：deadline 是否有具体外部锚点事件（监管申报、财报季、董事会汇报、合同续签），还是说不出具体事件的“越快越好”式软约束（见第5章 §11.1）
- [ ] 三个维度里任一维度落在红灯，已停止报价与排期，先把红灯项转成黄灯或绿灯（见第5章 §11.1）
- [ ] 三个合规门禁问题已在立项阶段问完：要不要办大模型备案、数据出境落在哪一档、客户是不是关基运营者。这三项的审批周期以月计，答不上来按红灯处理（见第5章 §11.1、第13章 §18.6）

**Scoping 文档（SOW）**

- [ ] SOW 已覆盖 12 个板块并逐条填空，而不是只保留标题不填具体内容（见第5章 §11.2）
- [ ] 第 6 板块「已知失效边界与人工兜底」已填，且客户方在这一页上签了字——**不是等验收当天才第一次拿出来**（见第5章 §11.2、第 13 章 §13.3）
- [ ] 每项交付物都各自附独立的验收标准，没有两项及以上共用同一条模糊描述（见第5章 §11.2）
- [ ] 退出评审（第11板块）已写明继续 / 重新定界 / 终止三分支的判定依据，且是在签署时写好，不是等试点结束才临时讨论（见第5章 §11.2）

**范围外 / 假设 / 依赖条款**

- [ ] 范围外条款采用收紧写法——“即便它能与本服务互操作，也不算在范围内”这一类把口子反着堵死的表述（英文合同样例见第 11 章 §11.3 来源 [4]），不给“反正用得上，应该算在里面”留扩权空间
- [ ] 假设条款已与变更管理流程绑定，写明“若上述假设发生变化，范围/时间线/费用可能相应调整”（见第5章 §11.3、§11.6）
- [ ] 依赖条款已点名到具体第三方和具体动作（如“客户方IT部门在两周内开通只读访问权限”），而非笼统写“依赖客户配合”（见第5章 §11.3）
- [ ] 作为分包方时，接口联调、内网与网闸审批、第三方组件缺陷定责这三类工作的责任主体已具名写到总包或甲方科技部门，条款里没有出现“由各方协商”（见第5章 §11.3、第11章 §16.4）
- [ ] 假设清单已请客户方决策人书面确认“以上假设准确且有效”，不是甲方单方面撰写、客户从未表态（见第5章 §11.3）

**验收标准**

- [ ] 每条验收标准满足 SMART（具体/可测量/可达成/相关/有时限）+ 3C（清晰/简洁/可核验），没有“提升效率”“增强体验”这类无法验收的表述（见第5章 §11.4）
- [ ] 精度类指标已按版本分级递进（如“第一版达到 Level 8，第二版提升到 Level 9”），而非一次性锁死终态数字（见第5章 §11.4）
- [ ] 验收动作的抽样规则、数量、复核方式已在 SOW 阶段定下，能直接变成第 13 章黄金集的第一批用例（见第5章 §11.4）
- [ ] 已知失效边界已单独成页，与验收指标一起请客户签字：超出语料覆盖时的处理方式、长尾召回失败率的实测值、明确不在本期范围的问题类型（见第8章 §13.3）

**拒绝与变更**

- [ ] 已识别四类必须当场拒绝或标记高风险的需求：无数据支撑的、要求100%准确率的、范围无边界的、要求绕过合规的（见第5章 §11.5）
- [ ] 任何口头提出的追加需求，当天或次日已生成对应的变更请求记录，即使最终结论是拒绝（见第5章 §11.6）
- [ ] 变更单已包含“不响应变更的影响”与“备选方案与建议”两栏，未被省略（见第5章 §11.6）
- [ ] 变更规模若已大到需要重新定义交付物和 KPI，走的是“重新定界”分支并更新原 SOW 文本，而不是让新旧需求在同一份文档里含糊共存（见第5章 §11.6）

## B.2 安全与合规审查清单

来源：第 18 章《合规与备案：哪些事必须在立项前做》，日志脱敏与审计留痕部分来自下册第 10 章 §10.5。适用时机：立项阶段先过一遍确认适用范围，上线前再过一遍确认材料齐全——第 18 章 §18.6 强调过，发现合规缺口的成本随项目阶段递增，立项阶段发现只是改方案，运维阶段才发现可能已经构成违规。

**关基认定**

- [ ] 已判断客户是否属于关键信息基础设施运营者（网络安全法 §31），这个判断结果决定后续等保定级门槛与数据出境口径（见第 18 章 §18.1）
- [ ] 若确认为关基运营者，向量库、日志、评估数据集默认不接境外托管服务，出境须走完整安全评估（见第 18 章 §18.1、§18.4）

**数据分级**

- [ ] 已完成数据分类分级摸底，给客户数据打一般 / 重要 / 核心标签（数据安全法 §21）（见第 18 章 §18.1）
- [ ] 数据标签已直接决定哪些数据能进 RAG 检索层、能不能交给外部大模型 API 处理（见第 18 章 §18.1、§18.6）
- [ ] 若客户被认定为重要数据处理者，年度风险评估报告已写入运维 SOW 的固定条目，不是一次性验收项（见第 18 章 §18.1、§18.6）

**备案适用性**

- [ ] 已判断系统是否向境内公众提供服务（生成式人工智能服务管理暂行办法第二条）——企业内部纯自用系统原则上不适用本办法（见第 18 章 §18.3）
- [ ] 已判断系统是否具有舆论属性或社会动员能力（第十七条）——两道门槛必须同时满足才需要走安全评估和算法备案，不是对公众开放就一律要备案（见第 18 章 §18.3）

**出境评估触发条件**

- [ ] 已按三档梯度估算出境个人信息 / 重要数据的量级：关基运营者出境（须申报评估）> 非关基但出境重要数据或个人信息≥100万人/敏感信息≥1万人（须申报评估）> 10万-100万人（标准合同或认证）> 更低量级且符合2024年新规豁免情形（豁免）（见第 18 章 §18.4）
- [ ] 已确认“用了境外 API 就一定要做完整安全评估”这个默认假设不成立——纯 B2B 内部工具、出境量远低于门槛时可能直接落在豁免区间（见第 18 章 §18.4）

**等保定级**

- [ ] 已按系统承载业务的重要性与影响面，将其纳入既有二级 / 三级等保框架（AI 系统目前没有专门的国家定级标准）（见第 18 章 §18.2）
- [ ] “系统不涉及个人信息所以不用管等保”这类推理已被排除——判断依据是业务重要性和影响面，不只是是否处理个人信息（见第 18 章 §18.2）
- [ ] 三级及以上系统的年度测评（二级视情况两年一次，以当地公安网安部门口径为准）已写入运维 SOW 的固定节奏（见第 18 章 §18.2、§18.6）

**行业专项与日志留痕**

- [ ] 金融客户涉及资金交易/信贷审批/理赔的高风险场景，已确认走风险管理委员会审批，且该环节已计入项目排期（见第 18 章 §18.5）
- [ ] 医疗客户的产品设计未让 AI 以医生身份直接对话患者完成诊疗——医师实名认证与最终把关是硬性要求，不是风格选择（互联网诊疗监管细则第十三条）（见第 18 章 §18.5）
- [ ] PII 脱敏已在写入日志 / trace 之前完成，不是在展示层或下游消费端才做（见下册第 10 章 §10.5）
- [ ] 脱敏方案已组合正则规则（覆盖身份证号/手机号/邮箱等结构化字段）与 NER 模型（覆盖人名/地址等非结构化文本），未只依赖单一手段（见下册第 10 章 §10.5）
- [ ] 审计记录已采用只追加写入或哈希链等防篡改机制（见下册第 10 章 §10.5）
- [ ] 审计记录本身的查看权限已有独立授权层级，不是全体工程师默认可访问（见下册第 10 章 §10.5）

## B.3 上线检查清单

来源：第 14 章 第 5 关 上线 §14.1–§14.3，Evals CI 门禁部分来自下册第 8 章 §8.5。适用时机：每一次灰度发布前，而不是只在系统首次上线时用一次——版本迭代同样要过这张表。

**灰度策略**

- [ ] 已明确本次上线用哪种切分方式（按用户比例 / 按用户分群 / 功能开关），并说明选择理由——只关心风险爆炸半径用按比例，价值风险在角色间不对称用按分群（见第9章 §14.1）
- [ ] 若需要做 A/B 统计显著性验证，采用“按用户比例 + Experiment Toggle”，未用按分群方式（分群天然不均匀会引入混杂变量）（见第9章 §14.1）
- [ ] Ops Toggle（Kill Switch）已就位，高负载时可一键降级非核心 AI 功能（见第9章 §14.1）
- [ ] Release Toggle 已有清理计划，未放任其长期堆积在代码库里成为技术债（见第9章 §14.1）

**可观测性基线**

- [ ] 调用量、延迟分位（P50/P95/P99）、错误率均已接入监控，且错误率已区分“系统错误”与“业务拒答”两类，未混在一起统计（见第9章 §14.3）
- [ ] Token 成本已按功能模块拆分统计，而非只看总账单（见第9章 §14.3）
- [ ] 评估指标在线值（RAGAS faithfulness、context recall 等）已抽样接入线上流量持续计算，与滚动基线对比，而非只在离线评估集上跑一次（见第9章 §14.3）
- [ ] override rate 与静默失败率已纳入监控，且遵循“静默失败比排队等待更危险”的判断原则（见第9章 §14.3）

**告警阈值**

- [ ] 告警阈值已通过在至少两三个历史版本/时间窗口上跑分数分布、找拐点的方式标定，不是照抄别处看到的数字（见第9章 §14.3）
- [ ] 阈值已建立定期上调机制，随系统整体质量提升调整，不是设完一次就一劳永逸（见第9章 §14.3）

**Evals CI 门禁**

- [ ] 黄金集综合分、回归集通过率、对抗集通过率、检索指标相对回退、生成指标相对回退，五类检查项已接入发布门禁（见下册第 8 章 §8.5）
- [ ] 回归集检查项为硬性阻断，历史故障复发零容忍，不给例外（见下册第 8 章 §8.5）
- [ ] 相对回退项允许人工审批后带风险发布，但发布记录必须写明回退了多少、为什么接受这次回退（见下册第 8 章 §8.5）
- [ ] 门禁有效性已用“故意引入一个劣化改动，门禁必须阻断；恢复后必须放行”的方式验证过，而不是只确认脚本能跑完（见下册第 8 章 §8.5，对应 Lab-05 验收标准）

## B.4 交接检查清单

来源：第 14 章 §14.5《运维交接：签字不算数，演练才算数》。这张清单的核心不是走完全部勾选，而是最后一组“故障演练验证”——前面的交接包和 PRR 判据全部打勾，如果没有一次真实故障复现验证，都不能证明客户运维团队真的接得住。

**交接包内容**

- [ ] 系统文档已包含架构图、数据流图、部署步骤、回滚方案（见第9章 §14.5）
- [ ] SLO/SLA 已书面明确，不是口头约定（见第9章 §14.5）
- [ ] On-call 手册已针对上一季度最常见的五类故障，各自写明具体命令、具体看板链接、具体升级联系人，不是一份笼统的“故障处理指南”（见第9章 §14.5）
- [ ] 交接纪要已发到团队可见的共享频道，不是只有口头或私聊交接（见第9章 §14.5）

**生产就绪评审（PRR）硬性判据**（正文只认这两条为硬判据）

- [ ] 所有导致用户侧降级或失败的异常情况都已上报，能被观测到（见第9章 §14.5）
- [ ] 所有用户可见的失败都已配置合适的告警（见第9章 §14.5）

**交接包补充项（不属于 PRR 硬判据，属于交接包内容）**

- [ ] 三层监控（内部状态监控、端到端行为监控、告警管理）均已就位，且有“监控的监控”防止哑巴故障（见第9章 §14.5）
- [ ] 机器/机架/集群离线时的处置方案、后端存活检测方式已交接清楚（见第9章 §14.5）
- [ ] 模型服务商限流或降级时的优雅降级方案已交接，避免连锁过载第三方服务（见第9章 §14.5）

**用一次故障演练验证接得住（不是签字了事）**

- [ ] 已完成至少一次故障演练，注入的是交接前真实发生过的故障场景复现，而不是凭空设计的极端场景（见第9章 §14.5）
- [ ] 演练采用“提前告知即将演练但不告知具体时间”的方式，既不是完全不打招呼，也不是提前告知具体故障点（见第9章 §14.5）
- [ ] 已记录故障发生时刻、MTTD（检测时刻）、MTTA（响应/升级时刻）、MTTR（缓解时刻）四个时间点（见第9章 §14.5）
- [ ] 已核对客户团队是否按 on-call 手册指引操作，而非脱离手册凭经验瞎试——手册没被用上，说明手册写得不好用或团队没被真正培训过，不能怪团队不专业（见第9章 §14.5）
- [ ] 复盘遵循 blameless（不问责）原则，聚焦故障的促成因素，未追究具体某个人或团队的责任（见第9章 §14.5）
- [ ] 复盘产出的是具体可执行的改进项（哪一步手册要改、哪个看板链接失效、升级联系人是否正确），不是“下次会注意”这类空泛结论（见第9章 §14.5）
- [ ] “接得住”的四条判定——团队独立完成检测、按手册正确升级、MTTA 落在提前约定的合理区间、复盘产出具体修订项——已全部满足；任一条明显不达标，交接视为未完成，需要补一轮培训再排一次演练（见第9章 §14.5）
- [ ] 客户运维负责人在交接单上签字，不能替代上面这次真实故障复现验证——签字只证明“文档收到了”（见第9章 §14.5）

## B.5 事故响应清单

来源：第 14 章 §14.3 与 §14.5，日志与审计部分来自下册第 10 章 §10.5–§13.6。适用时机：事故发生的当下按顺序过一遍，而不是留到复盘会才想起该做什么——尤其是前三条，晚做就来不及了。

- [ ] 事故分类已区分“系统错误”（超时、5xx、模型服务不可用）与“业务拒答”（模型主动判断无法回答），排查方向未因两者混算而走偏（见第9章 §14.3）
- [ ] 向业务方汇报延迟类事故时，已把 P99 等百分位数字翻译成“多少用户受影响”，而非只报一个抽象的百分位数（见第9章 §14.3）
- [ ] 静默失败（系统悄无声息给出错误结果）已被识别为比“排队等待人工审核”更高优先级的事故类型（见第9章 §14.3）
- [ ] 已确认模型服务商限流或降级时系统走的是优雅降级路径，未因重试风暴连锁冲击第三方服务（见第9章 §14.5）
- [ ] 事故响应已记录 MTTD（检测）、MTTA（响应/升级）、MTTR（缓解）三个时间点，而非只关注“最终是否解决”（见第9章 §14.5）
- [ ] 复盘遵循 blameless 原则，聚焦促成因素而非追究个人或团队责任（见第9章 §14.5）
- [ ] 复盘产出为具体可执行的修订项（手册哪一步要改、看板链接是否失效、升级联系人是否正确），不是“下次注意”式空泛结论（见第9章 §14.5）
- [ ] 事故排查期间，涉及 PII 的日志/trace 依然保持脱敏状态，未因“要排查问题”临时关闭脱敏中间件（见下册第 10 章 §10.5）
- [ ] 审计记录的查看权限在事故响应期间依然遵循独立授权层级，未因紧急情况绕过访问控制（见下册第 10 章 §10.5）
- [ ] 成本看板可按模型/租户/业务功能拆分定位异常放量来源，事故涉及成本异常时不是只看总账单排查（见下册第 10 章 §10.6）
- [ ] 事故复盘后，新的分数点已回填进历史分数分布，触发的告警阈值/门禁阈值已重新评估是否需要调整，不是阈值设完一次就不再变动（见第9章 §14.3）

## B.6 离场边界清单

来源：第 6 章 §6.3《沉淀的边界》，法规锚点见该节参考来源 [6][7][8]。
适用时机：**这张清单要用两次。** 第一次在签合同之前——那时候还改得动条款；
第二次在撤场之前——那时候只能执行已经写好的条款。
签约那次没做，撤场那次就只剩下靠默契。

> **这不是对客户的不信任，也不是对自己人的不信任。** 边界写清楚，双方都好办：
> 客户知道你能带走什么，你也不用在每一次复用的时候凭感觉猜。

**签约前：把三件事写进合同**

- [ ] 数据与衍生模型的处置方式已约定——项目结束后是销毁、返还还是可继续持有，
      以及“衍生模型”包不包括微调权重、向量库、评估集（见第14章 §6.3）
- [ ] 可进入模型训练的数据范围已明确列出（白名单式，不是“除敏感数据外均可”这种反向表述），
      与第 18 章数据出境与分类分级的口径对齐（见第13章 §18.1、§18.4）
- [ ] 经验复用的边界已书面约定——可复用的是方法与结构，不可复用的是这家客户的具体参数与运行现状；
      写法要落到“哪些可以”，不要只写“不得泄露商业秘密”这种引用法条的空条款（见第14章 §6.3）
- [ ] 已确认合同里的知识产权归属条款怎么写。若写着“本项目产生的全部成果归甲方”，
      交付范围已按底座与现场层分开写明：现场层源码与微调适配器权重归甲方，
      底座以许可方式提供、源码不在交付范围内（见第14章 §6.3）
- [ ] 驻场人员的保密承诺已逐人签署，不是靠公司层面一份总协议覆盖——银行项目这是《银行保险机构信息科技外包风险监管办法》的明文要求（见第11章 §16.1、第11章）
- [ ] 若约定了竞业限制，已核对三件事：人员范围没有扩大到未接触商业秘密的人、
      期限不超过两年、按月的经济补偿标准已写明（见第14章 §6.3 引用的人社部合规指引）

**项目期内：让边界可执行**

- [ ] 现场笔记按两类分开归档——方法一份，这家客户的具体情况一份。**分文件，不是分段落**（见第14章 §6.3）
- [ ] 团队知识库有入库前的抽象层级检查环节，判据是那一句：
      原样给这家客户的直接竞争对手，他会不会少走弯路（见第14章 §6.3）
- [ ] 底座与现场层在仓库和构建产物上是分开的，不是混在一个仓里共用一套构建——
      **讲不清哪些是底座的时候，条款按字面走**（见第14章 §6.3）
- [ ] 驻场期间对客户生产环境的操作有留痕，能事后审计——这既是客户要的，也是自证清白的凭据（见下册第 10 章 §10.5）
- [ ] 想写进个人作品集的客户指标，**已在项目期内取得书面授权**。
      离职或项目结束之后再补，基本要不到（见第14章 §6.3 本章清单；别册三第 9 章）

**撤场前：确认客户不是变弱了**

- [ ] B.4 交接清单已全部通过，包括那次故障演练——**这是撤场的前置条件，不是可选项**（见附录 B.4）
- [ ] 客户侧已有人能独立完成一次常规变更（改配置、加一条规则、更新一批数据），
      并已实际做过一次，不是“培训过了”（见第10章 §15.4）
- [ ] 三个自持度问题都有明确答案：最近一次配置变更是谁做的、出事第一通电话打给谁、
      客户能不能自己回滚（见第10章 §15.4）
- [ ] 按合同约定完成数据与衍生模型的销毁或返还，并留下书面确认——
      口头说“已经删了”在事后追责时不成立（见本清单第一组）
- [ ] 撤场后的支持边界已书面写明：哪些问题还管、管多久、超出部分怎么计费（见第11章 §16.7）

**任一条打不了勾就撤场，风险不在客户那边，在你这边。**
客户后续出了问题，第一个被问到的是最后一个碰过这套系统的人。

## B.7 死法自查表

前六张按交付阶段排。这一张按**失败方式**排——用法是反过来的：
不是“这一步该做什么”，而是“**我现在这个项目，像不像正在死**”。

每一条命中，去对应的章看完整案例。判据写成能当场回答的问句。

| # | 像不像正在死 | 命中说明失守在 | 去哪儿看 |
|---|---|---|---|
| 1 | 这个项目要花多久、多少钱才能验证“用户会不会真的用它”？如果答案以年和百万计—— | **第 1 关 选题** | 第 10 章 §10.9 |
| 2 | 数据能不能拿到问清楚了，**多久能拿到**问清楚了吗？ | **第 2 关 定界** | 第 11 章 §11.7 |
| 3 | 第二、三个客户提同类定制时，你是加了个分支，还是抽了个配置项？ | **第 2 关 + 反哺回流** | 第 11 章 §11.7、第 6 章 |
| 4 | 开工到今天，有没有任何一个时刻，一小块真的东西在真实数据、真实系统上跑过？ | **第 3 关 切片** | 第 12 章 |
| 5 | 出问题时，你能定位到是管线里哪一层错了吗？还是只能整体关停？ | **第 4 关 验收** | 第 13 章 §13.6 |
| 6 | 模型能对外做出价格或合同层面的承诺吗？上线前做过诱导测试吗？ | **第 4 关 验收** | 第 13 章 §13.6 |
| 7 | 什么信号出现时必须停、谁有权停——写下来了吗？上一次真的拦下过什么？ | **第 5 关 上线** | 第 14 章 |
| 8 | 技术指标全绿，**有多少人真的在用**？说得出这个数吗？ | **第 6 关 采用** | 第 15 章 §15.5 |
| 9 | 出事的时候，同事发邮件是发给你个人，还是发给一个团队邮箱？ | **人，不是项目** | 第 3 章 |

**第 9 条和前八条不是一类东西**，故意放在一起：前八条问项目，第 9 条问你自己。
一个项目可以八条全不中而第 9 条中——那说明项目是健康的，**被消耗的是你**。

### 这张表怎么用才有效

**别一个人填。** 前八条里多数的答案掌握在别人手上——数据审批周期在客户 IT 那儿，
真实使用率在运维后台里，定制分支的数量只有维护的人清楚。
**一个人填出来的自查表，填的是自己的印象。**

**在项目还顺利的时候填。** 这九条全部是**滞后指标转成的前瞻问句**——
等到已经能明显感觉出问题，前面几条早就中了。
建议的节奏：每个里程碑填一次，和第 11 章那份范围文档一起归档，
**这样下一次填的时候能看见上一次的答案。**

## B.8 五层自查表

前七张查的是**过程**：这一步该做什么、像不像正在死。这一张查的是**资产**：
**你手上到底建起来了什么。**

两个方向缺一不可。一个项目可以前七张全部勾满而这一张全是空的——
六关全过、系统上线、客户签字，然后团队发现下一个项目还是从零开始。
**那种项目过的是会，不是关**（第 4 章 §4.0）。

用法：每个里程碑填一次，和 B.7 一起填。**空着的层，记下它会在第几关炸。**

### 资产层（客户带得走的，各占一行）

- [ ] **本体**：业务名词有没有钉死的定义？拿一个名词问两个部门，答案一样吗（第 5 章）
- [ ] **本体**：每个对象至少挂一个真实业务动作，挂不上的已经删掉
- [ ] **本体**：能以文本导出、能进版本库、能做差异审查——**这是“本体属于客户”的工程落点**
- [ ] **技能**：这个行业的做法有没有落成可注册、可发现、可加载、可执行、可版本的东西（第 6 章 §6.4）
- [ ] **技能**：每条技能都绑了一组用例——**没有配套评估集的技能不是资产，是负债**
- [ ] **验收集**：三层齐了（黄金集、对抗集、回归集），不是只有黄金集（第 7 章 §7.0）
- [ ] **验收集**：七个维度都在测，不是只测结果正确性（第 7 章 §7.2）
- [ ] **验收集**：**客户方的人在客户环境里能自己跑出一份报告**——跑不了，它就不是客户的资产

### 设施层（可以换的，查的是规矩不是选型）

- [ ] **工具**：列出系统输出的所有数字，逐个问“这个数谁算的”，没有一个是模型算的（第 8 章 §8.1）
- [ ] **智能体**：模型没有自己的账号，工具调用在**调用者本人**的权限内执行（第 8 章 §8.2）
- [ ] **智能体**：自动执行的开关做成一张表，逐类动作标明自动／人批／禁止，**并有具名的人签字**
- [ ] **治理**：角色词表在第 2 关就钉进了本体，没有留到上线前补权限（第 8 章 §8.4）
- [ ] **治理**：对抗性安全有独立的用例，没有被“权限配好了”顶掉

### 一句话结账

- [ ] 项目结束时，客户手上多了**本体、技能、验收集**里的哪几样？
      **一样都没有，这一单是纯服务**——不管前七张勾得多满

### 空着的层会在哪一关炸

| 空的是 | 通常炸在 | 长什么样 |
|---|---|---|
| 本体 | 第 4 关 验收 | “这跟我们想要的不一样”，而双方都说不清哪里不一样 |
| 技能 | 第 6 关 采用 | 人一走系统就停，不是坏了，是没人知道该怎么用 |
| 验收集 | 第一次模型升级 | 修好过的问题复发，两周之内没有人发现 |
| 工具 | 上线后某一天 | 一个数字错了，而且说不清是谁算的 |
| 治理 | 第一次审计 | 日志里所有操作都是同一个账号做的 |

## 八张清单怎么串起来用

前六张表不是互相独立的检查项集合，它们对应一个项目从立项到运维的时间线：B.1 用在立项谈判阶段，判断这单能不能接、接了怎么定边界；B.2 贯穿立项到运维全程，越晚发现合规缺口代价越大；B.3 用在每一次发布前，不只是首次上线；B.4 用在项目移交给客户运维团队的节点，唯一的硬通过标准是故障演练而不是签字；B.5 用在系统进入常态运维之后，事故发生时按清单顺序响应。B.1 里验收标准写清楚的那批用例，会直接变成 B.3 里 Evals CI 门禁的黄金集输入；B.4 的故障演练记录下来的 MTTD/MTTA/MTTR，又是 B.5 事故响应清单里同一套时间点定义的来源——B.6 横跨首尾——它的第一组要在 B.1 定界的同一场谈判里落进合同，最后一组要在 B.4 交接通过之后才允许勾选，撤场是整条时间线的收口。B.7 不占时间线上的位置——它按失败方式横切前面全部六关，在每个里程碑拿出来填一次。**B.8 也不占位置，但它切的方向和前七张都不同**：前七张问“这一步做了没有”，B.8 问“这一层建了没有”——过程和资产是两根独立的轴，一个项目可以在其中一根上满分而在另一根上是零分。八张表用的是同一套方法论在不同阶段、不同方向上的具体化，不是八套互不相干的规范。
