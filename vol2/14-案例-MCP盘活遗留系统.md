# 第 14 章 · 案例一：用 MCP 盘活遗留大型机

> **一句话结论**：模型有脑无手，不是模型能力问题，是遗留系统缺一层安全、可审计、带权限边界的执行接口。

> ⚠️ **教学合成案例**：本章的项目叙事、架构决策过程与踩坑细节为基于行业常态构建的教学案例，
> 非特定客户的真实项目。全书调研未能找到任何一家企业公开发布的、具名的“用 MCP 打通遗留系统”
> 完整案例研究——Anthropic 官方客户故事页、企业技术博客与行业媒体报道，
> 全都止步于“某企业采用了 MCP”这一层的公告，没有一家披露过对接大型机的架构、指标或效果数字。
> 文中标注了来源的内容（MCP 协议本身的发布时间、早期采用者名单）为可查证的公开事实，已注明
> 出处；其余项目叙事、数字与踩坑细节均为合成，不对应任何真实客户。

## 它能说出该怎么做，但做不了

演示很成功：问它这笔异常交易该怎么处理，它条理清晰地说出了五步操作。

客户运维负责人问了一句：那它能自己做吗？

不能。那五步要在一台跑了二十年的大型机上执行，接口是固定长度报文，
权限走的是另一套体系，每一次操作都要留审计痕迹。

**“能给建议”和“能执行动作”之间隔着一层，而这一层在强监管的遗留系统里格外深。**

## 读完这章你能做什么

1. 说清“能给建议”和“能执行动作”的鸿沟出现在哪一层，以及为什么它在强监管系统里格外深。
2. 理解为什么“直接改造遗留系统”和“屏幕自动化”这两条看似省事的路径，
   在这类场景下经常**在评审阶段就出局**。
3. 掌握用协议封装遗留接口、三智能体分工、人在回路的架构模式，以及这套模式的判据。
4. 拆解一个笼统的“XX% 自治率”指标——哪部分真能自治、剩下为什么不能、护栏成本占多少工作量。

## 14.1 客户背景

本章的客户是一家教学合成的跨国零售银行（以下称“寰宇跨境银行”，虚构化名），业务覆盖
东亚、东南亚与中东三个区域，核心账务系统是一套运行了近三十年的大型机（COBOL + CICS +
IMS/DB2 组合），承担存贷款账务、交易清算与批量对账。CRM 层则是并购历史留下的碎片：
三个区域各自保留着并购时留下的独立 CRM 系统，其中最老的一套是二十年前部署的 Siebel
定制版，字段命名和业务口径三套系统各不相同，从未做过统一数据治理。

运营团队规模超过两千人的客服与后台专员，日常处理的工单集中在退款审批、账户资料变更、
异常交易复核三类，平均处理周期以小时计——不是因为业务逻辑本身复杂，而是因为专员要先
在 CRM 里查历史、再切到大型机终端里逐笔核对、最后在另一套审批系统里走流程，三套系统
之间没有任何自动化衔接，每一步切换都要专员手动搬运信息。

## 14.2 真实冲突

管理层最初的诉求很朴素：给客服和后台专员配一个能“看懂”客户历史、“理解”业务规则的
AI 助手，减少专员在三套系统之间来回切换查证的时间。第一版原型做出来之后，业务方给出
的评价是“建议给得很准，但没有用”——这句话点破了真实冲突所在。

LLM 读了 CRM 的工单历史和大型机批量报表的只读抽取，能准确判断“这笔退款该批”“这笔
异常交易该转人工复核”，判断力本身没有问题。问题出在执行侧：大型机没有任何现代化 API，
唯一的对外接口是 3270 终端仿真协议，专员要把 AI 给出的判断结果重新手动敲进终端完成
实际操作。这不是“AI 还不够聪明”的问题，是“AI 有脑无手”——建议生成的那几秒钟节省
下来了，重新敲键盘、核对终端回显字段这道工序一秒没少，反而多了一道“确认 AI 说得对
不对”的核对成本，综合下来专员的实际处理时长几乎没有变化。管理层期待的是“AI 接管
一部分操作”，工程团队交付的是“AI 生成一段专员仍要手动执行的建议”，这道鸿沟才是
项目真正要跨过去的坎，不是模型准确率。

## 14.3 被否决的方案

**方案一：直接改造遗留系统，把大型机核心账务能力重写或包一层现代化 REST API。**
这是技术团队最初的直觉方案——听起来一劳永逸，以后所有系统都能通过标准接口调用。
评审阶段就被否决：核心账务系统承载着实时清算和夜间批量对账，任何改造都要经过监管方
重新认证，这家银行内部历史上类似规模的核心系统改造项目是三年起步、预算千万美元级别，
还要接受停机窗口和业务连续性的额外审批。第 6 章讲过企业集成常见的几类遗留对接方式
各有取舍，“改造/替换遗留系统”通常是成本与风险最高的一档——本项目的时间预算是季度级，
直接排除。

**方案二：RPA 屏幕自动化，用机器人模拟专员在 3270 终端和 CRM 界面上的点击与键入操作。**
这条路线的吸引力在于不用碰大型机后端一行代码，原型两周就能出效果演示。小规模试点后
被否决：终端仿真界面的字段位置在不同业务模块之间并不统一，一次终端仿真客户端的版本
升级就让识别脚本大面积失效；专员日常处理的请求存在大量自然语言层面的变体（同一类
退款请求，客户描述方式五花八门），RPA 脚本靠固定坐标和固定文本匹配，根本无法覆盖这种
语义变体，勉强能跑的场景也需要为每一种业务变体单独写一条脚本，维护成本随场景数量
线性甚至超线性增长。团队内部对这条路线的评价是“看起来能跑，实际是个每周都要救火的
黑盒”。

**方案三：让 Agent 直接连大型机数据库做写操作，绕开业务逻辑层。** 有工程师提议既然
要效率，不如让 Agent 通过数据库直连的方式直接改数据，省掉中间所有接口层。这条路线在
架构评审阶段就被一票否决：银行的账务写操作必须经过业务规则校验（账户状态、额度、
反洗钱规则）和完整的审计留痕，数据库直连意味着彻底绕开这些校验层，一旦 Agent 判断有误，
后果是脏数据直接进了核心账务系统，没有任何拦截点。这条路线的风险等级和收益完全不成
比例，连原型验证的机会都没给。

三个方案的否决理由指向同一个结论：需要一层中间层，既不改造遗留系统本身，也不依赖
脆弱的界面模拟或绕开业务规则的直连，而是用标准化协议把遗留接口“包”起来，让 Agent
只能通过明确定义、带权限校验的工具调用它。

## 14.4 最终架构决策

MCP 协议本身有据可查的背景是：Anthropic 于 2024 年 11 月发布 MCP，官方公告点名
Block、Apollo 为早期采用者，Sourcegraph（Cody）随后在自己的技术博客确认接入了 MCP
支持[1]。这些公告都止步于“采用了 MCP”层面，没有一家披露过对接大型机这类遗留系统的
具体架构或效果数字——这也是本章要打教学合成案例标注的原因。但协议本身的采用轨迹说明
它不是一个昙花一现的实验性方案，这是团队选择用 MCP 而不是自造一套私有协议的前提判断。

判据只有一条：**Agent 对遗留系统的每一次操作，都必须经过一个有权限边界、可审计、
可降级的中间层，而不是直接触达遗留接口本身。**（对回六关：这条中间层判据是第 2 关定界
在智能体场景的形态——方案评审否决“直连”，就是定界关在否决；中间层交付的审计与降级能力，
是第 5 关上线的护栏原样搬过来。）据此做出四项决策：

1. **MCP Server 封装遗留接口**：在大型机与 CRM 之前架一层 MCP Server，把原本只能
   通过终端仿真或批量文件交换访问的能力，包装成三类工具——查询类（账户状态、交易
   历史）、写入类（退款提交、资料变更）、审批类（异常交易复核决议）。MCP 协议本身的
   工具设计原则（单一职责、清晰边界、鉴权桥接）第 9 章 §9.5 已经讲过，这里不重复，
   直接复用那套判断标准。
2. **三智能体分工**：发现智能体只持有查询类工具权限，负责从 CRM 和大型机只读抽取里
   拼出客户请求的完整上下文；操作智能体持有写入类工具权限，负责生成具体的操作提案
   （比如“这笔退款金额 X，建议批准”），但提案不直接落地执行；合规智能体审查操作
   智能体的提案，校验是否符合反洗钱、额度、账户状态等业务规则，决定“自动放行”还是
   “转人工审批”。三个角色权限互相隔离，任何一个角色被攻破或出错，影响范围都被限制
   在自己的权限边界内。
3. **LangGraph 编排与人在回路**：三个智能体用 LangGraph 编排成一张图，合规智能体
   判定需要人工介入的节点用 `interrupt()` 暂停执行，专员在前端确认后用
   `Command(resume=...)` 恢复——具体的图结构与人在回路机制不在这里展开，见 §9.6。
4. **鉴权桥接复用第 6 章的桥接模式**：MCP Server 对外（面向 Agent）用标准 API Key
   或 OAuth2，对内（面向大型机）转换为遗留系统认可的凭据形式，这一层认证转换的通用
   做法第 6 章已经讲过，不在本章重复展开，只强调一点本章特有的约束——大型机侧的
   权限模型是按柜员角色和机构代码划分的粗粒度权限，MCP Server 必须做一次精细化的
   二次映射，把“能登录终端”细化成“能调用哪个具体工具”，这一步是本项目独有的工作量，
   不是通用鉴权桥接能直接照搬解决的。

**这套架构不是万能药，有它明确不适用的边界。** 如果遗留系统连一个可稳定读取的批量
报表或数据库只读副本都不存在，发现智能体连拼上下文的原材料都拿不到，MCP 封装的收益
会大打折扣——这种情况下第一步该做的是先补一层数据同步管道，而不是急着上 MCP Server；
如果客户的业务规则本身就要求“任何写操作都必须先有人签字才能提交”（部分司法辖区的
反洗钱合规要求就是这样），那么“自动放行”这条分支根本不该存在，三智能体架构会退化成
“发现 + 人工全审批”，这时候引入操作智能体和合规智能体的自动判定环节反而增加了一层
不必要的复杂度，不如让发现智能体直接把结构化提案交给人工审批系统。判断这套架构是否
适用，先看两件事：遗留系统能不能提供稳定的只读数据源，以及业务规则是否留有“部分操作
可以自动放行”的空间——两个条件有一个不满足，就要回到更简单的架构，而不是硬套本章
的模式。

**关于“运营任务自治率”这个数字，必须先说清楚它从哪来、为什么不能当真实数据用。**
业内流传的一份方法论宣传材料声称“80% 运营任务自治率”，查不到任何出处，判定为疑似编造。
这个数字不能当行业实测数据引用；本章用到它时，只作为教学合成案例自设的目标值，
不代表任何真实客户的运营数据。比起直接照抄或者干脆弃用这个
数字，更有工程价值的做法是把它拆开：本项目里，“发现”环节（查询、拼上下文）和绝大多数
低风险、小额、历史命中率高的退款/资料变更操作，合规智能体可以直接自动放行，这部分
构成了“能自治”的主体；涉及大额、异常模式、客户投诉关联记录的操作，合规智能体的规则
会主动把它们路由到人工审批，这部分天然不能自治，不是模型能力不够，而是“关键决策必须
有人签字”这一条监管红线不能碰。护栏本身也是一块不小的工作量——合规智能体的规则维护、
审批节点的人机交互设计、异常路由的持续调优，这些工作在项目立项估算时经常被算进“模型
开发”的尾巴里一并低估，实际投入的工程量和三智能体的核心编排逻辑相当，不是一次性配置
就能长期免维护的附属品。把“80%”这个数字换成“哪些操作能自治、哪些操作按规则必须转
人工、护栏维护占多少长期工作量”这三个问题的答案，才是这类项目真正该向客户汇报的内容。

| **4** | 鉴权桥接对外 OAuth2、对内转遗留凭据 | 大型机权限按柜员角色和机构代码划分，是粗粒度的 | 直接复用第 6 章的通用桥接就完事 | **多出一张工具级二次授权映射表，且要长期维护** | **认知变过**：原以为是一次性配置，实际成为持续运维项（§14.6） |
| **5** | 不用 RPA 屏幕自动化 | 终端字段位置各模块不统一，客户端一次升级脚本就大面积失效；请求存在大量语义变体 | RPA（方案二，两周就能出演示） | 见效比 RPA 慢，项目中期被反复质疑 | 未变，**但这条否决被迫重讲了好几次**（§14.6） |

**第 5 行那个“后来”值得单独看，它是这张表里最不像技术问题的一行。**
方案在评审时被否决过一次，项目中期业务方仍然几次以“先用 RPA 顶一阵子”为由要求切回去。
**否决一个方案，不是在架构文档里写一次理由就完事了**——进度压力下，
被否决的方案会带着“快”这个卖点反复回来，而它当初被否决的理由那时候没人记得。

**第 3 行和第 4 行都写着“改过”，这是一张可信的决策日志该有的样子。**
一张所有行都写“未变”的表，多半是复盘时补记的，不是当时记的。

### 五层坐标

这一章的架构决策落到五层上是这个样子。**这张框每章都有，用法是对着看四则案例
各自厚在哪一层、空在哪一层**（五层的定义见上册第 4 章）：

| 层 | 这个案例里长什么样 |
|---|---|
| **本体** | **薄。** 只有三类工具签名隐含的对象（账户、交易、退款单），没有建对象-关系模型——遗留系统的数据模型就是既成事实，改不动 |
| **技能** | **空。** 三个智能体的做法写在提示词与图结构里，没有沉淀成可注册、可版本的技能 |
| **工具** | **主战场。** MCP Server 把终端仿真与批量文件交换封装成查询/写入/审批三类工具；粗粒度柜员权限到细粒度工具权限的二次映射是本项目独有的工作量 |
| **验收** | **薄。** Lab-03 实测了工具签名形态，业务侧的验收集本章没有展开 |
| **智能体** | **主战场。** 三智能体权限隔离（发现只读、操作出提案、合规判定），LangGraph 编排加 `interrupt()` 人在回路 |
| **治理**（横切） | **强。** 「每一次操作都必须经过有权限边界、可审计、可降级的中间层」这条判据就是治理判据；提案≠执行在这里是架构的骨架，不是补丁 |

**这一章是「工具＋智能体＋治理」三层撑起来的案例，本体和技能都薄。**
这不是设计缺陷，是这类项目的形状：**遗留系统的世界模型早就固化在那台大型机里了，
FDE 能动的是给它接一层手，不是重建它的世界。** 反过来说，
这也是这类项目复利低的原因——下一个客户的大型机，工具层要重写一遍。

## 14.6 踩过的坑

- **当时以为**把三个 MCP 工具接出来之后，大部分操作就能顺畅走完自动化流程，**实际**
  大型机的写入操作大多要排进夜间批处理窗口，白天提交的退款请求要等第二天批跑完才能
  确认最终状态，Agent 必须处理“提交成功但结果要等到明天”的异步语义，而不是像普通
  API 调用那样同步拿到最终结果。
- **当时以为**鉴权桥接只是把 OAuth2 令牌转换成大型机认的那种凭据格式，**实际**大型机
  侧的权限模型是按柜员角色和机构代码划分的粗粒度权限，根本没有“只能调用某个具体工具”
  这种细粒度概念，MCP Server 必须自己维护一层工具级别的二次授权映射表，这张表的维护
  和更新成为了一项持续性的运维工作，不是一次性配置。
- **当时以为**把合规节点做成一个 LangGraph `interrupt()` 就解决了人在回路，**实际**
  第一版把三个智能体的状态设计成共享一个大字典，合规智能体不小心读到了发现智能体
  尚未完全校验的中间结论就直接放行，说明子图之间的状态需要按输入输出边界隔离，不能
  图省事共享全部字段。
- **当时以为**RPA 方案在评审阶段被否决之后就不会再被提起，**实际**项目中期业务方
  几次以“先用 RPA 顶一阵子，别等 MCP Server 做完”为由要求临时切回 RPA，说明否决一个
  方案不能只在架构文档里写一次理由，还要在项目全程反复用同一份理由说服业务方，否则
  很容易在进度压力下被悄悄绕开护栏、临时上线一条脆弱路径。
- **当时以为**“运营任务自治率”这类整体性指标可以在项目早期先定一个数字再往上凑，
  **实际**这个数字一旦被写进项目汇报材料，后续任何一次拆解审批规则、扩大自动放行
  范围的讨论，都会被简化成“自治率要不要往上提”这种失去信息量的争论，不如从一开始
  就用“能自治的场景清单 + 转人工的规则清单 + 护栏维护工作量”这三份具体清单去沟通，
  不给一个笼统数字任何被误用的空间。

## 14.7 复盘与可迁移经验

**可迁移的经验**：用 MCP 统一封装遗留接口、避免为每个消费方重复写定制适配代码，这个
收益本身不限于银行场景，任何“业务逻辑深埋在没有现代 API 的遗留系统里”的行业都适用；
发现/操作/合规三角色分权 + 人在回路的架构模式，本质是给“LLM 有脑无手”这个通用困境
提供了一条工程解法，可以直接迁移到保险理赔、政务审批等同样存在强监管人工签字要求的
场景；把一个笼统的“XX% 自治率”拆解成“能自治的场景清单、转人工的规则清单、护栏
维护工作量”这三份具体材料去汇报，是应对任何来路不明或容易被滥用的整体性指标的通用
工程纪律，不止适用于本章这个数字。

**不可直接迁移的部分**：大型机侧粗粒度权限模型到工具级权限的映射规则，是这家银行
遗留系统的具体产物，换一家银行、换一套核心账务系统基本要重新梳理；三个 MCP 工具
（查询/写入/审批）的具体粒度划分是这个业务域（退款、资料变更、异常复核）专属的，
换成保险理赔场景，工具边界需要按理赔流程重新设计；“80%”这个具体数字更不能迁移——
它连本项目自己的真实运营数据都不是，只是教学案例设定的目标值，任何试图把这个数字
当作行业基准套用到别的项目上的做法，都是在重复源材料本身犯过的错误。

下一章把“人在回路的信任问题”推向另一个极端——完全物理隔离的空气隙环境里，连人在
回路的确认渠道本身都要重新设计，这是下一章要处理的问题。

### 这个案例留下了哪一类结果

**接管。**

可迁移的那条经验——用 MCP 统一封装遗留接口、不为每个消费方重复写适配代码——
它的价值不在于少写了代码，在于**客户 IT 以后要维护的是一个封装层，而不是 N 套彼此不同的适配**。
维护得动，才谈得上接管。

而不可迁移的那部分也说明了同一件事：大型机侧粗粒度权限到工具级权限的映射规则，
**是这家银行自己的制度**。它必须留在现场层，也只有客户自己维护得了——
这正是上册第 5 章说的“权限属于业务模型”在一个真实项目里的样子。

## 本章清单

- [ ] 遇到“模型能说不能做”的场景，先找那层缺失的执行接口，**不要先想着换模型**
- [ ] 评审阶段就把“直接改造”和“屏幕自动化”两条路的成本与脆弱性摆出来，
      不要等大规模试点才发现
- [ ] 每一次操作都要经过一个有权限边界、可审计、可降级的中间层
- [ ] 遇到来路不明的整体性指标，既不直接引用也不简单弃用，**拆成场景清单和护栏工作量**——拆出来的三份清单就是第 4 关验收集的雏形
- [ ] 把护栏本身的工作量算进报价。它通常比核心逻辑更费时间

## 自检问题

1. 为什么“AI 能准确判断该不该批这笔退款”这件事本身，不足以说明这个项目已经成功？
   参考答案要点：判断力（脑）和执行力（手）是两个独立的能力维度，遗留系统没有安全
   的执行接口时，再准确的判断也要靠人工重新敲键盘落地，专员的实际处理时长不会因为
   “建议更准”而明显缩短。

2. “RPA 界面一变就崩”和“直接改造遗留系统成本风险不可接受”，这两个被否决的方案，
   分别对应哪一类工程风险？能不能对调结论——比如改用改造方案而不是 MCP？
   参考答案要点：RPA 对应的是脆弱性风险（界面/流程微小变化就大面积失效），改造方案
   对应的是成本与业务连续性风险（多年周期、监管重新认证）；两者风险类型不同，不能
   简单对调结论，但如果客户遗留系统的改造成本和风险显著低于本章场景（比如系统更新、
   监管约束更松），改造方案未必总是被否决的一档，需要按具体项目重新评估。

3. 三智能体（发现/操作/合规）分权设计，如果把三者的权限合并成一个“全能 Agent”，
   会带来什么具体风险？
   参考答案要点：权限不隔离意味着任何一次判断失误或提示注入攻击都可能直接触达写入
   和审批两类高权限工具，分权设计的价值在于把风险面限制在单一角色的权限边界内，
   即使某个环节被攻破或出错，影响范围也可控。

4. 本章为什么不能直接引用“80% 运营任务自治率”这个数字，即使加上“教学合成案例”的
   标注也不行？
   参考答案要点：这个数字经多轮检索零来源，源头本身疑似编造，即便标注为合成案例的
   设定值也不应该暗示它曾出现在任何真实的官方材料或客户数据里；正确的处理方式是把
   这类数字拆解成可验证的场景清单和护栏工作量，而不是继续沿用一个无法验证真伪的
   整体性数字。

5. 为什么“否决一个方案”这件事需要在项目全程反复重申理由，而不是在架构评审文档里
   写一次就够？
   参考答案要点：业务方对成本、风险的敏感度会随进度压力波动，评审阶段的否决理由
   如果不在后续沟通中反复被提起，很容易在赶工期时被“先用 XX 顶一下”的临时决定
   悄悄绕开，护栏被绕开往往不是因为架构设计有漏洞，而是因为沟通纪律没跟上。

6. §14.4 提到这套三智能体架构“不是万能药”，具体在什么条件下不适用，该退回到什么
   更简单的方案？
   参考答案要点：遗留系统没有稳定只读数据源时，发现智能体拿不到拼上下文的原材料，
   应先补数据同步管道而不是急着上 MCP Server；业务规则要求所有写操作必须人工签字时，
   “自动放行”分支不该存在，架构应退化为“发现 + 人工全审批”，而不是为了套用本章模式
   强行保留一层不必要的自动判定环节；反过来，如果遗留系统已经具备稳定的只读接口、且
业务规则明确划出了一块“低风险可自动放行”的空间，本章这套架构才真正有用武之地，
否则只是在给一个本来可以更简单解决的问题，套上一层不必要的编排复杂度。
