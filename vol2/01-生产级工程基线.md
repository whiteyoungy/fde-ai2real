# 第 1 章 · 生产级工程基线

> **一句话结论**：算法一样、功能一样的两份代码，一份能在别人的机器上跑起来，
> 一份不能。差别不在聪明，在四条硬线。

## 在自己电脑上跑得好好的

交付第一天，把脚本拷到客户的服务器上，报错。

路径是硬编码的，客户机器上没有那个目录。改完路径，再报错——某个包的版本不对。
换版本，第三个错：客户的内网装不了这个包，私有源里没有。

折腾到下午，终于跑起来了，结果和本地不一样。查了两个小时，
发现某一步静默吞掉了一个异常，本地数据恰好不触发。

**这四个问题都不是算法问题，全是工程习惯问题。** 这一章讲的就是这些习惯。

> **在骨架里的位置**：**接管。** 可复现构建、依赖锁定、离线安装包——这一章的每一样，回答的都是同一个问题：**你不在的时候，客户能不能自己把这套东西重新建出来。** 建不出来，就没有接管，只有一台没人敢碰的机器。

## 读完这章你能做什么

1. 看一眼陌生的 Python 代码，指出它是笔记本习惯还是生产习惯，并说清要改哪几处才能上线。
2. 在类型标注、结构化日志、显式错误处理、可测试性四条线上，给出自己代码的最小合规版本。
3. 进客户现场第一天，用五个 SQL 模板把一张陌生表的数据质量摸清楚，
   而不是干等业务方口头保证“数据挺干净的”。
4. 遇到装不上包时，判断问题出在版本冲突、网络隔离还是私有源配置，选对应对方式而不是逐个瞎试。
5. 在“成果全归甲方”的合同下，把底座和现场层拆成两个仓库、两件构建产物，
   让撤场时“哪些是我们的”这个问题有据可查，而不是靠口头解释。

## 1.0 可复现先于聪明

这一章排在第一，不是因为工程基线比模型重要，是因为它先发生。

**客户环境从来不是你的电脑。** 这句话是整册书所有工程判断的起点：
另一台机器、另一个工程师、另一个客户机房、另一套芯片和操作系统——
你的东西要能在这些地方重新被构建出来，然后才轮得到讨论它聪不聪明。

一条可以当纪律用的排序：

> **能不能被别人重新构建出来，是比“效果好不好”更靠前的问题。
> 重建不出来的效果，不是效果，是一次演示。**

这条排序在后面几章反复出现，只是换了说法：第 8 章的离线部署包（换一台断网机器能不能起来）、
第 12 章的信创适配（换一套芯片和数据库能不能起来）、第 9 章的验收集
（换一个模型还知不知道什么算对）。**它们问的是同一个问题。**

这一章给的四样东西各自守着这条排序的一个方向：

| 节 | 守的是 | 不守会怎样 |
|---|---|---|
| §1.1、§1.2 | 代码本身在别人手上跑得起来、看得懂、改得动 | 交付物变成只有原作者能维护的东西（上册 §3.1 英雄主义陷阱） |
| §1.3 | 出问题时能定位到哪一层 | 每次故障都要原班人马到场 |
| §1.4 | 在没有网的机器上装得起来 | 到了现场才发现依赖装不上，工期按周计地丢 |
| §1.5 | **哪些是底座、哪些是这家客户的，分得清** | 每个客户一个分支——上册 §3.4 定制化债务陷阱的工程形态 |

**§1.5 那一行值得单独说一句。** 上册把定制化债务讲成一个组织和商业问题；
它在工程上的形态就是一句话：**底座和现场层混在同一个仓库、同一个构建物里。**
混了之后，“这部分是我们的既有产品”这句话就再也拿不出证据，
撤场评审会上说不清，换下一个客户时也抽不出来。**这条边界是这一章唯一一条
画错了以后要用年来还的。**

## 1.1 两种 Python 的对照

同一个功能：从交易流水里按门店汇总当日营业额。两份代码功能完全一样，风格是两种工程文化。

**notebook 风格**（数据科学家探索阶段的典型写法）：

```python
import pandas as pd

df = pd.read_csv("/Users/wang/Desktop/sales_0728.csv")
df["amount"] = df["amount"].astype(float)
daily = df.groupby("store_id")["amount"].sum()
daily.to_csv("/Users/wang/Desktop/daily_result.csv")
print(daily)
```

**生产风格**（FDE 交给客户环境跑的写法，示意性骨架，未经实测验证，不要直接用于生产）：

```python
import logging
from pathlib import Path

import pandas as pd

logger = logging.getLogger(__name__)


class MalformedTransactionError(Exception):
    """交易流水中存在无法解析的金额字段。"""


def compute_daily_store_revenue(transactions: pd.DataFrame) -> pd.Series:
    """按门店汇总当日营业额。

    Args:
        transactions: 至少包含 store_id、amount 两列的交易流水。

    Returns:
        以 store_id 为索引的当日营业额汇总。

    Raises:
        MalformedTransactionError: amount 列存在无法转换为浮点数的值。
    """
    working = transactions.copy()
    numeric_amount = pd.to_numeric(working["amount"], errors="coerce")
    bad_rows = working[numeric_amount.isna()]
    if not bad_rows.empty:
        logger.error(
            "transaction_amount_parse_failed",
            extra={"bad_row_count": len(bad_rows), "sample_ids": bad_rows.index[:5].tolist()},
        )
        raise MalformedTransactionError(f"{len(bad_rows)} 行 amount 字段无法解析")
    working["amount"] = numeric_amount

    negative = working[working["amount"] < 0]
    if not negative.empty:
        logger.warning(
            "negative_amount_detected",
            extra={"row_count": len(negative), "store_ids": negative["store_id"].unique().tolist()},
        )

    return working.groupby("store_id")["amount"].sum()


def load_and_export(input_path: Path, output_path: Path) -> None:
    """生产入口：读取输入、计算、落盘，与纯计算逻辑分离以便单测。"""
    transactions = pd.read_csv(input_path)
    result = compute_daily_store_revenue(transactions)
    result.to_csv(output_path)
    logger.info(
        "daily_revenue_exported",
        extra={"store_count": len(result), "output_path": str(output_path)},
    )
```

逐点对照，六处差异：

1. **路径硬编码 → 参数化。** notebook 版本把本地桌面路径写死在代码里，换一台机器、换一个客户环境就跑不通。生产版本用 `Path` 参数注入，路径由调用方（配置文件、CLI 参数、编排系统）决定。
2. **无类型标注 → 完整类型标注。** notebook 版本里 `df`、`daily` 是什么类型全靠猜。生产版本函数签名写清楚输入输出类型，IDE 和类型检查器能在调用处直接报错，而不是等到运行时才炸。
3. **`print()` → 结构化日志。** notebook 版本把结果糊在标准输出里，出问题只能重新跑一遍去肉眼核对。生产版本用 `logger.info/warning/error` 并带 `extra` 字段，日志系统能按 `store_count`、`bad_row_count` 这类字段直接检索和告警。（一个会当场翻车的细节：stdlib logging 的默认 formatter **不会**输出 `extra` 字段，要配 JSON formatter——如 `python-json-logger`——字段才会真的落进日志；只加 `extra` 不换 formatter，检索和告警都落空。）
4. **隐式类型转换失败 → 显式捕获并分类。** `df["amount"].astype(float)` 遇到脏数据，要么直接抛出未经处理的异常炸到用户面前，要么在某些调用路径下悄悄产生 `NaN` 混进后续计算。生产版本先用 `pd.to_numeric(errors="coerce")` 定位到具体哪些行有问题、记录下来，再转换成一个语义清晰的自定义异常抛给上层。调用方看错误类型就知道是数据问题而不是代码 bug。
5. **负数金额没人管 → 显式标记但不阻断。** 负数可能是退款也可能是脏数据，notebook 版本直接汇总进总营业额，退款和正常消费混在一起没人发现。生产版本记警告日志留痕，把判断权交给下游而不是替业务方悄悄做了决定。
6. **I/O 和计算耦合 → 拆分为两层。** notebook 版本读文件、算数、写文件挤在一段脚本里。生产版本把纯计算 `compute_daily_store_revenue` 单独拎出来，输入输出都是内存对象。测试时直接喂一个构造好的 `DataFrame` 就能跑，不需要真的往磁盘写一个 CSV 文件才能验证逻辑对不对。

这六条不是风格洁癖。每一条背后都对应着一次客户现场真实会发生的事故：

- 机器换了
- 字段类型变了
- 脏数据来了
- 退款订单出现了
- 需要在 CI 里跑测试却没法造数据

下一节把其中最关键的四条抽出来，单独给出各自的最小合规标准。

## 1.2 四条硬线

四条线各自独立，互不替代——有类型标注不代表有错误处理，能跑单测不代表日志可检索。每条给一个脱离业务上下文的最小合规示例，方便对照自己的代码逐条自检。

**类型标注。** 合规标准不是“有没有写 `: str`”，而是签名里是否还残留裸露的 `Any`（反序列化 JSON 的最外层等确有必要之处除外），以及能否用 `mypy --strict` 或 `pyright` 跑过而不报错。

```python
def parse_amount(raw: str) -> float | None:
    """将字符串金额解析为 float，无法解析时返回 None 而不是抛出未声明的异常。"""
    try:
        return float(raw)
    except ValueError:
        return None
```

**结构化日志。** 合规标准不是“有没有调用 `logging` 模块”，而是日志能不能被当结构化数据检索。把变量拼进一句人话里（`logger.info(f"处理了订单 {order_id}")`）是反例。`order_id` 变成了字符串的一部分，日志系统只能用正则去猜，没法按字段精确过滤或聚合。

```python
import logging

logger = logging.getLogger(__name__)

logger.info(
    "order_processed",
    extra={"order_id": order_id, "amount": amount, "latency_ms": latency_ms},
)
```

**显式错误处理。** 合规标准是每一个 `except` 分支要么记日志、要么重新抛出、要么两者都做，不允许空 `pass`。`except Exception: pass` 或裸 `except: pass` 在实验代码里很常见，反正一次失败不影响整体探索。但在生产代码里，吞掉的异常等于把故障原因永久抹掉。下次同样的问题出现时，排查者要从零开始。

```python
class UpstreamTimeoutError(Exception):
    """调用客户内部系统超时。"""


try:
    response = call_customer_api(payload, timeout=5)
except requests.exceptions.Timeout as exc:
    raise UpstreamTimeoutError(f"调用 {ENDPOINT} 超过 5 秒无响应") from exc
except requests.exceptions.ConnectionError:
    logger.error("customer_api_unreachable", extra={"endpoint": ENDPOINT})
    raise
```

**可测试性。** 合规标准是：单元测试能不能在不改动生产代码、不连接任何外部资源（数据库、API、文件系统）的前提下，跑通对应函数的核心分支。下面的例子把风险阈值通过依赖注入传入，而不是在函数体里直接读全局配置或调用远程配置中心。测试时传入 `lambda: 0.8` 就能跑，不需要真的连一次配置中心。

```python
from typing import Callable


class RiskScorer:
    def __init__(self, threshold_provider: Callable[[], float]) -> None:
        self._threshold_provider = threshold_provider

    def is_high_risk(self, score: float) -> bool:
        return score >= self._threshold_provider()
```

这四条示例都刻意脱离了具体业务场景，是为了说明它们是可以独立检验的通用标准，不依赖你在做哪个客户的哪个项目。真正棘手的不是记住这四条，是在客户现场第一天，面对一张从没见过的表，判断数据本身到不到底能不能用。这是下一节的内容。

## 1.3 SQL 诊断技法

进客户现场第一天，不要先去读数据字典文档。文档写的是“应该”是什么样，下面五个模板告诉你数据“实际”是什么样。两者的落差就是这个项目后续真正要处理的工作量。

以下 SQL 用通用 ANSI 语法写，示意性骨架，未经实测验证。具体到某个数据库（Postgres/MySQL/Snowflake）时，窗口函数与日期函数写法可能需要微调。

**模板一：空值率。** 对每个关键字段算一次，别等业务方口头告诉你“这个字段很少为空”。

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(*) - COUNT(customer_id) AS null_customer_id,
    ROUND(100.0 * (COUNT(*) - COUNT(customer_id)) / NULLIF(COUNT(*), 0), 2) AS null_customer_id_pct,
    COUNT(*) - COUNT(email) AS null_email,
    ROUND(100.0 * (COUNT(*) - COUNT(email)) / NULLIF(COUNT(*), 0), 2) AS null_email_pct
FROM customers;
```

**模板二：重复率。** 先看总体重复率有没有超出预期，再钻到具体重复的主键上。

```sql
-- 总体重复率
SELECT
    COUNT(*) AS total_rows,
    COUNT(DISTINCT order_id) AS distinct_keys,
    ROUND(100.0 * (COUNT(*) - COUNT(DISTINCT order_id)) / NULLIF(COUNT(*), 0), 2) AS duplicate_rate_pct
FROM orders;

-- 定位具体重复的主键
SELECT order_id, COUNT(*) AS dup_count
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1
ORDER BY dup_count DESC
LIMIT 100;
```

**模板三：分布偏移。** 按天摊平某个分类字段的占比，跟历史基线比对，能看出上游系统变更或字段口径漂移的信号。

```sql
SELECT
    order_date,
    payment_method,
    COUNT(*) AS cnt,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (PARTITION BY order_date), 2) AS pct_of_day
FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY order_date, payment_method
ORDER BY order_date, pct_of_day DESC;
```

把结果画成折线图。如果某个类别的占比在某一天突然从 5% 跳到 40%，大概率不是业务真实变化，是上游系统改了字段编码或者接入了一条新数据源。

**模板四：外键孤儿。** 子表里存在、父表里查不到的记录，几乎每个“数据同步”或“分批迁移”场景都会有。

```sql
-- 孤儿记录明细
SELECT o.order_id, o.customer_id
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE o.customer_id IS NOT NULL
  AND c.customer_id IS NULL
LIMIT 100;

-- 孤儿总量
SELECT COUNT(*) AS orphan_count
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE o.customer_id IS NOT NULL AND c.customer_id IS NULL;
```

**模板五：时间戳异常。** 三类最常见的异常：时序矛盾、未来时间戳、哨兵值时间戳。

```sql
SELECT order_id, created_at, updated_at
FROM orders
WHERE updated_at < created_at
   OR created_at > CURRENT_TIMESTAMP
   OR created_at < TIMESTAMP '1990-01-01'
LIMIT 100;
```

- `updated_at < created_at`：通常是 ETL 批次乱序写入或时区转换错误。
- `created_at` 晚于当前时间：通常是时区没转换，或者写入时用了错误的默认值。
- 早于 1990 年这类明显的哨兵值：通常是某个字段的默认值（比如数据库的 `0000-00-00` 或 Unix epoch 零点）没有被正确替换成真实业务时间。

这五个模板不是终点，是起点。具体到哪个空值率、哪个重复率算“有问题”，取决于字段的业务含义（一个可选字段空值率 60% 很正常，一个主键字段空值率 0.1% 就该警惕）。这个判断标准要靠跟业务方对话来确认。SQL 只负责把事实摆出来，不负责替你下结论。

## 1.4 客户环境的依赖地狱

在自己的笔记本上 `pip install` 从不报错，是因为本地环境是逐渐“喂养”出来的。缺什么装什么，装了多少个版本冲突的库自己都记不清。客户环境不会给你这个特权：内网可能连不上外网、基础镜像可能锁死在一个旧的 Python 版本、包管理只认公司私有源。

这一节是上册第 15 章（物理隔离部署）的前置知识。那一章处理的是完全断网的极端情况，这里先把三种更常见的“半隔离”场景讲清楚。

**锁版本。** `requirements.txt` 配合 `pip freeze` 只锁定顶层依赖的版本号，锁不住依赖的依赖。生产项目应该用带 lock 文件的工具（`poetry.lock`、`uv.lock`），把整棵依赖树的精确版本和哈希都固定下来。同一份 lock 文件在任何机器上装出来的环境逐字节一致。

不锁版本会踩到的坑不是假设性的。MCP（Model Context Protocol）Python SDK 包名 `mcp` 在 2.0.0 版本发生了破坏性重写：`FastMCP` 类被重命名为 `MCPServer`，导入路径从 `mcp.server.fastmcp` 变成 `mcp.server.mcpserver`。而 `pip install mcp`（不加版本号）现在默认装的就是 2.x。官方 README 原文直接给出告警：“Since `pip install mcp` now installs 2.x, keep a `<2` upper bound on your requirement (for example `mcp>=1.28,<2`) until you've migrated.”[1] 照抄一段针对 v1 `FastMCP` 写的教程代码到没锁版本的环境里，会直接报 `ModuleNotFoundError`。

**离线安装。** 客户网络只让走白名单代理、连不上 PyPI 时，标准做法是在一台能联网的机器上把整套依赖打包成 wheelhouse，再把这个目录搬进隔离环境。官方文档给出的组合是 `--platform`、`--python-version`、`--implementation`、`--abi` 四个参数配合 `--only-binary=:all:`，用来精确指定目标机器的平台标签，而不是用当前机器的标签[2]：

```bash
# 在联网机器上打包（假设目标环境是 Linux x86_64、Python 3.11、CPython）
pip download -d ./wheelhouse -r requirements.txt \
    --platform manylinux2014_x86_64 \
    --python-version 3.11 \
    --implementation cp \
    --abi cp311 \
    --only-binary=:all:

# 把 wheelhouse 目录整体拷贝到隔离环境后
pip install --no-index --find-links=./wheelhouse -r requirements.txt
```

`--only-binary=:all:` 是必需项，不加的话 `pip download` 在指定了 `--platform` 等跨平台参数时会拒绝执行[2]。踩坑高发点是平台标签没对准。打包机器是 macOS、目标是客户的 Linux 服务器，四个参数漏填一个就可能下载到不兼容的 wheel。隔离环境里连报错都报不明白，只会显示“找不到匹配的分发版本”。

**Python 版本冲突。** 不少监管行业的客户环境用的是审批流程很长的“黄金镜像”，Python 版本可能锁在 3.8 甚至更早。而现在主流 AI 技术栈的最低要求已经普遍上移，以几个核实过的版本约束为例：

- MCP Python SDK 2.0.0 要求 `requires-python >=3.10`[1]
- `qdrant-client` 在 1.16.2 版本移除了 Python 3.9 支持、现要求 `>=3.10`[3]
- LangGraph v1 迁移指南原文写得很直接：“All LangChain packages now require Python 3.10 or higher.”[4]

如果客户的基础镜像还在 3.8/3.9，这些库根本装不上。这不是技术问题，是需要走 IT 审批流程升级基础镜像的组织流程问题。应该在项目立项阶段就问清楚客户的基础镜像版本，而不是等到写代码时第一次 `pip install` 报错才发现。

**公司私有源配置。** 大部分企业客户不允许直连 PyPI，要求所有安装走内部 Nexus/Artifactory 镜像。全局配置文件 `pip.conf`（Linux/macOS）或 `pip.ini`（Windows）里最常用的是 `index-url` 指定默认源、`extra-index-url` 追加备用源、自签证书环境下用 `trusted-host` 跳过证书校验[5]：

```ini
[global]
index-url = <https://nexus.internal.company.com/repository/pypi/simple>
trusted-host = nexus.internal.company.com
```

同样的配置也可以走环境变量（`PIP_INDEX_URL`、`PIP_EXTRA_INDEX_URL`、`PIP_TRUSTED_HOST`），在 Docker 构建阶段传入环境变量往往比往镜像里塞一份 `pip.conf` 更适合做多环境复用[5]。

这一节到此解决的是“能连内网但只让走白名单”和“能装但版本对不上”这两类问题。如果客户环境是完全物理隔离、连白名单代理都没有，wheelhouse 打包方式会被扩展成一整套离线交付包的核心机制。这正是上册第 15 章要处理的场景。

## 1.5 底座与现场层的物理边界

上册第 14 章讲过一条条款：**本项目产生的全部源代码、文档、定制开发成果及相关知识产权，均归甲方所有。**
应对办法是把代码分成两层——底座是项目开始之前就存在的通用组件，现场层是项目期内为这个客户写的东西。
那一章给的是归属的划法，这一节讲工程上怎么让这条线**查得清**。

这条线不是在合同里画的，是在仓库和构建里画的。撤场评审会上，
你说“这部分是我们的既有产品”，对方问“怎么证明”，能拿出来的只有四样东西：

**一、两个仓库，依赖方向单向。** 现场层按版本号依赖底座的发布件，底座不许反过来引用现场层的任何东西。
自查的办法很土但有效：在底座仓库里搜客户名、客户的库表名、客户的接口地址，命中数必须是 0。
搜出来一条，这条边界就已经破了。

**二、构建产物是两件，不是一件。** 底座产出带版本号的依赖包或镜像层，现场层产出随项目交付的源码包。
如果一条流水线最后吐出一个 tar，里面什么都有，那么“哪些是底座”就只剩口头解释。
**撤场评审会上，口头解释的证明力是零。**

**三、版本戳要能证明“先于项目”。** 底座包的版本号要能对应到一个早于合同签署日的提交或 tag。
这一条最容易被忽略，也最要命：如果底座是在项目做到一半时从现场层里“抽”出来的，
git 历史会诚实地把这件事记下来。想让底座成立，就得在第一个项目之前先有底座。

**四、许可声明随包走。** 底座包里带 LICENSE/NOTICE，写清楚授权给谁、授权范围、能不能转授。
交付清单里它是一行“第三方/乙方组件”，不是一行“本项目源码”。

反过来说，有一件事不用做：不用为了这条边界去搞两套技术栈。
底座和现场层可以用同一套语言、同一个框架、同一份工程基线，只是不放在同一个仓库、不出同一个构建物。

还有一个很实在的自查点：**别把客户名写进底座。** 常见的泄露位置是包名、模块名、配置默认值、
测试夹具、日志前缀、镜像 tag。这几处一旦带上客户名，撤场时是把柄，
换下一个客户时又得改一遍——而且下一个客户看到前一家的名字，观感不会好。

这件事和第 8 章的离线部署包不冲突。离线包可以打成一个压缩包搬进现场，
但 §8.2 那份物料清单里，底座物料和现场层物料要分成两组列，各自带各自的版本号和校验值。
清单是给客户看的，也是给三年后来接手的人看的。

## 本章清单

- [ ] 全文搜一遍硬编码路径，全部换成配置或环境变量
- [ ] 函数签名里不许有裸露的 `Any`，跑一遍 `mypy --strict`
- [ ] 日志改成结构化字段，能被检索。**不要拼成一句人话**
- [ ] 每个 `except` 分支要么记日志要么重新抛出，**不许出现空 `pass`**
- [ ] 核心分支要能在不连任何外部资源的前提下跑单测
- [ ] 进现场第一天就跑五个 SQL：空值率、重复率、分布偏移、外键孤儿、时间戳异常
- [ ] 跑出来的异常率拿去和业务方对一遍。**SQL 只摆事实，下结论要靠对话**
- [ ] 锁版本锁到整棵依赖树（生成 lock 文件），只锁顶层锁不住依赖的依赖
- [ ] 离线安装前，精确匹配目标机器的平台标签
- [ ] **立项阶段**就问清客户基础镜像的 Python 版本。等写代码时才发现就晚了
- [ ] 底座和现场层放在两个仓库，依赖方向单向。**在底座仓里搜客户名，命中数必须是 0**
- [ ] 底座包的版本号能对应到一个早于合同签署日的提交。抽不出这个版本戳，这一层就不成立

## 自检问题

1. 一位同事的函数签名是 `def process(data: dict) -> dict`，他说“我写了类型标注，符合要求了”，这个说法站不站得住？
   **参考答案要点**：站不住。`dict` 没有指定键值类型，本质上和没标注一样宽松，`mypy --strict` 其实会报 `type-arg`（strict 档包含 disallow-any-generics，裸 `dict` 过不去），但只开默认配置的 mypy 不会拦，调用方依然不知道该传什么结构。应该用 `TypedDict` 或具体的 `dict[str, float]` 这类精确标注。“有没有写类型标注”和“类型标注是否提供了真实信息量”是两回事。

2. 一段代码里 `except Exception as e: logger.error(str(e))` 后没有 `raise`，也没有返回任何错误标识，这符合本章“显式错误处理”的标准吗？
   **参考答案要点**：不符合。记了日志但吞掉了异常，调用方拿到的是一个看起来成功但实际失败的返回值。下游会拿着错误结果继续跑而不自知，这比完全不处理更危险。显式错误处理要求调用方能感知到失败，记日志只是留痕，不能替代向上传播错误状态。

3. 你在客户的一张订单表上跑了空值率模板，`customer_id` 空值率 8%，业务方说“这个正常，游客下单不需要登录”，这个解释能不能直接采信？
   **参考答案要点**：不能直接采信，但也不能直接否定。需要进一步验证这 8% 是否确实集中在“游客下单”这一业务场景（比如交叉一个 `order_type` 或 `is_guest` 字段核实），而不是业务方凭印象给出的口头解释。SQL 摆出的是“8% 为空”这个事实。具体原因是否成立需要用另一条查询验证，不能止步于一句听起来合理的解释。

4. 外键孤儿模板跑出来发现 `orders` 表里有 200 条记录的 `customer_id` 在 `customers` 表里找不到，这一定说明数据同步出了故障吗？
   **参考答案要点**：不一定。也可能是 `customers` 表本身做了软删除或者定期清理历史数据，导致老订单指向的客户记录被合法移除。判断是不是故障，要看这 200 条记录的时间分布（是否集中在某次同步窗口）和业务规则（是否存在客户数据保留期限）。不能看到孤儿记录就默认是故障。

5. 客户 IT 说“我们内网可以走白名单代理访问 PyPI”，你据此判断不需要做离线安装准备，这个判断有什么风险？
   **参考答案要点**：白名单代理通常只放行 `pypi.org` 域名本身。很多包的依赖会从 GitHub Releases、专属 CDN 甚至第三方镜像站拉取二进制或数据文件，这些域名不一定在白名单里。应该先用完整依赖列表实际跑一次安装验证，而不是仅凭“能走代理”这句话就假设全部依赖都装得上。

6. 一份 `requirements.txt` 锁了顶层包的版本号（如 `mcp==1.29.0`），团队认为这样就实现了“锁版本”，这个判断哪里不完整？
   **参考答案要点**：`requirements.txt` 通常不会连带锁定所有传递依赖的精确版本（除非是用 `pip freeze` 完整导出且从未增删包）。换一台机器重新安装时，未被显式锁定的间接依赖可能解析到不同版本，导致“同一份 requirements.txt 装出不同环境”。真正的锁版本应该用带哈希校验的 lock 文件（如 `poetry.lock`/`uv.lock`），把整棵依赖树都固定住。

7. 一段生产代码的核心业务函数里直接调用了 `requests.get()` 访问客户内部系统，你被要求给它补单元测试，这暴露了本章哪条硬线的缺失？
   **参考答案要点**：可测试性。函数把网络调用硬编码在内部，测试时要么真的连一次客户系统（不稳定、不可重复、可能有副作用），要么无从下手。应该把 HTTP 客户端作为参数注入（依赖注入），测试时传入一个 mock 对象，让核心逻辑可以脱离真实网络环境验证。

8. 团队在项目做到第四个月时，把项目里写得比较通用的一批检索代码抽出来，打成一个带版本号的内部包，对客户说“这部分是我们的底座”。撤场评审时这个说法站不站得住？
   **参考答案要点**：站不住。上册第 14 章的判据是产生时间，不是抽象程度。这批代码第一次被写出来是在项目期内，git 历史会如实记录，“本项目产生的成果”涵盖得到它。打成包、加版本号，改变的是交付形态，不是产生时间。底座要成立，必须在这个项目开始之前就已经存在。那第一份底座从哪来？只能来自合同之外——自有资金养的内部项目、没有“成果全归甲方”条款的项目、或者交付间隙的自留时间；正因为没有捷径，这件事才必须从第一个项目结束后就立刻开始攒。
