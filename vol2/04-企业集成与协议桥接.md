# 第 4 章 · 企业集成与协议桥接

> **一句话结论**：从“模型吐出一个结果”到“这个结果能安全进出客户那套没人愿意碰的遗留系统”，
> 中间隔着一整层没人愿意报价、但出了事第一个背锅的工程。

## 同一笔款，扣了两次

上线第三周，客户财务发现有一笔付款被扣了两次。

查日志：第一次调用超时了，客户端按重试策略又发了一次。而对方系统那边，
第一次其实成功了，只是响应回来得慢。

这不是罕见故障。**在任何一个跨系统调用里，“超时”都不等于“没执行”**，
而重试是所有集成层的默认行为。少了一个幂等键，重试就从容错机制变成了二次事故源。

这一层工程不性感：没有模型精度可以拿出来讲故事，出问题时的表现是“偶发超时”
“重复扣款”“证书过期报警”。客户听不懂堆栈跟踪，只看到“AI 系统又崩了”。

**把这些机制一次做对，比等出了生产事故再回头补便宜得多。**

## 同一件事，做了二十一次

上面那件事有个 2026 年的版本，代价换了一种计量方式。

一家公司的财务总监——**不是工程师**——用 AI 编程工具，两天把一套 SaaS 送上了生产环境。
后来工程师去翻账单，发现某一天的曲线直冲云霄：**光那一天的 AI 花费，
就超过了整个服务器机房跑一整月** [2]。

根子是一个本该只跑一次的批处理，对着同一个租户跑了二十一次。
每一次调用大模型都成功了，全是 200，**所以每一次都照常计费** [2]。
卡住的是最后一步：往数据库写的时候，代码引用了一个本该建好、实际还没建的字段，
数据库抛出“列不存在”，整个任务算失败——于是重试。
下一轮同样跑完、同样计费、同样在最后一步倒下。

打个比方：你吃完一整桌菜，账也结了，临出门摔一跤失了忆，
醒来发现自己又坐回座位上，从头把同一桌菜重新点一遍。连着二十一次。

原文把成因拆成三个相乘的因子：**确定性失败 × 自动重试 × 非幂等** [2]。
前两个单独都不致命——确定性失败第一次就会暴露，自动重试是所有集成层的默认行为。
**是第三个把前两个连成了一台碎钞机。**

### 这不是新病，是老病换了计价方式

古法编程时代有它的对应物：一个没人注意的死循环，一个忘了关的数据库连接。
形状是同一个——**某个没人盯着的地方在无声地重复。** 这类缺陷从来不靠功能测试发现，
因为功能是对的：死循环里的每一轮计算都算对了，泄漏出去的每一条连接都连上了，
上面那二十一次调用也每一次都返回了正确结果。

但有两处变了，都朝坏的方向：

- **代价从固定成本变成了可变成本。** 死循环烧的是自己那台机器的 CPU，
  连接泄漏耗尽的是自己那个连接池——**都有天花板，撞到顶就崩，崩了你就知道了。**
  按调用计费的外部模型没有这个天花板：它不崩，它一直成功，一直计费。
  **过去那个“撞到顶”的时刻，恰恰是这类故障的免费报警器。这个报警器现在没了。**
- **报错指向的地方是错的。** 日志里反复出现的是“列不存在”。顺着这条线查，
  查到的是一次没跟上的数据库变更——那确实是个真问题，但它不是账单的成因。
  **账单的成因是这条日志出现了二十一次，而不是它写了什么。**

所以这一层不是“接口对一下”的收尾工作。它是这类系统的止损阀门，
而阀门的第一道就是下一节四件套里的幂等。

> **在骨架里的位置**：**接管的分界线画在这一章。** 集成把系统接进客户的遗留环境，而接进去的每一条链路，将来都要有人维护——**这一段归你还是归客户 IT，在这一章就定下来了**。定不清楚，第 6 关采用时会表现为“出了问题找不到人”。

## 读完这章你能做什么

1. 给一次跨系统调用设计幂等键、退避策略与超时预算，**让重试成为默认安全操作**。
2. 独立搭一个能扛住重放、乱序与重复投递的回调接收器，说清每一处防御对应哪种攻击或故障。
3. 在四种可用的授权模式之间做选型，识别出客户系统还在用已被弃用的模式时该怎么提示风险。
4. 拿到网络报错时，用一棵决策树把“连不上”拆成域名解析、端口、传输层安全、认证四层逐层定位。
5. 用一张七项清单核对一次集成做没做完，并说清为什么这七项在演示时全都用不到。

## 4.0 集成常常就是交付物本身

这一章排在系统五层的第一层，位置是刻意的。

讲 AI 系统的材料里，集成通常被当成“接口对一下”的收尾工作，一笔带过。
真实现场的比例是反过来的：**模型产生价值之前，先得接进客户系统；

## 4.1 韧性四件套

跨系统调用会失败，这是前提不是意外。网络会抖动，对方系统会重启，超时会发生在“请求到底有没有被处理”这个最尴尬的模糊地带。韧性工程要解决的不是“如何避免失败”，是“失败发生后，系统能不能自己收场”。四件套缺一不可：

- **幂等性**决定重试是否安全。
- **退避**决定重试的节奏。
- **超时预算**决定什么时候放弃。
- **熔断与降级**决定放弃之后系统怎么继续活下去。

**幂等性：重试安全的前提。** 客户端发起一次扣款请求，网络在响应返回前断开。客户端不知道服务端到底有没有处理成功。这时候唯一安全的动作是“用同一个幂等键重试”，而不是“猜一下再决定要不要重试”。幂等键的设计有三条容易被忽视的规则：

1. **键必须在一次逻辑操作的起点生成一次，而不是每次重试都重新生成**——这是最常见的实现错误。如果客户端每次重试都生成新的 UUID，幂等键机制形同虚设，服务端看到的永远是“新请求”。
2. **键的作用域要精确**：只在“同一个租户 + 同一个业务接口”内保证唯一。不要用全局唯一键去比对完全不相关的操作，否则两个业务毫不相关的请求会因为键冲突互相覆盖结果。
3. **键的生命周期要匹配业务的重放窗口**，不是越长越好。支付类操作通常需要保留 24 小时（覆盖客户端离线重试的极端情况），纯查询类操作可以短至几分钟。

服务端的实现模式是“键 → 结果”的一次性缓存。第一次见到某个键时正常处理并存下结果；后续同一个键直接返回存好的结果，不重新执行业务逻辑。

```python
# 示意性骨架，未经实测验证，不要直接用于生产
import time
from dataclasses import dataclass
from typing import Any, Callable

@dataclass
class IdempotencyRecord:
    result: Any
    status: str          # "in_progress" | "done" | "failed"
    created_at: float

class IdempotencyStore:
    """键值存储的最小接口，生产环境应替换为 Redis（带 TTL）。"""
    def __init__(self, ttl_seconds: int = 24 * 3600):
        self._data: dict[str, IdempotencyRecord] = {}
        self.ttl_seconds = ttl_seconds

    def get(self, key: str) -> IdempotencyRecord | None:
        rec = self._data.get(key)
        if rec and time.time() - rec.created_at > self.ttl_seconds:
            del self._data[key]
            return None
        return rec

    def put(self, key: str, rec: IdempotencyRecord) -> None:
        self._data[key] = rec


def call_with_idempotency(
    store: IdempotencyStore,
    idempotency_key: str,
    handler: Callable[[], Any],
) -> Any:
    existing = store.get(idempotency_key)
    if existing is not None:
        if existing.status == "done":
            return existing.result          # 直接返回上次结果，不重新执行
        if existing.status == "in_progress":
            raise RuntimeError("同一幂等键的请求正在处理中，拒绝并发重试")
        # status == "failed"：允许重新执行，但要覆盖旧记录

    store.put(idempotency_key, IdempotencyRecord(result=None, status="in_progress", created_at=time.time()))
    try:
        result = handler()
    except Exception:
        store.put(idempotency_key, IdempotencyRecord(result=None, status="failed", created_at=time.time()))
        raise
    store.put(idempotency_key, IdempotencyRecord(result=result, status="done", created_at=time.time()))
    return result
```

这段代码里 `in_progress` 状态的处理容易被漏掉。如果不拦截“正在处理中”的并发重试，两个几乎同时到达的重试请求会同时穿透缓存、同时执行两遍业务逻辑，幂等性照样被破坏。

**指数退避：给重试的节奏定规矩，别用固定间隔。** 固定间隔重试有个致命问题。当下游服务短暂过载时，所有客户端会在同一个时间点扎堆重试，形成“惊群”（thundering herd），把刚刚喘过气的服务重新打垮。

AWS 2015 年那篇被广泛引用的架构博客把这个问题和解法讲得很清楚：

> **“capped exponential backoff（封顶指数退避）指客户端每次失败后按固定倍数增加等待时间，直到某个上限”**[3]

但博客同时指出，纯粹的指数退避仍然不够。“N 个客户端在第一轮同时竞争，第二轮又有 N-1 个同时竞争”[3]，退避时间本身仍然是同步的。

解法是加入随机抖动（jitter）。文中给出三种变体并做了对比[3]：

- **Full Jitter**：退避时间在 0 到理论值之间完全随机。
- **Equal Jitter**：保留一半固定退避 + 一半随机，避免退避时间被抖成 0。
- **Decorrelated Jitter**：在 Full Jitter 基础上让新的抖动上限依赖上一次的随机值。

三者的实测对比结论：

- 无抖动方案调用次数最多、耗时最长，是“明显的输家”。
- Equal Jitter 调用次数略高于 Full Jitter 且耗时更长。
- Decorrelated Jitter 与 Full Jitter 之间“调用次数大致相当，Full Jitter 更省客户端工作量，Decorrelated Jitter 耗时略短”，二者的取舍“并不十分明确”[3]。

文章原文的抖动算法以配图形式给出，未提供可直接复制的文本。以下是业界据这套 Full Jitter 思路复现的通用写法（非逐字摘录，需自行实测校验边界条件）：

```python
# 示意性骨架，据 AWS 架构博客 Full Jitter 思路复现，未经实测验证，不要直接用于生产
import random
import time

def backoff_with_full_jitter(
    attempt: int,
    base_seconds: float = 0.5,
    cap_seconds: float = 30.0,
) -> float:
    """attempt 从 0 开始计数。返回值是本次重试前应该睡眠的秒数。"""
    exp_backoff = min(cap_seconds, base_seconds * (2 ** attempt))
    return random.uniform(0, exp_backoff)


def call_with_retry(handler, max_attempts: int = 5):
    last_exc = None
    for attempt in range(max_attempts):
        try:
            return handler()
        except TransientError as exc:          # 只重试可恢复的瞬时错误，不重试业务校验失败
            last_exc = exc
            if attempt < max_attempts - 1:
                time.sleep(backoff_with_full_jitter(attempt))
    raise last_exc


class TransientError(Exception):
    """网络超时、5xx、限流响应等可重试错误的基类，业务校验失败不应继承此类。"""
```

这里有个容易被忽略的边界：**只重试“瞬时性”错误，不能重试所有异常**。把 400 参数错误、401 认证失败这类“重试了也不会变好”的错误一起塞进重试循环，只会白白拖长故障恢复时间。还可能因为不断打向一个明确拒绝你的端点，触发对方的限流封禁。

**超时预算分配：端到端预算要往下分，而不是每一跳各定各的。** 一次用户请求如果承诺 5 秒内响应，这 5 秒要在调用链路的每一跳之间分配。不要让网关、认证服务、遗留系统适配层、数据库各自独立设置“看起来合理”的超时值。

独立设置的后果是叠加。网关超时 5 秒、认证服务超时 4 秒、遗留系统适配层自己又超时 3 秒，三者叠加后用户可能要等 12 秒才会看到失败，而不是承诺的 5 秒。每一跳都“觉得自己设置得很保守”，叠加起来却远超预算。

正确做法是“截止时间传播”（deadline propagation）：调用链路起点算出一个绝对截止时间戳，往下透传。每一跳用“截止时间减当前时间”算出自己还剩多少预算，而不是用一个固定的静态超时值。

```python
# 示意性骨架，未经实测验证，不要直接用于生产
import time
from dataclasses import dataclass

@dataclass
class Deadline:
    deadline_ts: float

    @classmethod
    def from_now(cls, budget_seconds: float) -> "Deadline":
        return cls(deadline_ts=time.monotonic() + budget_seconds)

    def remaining(self) -> float:
        return max(0.0, self.deadline_ts - time.monotonic())

    def check_or_raise(self, margin: float = 0.05) -> None:
        if self.remaining() <= margin:
            raise TimeoutError("调用链路截止时间已耗尽，放弃继续往下游发起调用")


def call_auth_service(deadline: Deadline):
    deadline.check_or_raise()
    timeout = deadline.remaining() * 0.6          # 给认证服务分配剩余预算的 60%，留 40% 给后续跳
    return http_call(url="https://auth.internal/token", timeout=timeout)


def call_legacy_adapter(deadline: Deadline):
    deadline.check_or_raise()
    timeout = deadline.remaining()                # 已是最后一跳，用完剩余全部预算
    return http_call(url="https://legacy-adapter.internal/invoke", timeout=timeout)


def http_call(url: str, timeout: float):
    raise NotImplementedError("占位：实际实现替换为具体 HTTP 客户端调用")
```

这套机制还要处理一个反直觉的情况：**下游的重试次数要受剩余预算约束，而不是固定重试 N 次**。如果一跳内部还在做前面讲的指数退避重试，退避时间必须和 `deadline.remaining()` 比对。预算耗尽就必须放弃重试、直接失败返回。不能让退避逻辑“礼貌地”等满固定的重试轮数，那样会让上游的截止时间检查形同虚设。

**熔断与降级：放弃之后系统怎么继续活下去。** 熔断器模式最早由 Michael Nygard 在《Release It!》一书中系统化提出，后来 Netflix Hystrix 把它做成了工业界的标准实现。Hystrix 已进入维护模式，社区现在更多用 resilience4j 一类的替代品，但状态机模型没有变。核心是一个三态状态机：

- **Closed（闭合）**：正常放行请求，同时统计失败率；失败率超过阈值时跳转到 Open。
- **Open（打开）**：直接拒绝所有请求，不再打向下游——这是保护下游、给它喘息时间的关键动作；打开状态维持一段冷却时间后跳转到 Half-Open。
- **Half-Open（半开）**：放行少量试探请求；试探成功则回到 Closed，试探失败则退回 Open 并重新计时。

```python
# 示意性骨架，未经实测验证，不要直接用于生产
import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 5, open_seconds: float = 30.0):
        self.failure_threshold = failure_threshold
        self.open_seconds = open_seconds
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.opened_at: float | None = None

    def _should_attempt(self) -> bool:
        if self.state == CircuitState.CLOSED:
            return True
        if self.state == CircuitState.OPEN:
            if time.monotonic() - (self.opened_at or 0) >= self.open_seconds:
                self.state = CircuitState.HALF_OPEN
                return True
            return False
        return True  # HALF_OPEN：放行试探请求

    def call(self, handler, fallback):
        if not self._should_attempt():
            return fallback()
        try:
            result = handler()
        except Exception:
            self.failure_count += 1
            if self.state == CircuitState.HALF_OPEN or self.failure_count >= self.failure_threshold:
                self.state = CircuitState.OPEN
                self.opened_at = time.monotonic()
            return fallback()
        else:
            self.failure_count = 0
            self.state = CircuitState.CLOSED
            return result
```

熔断打开之后，`fallback` 具体怎么写决定了用户能不能感觉到系统还活着。常见的三种降级策略按代价从低到高排列：

- 返回最近一次成功的缓存结果。代价最低，前提是业务能接受数据略微陈旧。
- 切换到功能更简单的备用路径，比如放弃个性化推荐，返回通用兜底列表。
- 把请求转成异步排队而不是同步失败。用户体验上从“立刻报错”变成“稍后处理”，适合本来就不要求实时的操作。

选哪种取决于业务对“数据新鲜度”和“实时性”的容忍度，没有放之四海而皆准的默认项。

## 4.2 Webhook 高可用接收器

企业集成里有相当一部分场景是反过来的：不是你的系统去调客户系统，而是客户的老系统（工单系统、ERP、支付网关）主动往你的系统推事件。Webhook 接收器看起来只是一个 HTTP 端点，实际上要同时扛住四类问题：重复投递、伪造请求、乱序到达、以及“投递成功但处理失败”的中间态。这四类问题不是理论假设。多家 Webhook 供应商（如 Stripe、GitHub）的官方文档明确声明自己是“至少一次”（at-least-once）投递语义，而不是“恰好一次”。接收端必须自己扛住重复。

**去重：用事件 ID 而不是请求内容做幂等键。** 至少一次投递意味着同一个事件可能因为客户端超时重发、供应商内部重试等原因被投递多次。去重键应该用事件自带的唯一 ID，大多数 Webhook payload 都会带一个 `event_id` 或类似字段。不要对整个请求体做哈希。同一个事件如果供应商在重试时改了个别元数据字段（比如重试次数计数器），内容哈希会不一致，但事件 ID 不会变。

这正是 §4.1 幂等键机制的直接复用。收到请求先查事件 ID 是否处理过：处理过直接返回 200（对供应商而言“已确认”，避免继续重试轰炸），没处理过才进入业务逻辑。

**重放攻击防御：签名 + 时间戳双重校验，缺一个都不够。** 只做签名校验，防不住“重放一条几天前被截获的合法请求”。签名本身没有过期概念，一条真实签发过的请求可以被攻击者原样重放，签名照样能验证通过。

业界通用的做法是在待签名内容里拼入时间戳。服务端校验时做两件事：

- 验证签名。
- 验证时间戳与当前时间的差值是否在一个短窗口内。常见做法是 5 分钟量级，具体取值取决于业务对时钟偏差的容忍度。

超出窗口的请求即使签名正确也要拒绝。这一步不是可选项：没有这一步，签名校验对重放攻击是无效的。

**乱序处理：不能假设网络会按发送顺序投递。** HTTP 请求经过负载均衡、多实例并发处理之后，到达服务端的顺序和供应商发出的顺序完全可能不一致。如果 Webhook 承载的是“资源状态变更”类事件（比如“订单状态从待支付变为已支付，又变为已发货”），乱序处理会导致状态被旧事件覆盖回退。防御手段是让每条事件携带一个单调递增的版本号或序列号。接收端处理前先比对：新事件的版本号必须大于当前已记录的版本号才允许覆盖，否则丢弃。丢弃的事件仍要返回 200 确认收到，避免供应商无意义重试一条注定要被丢弃的旧事件。

```python
# 示意性骨架，未经实测验证，不要直接用于生产
import hashlib
import hmac
import time
from dataclasses import dataclass

WEBHOOK_SECRET = b"replace-with-real-secret-from-vault"
TIMESTAMP_TOLERANCE_SECONDS = 300  # 5 分钟窗口，具体取值按业务时钟偏差容忍度调整


class WebhookRejected(Exception):
    pass


def verify_signature(raw_body: bytes, timestamp: str, signature_header: str) -> None:
    """签名 + 时间戳双重校验，二者缺一都不能防重放。"""
    try:
        ts = int(timestamp)
    except ValueError:
        raise WebhookRejected("时间戳格式非法")

    if abs(time.time() - ts) > TIMESTAMP_TOLERANCE_SECONDS:
        raise WebhookRejected("时间戳超出容忍窗口，疑似重放攻击")

    signed_payload = f"{timestamp}.".encode() + raw_body
    expected_sig = hmac.new(WEBHOOK_SECRET, signed_payload, hashlib.sha256).hexdigest()

    # 用 compare_digest 做常量时间比较，避免时序攻击泄露签名信息
    if not hmac.compare_digest(expected_sig, signature_header):
        raise WebhookRejected("签名不匹配")


@dataclass
class EventStore:
    """事件去重 + 版本号跟踪的最小接口，生产环境应替换为 Redis/数据库。"""
    seen_event_ids: set[str]
    latest_version_by_resource: dict[str, int]

    def is_duplicate(self, event_id: str) -> bool:
        return event_id in self.seen_event_ids

    def mark_seen(self, event_id: str) -> None:
        self.seen_event_ids.add(event_id)

    def accept_if_newer(self, resource_id: str, version: int) -> bool:
        current = self.latest_version_by_resource.get(resource_id, -1)
        if version <= current:
            return False               # 旧事件，拒绝覆盖，但上层仍应返回 200 确认收到
        self.latest_version_by_resource[resource_id] = version
        return True


def handle_webhook(raw_body: bytes, timestamp: str, signature: str, store: EventStore, event: dict):
    verify_signature(raw_body, timestamp, signature)          # 第一层：伪造请求防御

    event_id = event["event_id"]
    if store.is_duplicate(event_id):                          # 第二层：重复投递去重
        return {"status": "already_processed"}
    store.mark_seen(event_id)

    resource_id = event["resource_id"]
    version = event["version"]
    if not store.accept_if_newer(resource_id, version):       # 第三层：乱序丢弃旧事件
        return {"status": "stale_event_ignored"}

    process_business_logic(event)                              # 真正的业务处理
    return {"status": "processed"}


def process_business_logic(event: dict) -> None:
    raise NotImplementedError("占位：替换为真实业务处理逻辑")
```

这段骨架里有个容易被忽略但很关键的设计：**乱序事件和重复事件都要返回 200，而不是错误状态码**。多数 Webhook 供应商把非 2xx 响应当作“投递失败”信号，会触发重试。如果对一条“已处理”或“过期”的事件返回 4xx/5xx，只会引来供应商没完没了地重投同一条注定不会被处理的事件，浪费双方资源。200 + 一个说明性的 `status` 字段，才是对供应商“我已经妥善处理了，不用再发了”的正确表达。

## 4.3 认证协议桥接

企业集成里最容易被低估工作量的一块，是“客户对外要求 OAuth2，内部遗留系统只认 mTLS”这种协议不匹配。桥接层的代码已在正文中标明未实测状态。

**OAuth2 四种可用 grant，以及两种已被弃用的 grant。** OAuth2 核心规范 RFC 6749 定义了多种 grant type，但经过十余年生产实践淘汰，当前推荐使用的只剩四种，各自对应不同的信任场景：

| Grant | 适用场景 | 关键约束 |
|---|---|---|
| Authorization Code（+ PKCE） | 有用户参与、需要用户授权同意的场景（如客户业务人员登录你的系统去调用他们自己的 CRM 数据） | RFC 6749 §4.1 定义基础流程；PKCE（RFC 7636）用于防止授权码被截获后被冒用，OAuth 2.1 草案要求所有客户端类型都必须使用 PKCE，不再仅限公共客户端[4][5] |
| Client Credentials | 机器对机器，没有终端用户参与（如你的适配层以自己的身份调用客户系统的后台 API） | RFC 6749 §4.4；只涉及两方（客户端与授权服务器），不涉及资源所有者 |
| Device Authorization Grant（设备码） | 无浏览器或输入受限的设备（如只能通过命令行或简单终端操作的现场网关设备，需要一次性完成账号绑定） | RFC 8628；客户端展示用户码，用户在另一台有浏览器的设备上完成授权，客户端轮询换取令牌 |
| Refresh Token | 用长期有效的刷新令牌换取新的短期访问令牌，避免用户反复重新登录 | RFC 6749 §6；生产环境应启用刷新令牌轮换（每次使用后签发新令牌、旧令牌失效），一旦检测到已作废的刷新令牌被重复使用，应视为令牌泄露并撤销整个令牌家族 |

**Implicit grant 与 Resource Owner Password Credentials（ROPC）grant 已被正式移出 OAuth 2.1。** OAuth 2.1 草案第 10 节明确写出两条移除依据：

- Implicit grant“因其在 RFC 9700 中已被弃用”而从规范中省略[6]。
- ROPC grant 同样“依据 RFC 9700 §2.4 被省略”[6]。

移除 Implicit 的动机是“不再在授权响应里直接下发访问令牌”，因为这类令牌“容易被截获或注入，且无法被绑定到特定客户端”[6]。

这一条在遗留系统对接现场很实用。如果客户的老系统集成方案里还在要求你用“用户名+密码直接换令牌”的方式对接，那就是 ROPC 的典型形态。这是一个已被官方安全最佳实践明确否定的模式。FDE 应该主动向客户指出这是遗留设计，而不是照单全收当成“客户的正式要求”接进新系统。

各 grant 常见故障：

**Authorization Code**

- `redirect_uri` 必须与注册值完全字符串匹配，不接受“看起来等价”的变体，如末尾多一个斜杠。这是排查“明明配置对了却报 redirect_uri_mismatch”最常踩的坑。
- `state` 参数缺失会让流程失去 CSRF 防护。
- PKCE 的 `code_verifier` 与 `code_challenge` 不匹配，通常源于客户端在多进程/多实例部署下会话状态没有正确共享。

**Client Credentials**

- 客户端时钟与授权服务器时钟偏差过大会导致 `invalid_grant`。
- 客户端本地缓存了令牌，但没有正确处理令牌轮换后的失效。表现是偶发性认证失败，且不易复现。
- `scope` 请求与授权服务器实际配置不一致时，有的实现会静默降级 scope 而不是报错。下游调用因权限不足失败，却查不到认证环节的问题。

**Device Authorization Grant**

- 客户端轮询间隔过短会触发 `slow_down` 错误，服务器要求放慢轮询频率。
- 用户码在设备端展示后，如果用户迟迟不完成授权，会话会过期。需要给现场操作人员足够清晰的时间提示。

**Refresh Token**

- 没有启用轮换检测时，一旦刷新令牌泄露，攻击者可以无限期续期访问。
- 启用轮换后，如果多个客户端实例共享同一个刷新令牌又没做好并发控制，会出现“合法客户端的刷新请求被误判为令牌重用攻击”的假阳性。

**SAML：配置要点与常见故障。** SAML 2.0 的信任建立依赖 IdP（身份提供方）与 SP（服务提供方）预先交换元数据（entityID、断言消费服务地址、签名证书），OASIS 官方核心规范定义了断言、协议、绑定三层结构[7]。常见故障集中在四类：

1. **时钟偏差**：SAML 断言携带 `NotBefore`/`NotOnOrAfter` 时间窗口。IdP 与 SP 服务器时钟哪怕只差几分钟，都可能导致一条刚刚签发的合法断言被判定为“尚未生效”或“已过期”。这是 SAML 对接报“assertion expired”时第一个该查的地方，而不是先怀疑证书或配置。
2. **证书轮换断裂**：IdP 轮换签名证书后，如果 SP 侧的信任配置还缓存着旧证书，所有新签发的断言签名验证都会失败。这类故障往往在 IdP 完全没有通知 SP 侧的情况下发生，排查时要主动问客户“IdP 最近是否轮换过证书”。
3. **ACS URL 不匹配**：断言消费服务地址必须与 SP 在 IdP 侧注册的地址完全一致。环境迁移是这类故障的高发场景：测试环境地址复制到生产环境忘记改。
4. **NameID 格式不匹配**：SP 期望拿到邮箱格式的 NameID，IdP 却按其内部默认策略下发了一个不透明的 persistent/transient 标识符，SP 侧的用户匹配逻辑因此找不到对应账号。这类故障的报错信息通常只说“登录失败”，不会直接告诉你是 NameID 格式的问题。

**OIDC：discovery、JWKS 轮换、两个令牌不要用混。** OpenID Connect 建立在 OAuth2 之上，官方核心规范定义了身份层的补充语义[8]。集成时最容易踩的两个坑：

- **JWKS 轮换必须保留过渡期**：授权服务器的公钥通过 `/.well-known/openid-configuration` 指向的 JWKS 端点分发，每个密钥有一个 `kid`（key ID）。如果轮换密钥时直接删除旧密钥而不保留一段重叠期，所有用旧密钥签发、尚未过期的 in-flight 令牌会全部验证失败。这条和 §4.3 末尾要讲的凭据轮换重叠窗口原则是同一个道理。
- **`id_token` 和 `access_token` 不能混用**：`id_token` 是身份断言，受众（`aud`）是发起认证的客户端本身，用途是“证明这个用户是谁”。`access_token` 才是用来调用资源服务器 API 的凭证。一个常见的集成错误是拿 `id_token` 去当 Bearer token 调业务 API。多数规范严谨的资源服务器会因为受众不匹配而拒绝。但少数实现校验不严格，会“侥幸”放行，埋下后续升级校验逻辑后突然大面积失败的隐患。

**mTLS：证书链、SNI 与网关模式选择。** 双向 TLS 要求客户端也出示证书，服务端校验客户端证书是否链到一个受信任的 CA。两个高频故障：

- **证书链不完整**：服务端只配置了信任根证书，但客户端出示的证书链中间缺了中间 CA 证书。部分 TLS 客户端库不支持 AIA 扩展自动补链，验证失败；另一些库支持自动从证书里的 AIA 扩展地址补拉中间证书，却能验证通过。这种“同一套证书在不同客户端表现不一致”的诡异现象，根源往往就是链不完整，只是被部分客户端的自动补链能力掩盖了。
- **SNI 缺失或路由错配**：TLS 握手阶段，服务端需要依赖客户端在 `ClientHello` 里携带的 SNI（Server Name Indication）字段来决定出示哪张证书。这个环节发生在 HTTP 层的 Host 头可见之前。老旧客户端库或者手写的底层 socket 代码有可能压根不发送 SNI。如果服务端是多租户网关（一个 IP 后面挂了多个域名/多张证书），未携带 SNI 的请求会拿到一张不匹配的默认证书。证书链没问题，仍然会因为主机名校验失败而握手失败。

网关模式的选择上，mTLS 有两种做法：

- **网关层终结**：对外承接客户方的证书校验，对内网关用自己的服务身份去调遗留系统。
- **端到端直通**：网关只做转发，遗留系统自己校验最终客户端证书。

Lab-02 采用的是网关终结模式。网关对外呈现为标准的 OAuth2 资源服务器，对内持有一套独立签发给自己的客户端证书去访问要求 mTLS 的遗留系统。这样遗留系统完全不需要感知外部客户到底用的是 OAuth2 还是别的什么协议。

*✓ 本段取自 Lab-02，`verify.sh` 7/7 实测通过。完整实现见 `labs/lab-02-auth-bridge/`。*
```python
"""认证网关核心：对外 OAuth2 资源服务器，对内 mTLS 调遗留系统。

取自 Lab-02，`verify.sh` 7/7 实测通过。完整实现见 `labs/lab-02-auth-bridge/src/gateway.py`。
全用标准库（urllib ＋ http.client）而不引 httpx——遗留环境常装不了额外依赖，
少一个包少一层风险。本页为节选，import 与常量按节选用到的部分列出，
与源文件一致。
"""
import json
import socket
import ssl
import urllib.error
import urllib.parse
import urllib.request
from http.client import HTTPSConnection
from http.server import BaseHTTPRequestHandler

REQUIRED_SCOPE = "orders.read"   # 网关放行所需的 scope（源文件常量）
IDP_TIMEOUT = 1.0
LEGACY_TIMEOUT = 1.5  # 秒。遗留侧慢 3s 的接口必须在此之前被网关掐断


class Handler(BaseHTTPRequestHandler):
    """网关的 HTTP 处理器。此处只摘出认证与穿透两个核心方法。"""

    def _introspect(self, token: str) -> dict:
        data = urllib.parse.urlencode({"token": token}).encode()
        url = f"{self.server.idp_base}/oauth2/introspect"
        req = urllib.request.Request(url, data=data, method="POST")
        with urllib.request.urlopen(req, timeout=IDP_TIMEOUT) as resp:
            return json.loads(resp.read().decode())

    # ── 路由 ────────────────────────────────────────────────────

    def _handle_order(self, order_id: str):
        auth = self.headers.get("Authorization", "")
        if not auth.startswith("Bearer ") or not auth[len("Bearer "):].strip():
            return self._unauthorized("missing bearer token")
        token = auth[len("Bearer "):].strip()

        try:
            info = self._introspect(token)
        except (urllib.error.URLError, socket.timeout, TimeoutError, ConnectionError) as e:
            # IdP 自己不可用是网关的问题，不是调用方凭据的问题：503，不是 401。
            return self._json(503, {"error": "idp_unavailable", "error_description": str(e)})

        if not info.get("active"):
            return self._unauthorized("token inactive or expired")

        scopes = set((info.get("scope") or "").split())
        if REQUIRED_SCOPE not in scopes:
            return self._json(403, {"error": "insufficient_scope",
                                     "required_scope": REQUIRED_SCOPE})

        # 对内：mTLS 调遗留系统。客户端（调用这个网关的人）从头到尾
        # 不知道、也不需要知道这一步的存在。
        state = self.server.certs.get()
        state.acquire()
        try:
            conn = HTTPSConnection(self.server.legacy_host, self.server.legacy_port,
                                    context=state.ssl_context, timeout=LEGACY_TIMEOUT)
            try:
                conn.request("GET", f"/legacy/v1/orders/{order_id}")
                resp = conn.getresponse()
                raw = resp.read()
                status = resp.status
            finally:
                conn.close()
        except (socket.timeout, TimeoutError):
            # 超时预算生效的地方（§4.1）：遗留系统慢，网关不陪它慢。
            return self._json(504, {"error": "gateway_timeout",
                                     "error_description":
                                         f"legacy did not respond within {LEGACY_TIMEOUT}s budget"})
        except (ConnectionRefusedError, ssl.SSLError, OSError) as e:
            return self._json(502, {"error": "bad_gateway", "error_description": str(e)})
        finally:
            state.release()

        if status == 404:
            return self._json(404, {"error": "order_not_found", "order_id": order_id})
        if status != 200:
            return self._json(502, {"error": "bad_gateway",
                                     "error_description": f"legacy status {status}"})

        try:
            legacy_obj = json.loads(raw.decode())
        except json.JSONDecodeError:
            return self._json(502, {"error": "bad_gateway",
                                     "error_description": "legacy returned non-JSON body"})

        # 网关顺手把遗留系统的老式大写字段翻译成现代小写 API 形状；
        # 同时保留原始报文，方便排障。字段翻译本身不是本 Lab 的重点，
        # 但这正是"网关终结模式"里网关该干的事：协议 + 形状的转换都在
        # 这一层做完，两边谁也不用迁就对方。
        payload = {
            "order_id": legacy_obj.get("ORDER_ID", order_id),
            "status": legacy_obj.get("STATUS"),
            "amount_cents": legacy_obj.get("AMOUNT_CENTS"),
            "updated_at": legacy_obj.get("UPDATED_AT"),
            "_legacy_raw": legacy_obj,
        }
        return self._json(200, payload)

    # ── /admin/rotate、/admin/status ───────────────────────────
```

**凭据轮换与密钥管理：核心原则是重叠窗口，不是一刀切替换。** 无论轮换的是 TLS 证书、OAuth2 client secret 还是长期 API Key，都不应该“签发新的、同时立即吊销旧的”。应该保留一段双方都有效的重叠窗口：先签发新凭据、确认新凭据已在所有消费方生效、再吊销旧凭据。这正是 Lab-02 验收标准里“证书轮换过程中零失败请求”要考察的能力。如果轮换的实现方式是新旧证书不重叠地“硬切换”，切换的那一刻必然有一部分尚未完成配置刷新的调用方会被拒绝。

*✓ 本段取自 Lab-02，`verify.sh` 7/7 实测通过。完整实现见 `labs/lab-02-auth-bridge/`。*
```python
"""客户端证书轮换：切换期间零失败。

取自 Lab-02，实测 40 并发请求跨越轮换窗口 failures=0。

两个关键设计：
1. 每一代证书是独立对象，各自持有 SSLContext 与在途请求引用计数。
   rotate() 先完整加载新 context（失败则整体不生效），再原子替换指针——
   不存在"半成品"状态。旧请求早已把旧对象攥在自己的调用帧里，与替换无关。
2. 对遗留系统不做连接池，每请求新建连接、用完即关。一条连接绑定哪代证书
   在创建瞬间就定死，天然没有"池子里挂着旧证书连接"的问题。
   代价是每次重新握手，换来的是正确性上的简单可靠。
本页为节选，import 按节选用到的部分列出。
"""
import pathlib
import ssl
import threading
import time


class ClientCertState:
    """一份"网关对遗留系统的 mTLS 身份"快照：证书/私钥 + 由它们构造的
    SSLContext，外加一个"这一代证书当前有多少请求正在用它跟遗留系统
    通话"的引用计数。

    引用计数是重叠窗口能够"零中断"的关键：轮换只是让 CertManager 不再
    把这个状态对象发给*新*请求，但已经拿到它的*旧*请求会把它用完、
    close 掉连接、release 计数，全程不受影响。
    """

    def __init__(self, name: str, crt: pathlib.Path, key: pathlib.Path, ca: pathlib.Path):
        self.name = name
        ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
        ctx.load_verify_locations(str(ca))
        ctx.load_cert_chain(str(crt), str(key))
        self.ssl_context = ctx
        self.crt_path = str(crt)
        self.created_at = time.time()
        self._lock = threading.Lock()
        self._inflight = 0

    def acquire(self):
        with self._lock:
            self._inflight += 1

    def release(self):
        with self._lock:
            self._inflight -= 1

    @property
    def inflight(self) -> int:
        with self._lock:
            return self._inflight


class CertManager:
    """持有"网关当前用哪套客户端证书跟遗留系统握手"，支持原子轮换。

    现场教训（README 里详细展开）：证书快过期了才临时去换，是来不及的——
    生成新证书、验证链路、灰度切换都需要时间。正确做法是让"下一代"证书
    提前签好、提前部署到位，在**重叠期**内新旧证书都对 CA 有效、都被
    遗留系统信任，网关随时可以原子切换过去；确认旧证书不再被任何飞行
    请求使用后，再吊销/归档旧证书。本 Lab 的 gateway-client（3 天有效）
    与 gateway-client-next（3650 天有效，同一 CA 签发）就是这个模型的
    最小复现。
    """

    NAMED = {
        "current": ("gateway-client.crt", "gateway-client.key"),
        "next": ("gateway-client-next.crt", "gateway-client-next.key"),
    }

    def __init__(self, cert_dir: pathlib.Path):
        self.cert_dir = cert_dir
        self.ca_path = cert_dir / "ca.crt"
        crt, key = self.NAMED["current"]
        self._current = ClientCertState("gateway-client:current", cert_dir / crt,
                                         cert_dir / key, self.ca_path)
        self._previous = None
        self._lock = threading.Lock()

    def get(self) -> ClientCertState:
        """新请求调用它拿"当前"状态。这一步只是读一个引用，天然线程安全
        （Python 引用赋值/读取在 GIL 下是原子的），不需要额外加锁就能保证
        "拿到的要么是旧的要么是新的，绝不会拿到一半"。"""
        with self._lock:
            return self._current

    def rotate(self, to: str = "next"):
        """切换到 ``to`` 指定的证书对。这是唯一的"写"操作：
        1. 先把新证书加载进一个全新的 SSLContext（失败就整体不生效，
           不会把网关切到一个加载失败的半成品状态）；
        2. 再原子地把 ``self._current`` 指针换过去。

        切换的瞬间之前已经在跑的请求，早已经从 ``get()`` 拿到了*旧*的
        ClientCertState 对象引用并调用了 ``acquire()``——它们跟这次
        指针替换无关，会用旧证书把自己的这次遗留系统调用走完。
        之后进来的新请求，``get()`` 拿到的就是新对象了。
        """
        if to not in self.NAMED:
            raise KeyError(to)
        crt, key = self.NAMED[to]
        new_state = ClientCertState(f"gateway-client:{to}", self.cert_dir / crt,
                                     self.cert_dir / key, self.ca_path)
        with self._lock:
            old_state = self._current
            self._current = new_state
            self._previous = old_state
        return old_state, new_state

    def drain_status(self):
        with self._lock:
            prev = self._previous
        if prev is None:
            return None
        return {"name": prev.name, "inflight": prev.inflight}
```

密钥管理上还有两条实践原则：

- **不要一次性轮换所有消费方的凭据。** 分批灰度轮换能把轮换本身引发的故障爆炸半径控制在一个可回滚的范围内。
- **长期有效的静态密钥应尽量替换为短生命周期的动态凭据**，如 HashiCorp Vault 一类的动态密钥服务按需签发、到期自动失效。静态密钥一旦泄露的影响窗口是“直到下次人工轮换之前”，动态凭据的影响窗口则被压缩到密钥本身的 TTL 之内。

## 4.4 企业网络环境

前面三节讲的是协议层怎么对接，这一节讲的是“协议对接对了，但请求根本出不了客户的网络”这类更基础、也更容易被工程师忽视的问题。这些坑不是理论推演，是客户现场天天发生的真实卡点。很多项目延期不是因为模型不行，是因为一张防火墙白名单申请工单在客户 IT 部门躺了两周没人处理。

**企业代理：透明代理与显式代理的区别，决定了你要不要改代码。** 显式代理需要客户端主动配置代理地址，常见做法是设置 `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` 环境变量。透明代理则在网络层拦截流量、客户端无感知。

显式代理场景下最容易漏配的是 `NO_PROXY`。如果内网服务之间的调用也被错误地路由经过代理，轻则增加一跳延迟，重则代理本身不支持访问内网地址导致连接失败。

企业代理还经常做 TLS 检查（SSL/TLS Inspection）：代理会中间人式地解密流量再重新加密。客户端看到的服务器证书其实是代理自己签发的，而不是目标服务器的真实证书。如果客户端的信任库里没有企业代理的根证书，会报出“证书验证失败”，但故障现场看起来就像目标服务真的换了一张不受信任的证书。

排查这类问题要检查客户端的 CA 信任库有没有导入企业代理的根证书：Python 的 `certifi` 包、Node.js 的 `NODE_EXTRA_CA_CERTS` 环境变量、Java 的 `cacerts` 密钥库。

另外，部分企业代理要求代理认证（Basic、NTLM 或 Kerberos）。一些简单的 HTTP 客户端库不原生支持 NTLM/Kerberos 认证协商，需要额外的适配库或者退回到网络层面申请代理认证豁免。

**防火墙白名单申请：这是一个流程问题，不是技术问题，提前排期。** 企业防火墙的出站白名单申请通常需要经过 IT 安全部门审批。现场经验是这个流程往往要走几天到几周，是很多项目排期里被低估的一环。技术方案定下来之后应该立刻同步提交白名单申请，不要等到集成开发完成、临上线才发现网络不通。

申请时还有个容易被忽视的问题：**云端 SaaS 服务的出口 IP 会变化**。如果客户防火墙只支持按 IP 地址做白名单而不支持按域名，过一段时间供应商更换或扩容了服务器 IP，之前放行的白名单就会失效。故障表现是“上周还好好的，这周突然连不上了”。

能选的话优先申请按域名的白名单规则。如果客户防火墙只支持 IP 白名单，应该和供应商确认是否提供固定的出口 IP 段。另一条路是在客户网络内部署一个专用的出口网关/NAT，把出口 IP 收敛成一个客户可以长期稳定信任的固定地址。

**内网 DNS：分离视界（split-horizon）DNS 是排查“同一个域名两种解析结果”的关键词。** 很多企业内网对同一个域名做了内外分离解析。员工在办公网内访问某个域名解析到内网地址，同一个域名从公网访问则解析到完全不同的公网地址。

这类配置对做集成的工程师是隐形的。如果承载集成逻辑的服务器/容器没有正确接入客户内网 DNS 服务器，会解析到错误的地址。比如走了 VPN 分离隧道，只把办公流量导入隧道，而 API 调用走了直连。报错通常是“连接超时”而不是“域名解析失败”，容易被误判为网络层问题而不是 DNS 层问题。

排查时第一步应该是在集成服务器上直接跑 `nslookup`/`dig` 对比解析结果，而不是先怀疑防火墙。

**自签证书链：内网 CA 的信任分发问题。** 很多企业内部系统使用自建 CA 签发的证书，而非公开信任的证书颁发机构。这套证书链天然不在任何标准操作系统或语言运行时的默认信任库里。必须手动把客户的内部根证书/中间证书导入到每一个需要访问该系统的消费方的信任库。常见故障有两类：

- 客户只给了叶子证书，没给完整的中间证书链，部分客户端验证失败。
- 证书里的 CN/SAN 字段和实际访问的主机名不一致。内部系统经常用简写主机名签证书，但集成方用完整域名去访问。

**SNI 问题：和 §4.3 mTLS 部分的坑是同一类问题，但触发场景更广。** 除了 mTLS 场景，任何“一个 IP 后面挂多个域名/多张证书”的架构（企业内部的多租户网关、共享负载均衡器）都依赖 SNI 做证书路由。排查 SNI 问题最直接的手段是用 `openssl s_client -connect host:port -servername <目标域名>` 手动指定 SNI 发起握手，对比不指定 `-servername` 时握手拿到的是不是同一张证书。如果两次握手拿到的证书不一样，说明服务端确实依赖 SNI 路由，客户端库没有正确发送 SNI 就会拿错证书。

**网络连通性排查决策树：把“连不上”拆成四层逐层定位。** 现场排查最容易犯的错误是拿到一个笼统的“connection failed”就开始瞎猜。正确做法是按 DNS、TCP、TLS、应用层认证四层顺序排查，每一层都有独立的验证手段：

```{=latex}
\fdfig{\fdconnladder}
```

这棵树的价值不在于覆盖所有情况，而在于**排查顺序本身**。很多工程师习惯一上来就怀疑认证配置，因为认证报错信息最显眼。实际上认证层的问题必须建立在前三层都已经排除的前提下才有意义排查，否则很容易在错误的层级里打转。

## 4.5 遗留系统对接的四种方式

前面几节讲的都是“协议层面怎么打通”，但企业现场经常遇到的遗留系统压根没有现代意义上的 API。它可能只有一份十年前写的 WSDL，可能只接受定长报文，可能只会往一个共享文件夹里吐文件，甚至唯一的接口就是它自己的数据库。这四种方式没有绝对的优劣，只有“在这个客户的约束条件下选哪个坑最小”。

四种按「出错时会不会报错」排，**定长报文排在最前，因为它是唯一一种出错时不报错的**：

```{=latex}
\fdfig{\fdlegacy}
```

**SOAP：契约先行，类型严格，但重。** SOAP 走 WSDL（Web Services Description Language）契约先行的路子，接口的每个字段类型都在 WSDL 里静态声明。客户端可以直接根据 WSDL 生成强类型的调用代码，这是它相对 REST/JSON 的优势。遗留企业系统大量存活的正是这类接口，尤其是 Java EE/.NET 时代的系统。认证通常走 WS-Security 头（UsernameToken 或 X.509 证书签名），而不是 HTTP 层的 Bearer token。

常见的坑有三类：

- **开发环境和生产环境的 WSDL 版本经常不同步。** 客户给的 WSDL 文档是几个版本之前的快照，实际接口已经加了新的必填字段，直接照着旧 WSDL 生成的客户端代码调用会报“缺少必需元素”。
- 命名空间（namespace）声明稍有差池就会报“找不到匹配的全局元素”，排查起来比 JSON 的字段拼写错误费劲得多。
- SOAP 信封（envelope）本身比 JSON 冗长，老旧应用服务器的默认请求体大小限制在批量操作场景下容易被打满。报错却常常是笼统的连接被重置，不会直接告诉你是请求体太大。

**固定长度报文：没有分隔符，一个字节错位就是静默数据损坏。** 这是金融、电信、制造行业遗留系统里最古老也最危险的一种对接方式。每个字段按固定的字节偏移量和长度排布，没有 JSON/XML 那样的自解释分隔符。几个特有的坑：

- 报文编码经常是 EBCDIC 而不是 UTF-8/ASCII，需要显式转码。
- 数值字段经常用压缩十进制（COMP-3/Packed Decimal）编码，不能按普通字符串解析。
- 字段的补位规则（左补零、右补空格等）在不同报文规范里并不统一。

**最危险的失败模式是它不会报错。** 如果某个字段的长度定义理解错了，解析代码只会把后续所有字段错位地读出一堆“看起来合理但完全错误”的值，而不会抛异常。这比一次明显的连接失败危险得多，因为它可能在生产环境里默默跑很久才被发现。

```{=latex}
\fdfig{\fdmetabutton}
```

防御手段是给每条报文强制做结构校验：记录长度、字段数量对不上就立刻拒绝并告警。同时尽量要求对方在报文末尾提供校验位或记录数汇总字段用于交叉核对。

**文件交换（FTP/SFTP 落盘）：批量、异步，要解决“文件写完了没有”的问题。** 这是最“古老”但至今仍然广泛存活的对接方式：一方把数据文件放到约定目录，另一方轮询或被通知后读取处理。核心坑是**大文件写入不是原子操作**。如果接收端在文件还没写完的时候就开始读取，会读到一份不完整的数据。标准解法是“完成标记文件”约定：数据文件写完之后，再额外写一个空的 `.done`/`.ok` 标记文件。接收端只在看到标记文件存在时才认为对应的数据文件可以安全读取。

此外还要处理三件事：

- 文件命名与去重，避免同一批数据因为重试被处理两次。
- 处理完之后要归档而不是删除，用于事后排查和重放。
- 失败的文件要放入专门的隔离目录，而不是留在待处理目录里反复被扫描到。

如果源系统是 Windows 环境，还经常要处理换行符（CRLF vs LF）和文件编码（GBK/UTF-8）不一致的问题。

**数据库直连：技术上最简单，工程上耦合最深。** 直接连遗留系统底层数据库读写，跳过它自己的应用层。这条路径实现起来往往最快，但代价也最大：

- **遗留系统的 schema 变更完全不会通知你。** 供应商升级一次版本、加一列改一个字段类型，你的集成代码可能悄无声息地开始读到错误数据或者直接报错。
- **绕过应用层意味着绕过了它的业务校验和触发器逻辑。** 直接写库的操作可能违反遗留应用自己维护的业务不变式，导致遗留系统自己的界面显示出不一致的数据。
- 很多商业软件的授权协议明确禁止绕过应用层直连数据库，这么做可能直接导致原厂支持失效。

只读场景下用只读副本可以缓解性能冲击，但缓解不了 schema 耦合和“数据一致性由谁负责”这两个根本问题。

四种方式的取舍矩阵，按**实时性、对遗留系统的侵入性、典型故障模式、适用场景与不适用场景**五个维度对比。前两个维度可以快速判断“这个场景技术上行不行得通”。故障模式提示“选了之后要为哪类风险买单”。最后一列专门用来防止“看起来能用但其实不该用”:

| 方式 | 实时性 | 对遗留系统的侵入性 | 典型故障模式 | 不适用场景 |
|---|---|---|---|---|
| SOAP | 准实时（同步请求-响应） | 低（走遗留系统官方暴露的接口） | WSDL 版本漂移导致的字段不匹配；信封过大导致的老应用服务器连接重置 | 遗留系统压根没有暴露任何 Web Service 接口时无从谈起 |
| 固定长度报文 | 通常批量/准实时皆有，取决于传输通道 | 低（遗留系统只需按既有报文规范收发） | 字段错位导致的静默数据损坏，不抛异常、难以及时发现 | 数据结构频繁变化的场景——报文格式的每一次变更都需要双方协同升级解析逻辑，变化快的场景维护成本会失控 |
| 文件交换（FTP/SFTP） | 批量、异步，通常有明显延迟（分钟到小时级） | 极低（遗留系统甚至不需要知道对方是谁，只需读写约定目录） | 读取到未写完整的文件；重复文件导致的重复处理 | 需要实时响应的交互场景（如需要同步返回结果的用户交互流程）完全不适用 |
| 数据库直连 | 可以做到接近实时 | 极高（直接操作对方核心数据存储，完全绕过其业务逻辑层） | schema 变更无预警导致集成代码悄然失效；绕过业务校验导致的数据不一致 | 供应商合同明确禁止直连、或遗留系统业务逻辑复杂到“直接写库大概率破坏业务不变式”的场景 |

选型的实际决策顺序建议是：**先看供应商/客户合同和技术能力允许什么，而不是先看什么方式对你最省事**。很多时候真正决定用哪种方式的不是技术偏好，而是“客户的遗留系统这些年就只对外暴露过这一种接口。重新开发新接口的成本，客户不愿意承担”。

四种方式经常会在同一个项目里混用：比如用数据库直连做只读的历史数据回填，同时用文件交换做日常增量同步。不必强求整个项目统一成一种对接方式。这四种方式在一个真实工业客户身上完整跑一遍的样子，见第 14 章案例 [1]；把对接好的遗留系统进一步包成智能体可调用的工具，见第 13 章案例。

## 4.6 国内 IM 平台作为集成端点

上册第 10 章讲过一条判断：用户为了用上这个能力，需要多学几个动作，理想值是零。
在国内客户现场，那个用户每天已经打开的窗口，大概率是企业微信或者钉钉。
所以“把能力做进 IM 里”不是锦上添花的交互选择，它经常是采用率能不能起来的分水岭。

落到工程上，这两个平台不是“又一个 REST API”。前面五节讲的东西在这里有三处对不上。

**一、回调是加密的 XML，不是 JSON。** 企业微信把消息推给你的时候做 AES 加密，以 XML 形式 POST 到你配置的 URL；
你被动响应时也要加密后以 XML 返回。配置回调 URL 这一步本身就是一道验证：
平台先发一个带签名和密文的 GET 请求，你要验签通过并把密文解成明文原样返回，配置才保存得下来[9]。

这一步卡住的人比想象中多，原因往往和代码无关：本地开发机没有公网地址，那个 GET 根本到不了你手上。
**这是一个环境问题，别在解密逻辑里找原因。**

**二、被动响应的窗口很短，长任务必须转异步。** 企业微信服务器五秒内收不到响应就断开连接并重新发起请求，
总共重试三次；处理不完可以先返回一个空串，之后再用主动发消息接口异步回复[9]。
大模型生成要稳定压进五秒，多数场景做不到。

按“收到请求 → 调模型 → 返回结果”这个同步写法做，故障表现是用户收到三条一模一样的回复，或者一条都收不到。
**这就是 §4.1 那套幂等在另一个场景里的化身**：重试是平台替你发起的，你没有选择权，
只能靠幂等键把重复的那两次吃掉。正确的骨架是收到消息立刻应答、把活扔进队列、算完了主动推回去。

**三、凭据和入口在甲方 IT 手里。** 应用密钥、可信 IP 名单、回调地址的配置权限，通常挂在客户管理员账号下，
不在你的账号下。这意味着 §4.4 那张白名单表要多一行——不只是你的服务要出去，还有平台要进得来。

内网部署的现场，“平台访问得到你的回调地址”这个前提往往根本不成立。
钉钉的 Stream 模式正好绕开这一条：由你的程序主动建立长连接来接收事件和回调，
不需要公网服务器、公网 IP 和域名[10]。企业微信侧也有面向机器人的长连接接入方式。

**判断标准可以很简单：现场能不能给你一个平台访问得到的公网入口。给不了，就别在回调模式上耗时间，
直接评估长连接路径。** 这个判断要在第 2 关定界阶段做，不是等到集成开发做了一半才发现。

> **可信度说明**：五秒超时、三次重试、回调加解密方式与长连接模式的存在性，
> 取自两家平台的公开开发者文档。这类平台接口和限额的调整频率高于标准协议，
> 写进技术方案或验收条款之前，按当前版本的官方文档再核一遍。

## 本章清单

- [ ] 幂等键在一次逻辑操作**起点生成一次**，所有重试复用同一个。
      每次重试重新生成，是这套机制最常见的实现错误
- [ ] 指数退避必须加抖动。不加抖动的方案在调用次数和总耗时上都是明确的输家
- [ ] 超时用“截止时间传播”在链路各跳之间分配，不要每跳各设一个静态值
- [ ] 回调接收器同时防住三件事：重复投递用事件 ID 去重、重放要**签名和时间戳窗口都验**、
      乱序靠单调递增的版本号
- [ ] 检查客户系统用的授权模式。还在用已被移除的两种，主动提示风险
- [ ] 排查协议故障时先看运维细节：时钟偏差、证书轮换未同步、证书链不完整、服务器名称指示缺失
- [ ] 遗留系统对接按四个维度逐一核对：实时性、侵入性、故障模式、适用边界。
      **不要按“哪个实现起来最快”来选**
- [ ] 固定长度报文格式要专门测静默数据损坏——它不报错
- [ ] 听到“申请一下就行”，当场追问三件事：谁批、多久、批不下来谁受影响
- [ ] IM 平台的回调按异步写：先应答、进队列、算完主动推回。**同步写法会让用户收到三条重复回复**
- [ ] 内网现场先确认平台进不进得来。给不了公网入口就直接评估长连接模式，别在回调上耗

## 自检问题

1. 一个支付回调接口的幂等键，设计成“对请求体做 SHA256 哈希”而不是“用事件自带的 event_id”，可能会踩到什么坑？
   **判断标准**：如果供应商重试时会改动请求体里的某些元数据字段（如重试计数器、时间戳），同一逻辑事件的哈希值会不一致，幂等机制失效。应该用业务上定义为“同一事件”的稳定标识符做键，而不是对易变内容做哈希。

2. 你的团队给一次跨系统调用的每一跳都各自设置了“看起来合理”的超时值：网关 5 秒、认证服务 4 秒、遗留适配层 3 秒。为什么这仍然可能违反对用户 5 秒的响应承诺？
   **判断标准**：多跳独立设置的超时值会叠加，链路总耗时可能远超单一环节的超时设定。正确做法是用截止时间传播机制，让每一跳按“剩余预算”而不是固定值决定自己的超时。

3. 客户的老系统集成方案要求你用“客户账号密码直接换取访问令牌”的方式对接，这属于 OAuth2 的哪种 grant？你该如何回应客户？
   **判断标准**：这是 Resource Owner Password Credentials（ROPC）grant，已依据 RFC 9700 被 OAuth 2.1 草案正式移除。应向客户说明这是已被官方安全最佳实践否定的遗留模式，而不是把它当作理所当然的正式需求直接实现。

4. 一个 SAML 单点登录集成报错“assertion expired”，但你确认断言签发和验证之间只隔了几秒钟，下一步该排查什么？
   **判断标准**：优先检查 IdP 与 SP 服务器之间的时钟偏差，而不是先怀疑证书或网络问题。`NotBefore`/`NotOnOrAfter` 时间窗口对时钟偏差极其敏感，几分钟的偏差就足以让刚签发的合法断言被判定为过期或未生效。

5. 某遗留系统只提供固定长度报文接口，你的团队打算跳过结构校验、直接按约定的字段偏移量解析，理由是“反正双方约定好了，不会出错”。这个假设的风险在哪？
   **判断标准**：固定长度报文最危险的失败模式是字段错位导致的静默数据损坏。它不会抛异常，可能在生产环境里默默跑很久才被发现。必须做记录长度/字段数校验，并要求对方提供校验位或记录数汇总字段用于交叉核对，不能只依赖“约定不会变”这个假设。

6. 什么情况下“数据库直连”看起来是最优解，但实际上应该优先排除这个选项？
   **判断标准**：一是供应商合同明确禁止绕过应用层直连数据库时。二是遗留系统业务逻辑复杂到直接写库大概率会破坏其自身维护的业务不变式时。这两种情况下即使数据库直连技术上最快最简单，也应该优先考虑 SOAP/文件交换等侵入性更低的方式。

7. 证书轮换时，为什么“先吊销旧证书、再签发新证书”是错误的顺序？
   **判断标准**：这种顺序会在旧证书失效到新证书生效之间产生一个所有调用方都无法通过认证的窗口期。正确顺序是先签发新证书、确认所有消费方已切换、再吊销旧证书，保留一段新旧凭据都有效的重叠窗口。

8. 一个团队把企业微信里的问答机器人写成“收到回调 → 调大模型 → 把结果放进响应体返回”，测试环境一切正常。上线后用户反馈“经常收到三条一模一样的回复，偶尔一条也收不到”。问题出在哪？
   **判断标准**：能不能指出被动响应的窗口只有五秒，超时会断开并重试三次。测试环境正常，是因为测试用的问题短、模型返回快，压不到窗口边界。正确骨架是收到消息立刻应答，把任务放进队列，算完用主动发消息接口推给用户；同时用事件 ID 做幂等去重，把平台重试的那两次吃掉——这就是 §4.1 的幂等在这个场景里的用法。
