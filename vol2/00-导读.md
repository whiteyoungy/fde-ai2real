# 导读 · 下册怎么读、Lab 怎么跑

> **一句话结论**：上册给的是判据，下册给的是让判据能被自动验证的代码。
> 每个实验都有 `verify.sh`，全项通过且退出码为 0 才算做完。

## 先说一件事

一段正文里写着“高危阻断、中低危降级”，同一章的代码却在做整体阻断。

这个矛盾在书稿里躺了两个月，通读了不知道多少遍，没人看出来。直到把这段代码
真的跑起来，跑出的结果和正文对不上，才发现是正文和实现从来没对过。

**这类错误光靠读是审不出来的。** 只有真把代码跑起来才会现形。

这就是下册每一章都挂着一个可执行实验的原因，也是全书代码块标注体系存在的原因。

## 这册写给谁

假设你能独立写生产级 Python 或类似语言的代码，碰过至少一条真实的数据管道或 API 集成，
用大模型 API 做过点什么——写过提示词、接过检索增强、调过智能体框架。

你缺的不是这些零件，是把零件在一个真实客户现场拼成一套能上线、
能扛得住采用率下滑的完整交付。

**不适合谁**：想学 Python 基础语法、想学模型训练和微调理论的读者。
下册第 7 章会讲“微调 / 检索 / 提示词”的工程决策表，但那是决策框架，不是训练教程。

## 和上册的关系

下册的每一章都在守上册的某一条判据。翻不动上册的话，记住这张表就够了：

| 关卡 | 上册给的判据 | 下册哪几章负责实现 |
|---|---|---|
| **第 1 关 选题** | 这件事降低了哪一个不确定性 | 无对应工程章——它死在写代码之前，判据全在上册第 4 章 |
| **第 2 关 定界** | 范围文档要能被引用、被检查 | 第 2、3 章 规约驱动开发；业务建模的工程侧在第 6 章 本体 |
| **第 3 关 切片** | 用真实数据端到端跑通，客户能自己复现 | 第 1、4、5、7 章 |
| **第 4 关 验收** | 评估集 ≥20 条真实历史用例，指标要签字 | 第 9 章 |
| **第 5 关 上线** | 生产就绪清单全过，小流量观察窗口无事故 | 第 8 章 |
| **第 6 关 采用** | 人走了系统还得转，本事要留在组织里 | 第 10 章 技能 |

下册第 11、12 章（国产模型选型、信创适配）不挂在某一关上，它们是横切的约束——
六道关每一关都可能撞上。第 4、5 章（集成、数据管道）主要伺候第 3 关的“真实数据端到端”，
第 13–16 章的四则案例把全部六关各自跑了一遍。

还有一层关系值得先说。上册第 2 章立了一副四层骨架：为什么有这个岗位（风险转移）、
按什么顺序走（六道关卡）、走到哪儿算到（证据、控制、接管）、什么东西留得下来（验收集）。
上册讲前两层怎么判断，**下册讲后两层怎么做成工程事实**——证据靠第 9 章的三层评估集与
CI 门禁，控制靠第 8 章的部署护栏与可观测性，接管靠第 1 章的工程基线与第 10 章的技能：
别人看得懂、跑得动、改得了（第 2 章的规约属证据一侧——它是“什么算对”的第一次可执行表述，
评估集从它这儿起步，到第 9 章收敛）。

**资产层要多说一句，因为它现在有两样东西。** 第 9 章的评估集回答“什么算做对了”，第 10 章的技能回答“这件事怎么做”。两者不是并列的两个中心——**没有配套评估集的技能不是资产，是负债**：它以组织的名义，把一个没人验证过的做法推给了所有人。所以这两章同属第三部，判据一章、过程一章。

读下册时可以随时回头问一句：**我现在写的这段代码，是在攒证据、攒控制，还是攒接管？**
三样都不沾的，通常是可以先不做的。

### 下册这十六章，合起来在做一件事

**先说这条链为什么存在。** 上册第 2 章“这副骨架凭什么站得住”那一节，
给了下册整册一句前提：

> **在传统软件里，管理规则大多发生在代码之外；
> 在 AI 系统里，越来越多的管理规则必须被编译进系统本身。**

权限边界过去写在制度文件里，现在要写进 RBAC 与工具权限（第 8 章）；
验收标准过去在验收会上讨论，现在要变成验收集加流水线门禁（第 9 章）；
责任边界过去写在岗位职责里，现在要决定智能体的哪些动作允许不经人确认就执行（第 7、8 章）；
经验沉淀过去叫知识管理，现在要变成回归集、护栏策略和可执行规约（第 3、9、10 章）。
**下册讲的就是这个“编译”过程**——下面这条链，每一环都是一次编译。

上面那张表是按关卡分的。换个角度，按“承诺怎么变成工程事实”排，是一条链：

| 环 | 这一环把什么变成机器能检查的 | 哪几章 |
|---|---|---|
| **规格可执行** | “做到哪儿算完”从一句话变成能跑的验收 | 第 2、3 章 |
| **集成可靠** | 跨系统调用失败之后能自己收场 | 第 4 章 |
| **数据可追溯** | 答错的时候能定位到是哪一层错了 | 第 5 章 |
| **业务可执行** | 对象、动作、判据、权限、证据成为系统里的一等公民 | 第 6 章 |
| **决策可约束** | 模型能做什么由代码决定，不由提示词请求 | 第 7、8 章 |
| **系统可观测** | 发生了什么看得见，出问题能停、能退、能隔离 | 第 8 章 |
| **验收可自动化** | “什么算对”不依赖任何人还记得 | 第 9 章 |
| **客户可接管** | 你走了之后它还能被改、被修、被复核 | 第 1 章 + 附录 E |

> **下册有四章带“源 · 理 · 证 · 界”小结**：第 2 章规约驱动、第 6 章本体的工程实现、
> 第 9 章评估、第 10 章技能。这四章有真正的判据，所以要交代来路。
> 其余各章讲的是实现，来路多半是官方文档和 RFC，硬写成四行反而稀释——**故意不加。**
> 这套格式的完整说明在上册第 2 章“这副骨架凭什么站得住”那一节；
> **下册的“源”比上册多一层：它还要说清自己在实现上册的哪一条判据。**

**这条链上的每一环，工具都会换，环本身不会。** 第 3 章那三套工具、第 7 章那些框架、
第 11 章那张模型表，都是 2026 年的实现；链条是这本书想留下来的东西。
读到具体产品名的时候，可以顺手问一句：**它在这条链上补的是哪一环？**
答得出来，换工具的时候你知道要找什么替代品；答不出来，那多半是在学按钮。

有一句话可以当这条链的总结，它也是下册和上册骨架第四层接上的地方：

> **模型是耗材，验收集才是资产。**

第 9 章会把它讲透，第 12 章会给它一个最狠的检验：芯片、操作系统、数据库、
模型全换一遍之后，你手上还剩什么不用重建。

## 下册结构

```{=latex}
\fdfig{\fdbookmaptwo}
```

- **第一部 开工之前（1–3 章）**：工程基线，以及规约驱动开发——先写能验收的规格，
  再照着造。**第 3 章先讲三种能力**（规格、变更治理、执行纪律），
  再讲 2026 年分别用什么实现——Spec Kit、OpenSpec、Superpowers。
- **第二部 系统的五层（4–8 章）**：企业集成、数据管道与向量层、**本体的工程实现**、智能体编排、
  部署与可观测性。按落地顺序排列。
- **第三部 验收与沉淀的工程实现（9–10 章）**：评估集怎么造、裁判模型怎么用、CI 门禁怎么挂；以及怎么把一个人的判断萃取成一份能被执行、能被验收、能被下架的技能。**第 10 章是上册第 14 章那道梯子的工程实现。**
- **第四部 国产栈（11–12 章）**：国产模型与平台选型、信创改造。
- **第五部 工程案例（13–16 章）**：四个真实项目的架构决策复盘，
  重点是“被否决的方案为什么被否决”。

原来还有一个“第六部 上手”，装 90 天上岗计划和面试与作品集。
**它已经抽出去单独成了别册三**——前五部讲的是这套工程怎么做，那两章讲的是一个人怎么练成，
不是同一种东西。判据是：**已经在岗的读者把那两章整部跳过，正文的判据链条一环不缺。**
一段内容如果对相当一部分读者可以整章跳过，它就不该占正文的位置。
要按 13 周排学习计划、或者要准备面试的读者，去看别册三。

### 会过期的那部分，在配套手册里

**这一册有一部分内容的保质期是按月算的**：模型型号与 License、国产芯片与数据库的
适配现状、各类 SDK 的版本号、薪酬区间。它们印在书上的那一刻就开始过期，
而且**过期之后会连累同一页上那些不会过期的判断**——读者查了一下发现数字对不上，
就不会再相信这一章的任何结论。

所以它们被抽出去了，放在仓库的 `companion/` 目录，**四份，各有复核周期**：

| | 装什么 | 抽自 | 复核 |
|---|---|---|---|
| **C1** | 模型选型全表；三家托管平台的计费与私有化条款 | §11.1、§11.3 | 每季度 |
| **C2** | 国产芯片 / OS / 数据库的型号、适配现状与性能数字 | §12.2、§12.3 | 每半年 |
| **C3** | 书里断言过的所有工具版本，以及它们今天还成不成立 | 新建台账 | 每季度 |
| **C4** | 各公司官方披露的薪酬区间与国内对标岗位 | 上册 §1.2、别册三 §2.4 | 每年 |

**正文里留的是判断和方法，外加一份带日期的缩减快照**——
没有网也读得下去，只是数字可能旧了。真要做选型、报价、写进合同的时候，
再打开配套手册，然后做一件更要紧的事：**按它给的一手 URL 自己核一遍当天的数。**

配套手册**不进 PDF**（`build.sh` 只收 `vol1/`、`vol2/`）。这是有意的：
书印出来改不了，那一层可以随时改。它的维护协议写在 `companion/README.md`，
其中最要紧的一条是——**改配套手册的时候要回头看一眼书，
确认这次变化有没有推翻正文里的某句判断。**

### 下册要留下的八个词

上册导读列了七个（风险转移、六道关卡、证据 / 控制 / 接管、验收集、
最小可执行业务模型、采用率、定制化债务）。下册再加八个，**全部是不依赖任何工具的**：

| 词 | 一句话 | 在哪 |
|---|---|---|
| **可复现先于聪明** | 重建不出来的效果不是效果，是一次演示 | §1.0 |
| **底座 / 现场层边界** | 定制化债务的工程形态，就是这条线没画 | §1.5 |
| **可执行规格六块** | 用户故事那套写法漏了不变量和退路 | §2.2 |

| **六层诊断梯** | 说“模型不行”之前，先指出错在哪一层 | §5.0 |

## 正文里的代码可不可以照抄

分三类，标注方式不同：

| 标注 | 含义 |
|---|---|
| `✓ 本段取自 Lab-XX，verify.sh N/N 实测通过` | 代码从跑通的实验里回填的，可以照抄 |
| 代码首行注释“示意性骨架，未经实测验证” | 讲清思路用的，别直接上生产 |
| `⚠️ 未实测代码` | 全书**仅剩 3 处**，每一处都写明了缺什么条件 |

这个标注体系从写作初期就在，最初有 27 处 `⚠️`。做实验的过程反复暴露出正文与实现的矛盾，
每暴露一处就改一处，剩下的 3 处不是遗漏，是如实标注——
第 13 章 2 处（外联地址审计、本地向量库硬接线）与第 14 章 1 处（合规节点）
都超出任何实验的验证范围，需要对应的真实环境才能验。

**“你有 GPU 就能验”和“不知道能不能用”对读者是两回事**，这个区分值得保留。
附录 A 逐处写明了缺什么条件。

## 12 个实验怎么做

**先说这 12 个实验和课后习题的区别。** 习题的判定人是你自己；这 12 个实验的判定人是
`verify.sh`——README 先写死验收标准，脚本把标准变成能自动跑的检查，全项通过且退出码为 0
才算做完。**做完不是“我觉得做完了”，是机器验过了。**

这不是偷懒的评分方式，是这本书的方法论用在这本书自己身上：
第 2 章讲“先定 Done 再动手”，第 9 章讲“评估集不进门禁等于没有”，
而这 12 个实验就是这两句话的实例。**所以它们的说法应该是“机器验证过你做到了”，
不是“你看过了”。**


```bash
cd labs/lab-01-invoice-pipeline
cat README.md                  # 先读需求、验收标准与可替换组件
python3 fixtures/generate.py   # 生成夹具（夹具是产物，不入库）
bash verify.sh                 # 验收。全过则退出码 0
```

几条会省你时间的：

- **夹具要自己生成。** 仓库只带源码、夹具生成器和安装脚本，不带依赖包、模型权重和生成产物。
  生成器都是确定性的（固定随机种子），跑一次得到和作者完全相同的夹具。
- **别把 `verify.sh` 放进管道测退出码。** `verify.sh | tail; echo $?` 拿到的是 `tail` 的退出码。
  正确写法：`bash verify.sh > /tmp/v.log 2>&1; echo $?`
- **部分实验需要虚拟环境**（Lab-03/04/06/08/10）。`verify.sh` 会自动识别同目录下的 `.venv`，
  不用手动激活。装 `sentence-transformers` 前先装 CPU 版 torch，
  否则会拉进整套 CUDA 依赖，白占几个 GB。
- **部分实验需要 Docker**（Lab-04 的 Qdrant、Lab-10 的 Kafka）。`verify.sh` 自己拉起容器，
  退出时清理。

需要接模型的实验支持双路径：

```python
import os
if os.getenv("DEEPSEEK_API_KEY"):        # 首选：真实推理质量
    base_url, model = os.getenv("DEEPSEEK_BASE_URL"), "deepseek-chat"
else:                                     # 降级：本地 CPU 小模型
    base_url, model = "http://127.0.0.1:11434/v1", "qwen2.5:0.5b"
```

没有 key 时验收标准放宽为“机制正确”而非“效果达标”，差异写在各实验的 README 里。
**放宽是如实放宽的，不是把夹具改软**——Lab-06 的无 key 档甚至在 README 里明写
“这一档配置不安全，只用于跑通链路，别照搬到生产”。

## 密钥怎么放

一条硬规矩，全书任何一处代码都不违反：**API key 只从环境变量读，
永远不落盘、不进日志、不写进任何文件。**

`.env` 加进 `.gitignore` 并确认没被跟踪：

```bash
git check-ignore -v .env       # 有输出说明已被忽略
git ls-files --error-unmatch .env 2>/dev/null && echo "危险：.env 已入库"
```

项目做完之后轮换一次密钥。这不是洁癖，是因为你不知道这台机器上还跑过什么。

## 还有三本别册

前两本是独立成册的实践手册，讲的是同一层东西——**模型外面那层壳**：
沙箱、审批、留痕、边界。它们补的是第 3 章那三种能力都没覆盖的一块（执行环境），
**执行环境层**。第三本讲的不是系统，是人。

**别册一《用 Codex 做一个 FDE 项目》**：讲一个成熟的开源 harness
在客户现场怎么配，面向“要回答甲方安全部门提问”的场景。
按读者门槛分了轻/中/重三档：**只想把工具用顺手的读第 1、3、8 章
加附录 A 的“轻档五步”，十分钟能落地**。

**别册二《用 DeepSeek Harness 做一个 FDE 项目》**：讲一个可以逐个换零件的
插件式 harness 能拆到什么程度、拆开之后哪些零件能交到客户手里。
按用法分三档：当工具用／当组件改／当交付物给出去。
**它第 2 章讲的国产模型接入，是别册一那个最大的坑的另一条解法。**

**别册三《90 天上岗与求职》**：原来的第 16、17 章。一条 13 周的学习时间线，
把两册方法论和 12 个 Lab 咬合起来；外加十道系统设计题、现场演练题和作品集的组织法。
**已经在岗、只想查方法的读者不必打开它。**

**三本别册都不进上下册的目录。** 上下册讲“该做成什么样”，
别册讲“拿一个具体的东西怎么做到那样”——**具体的东西会过期，该做成什么样不会。**
上下册不依赖任何一本别册，可以单独读。

## 这本书是怎么写的：AI 辅助的部分

**署名只写人。** 写作过程中大量用了 AI 工具——Claude、Gemini，以及别册一讲的
那个 Codex。它们参与的是初稿撰写、结构重排、检索线索、代码与图表生成，
以及大量机械的一致性检查：章节编号、交叉引用、术语统一、体例核对。
这类活它们做得又快又稳，而且不会因为枯燥而漏。

**但有三样没有交给它们。**

**第一，选题与判断。** 哪些内容进书、哪一条判据成立、什么算“本书原创”、
哪个数字不采信——这些是人的决定。**这本书唯一值钱的部分就是这些判断，
它们不能外包，外包了这本书就没有存在的理由。**

**第二，出处的核对状态如实标注，不合并。** 逐字核对过的、只核了摘要的、
二手转述的，是三种不同的东西，正文和章末参考来源里分开写，不含糊过去。
这条纪律的由来是一件真事，记在上册 §14.2 里：写作过程中出现过一个带具体
数字的知名公司案例，读起来非常合理；回原文逐字一查，**原文根本没提过这家
公司，也没有这组数字，整个案例是搜索摘要凭空生成的。** 上一节说的那些限定语，
就是从那次开始加的。

**第三，实测。** 书里标“已实测”的，是在真机上跑过的，不是模型说它能跑。
跑不动、没条件跑的，正文标“未实测”，不含糊。

**为什么要把这一段写出来。** 这本书讲的是把 AI 交付到真实世界，
而它给的三条判据是证据、控制、接管。**一本用 AI 写的、讲怎么用好 AI 的书，
如果连自己用了什么、哪些地方不敢交给它都说不清，前面那些判据就是双标。**
