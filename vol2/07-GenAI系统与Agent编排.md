# 第 7 章 · 生成式系统与智能体编排

> **一句话结论**：出问题时的排查顺序是提示词 → 上下文 → 检索链路 → 编排逻辑 → 微调。
> 从最后一项开始查，是最贵也最慢的做法。

## 它自己发明了一个不存在的工具

一个多步骤智能体，跑到第七步的时候调用了一个叫 `get_customer_credit_score` 的工具。

这个工具不存在。系统里从来没有过。

它不是坏了——它是根据上下文推断出“这一步应该有这么个东西”，然后就调了。
调用失败之后，它换了个名字再试一次，又失败，再试。循环跑了四十多轮才被超时掐掉。

这一章要处理的就是这类事：**智能体不会告诉你它出错了，它会自信地继续往下走。**

> **在骨架里的位置**：这一章的产出物本身不是三类结果里的任何一类，它是**被约束的那个对象**。一条纪律：**编排出来的每一个动作，都该落在上册第 7 章那份本体定义的动作集合里**——多出来的那些，第 5 关无从施加控制，因为控制不了一个没被定义过的动作。

## 读完这章你能做什么

1. 给一个生产级系统提示词设计分层结构，并知道结构化输出该用格式约束还是纯提示词约束、失败了怎么重试。
2. 画一张上下文预算表，说清系统指令、检索结果、对话历史、输出预留各占多少，以及“上下文污染”是怎么发生的。
3. 搭一条查询重写 → 混合检索 → 融合 → 精排 → 自纠错的完整检索链路，
   **并对每一环说清什么情况下不值得上**。
4. 判断一个“全局归纳型”问题该用图谱检索还是长上下文直塞。
5. 写出一份能让模型准确调用的工具描述，并搭出一个带人在回路的多智能体拓扑。
6. 给工具调用失败、死循环、状态漂移、幻觉工具名这四类故障设计防御手段。
7. 把这一章出现的每一个框架和协议，定位到它补的是七项工程能力里的哪一项。

## 这一章的主线

按“输入怎么组织 → 知识怎么接入 → 系统怎么互联 → 多步怎么编排 → 出了问题怎么办 →
什么时候该换技术路线”展开。

**这条顺序也是实际项目里排查问题该走的顺序**：先看提示词和上下文有没有设计缺陷（成本最低），
再看检索链路，再看编排逻辑，最后才轮到“要不要微调”这个成本最高、周期最长的选项。

### 这一章的产品名最多，所以先说哪些会过期

这是全册出现具体产品和框架名最多的一章——提示词技巧、检索链路、MCP、LangGraph、
多智能体拓扑。**它们里面有相当一部分活不到这本书的下一版。**

所以先把不会过期的那一层单独摆出来。一个生产级的生成式系统，
不管用什么框架实现，都要回答七个问题：

| 能力 | 要回答的问题 | 2026 年的实现之一 | 在哪几节 |
|---|---|---|---|
| **上下文** | 这次任务需要的信息，怎么组织进去、放多少 | 分层系统提示词、上下文预算表 | §7.1、§7.2 |
| **知识** | 什么时候去外部查，什么时候用已有的 | 检索增强、图谱检索、长上下文直塞 | §7.3、§7.4 |
| **动作** | 模型能调什么、参数怎么给、边界在哪 | **MCP 是动作接口的一种实现** | §7.5 |
| **编排** | 一件事怎么拆成多步，谁决定下一步走哪 | **LangGraph 是有状态编排的一种实现** | §7.6 |
| **状态** | 多步之间的中间状态存在哪、谁能改 | 图状态、检查点 | §7.6 |
| **控制** | 哪些动作必须有人批准才能执行 | 人在回路节点 | §7.6、第 8 章 |
| **恢复** | 工具失败、模型跑偏、循环停不下来，怎么收场 | 重试、循环上限、状态校验 | §7.7 |

**这张表的第三列是唯一会变的一列。** MCP 可能被别的协议取代，
LangGraph 可能被别的框架取代，但“模型能调什么、由谁决定边界”这个问题不会消失，
“多步之间的状态存在哪”这个问题也不会消失。

**读这一章有一个建议的方式**：每读到一个产品名，先回到这张表上定位它补的是哪一行。
定位得出来，将来换工具的时候你知道要找什么替代品；定位不出来，
说明这一段读的是按钮，不是能力。

**七项里最容易被整章跳过的是「控制」和「恢复」。**
它们和演示不沾边——演示的时候不会有人批不通过，也不会有工具失败。
但上册第 2 章骨架第三层里的“控制”，工程上就落在这两行加第 8 章那套护栏上。
**一个七项里只做了前五项的系统，可以演示，不能上线。**

## 7.1 系统级 Prompt 工程

生产级系统的 prompt 不是一段字符串，是一份分层文档。

把“你是一个客服助手”和“用户的具体问题”堆在同一层里，会有三个后果：

- 改一次业务规则就要通读全篇，找哪句话要改；
- 出了问题说不清是哪一层在起作用；
- 团队协作时容易出现互相覆盖对方改动的情况。

分层的价值不是好看，是可维护。每一层职责单一，改动范围可控，出问题时也更容易定位到底是哪一层出的错。

**四层结构**，从稳定到易变排列（层号越小，改动应该越谨慎、评审门槛应该越高）：

1. **身份与边界层**：模型是谁、扮演什么角色、能做什么、绝对不能做什么。例如“不得承诺具体退款金额”“不得执行不可逆操作”。这一层几乎不随业务迭代而变化，改动需要走正式评审流程。
2. **能力与工具层**：可用工具清单、每个工具的调用条件、工具之间的优先级，例如“先查库存工具，库存不足才允许查询替代品工具”。工具增减时改这一层。
3. **风格与输出格式层**：语气、结构化输出的 schema、多轮对话中的引用规范。产品迭代时改这一层。
4. **任务与上下文层**：当次请求的具体任务、检索到的上下文、对话历史。每次请求都不同，是最易变的一层。

四层拆开写、分别管理、分别评审，是可维护性的核心。直接好处是可以分别版本化：身份边界层进代码评审流程，任务上下文层由检索管道动态拼装。两者的变更节奏完全不同，混在一起会让高频变化的部分把低频但重要的约束“稀释”掉。上下文越长，模型对靠前的强约束的遵从度会随位置和总长度衰减，这也是 §7.2 要讲的问题的源头之一。

**提示链（Prompt Chaining）**：复杂任务不要指望一次调用把“理解意图、检索、生成、校验”全做完。拆成多个更小的调用，前一步的结构化输出是后一步的输入，每一步职责单一、容易单独测试和替换。

典型链路是“意图分类 → 任务参数抽取 → 执行/检索 → 生成 → 自我校验”，五步分别对应五个更小的 prompt，而不是一个巨大的“万能 prompt”。

但不是越拆越细越好。链路变长会增加延迟和成本，这是要用测试数据实测权衡的取舍点。如果某一步的输出几乎不需要单独校验或替换，合并回上一步反而更省成本。

**结构化输出：两条路线，代价不同。**

- **提示词约束**：在 prompt 里给出目标 JSON Schema 和示例，要求模型按格式输出。实现成本最低，但没有硬保证。模型仍可能输出格式错误的 JSON，多一个逗号、漏一个引号都有可能，需要额外的解析容错。
- **约束解码（Constrained Decoding）**：在推理层面强制模型只能生成符合给定语法（如 JSON Schema）的 token 序列，从根上排除格式错误的可能性。多数商用 API 与本地推理框架都提供某种形式的结构化输出/JSON 模式接口。具体参数名称和支持范围随厂商和版本变化快，本书不在正文列出会过期的接口细节。实现前应查对应 API 版本的当前文档，确认参数名与支持粒度。

两条路线不是二选一。约束解码解决“格式对不对”，解决不了“内容对不对”：模型可能生成语法合法但字段值胡编的 JSON，比如编了一个不存在的订单号。所以结构化输出之后仍然需要一层业务校验，两层各管各的问题。

**失败重试的三层退避**，按代价从低到高：

1. **原地重试**：格式错误时，把错误信息连同原输出一起喂回模型，要求修正。错误信息要具体，比如 JSON 解析报错的位置。这一步能解决大部分偶发格式错误，成本只是一次额外调用。
2. **降级简化**：连续重试失败后，把任务拆得更小、约束更明确，用简化后的确定性换回一次成功。例如从“输出完整订单对象”降级为“只输出订单号这一个字段”。
3. **兜底与转人工**：重试次数必须有硬性上限，不能无限循环下去，那是 §7.7“死循环”故障的一种具体形态。触发上限后走预设的默认值或转人工处理，并把失败记录写入日志供事后分析。静默重试到超时，比明确报错更危险。

重试次数上限、每层退避的触发条件，都应该做成可配置参数，不要写死成代码里的魔法数字。这样才方便针对不同任务的实际失败率随时调整。三层退避的校验逻辑可以用一个简单的骨架表达：

```python
# 示意性骨架，未经实测验证，不要直接用于生产
import json
from dataclasses import dataclass

@dataclass
class RetryConfig:
    max_inline_retries: int = 2      # 原地重试上限
    max_downgrade_retries: int = 1   # 降级简化上限

def call_with_structured_retry(prompt: str, schema: dict, call_model, config: RetryConfig):
    """三层退避：原地重试 -> 降级简化 -> 兜底转人工。"""
    for attempt in range(config.max_inline_retries):
        raw = call_model(prompt)
        try:
            parsed = json.loads(raw)
            validate_against_schema(parsed, schema)  # schema 校验：字段全不全、类型对不对（业务校验在下游单独一层）
            return {"status": "ok", "data": parsed}
        except (json.JSONDecodeError, SchemaValidationError) as e:
            prompt = build_repair_prompt(prompt, raw, str(e))  # 把错误信息喂回模型

    for _ in range(config.max_downgrade_retries):
        simplified_schema = shrink_schema(schema)  # 降级为更小的字段集合
        raw = call_model(build_simplified_prompt(prompt, simplified_schema))
        try:
            # 降级路径只保证 JSON 可解析，schema 校验被有意豁免——status 已标 degraded，
            # 下游必须按降级数据对待，不能当正常数据用
            return {"status": "degraded", "data": json.loads(raw)}
        except json.JSONDecodeError:
            continue

    log_failure(prompt, schema)  # 失败记录写日志，供事后分析，不能静默吞掉
    return {"status": "escalate_to_human"}
```

这段骨架的重点不是具体的函数实现，`validate_against_schema`/`build_repair_prompt`/`shrink_schema` 都需要按业务场景补全。重点是三层退避的调用顺序，以及“每一层都有明确的退出条件”这个结构本身。原地重试次数用完就必须进入降级，降级也用完就必须转人工，任何一层都不能无限重试下去。

## 7.2 长上下文管理

上下文窗口是共享资源，四个消费者互相挤占：系统指令、检索结果、对话历史、输出预留。

不预先分配预算，实际发生的通常是一条连锁反应：对话历史随轮次线性增长，挤占检索结果的配额，检索结果又被迫截断，回答质量随对话变长而悄悄下滑。用户感知到的是“这个助手聊着聊着就变笨了”，根因其实是预算没设计。

**预算分配表（示意，具体比例按任务类型调整）**：

| 消费者 | 典型占比 | 说明 |
|---|---|---|
| 系统指令（§7.1 四层结构） | 5%–10% | 相对固定，身份与工具层通常不随对话变化 |
| 检索结果（RAG 上下文） | 40%–60% | 单条查询能拿到的检索预算，直接决定“回答有没有依据” |
| 对话历史 | 20%–35% | 需要设置滚动窗口或摘要机制，不能无限累积 |
| 输出预留 | 10%–15% | 必须预留，输出预算不足会导致回答被截断 |

这张表是设计起点，不是精确配方。不同任务的最优比例本书没有找到可直接照抄的实证研究，需要用自己的评估集（第 9 章方法论）实测调整。设计的关键不是记住某个百分比，是“每类消费者都要有上限、不能相互抢占”这个原则本身。

举一个具体数字帮助建立直觉（数字为示意，非某个特定模型的实测值）。一个 32K token 的窗口按上表比例粗分：系统指令占 2K–3K，检索结果占 13K–19K，对话历史占 6K–11K，输出预留占 3K–5K。

如果对话历史没有滚动窗口机制，十几轮来回之后历史部分很容易膨胀到远超这个区间。此时最先被挤压的往往是检索结果配额，因为系统指令和输出预留通常是硬性下限，不会主动让步。所以“对话历史要有滚动窗口或摘要机制”不是锦上添花的优化项，是长对话场景下防止检索质量隐性劣化的必要设计。

**压缩与摘要策略**，按压缩时机分三种：

- **滚动摘要**：对话轮次超过阈值后，把最早的若干轮压缩成一段摘要，替换掉原始逐字记录。优点是实现简单，代价是摘要本身可能丢失细节，且摘要生成本身要占用一次额外调用。
- **检索结果的二次浓缩**：混合检索 + rerank 之后，如果候选文档仍然超出预算，用轻量模型对每篇文档做要点抽取，而不是整篇塞入。这是 §7.3 CRAG 的 Knowledge Refine 思路在上下文管理层面的复用。先分解成细粒度片段，只保留真正相关的部分再拼接，而不是整篇文档一股脑塞进去。
- **结构化记忆代替流水账**：把对话历史里的关键事实（用户偏好、已确认的参数）抽取成结构化字段单独维护。不要依赖模型每次重新从完整对话记录里“回忆”。这样对话历史本身可以更激进地截断，因为关键信息已经落到了结构化字段里，不依赖历史文本本身。

**上下文污染的三种成因**，这是比“上下文不够长”更容易被忽视的问题：

1. **陈旧信息未失效**：对话早期的错误假设或已被用户纠正的信息，仍然留在滚动历史里，模型后续引用时可能重新拾起这个已经作废的结论。规避手段是对已被显式纠正的信息做标记，或者直接从历史中移除。不要任由新旧信息并存，等模型自己判断该信任哪个。
2. **检索噪声挤占强约束的注意力**：混合检索召回的低相关度文档如果没有被 rerank 或阈值过滤掉，会和系统指令、真正相关的证据混在一起。噪声混进来的后果是稀释模型对高优先级约束的遵从度。这也是 §7.3 强调 rerank 和阈值过滤不是可选项的原因。
3. **提示链中间态污染下游**：§7.1 提示链的某一步如果输出了错误或格式异常的中间结果，又没有校验就直接传给下一步，错误会在链路上累积放大。原始错误的痕迹还可能在传递过程中被“抹平”，排查时很难定位到底是哪一步先出的错。所以提示链设计必须在每一步之间加校验点，这不只是为了拆分职责。

三种成因的共同应对原则是“主动清理，不要依赖模型自己甄别”。陈旧信息该删就删，检索噪声该过滤就过滤，中间态该校验就校验。都不能指望模型在噪声里自动分辨哪些该信、哪些该忽略。

## 7.3 RAG 进阶全链路

朴素 RAG（查询直接 embedding → 向量检索 top-k → 塞进 prompt）在 demo 阶段够用，在生产里会在五个地方翻车：

- 用户的口语化提问和知识库的书面语存在词汇鸿沟；
- 纯向量检索找不到精确关键词（型号、订单号）；
- 召回列表顺序不可靠；
- 候选文档里混着不相关内容；
- 检索到了错误或过时的文档，却毫无察觉地生成。

进阶全链路是针对这五个翻车点逐层加固：查询重写解决词汇鸿沟，混合检索解决精确关键词丢失，RRF 融合解决多路排序合并，Rerank 解决候选顺序不可靠，CRAG 解决“检索错了也不知道”。每一环都有成本，不是环环都要上。

**① 查询重写（Query Rewriting）**

- **为什么需要**：用户的原始问题往往简短、口语化、指代不清（“上次说的那个多久能到”），直接拿去检索命中率低。
- **怎么实现**：两条常见路线。HyDE（Hypothetical Document Embeddings）让模型先生成一篇“假想答案文档”，再用这篇假想文档去检索，利用编码器的稠密瓶颈过滤掉假想内容里的具体错误，只保留相关性模式[1]。RAG-Fusion 则是生成多个改写版本的查询，分别检索后用 RRF 融合结果[2]。
- **怎么验证有效**：在黄金集上对比“原始查询直接检索”与“重写后检索”的 Recall@k / nDCG，同时记录延迟增量。查询重写至少多一次模型调用：RAG-Fusion 论文的单一企业案例自测显示，端到端延迟从 19.52 秒增至 34.62 秒，变成约 1.77 倍[2]。这类量级的延迟代价必须摆到台面上，和收益一起比较。
- **什么情况下不值得上**：查询本身已经是结构化的精确检索（订单号、型号查询），重写只会引入噪声；对延迟极敏感的场景，多一次改写调用可能得不偿失。
  HyDE 原论文并未把“生成内容可能有事实错误”称为风险，而是把它当作被编码器过滤掉的可接受噪声。“HyDE 对精确事实类查询有幻觉风险”是社区实践观察，不是论文原文结论。写查询重写的局限时，不要把这条包装成论文结论。

**② 混合检索（BM25 + 向量）**

- **为什么需要**：向量检索擅长语义相近但用词不同的匹配，BM25（经典稀疏检索，基于词频统计）擅长精确关键词命中，两者互补。纯向量检索经常在专有名词、编号类查询上失手，纯 BM25 又找不出语义相近但用词完全不同的段落。
- **怎么实现**：主流向量数据库都提供原生混合检索接口。以 Qdrant 为例（`qdrant-client` 1.19.0），创建集合时同时声明 dense 与 sparse 两路向量配置，检索时用 `Prefetch` 分别取各自 top-N 候选，再在顶层用融合查询合并。**注意 Qdrant 1.16.0 起已移除 `search()`/`recommend()` 等旧方法（非仅弃用警告），必须使用 `query_points()`**[5]。
- **怎么验证有效**：分别测纯向量、纯 BM25、混合三种配置在黄金集上的 Recall@k，混合检索通常在两类查询（语义相似 + 精确关键词）上都不明显劣于单路最优。
  “混合一定比单路都好”是不是过强的预期，取决于查询群体。如果客户的查询几乎都偏向同一类，混合能做到不劣于最优单路就该收手。只有当两路检索器的失败集确实不相交时，混合才可能同时超过两者。
  Lab-04 在一份刻意构造成两类查询各占一半的语料上，量到混合 58/59、纯向量 53/59、BM25 54/59，同时超过两个基线。但那份语料是为此专门设计的：**先量你自己的查询分布，再决定该拿哪条标准要求混合**。
- **什么情况下不值得上**：知识库本身就是短小的结构化记录（如商品 SKU 表），BM25 单独已经够用。查询几乎不含专有名词或编号（纯自然语言问答）时，向量检索单独可能已经接近混合检索效果。这时多一路稀疏检索，增加的是索引维护成本而非明显收益。

**③ RRF 融合（Reciprocal Rank Fusion）**

- **为什么需要**：多路检索器返回的分数量纲不一致（向量相似度和 BM25 分数不能直接相加），RRF 只用排名不用绝对分数，天然规避了分数校准问题。
- **怎么实现**：公式 `RRF(d) = Σ_{r∈R} 1/(k+r(d))`，R 是检索器集合，r(d) 是文档 d 在检索器 r 结果中的排名（从 1 开始），k 是平滑常数[3]。**k 值不是普适常数，不同厂商默认值差异巨大**：Elasticsearch 的 `rank_constant` 默认 **60**[4]，Qdrant 的 RRF 默认 k=**2**[5]，两者相差 30 倍——k 越小，头部排名结果的权重占比越高。跨厂商照搬默认参数是常见错误，接入新的检索后端时要先确认它自己的 k 默认值。
- **怎么验证有效**：对比融合前各单路排名与融合后排名，在黄金集上看融合排名的 nDCG 是否优于任一单路。如果融合后效果不如某一路单独检索，先查三件事：
  - **是不是在两路的完整排序上做的融合。** 应各取 top-K 截断后再融合，否则一路排第 1、另一路排第 800 的文档仍能靠前者挤掉正确答案。Lab-04 实测中，这一处改动就是混合从“永远夹在两个基线中间”到“同时超过两者”的分界。
  - k 值是否合适。
  - 某一路的召回质量本身是不是有问题。

  这三条都不是 RRF 方法本身失效。
- **什么情况下不值得上**：只有一路检索器（纯向量或纯 BM25 单路），没有融合的必要；候选池已经很小（个位数到十几篇），排名合并的边际价值有限，直接精排即可。

**④ Rerank（精排）**

- **为什么需要**：第一阶段检索（向量/BM25/RRF 融合）为了速度，普遍用双塔结构或稀疏统计，排序精度有限。Rerank 用 Cross-Encoder 对 query-document 对做联合编码，精度更高但更慢，适合对候选池做二次精排，而不是替代第一阶段。
- **怎么实现**：常见做法是第一阶段召回 top-N（N 取决于成本预算），送入 Cross-Encoder 逐一打分后重新排序，只把 top-k 最终结果送进生成阶段。
- **怎么验证有效**：Elastic Search Labs 用 BM25 + BEIR 统一测了 6 款 reranker，给出两条可操作经验：量级上，rerank 到约百个文档即可拿到大部分收益、继续加深收益递减，浅层 rerank（top 30 级）也已有可观的 nDCG@10 提升[8]。这是一篇有署名的工程博客，方法论公开——但其具体 URL 本书调研时未存档一手核实，且 Elastic 自身也卖 reranker 产品，存在潜在利益关联，**故此处只转述量级方向，不引它的具体百分比**。
  **benchmark 数字跨厂商/论文不可直接比较。** 同一个 bge-reranker-v2-m3 模型，jina-reranker-v3 论文测得 BEIR nDCG@10 为 **56.51**[6]（注意这篇论文是 jina-reranker-v3，不是 jina-embeddings-v3，也不是 Jina Reranker v2，三者命名接近极易混淆），NVIDIA 论文测得同一模型平均 nDCG@10 为 **0.6585**[7]，跨论文分数差 9 个点以上。这说明分数高度依赖评测集、第一阶段检索器和 rerank depth 的具体配置，选型时不要直接把不同论文的数字并排比较。
- **什么情况下不值得上**：候选集本身只有个位数到十几篇时，rerank 的边际收益低，应优先查第一阶段召回质量。高 QPS/延迟敏感场景下，加一次 Cross-Encoder 调用的延迟代价可能超过收益，此时应选更小的 rerank 模型（如 MiniLM 级）或降低 rerank 深度，而不是直接放弃精排。Cohere 官方也不公开“候选集小于多少不值得 rerank”的阈值，建议用 30–50 条自己的代表性查询实测标定。

**⑤ CRAG 自纠错（Corrective RAG）**

- **为什么需要**：前四环解决的都是“怎么找得更准”，没有解决“找错了怎么办”。检索到的文档可能整体不相关、部分相关，或者知识库本身就没有覆盖这个问题。生成阶段如果对此毫无察觉，会拿错误或不相关的上下文强行生成一个看似自信的答案。
- **怎么实现**：CRAG 原论文（arXiv:2401.15884）用一个轻量级微调评估模型对检索文档打相关性置信分，设上下两个阈值做三分类。这个评估模型仅 0.77B 参数，远小于 Self-RAG 用的 7B critic。三档的处理方式分别是[9]：
  - 高于上阈值判定 **Correct**，触发 Knowledge Refine：把文档分解为细粒度“knowledge strip”，逐条打分过滤无关片段再拼接，避免噪声段落污染上下文。
  - 低于下阈值判定 **Incorrect**，丢弃检索结果，转而触发 Web Search。
  - 介于两者之间判定 **Ambiguous**，Knowledge Refine 与 Web Search 两者结合。

  原论文消融实验显示，去掉 Ambiguous 只做二分类，会因评估模型的判断误差导致效果明显下滑。三分类是一个经过验证的“软性折中”设计，不是随意加的第三档。
- **怎么验证有效**：CRAG 论文自测在 PopQA/Biography/PubHealth/Arc-Challenge 四个数据集上相比原始 RAG 有明显提升，**但这是论文作者自测数字，非第三方复现**[9]。
  2026 年出现的开源复现研究，用 Wikipedia API 替代原论文的 Google Search API，用 Phi-3-mini 替代 LLaMA-2。摘要确认复现管线达到“comparable performance”。这项研究还用 SHAP 可解释性分析发现“evaluator 主要依赖命名实体对齐而非语义相似度”，同时指出在科学类问题上存在领域迁移局限[10]。这是目前能找到的、对 CRAG 效果做独立验证的最接近“第三方复现”的证据，但复现论文没有给出可直接对比的精确数字。
- **什么情况下不值得上**：知识库覆盖度高、检索命中率本身已经很稳定的场景，三分类评估模型带来的额外调用和延迟可能得不偿失。引入 Web Search 兜底还意味着系统对外部网络有依赖。内网/离线部署场景需要用备选的兜底策略（如降级为“无法回答，转人工”）替代 Web Search 分支，而不是原样照搬论文设计。

**一个容易被搞混的引用陷阱**：讲 RAG 失败模式时常用的“七种失败模式”清单（missing content / search failure / context window limitations / poor answer generated by the LLM / incorrect output format / vague answers / incomplete answers），**逐字出自 IBM 论文（arXiv:2410.12812）对 Barnett et al. 的转述，不是 Barnett 原论文（arXiv:2401.05856）自己使用的标签**。

Barnett 原文的七类失败点正式名称是 FP1 Missing Content / FP2 Missed the Top Ranked Documents / FP3 Not in Context / FP4 Not Extracted / FP5 Wrong Format / FP6 Incorrect Specificity / FP7 Incomplete[11][12]。两套措辞只有 FP1、FP7 概念基本对应，其余差异较大。

设计 RAG 故障归因体系时可以直接借用 IBM 这版更直白的措辞，但引用来源要写清楚是“IBM 论文对 Barnett et al. 的复述”，不要冒充 Barnett 原文。这个区分在第 9 章已详细展开，这里不重复列对照表，只提醒容易混淆的地方。

## 7.4 RAG 之外

“上下文够长就不需要 RAG 了”是一句流传很广但被过度简化的说法。三篇独立论文拼出来的实证图景是这样的：

- **长上下文（LC）在资源充足时质量确实持续优于 RAG。** 一项对比研究显示 LC 平均领先 RAG 7.6%（Gemini-1.5-Pro）、13.1%（GPT-4O）、3.6%（GPT-3.5-Turbo），且越新的模型优势越明显。但同一研究在 ∞Bench 两个更长数据集上，GPT-3.5-Turbo 场景下 RAG 反而超过 LC，说明“越长越该用 LC”也不是单调成立的规律[15]。
- **没有单一规则能一刀切。** 另一项覆盖 7 个开源 + 4 个闭源模型、2326 个测试用例的研究给出更直接的结论：RAG 与 LC 之间的最优选择“取决于模型参数规模、长上下文能力、上下文长度、任务类型、检索片段特征的复杂交互”[16]。
- **“越长越好”被进一步证伪。** Databricks 团队对 20 个主流模型在 2000–128000 token 区间的系统测试显示，多数模型在超过 64k token 后无法维持稳定准确率，只有少数最新的旗舰模型能做到[18]。

三篇论文合在一起指向同一个可执行结论：**不是二选一，是按查询路由。** 能用检索窗口回答的查询走 RAG（省钱），检索质量存疑或需要跨文档综合的查询才升级到 LC。

前述对比研究提出的 Self-Route 方法，用模型自我判断某条查询是否用短上下文就能回答，实测能在保持效果的同时把成本降低 65%（Gemini-1.5-Pro）、39%（GPT-4O）。背后原因是六成以上的查询里 LC 和 RAG 给出的答案本就相同，此时硬塞长上下文纯属浪费[15]。

这条思路也不是唯一方向。另有研究把“长上下文能力”直接吸收进 RAG 检索单元本身，把检索粒度从传统百词级小段落放大到 4K token 级“长检索单元”，在无需训练的情况下于 NQ/HotpotQA 上达到与全量微调 SOTA 相当的效果[17]。这说明长上下文技术可以被吸收进 RAG 架构内部，而不是与 RAG 对立的替代品。

还有研究表明，在长上下文 LLM 上做推理算力的合理扩展（迭代检索、上下文学习等策略），相比标准 RAG 最多能带来 58.9% 的效果提升[19]。这条路径本质上是“用更贵的推理换更好的效果”，需要按预算判断值不值。

**GraphRAG：解决的是“全局归纳”问题，不是“检索不准”问题。**

微软原始论文明确指出，普通向量 RAG 擅长事实性、局部性问题，但面对“这个数据集的主要主题是什么”这类需要理解整个语料库的全局归纳性（sensemaking）问题会失效。这类问题本质是查询聚焦的摘要任务，不是显式检索任务[13]。

机制上，GraphRAG 从源文档抽取实体知识图谱，用 Leiden 社区检测算法对图做层级分区，自底向上为每层社区生成摘要。查询时每个相关社区摘要独立生成部分回答，再归约为最终答案[13]。

效果上，论文自测（125 道问题、5 次重复取平均，p<.001/p<.01 显著性检验）显示，全局检索方法相比向量 RAG 基线的综合性胜率达 72%–83%，多样性胜率 62%–82%。代价是向量 RAG 在“直接性”（更简洁）上仍占优。成本上，根层级社区摘要相比全文摘要能节省超过 97% 的 token，同时仍保持相对向量 RAG 的胜率优势，这是论文给出的“性能-成本平衡点”[13]。

**需要区分清楚的是**：原始论文本身没有使用“Local Search”这个正式术语，只对比了“全局方法”与向量 RAG 基线。Local/Global/DRIFT/Basic Search 是微软后续把 GraphRAG 产品化为开源库后，在官方文档里新增的查询模式术语：Local Search 适合理解文档中具体实体的问题，DRIFT Search 是把社区信息融入 local search 起点的后续改进[14]。写作或选型时不要把产品化库的新功能说成是原论文的实验结论。

**Agentic Retrieval：把检索变成一个可迭代的决策过程。** 前两条路线（长上下文、GraphRAG）都是“一次性”策略：检索一次或摘要一次就交给生成。

Agentic Retrieval 的思路不同，让一个 agent 循环执行“判断当前信息是否足够 → 不够就再检索/再分解子问题 → 综合结果”，直到信息足够或达到迭代上限。这正是 §7.6 LangGraph 循环拓扑要处理的编排问题。

它适合需要多跳推理、单次检索无法覆盖全部证据的复杂问题。代价是每一跳都是一次额外的模型调用和检索开销。迭代次数如果不设上限，会退化成 §7.7 要专门处理的“死循环”故障。

这条路线目前没有本书能找到的、具有可比性的公开量化基准数字，本节只给出机制性描述，不编造具体效果数字。机制上大致对应 §7.6 循环拓扑的一个具体实例：

```python
# 示意性骨架，未经实测验证，不要直接用于生产
def should_continue_retrieval(state) -> bool:
    if state["iteration"] >= state["max_iterations"]:
        return False  # 硬性上限，防止 §7.7 的死循环故障
    return not is_sufficient(state["collected_evidence"], state["query"])

def retrieve_more(state) -> dict:
    sub_query = decompose_next_subquery(state["query"], state["collected_evidence"])
    new_docs = hybrid_retrieve(sub_query)  # 复用 §7.3 的混合检索+RRF+Rerank 全链路
    return {
        "collected_evidence": state["collected_evidence"] + new_docs,
        "iteration": state["iteration"] + 1,
    }
```

`is_sufficient` 的判断逻辑（比如“已收集证据能否覆盖问题的所有子维度”）本身可以是一次轻量模型调用，也可以是规则化的覆盖度检查。判断逻辑越可靠，循环收敛得越快。`max_iterations` 是防止判断逻辑失灵时系统仍然安全退出的最后一道防线，两者缺一不可。

**三条路线的选型对照**。判断起点是问题类型，不是团队手头恰好会用哪种技术：“我们已经有 GraphRAG 的经验，这次也用它”是常见的反面决策路径。

| 路线 | 适用条件 | 成本特征 | 不适用场景 |
|---|---|---|---|
| 长上下文直塞 | 模型足够新且长上下文能力强；查询需要跨段落综合 | 单次调用 token 成本高，且多数模型超过 64k token 后准确率不稳定[18] | 查询本身能被检索窗口覆盖时纯属浪费；模型长上下文能力弱时收益不确定 |
| GraphRAG | 全局归纳性问题（“主题是什么”“几大类”），非具体实体事实查询 | 索引构建成本高（图谱抽取+社区检测+分层摘要一次性投入），查询期用根层摘要可大幅省 token[13] | 具体实体事实查询用 Local Search 或普通 RAG 更合适；索引构建的一次性成本对小知识库不划算 |
| Agentic Retrieval | 需要多跳推理、单轮检索证据不完整 | 按迭代次数线性增长的调用与检索开销，需要硬性迭代上限 | 单轮检索已能覆盖答案的简单问答场景，迭代反而增加延迟和出错面 |

三条路线不互斥，可以组合：用 GraphRAG 处理全局归纳类查询，用混合检索 RAG 处理事实类查询。再用 Agentic Retrieval 的循环机制去编排“先判断问题类型、再路由到对应策略”这件事本身。

## 7.5 MCP 深讲

MCP（Model Context Protocol）解决的是“每接一个数据源/工具就要写一套定制适配代码”的组合爆炸问题。客户端（Host，如 IDE 插件、聊天应用）通过统一协议连接任意数量的 Server，每个 Server 把自己的能力（工具、资源、提示词模板）用标准化方式暴露出去。客户端不需要为每个数据源单独写集成代码。

**版本现状必须先说清楚，否则代码会直接跑不起来**。当前协议规范版本是 `2026-07-28`，Python SDK 包名 `mcp`，当前版本 **2.0.0**。这个版本距今仅约十天，属于极新版本[20]。

**官方 README 明确警告**：“Since `pip install mcp` now installs 2.x, keep a `<2` upper bound on your requirement (for example `mcp>=1.28,<2`) until you've migrated”[21]。

不加版本上界直接 `pip install mcp`，装到的是 2.x。而市面上大多数教程代码是针对 1.x 的 `FastMCP` 写的，直接照抄会报 `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`。v2 中 **`FastMCP` 已重命名为 `MCPServer`**，导入路径从 `mcp.server.fastmcp` 变为 `mcp.server.mcpserver`：

```python
# v1（旧，市面上大多数教程用的版本）
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("Demo")

# v2（当前，2026-07-28）
from mcp.server.mcpserver import MCPServer
mcp = MCPServer("Demo")
```

`@mcp.tool()` / `@mcp.resource()` / `@mcp.prompt()` 装饰器签名在 v1→v2 未变[21]，大部分业务逻辑代码不用改，只需要改导入路径和类名。但外部 MCP host（Claude Desktop、各类 IDE 插件）是否已跟进支持 v2 的新机制，本书未核实到官方口径，存在真实的生态兼容风险[21]。

本书就此拍板：Lab-03 锁定 `mcp==2.0.0`。理由不是 v2 更好，而是 `pip install mcp` 不加版本号时装的就是它（2026-08-08 实测，装到 2.0.0）。读者照着任何一篇没写版本号的教程走，都会落在这条线上。与其绕开，不如把“锁版本”本身当成要教的东西。

同一次实测里，`import mcp.server.fastmcp` 报 `ModuleNotFoundError`，而 `mcp.server.mcpserver.MCPServer` 与 `mcp.server.MCPServer` 都存在。这正是前面说的那个陷阱的实际形态。

但这个选择有前提：Lab-03 用的是进程内客户端，不经过外部 host。如果你的交付要接 Claude Desktop 或 IDE 插件，先实测目标 host 支持到哪个规范版本，再决定锁 v2 还是锁 `mcp>=1.28,<2`。这一步没有官方兼容矩阵可查，只能自己测。版本决策必须落在实测上，不能靠“应该兼容吧”推断。

**传输层现状**：

- **stdio** 是核心标准传输，未受影响。
- **HTTP+SSE**（2024-11-05 版本的旧传输）“自 2025-03-26 版协议起已弃用”，新实现不应再采用[20]。
- 接替它的 **Streamable HTTP** 在 2026-07-28 版本本身又发生了破坏性调整：移除了 GET stream endpoint，移除了协议级 session（不再有 `Mcp-Session-Id`，也不再支持断线续传）[20]。

如果 Lab 或生产代码里的 host 端假设了旧的 session 机制，升级到 2026-07-28 规范会直接失效。

**Server 设计**：一个 MCP Server 暴露三类能力——工具（Tool，模型可调用的函数）、资源（Resource，模型可读取的数据，通过 URI 模板如 `greeting://{name}` 定位）、提示词模板（Prompt，预置的对话模板）。

设计原则是每个工具边界清晰、单一职责，不要把“查询+下单+发通知”揉进一个工具里。这样模型才能在恰当的时机只调用需要的那一步，出错时也容易定位是哪个工具的问题。

**鉴权桥接**：MCP 协议本身不规定具体鉴权方案。Server 桥接遗留系统时通常要处理两层认证：

- 客户端到 MCP Server 这一层，可以用标准的 API Key/OAuth2；
- MCP Server 到背后遗留系统这一层，可能是遗留系统专有的 mTLS 证书或内部 token 机制（第 4 章企业集成与协议桥接已详细展开这部分）。

桥接的关键是让模型侧完全不感知遗留系统的认证细节。工具函数内部完成凭据获取和刷新，模型只看到“调用成功/失败”这个抽象层。

桥接层的工具函数骨架大致长这样。模型侧只调用 `get_order_status`，凭据获取、刷新、遗留系统专有的认证细节全部封装在工具函数内部：

```python
# 摘自 Lab-03 src/server.py，verify.sh 8/8 实测通过
import functools
import inspect
from typing import Any

from mcp.server.mcpserver import MCPServer

def _guard(fn):
    """工具层兜底：任何异常都翻成结构化返回，绝不让它穿过 MCP 边界。

    functools.wraps 不只是为了好看——MCP 靠 inspect.signature 反推 input_schema，
    它会跟着 __wrapped__ 找回原函数。少了这一步，入参 schema 会退化成
    {args, kwargs}，模型就再也传不对 order_id 了。
    """
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        try:
            return fn(*args, **kwargs)
        except BridgeFailure as exc:          # 桥接层已归类好的失败
            return exc.failure.as_dict()
        except Exception as exc:              # 这里就是要兜住一切
            return Failure(
                "bridge_internal_error",
                f"桥接层内部错误（{type(exc).__name__}），已被拦截未影响会话。"
                "请联系桥接层维护者；直接重试大概率仍会失败。",
                retryable=False,
            ).as_dict()
    # docstring 会原样成为工具描述送进模型上下文，缩进必须先剥掉
    wrapper.__doc__ = inspect.cleandoc(fn.__doc__ or "")
    return wrapper

srv = MCPServer(
    name="erp-bridge",
    instructions=(
        "本 Server 桥接客户的遗留 ERP。所有工具都已在服务端完成身份鉴权，"
        "你不需要、也无法提供任何凭据。approve_order 是不可逆操作，"
        "仅在用户明确授权时调用。"
    ),
)

@srv.tool()
@_guard
def get_order_status(order_id: str) -> dict[str, Any]:
    """查询单个 ERP 订单的当前状态（完整工具描述见 §7.5 正面示例）。"""
    oid = _normalize(order_id)
    if oid is None:
        return _bad_order_id(order_id)
    row = erp.get_order(oid, timeout=TIMEOUT_QUERY)   # 证书、重试、熔断都在 erp 里
    return {"ok": True, "order_id": row.get("ORDER_ID"),
            "status": row.get("STATUS"), "eta": row.get("ETA")}
```

注意工具签名里没有任何凭据参数。证书路径、超时预算、退避策略全在 `erp` 这个客户端对象内部，模型侧看到的入参只有 `order_id` 一个。Lab-03 的验收脚本会直接扫描工具的 `input_schema`，出现 `token`/`cert`/`key` 一类字段就判失败。这条边界值得用机器来守，因为人写着写着就会为了“调试方便”把它捅破。

工具函数向模型返回的永远是结构化的 `{"error": ..., "retryable": ...}`，而不是把 `LegacyTimeoutError`/`LegacyAuthError` 这类底层异常直接抛出去。模型看到的是“要不要重试”这个业务语义，不需要理解遗留系统的异常类型体系。

顺带一条实测结论：如果工具函数需要框架注入的 `ctx: Context` 参数（取进度上报、日志句柄），它不会出现在工具的入参 schema 里——`list_tools` 返回的 `input_schema.properties` 只有业务参数。模型看不到它，也不会试图给它传值；上面的骨架不需要它，所以没带。

**两个命名陷阱**（2026-08-08 实测 `mcp` 2.0.0）：MCP 规范文档里的字段名是驼峰的 `isError` 和 `inputSchema`，Python SDK 用的却是蛇形的 `is_error` 和 `input_schema`。照规范文档写 `tool.inputSchema`，会直接抛 `AttributeError: 'Tool' object has no attribute 'inputSchema'`。这个还算好，报错够响亮，跑一次就发现了。

真正危险的是另一个。如果你在客户端侧用了 `getattr(result, "isError", False)` 这种看起来很稳妥的防御式写法，工具真出错时会静默取到 `False`，被当作调用成功一路传下去。模型拿着一段错误文本当业务结果继续推理。

带默认值的 `getattr` 在字段名写错时不会报错，只会给出一个“一切正常”的假象，这类静默失败比崩溃难查得多。判断成败请一律用 `is_error`：实测中它在入参校验失败时为 `True`，错误详情落在 `content[0].text`。

**不要拿 `structured_content` 是不是 `None` 来判断成败。** 它是不是 `None`，取决于你的返回类型标注写没写全：

| 工具的返回标注 | 是否生成 `output_schema` | **调用成功时**的 `structured_content` |
|---|---|---|
| `-> dict` | 否 | `None` |
| `-> dict[str, Any]` | 是 | `{"status": "shipped", ...}` |

裸 `dict` 不带元素类型，SDK 推不出输出结构，于是成功调用也拿不到 `structured_content`，结果只以 JSON 文本落在 `content[0].text` 里。这条写在这里是因为它专坑一种人：照着骨架把返回标成裸 `dict`，又用 `structured_content is None` 区分成败。两种情况都是 `None`，所有调用都会被判成功。本书后面所有 MCP 工具的返回标注都写成 `dict[str, Any]`，就是为了避开这个。

还有两处在写工具装饰器时会静默坑人的地方，都是 Lab-03 实现过程中踩出来的：

- **包装工具函数时必须加 `functools.wraps`。** MCP 靠 `inspect.signature` 反推 `input_schema`，`functools.wraps` 会留下 `__wrapped__` 让它找回原函数。少了这一步，实测中工具名会变成内层函数名 `inner`，入参 schema 退化成 `{args, kwargs}`。`list_tools` 照常返回工具，看起来一切正常，只是模型再也传不对参数了。
- **docstring 要过一遍 `inspect.cleandoc`。** SDK 不会替你去掉缩进，函数体里那几个空格会原样进入模型上下文。

**容错降级**：遗留系统响应慢或超时是 MCP Server 包装遗留 API 时的常态，不能让一次超时拖垮整个 Agent 会话。三层兜底：

- **工具函数级**：内部设置合理超时并捕获异常，返回结构化的错误信息，而不是让异常直接抛到模型侧。模型看到清晰的错误信息才能决定重试还是换路径，这也是 §7.7“工具调用失败”防御的具体落地。
- **Server 级别做熔断**：某个下游遗留接口连续失败达到阈值后临时熔断，直接返回“服务暂不可用”，而不是让每次调用都空等到超时。
- **Host 级别对 Server 本身的健康状态做探测**：一个 Server 挂了不应该影响其他 Server 的正常工作。

**工具描述的写法直接决定调用准确率**，这是最容易被忽视但影响最大的一环。模型没有读过你的代码，它只能根据工具名、docstring、参数说明来判断什么时候调用、怎么传参。

```python
# 反面示例：模型很难判断这个工具什么时候该用、参数怎么填
@srv.tool()
def query(id: str) -> dict:
    """查询数据。"""
    ...
```

这个反面示例有三处硬伤：

- 工具名 `query` 没有说明查询的是什么对象；
- docstring 只有四个字，没说明 `id` 是订单号、用户 ID 还是别的什么，也没说明返回结构；
- 没有给出典型调用场景或边界条件，比如 id 不存在时会发生什么。

模型面对这样的工具描述，要么瞎猜参数格式导致调用失败，要么干脆放着不用。

```python
@srv.tool()
@_guard
def get_order_status(order_id: str) -> dict[str, Any]:
    """根据订单号查询订单当前状态。

    适用场景：用户询问"我的订单到哪了""什么时候发货"等具体订单状态问题。
    不适用：用户想查询的是商品库存或退款进度，这两类请分别调用
    check_inventory / get_refund_status 工具。

    Args:
        order_id: 订单号，格式为 "ORD-" 开头的字符串，例如 "ORD-20260317-001"。
                  可以从用户消息中直接提取，也可以先调用 lookup_order_id_by_phone
                  工具根据手机号反查。

    Returns:
        dict，包含 status（枚举值：pending/shipped/delivered/cancelled）、
        estimated_delivery（预计送达日期，若已送达则为 null）、
        tracking_number（物流单号，若尚未发货则为 null）。
        若 order_id 不存在，返回 {"error": "order_not_found"}，不要重试，
        应提示用户确认订单号。
    """
    ...
```

正面示例把“什么时候用”“什么时候不用”“参数从哪来”“返回值什么结构”“错误怎么处理”都写清楚了。这些信息在代码里对人类读者可能是显而易见的（看函数名和类型标注就懂），但对模型来说，docstring 就是它能看到的全部上下文。

工具集变大之后（十几个甚至几十个工具），工具之间“什么时候该用哪个”的边界描述，重要性不亚于单个工具内部的参数说明。上面反面例子里缺失的“不适用场景”这一段，恰恰是多工具场景下模型选错工具的高发原因。

**工具不可逆时，“不适用”那一段要比“适用”那一段写得更长。** 查询工具选错了，代价是多一次无谓调用；审批工具选错了，代价是一笔钱批出去、且没有撤销手段。Lab-03 里 `approve_order` 的描述是这么写的：

```python
@srv.tool()
@_guard
def approve_order(order_id: str) -> dict[str, Any]:
    """提交订单审批，把订单状态从待审批推进到已审批。

    【这是不可逆操作】审批一旦提交，本工具没有任何撤销手段，钱就批出去了。
    误触发一次就是一起事故，不存在“重试一下就好”这种说法。

    适用场景：仅在用户**明确表达审批授权**时调用。判断标准是：说话人自己是决策人，
    且句子的动词直接指向“批准”这个动作。例如“ORD-20260317-002 审批通过，你直接
    批了吧”“我同意，走审批”“批准这一单”。

    不适用（这段比上一段重要）：模糊表述不构成授权。以下情形一律不要调用本工具——
    - “帮我把 ORD-20260317-002 处理一下”：“处理”语义模糊，不是审批授权；
    - “这单怎么还没动静／是不是卡住了”：这是在问进度，请改用 get_order_status；
    - “客户说 ORD-20260317-002 的审批都走了三天了”：这是转述他人抱怨，
      句中的“审批”是名词不是授权，请改用 get_order_status 或 add_order_note；
    - 用户只是提到了“审批”这个词，却没有说他同意、批准或让你去批。
    遇到上述情形，正确做法是先查状态或记备注，再请用户明确确认是否要审批。
    宁可多问一句，不可擅自批准。
    """
```

关键是那三条**带反面例句的**排除项。只写“仅在明确授权时调用”是不够的：模型对“什么算明确”的理解和你不一定一致，而例句把这条边界钉死了。

Lab-03 用 10 条自然语言请求实测，其中 3 条是上面这类诱导性表述。DeepSeek 的工具选择结果是 10/10 正确、危险工具零误触发，连测三轮稳定。

这个数字要谨慎解读：它说明**在这套描述下、对这个模型、这 10 条用例**成立，不是“这样写就绝对安全”的保证。真正该记住的是方法：把危险工具的误触发做成一条可重复运行的检查，而不是靠人读一遍描述觉得“应该没问题”。Lab-03 的验收脚本对这一项不设通过率门槛：其余用例允许 8/10，危险项一次误触发就判失败。不可逆操作没有“通过率 90%”这种说法。

## 7.6 LangGraph 多智能体

LangGraph（当前稳定版本 `1.2.10`）把 Agent 编排建模成一张显式的图。节点是执行单元（可以是模型调用、工具调用、普通函数），边是控制流转移，状态在节点之间流动并可持久化。

相比“一个大 prompt 让模型自己决定下一步做什么”，显式图的好处是控制流是可审查、可测试、可断点恢复的代码，而不是藏在模型输出里的隐式决策。

**四种拓扑模式**：

```{=latex}
\fdfig{\fdtopologies}
```

- **顺序**：固定流水线，每一步的输出是下一步的输入，对应 §7.1 的提示链思路，适合任务边界清晰、步骤间无需动态决策的场景。
- **分支**：路由节点根据状态做条件判断，把执行流导向不同分支，适合“先分类任务类型，再按类型走不同处理路径”的场景。
- **循环**：节点反复执行直到满足终止条件，适合 §7.4 Agentic Retrieval 这类“判断信息是否足够，不够就再来一轮”的场景。循环拓扑必须配合 §7.7 的迭代上限机制，否则它就是“死循环”故障的直接来源。
- **主管（Supervisor）**：一个主管节点协调多个专家子智能体，决定下一步交给哪个专家处理、什么时候收尾。适合的场景是任务需要拆分给不同专长的子智能体分别处理，又需要一个统一协调者判断整体进度。

**分支和主管容易混用，区分的关键是“决策是一次性的还是持续的”**：

- 分支拓扑的路由节点只判断一次，判断完就把控制权交出去，不再介入后续执行。
- 主管拓扑的协调节点在每个专家完成一步之后都会被重新调用，持续判断“接下来该轮到谁、任务是不是已经完成”。

如果一个任务只需要“先分类，再固定走一条路径处理到底”，用分支就够，没必要引入主管模式的持续协调开销。如果任务需要在多个专家之间反复切换，且切换逻辑依赖执行过程中才知道的中间结果，才需要主管模式。

把简单的分支场景过度设计成主管模式，是常见的“为了用框架的高级特性而增加不必要复杂度”的反例。

**状态设计**：LangGraph 推荐用 `TypedDict` 搭配 `Annotated[..., reducer_fn]` 定义状态 schema。reducer 函数决定多个节点写同一个状态字段时如何合并，例如消息列表用“追加”而不是“覆盖”[22]。

下面这版 StateGraph 骨架，是对官方 Multiple-schemas 示例的简化改写，去掉了原示例里 `InputState`/`OutputState`/`PrivateState` 的多 schema 拆分与类型标注：

> **可信度说明**：这不是“官方示例”，是笔者简化后的教学版本，本书未在官方文档页面找到与之逐字对应的简化版本。**Lab 实现时必须先实测冒烟验证**，不要直接照抄进生产代码。

```python
# 示意代码，简化自官方文档，未逐字核对，Lab 实现前须实测冒烟验证
from typing import TypedDict
from langgraph.graph import END, START, StateGraph

class OverallState(TypedDict):
    foo: str
    bar: str
    user_input: str
    graph_output: str

def node_1(state) -> dict:
    return {"foo": state["user_input"] + " name"}

def node_2(state) -> dict:
    return {"bar": state["foo"] + " is"}

def node_3(state) -> dict:
    return {"graph_output": state["bar"] + " Lance"}

builder = StateGraph(OverallState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_node("node_3", node_3)
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
builder.add_edge("node_2", "node_3")
builder.add_edge("node_3", END)

graph = builder.compile()
graph.invoke({"user_input": "My"})
```

**checkpointer 持久化**：图的状态默认只存在于单次 `invoke` 调用的生命周期里。要支持“暂停后恢复”“跨会话保留状态”，必须在 `.compile(checkpointer=...)` 时传入一个 checkpointer 实例：调试用 `InMemorySaver`，生产用 `SqliteSaver`/`PostgresSaver`。后两者是独立 PyPI 包 `langgraph-checkpoint-sqlite`、`langgraph-checkpoint-postgres`，不随主包安装，需要显式声明依赖[22]。

三者的选择不只是“调试用内存、生产用数据库”这么简单。单机部署、状态量不大、不需要跨进程共享时，SQLite 够用且运维成本最低。多实例水平扩展、需要多个 worker 进程共享同一批会话状态时，必须用 Postgres 这类支持并发访问的方案——SQLite 的文件锁机制在高并发写入下会成为瓶颈。



**用 `interrupt()` 实现人在回路**：官方明确写了**静态中断（`interrupt_before`/`interrupt_after` 编译参数）不推荐用于人在回路场景**，原文是“静态中断不推荐用于人在回路的工作流，请改用动态中断函数。”[23] 静态中断仍然是 `compile()` 的合法参数，但定位是调试/测试用的断点，不是动态人机交互机制。

当前推荐机制是在节点函数内部调用 `interrupt(value)`：首次调用时抛出可恢复异常，暂停图执行并把 `value` 暴露给客户端。恢复执行时，`interrupt()` 的返回值就是调用方传入的 resume 值。

**这个机制依赖 checkpointer 才能工作。** 源码 docstring 原文写明“要使用中断，必须启用检查点，因为这个特性依赖于把图状态持久化下来”，没有 checkpointer 直接调用会报错[22]：

```python
# 示意代码，节点函数体逐字摘自官方文档，调用方式为笔者据官方文字说明改写，未逐字核对
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph

def approval_node(state):
    approved = interrupt("Do you approve this action?")
    return {"approved": approved}

# ... builder.add_node("approval_node", approval_node) 等图构建省略 ...
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "thread-1"}}
graph.invoke({"input": "data"}, config=config)       # 命中 interrupt 后暂停
graph.invoke(Command(resume=True), config=config)     # 恢复执行，resume 值成为 interrupt() 的返回值
```

**恢复机制的两条路径**：

- `invoke() + Command(resume=...)` 是官方称的默认恢复路径，适合请求-响应式的调用场景。
- 需要实时展示中间过程的场景才用 `stream_events()`，其返回对象通过 `.interrupts`/`.interrupted`/`.output` 属性暴露中断状态[23]。

选哪条路径取决于前端是否需要流式展示，不是任意二选一。用 `stream_events()` 的复杂度明显更高，没有流式展示需求时用 `invoke()` 就够了。两条路径最终都要落到 `Command(resume=...)` 这一套恢复语义上，不存在“流式场景就不需要 resume 机制”这种误解。

**一个容易踩的坑**：`interrupt()` 恢复是按节点内调用顺序（index-based）匹配的，同一节点内多次调用要保证顺序稳定。单次 resume 后节点会从头重新执行，节点如果有副作用（写库、调外部 API），需要做幂等设计，否则恢复执行会把副作用重复执行一遍[22]。

另外，`langgraph.prebuilt.create_react_agent` 已在 v1 迁移指南中标记弃用，应改用 `langchain.agents.create_agent`（注意这是 `langchain` 主包而非 `langgraph`）[24]。新写的多智能体代码不建议再引用 `prebuilt` 模块。

## 7.7 Agent 可靠性工程

单次模型调用出错，最坏结果是一次错误回答。Agent 把多次调用串成自主决策的循环，出错模式会被放大：一次工具调用失败可能触发连锁重试，一次状态误判可能让后续所有步骤都建立在错误前提上。

下面四类故障是生产 Agent 系统里最常见、也最容易被低估的失效模式。

> **可信度说明**：对应的防御手段以“工程归纳”为主，本书未找到对应的学术实证研究支撑具体阈值，需要按自己系统的实际故障率标定。

**① 工具调用失败**：网络超时、下游服务限流、参数不合法都会导致工具调用失败，这是四类故障里最“正常”的一类。重点不是消除它，是让 Agent 能够区分失败类型并做出不同反应。至少要区分三种失败：

- **可重试的瞬时失败**（超时、限流）：按 §7.1 讲的退避策略原地重试。
- **参数错误导致的确定性失败**（订单号格式不对）：重试没有意义，应该让 Agent 重新生成参数或转人工。
- **工具本身不可用**（服务下线）：应该降级到备选路径，或明确告知用户当前能力受限。

三类失败混在一起用同一套“重试 3 次就放弃”处理，会让确定性失败也浪费掉重试预算，而瞬时失败又可能重试次数不够。区分失败类型比统一加大重试次数更能解决根本问题。

**② 死循环**：§7.6 的循环拓扑和 §7.4 的 Agentic Retrieval 都依赖“判断是否完成，不完成就继续”这个机制。一旦终止条件设计有缺陷（比如判断逻辑本身依赖的信息永远不会满足），图会无限循环下去，白白消耗调用预算，直到触发外部超时或用户投诉。

防御手段：**硬性迭代上限是必选项，不是可选项。** 不管终止条件设计得多可靠，都要在图层面设置一个绝对不能超过的步数上限，超过后强制退出，转人工或返回已收集到的部分结果。上限触发本身要被记录和告警，而不是静默截断——静默截断的危险和本章 §7.1 说过的一个判断是同一个道理：悄无声息的错误比明确报错更难查。

**③ 状态漂移**：多智能体协作时，共享状态可能被某个节点的错误更新污染，后续节点在错误状态基础上继续决策。偏差逐步累积，又不像单次报错那样容易被立刻发现。这是 §7.2“提示链中间态污染下游”问题在多智能体场景下的放大版。

防御手段有三条：

- 状态更新走 reducer 函数，而不是任意覆盖。§7.6 `Annotated[..., reducer_fn]` 的设计初衷之一就是约束状态怎么合并，不让任意节点随意覆写关键字段。
- 关键状态字段的写入加轻量校验。比如“订单状态”字段只能是预定义的几个枚举值之一，写入非法值直接拒绝，而不是静默接受。
- 用 checkpointer 的持久化能力，定期或在关键节点做状态快照。出问题时能够回溯到具体是哪一步开始偏离预期，而不是只能看到最终的错误结果。

**④ 幻觉工具名**：模型有时会“发明”一个听起来合理但实际不存在的工具名去调用，尤其是在工具集很大、或者上下文里出现了容易联想到某个工具名的表述时。这属于 OWASP LLM Top 10 里 **LLM06（过度自治，Excessive Agency）** 风险的一种具体表现：系统给了模型超出其可靠决策能力的自由度[25]。

防御手段有三条：

- Host/Server 层面对工具调用请求做白名单校验。调用不存在的工具名时不能让请求穿透到下游，而是立刻返回明确的“工具不存在”错误，并引导模型重新选择。
- §7.5 强调的“工具描述要写清楚适用/不适用场景”本身就是预防手段之一。工具边界描述得越清楚，模型越不容易在多个相似工具之间产生混淆性的联想。
- 工具集过大（几十个以上）时，考虑分层暴露：先路由到工具类别，再在类别内选具体工具，而不是把所有工具平铺在同一层让模型一次性挑选。

**四类故障的检测信号与兜底动作汇总**：

| 故障类型 | 典型检测信号 | 防御手段 | 兜底动作 |
|---|---|---|---|
| 工具调用失败 | 超时、下游返回错误码、参数校验失败 | 区分瞬时/确定性/不可用三类失败分别处理，退避策略见 §7.1 | 达到重试上限后返回明确失败原因，不静默吞掉 |
| 死循环 | 步数超过历史正常分布上界、状态字段长时间不变化 | 硬性迭代上限（§7.6 循环拓扑必选项），上限触发要被记录 | 强制退出，转人工或返回已收集的部分结果 |
| 状态漂移 | 关键字段出现非预期枚举值、多节点写入冲突 | reducer 函数约束合并逻辑、关键字段写入校验、checkpointer 定期快照 | 回溯到最近一个合法快照，而非在错误状态上继续 |
| 幻觉工具名 | 调用请求指向白名单外的工具名 | 白名单校验、工具描述边界清晰（§7.5）、工具集分层暴露 | 拒绝穿透到下游，返回“工具不存在”并引导模型重选 |

这张表的价值不在于穷尽所有故障，是提供一个“发现问题该往哪个方向查”的索引。生产环境里四类故障经常混合出现，比如状态漂移触发了错误的工具调用，进而幻觉出一个不存在的工具名。排查时先按检测信号定位到最可能的根因类型，再顺着对应的防御手段链路去查，比从头排查整条调用链更快。

四类故障的共同点：**没有一种能被完全消除，只能把发生概率和影响范围压到可接受区间。** 这和第 9 章讲 LLM-as-Judge 三类偏差“缓解不是消除”是同一个工程原则。可靠性设计的落脚点不是追求“Agent 永远不出错”，是“Agent 出错时，系统知道它出错了，并且有一条不会把损失放大的退出路径”。

## 7.8 微调 vs RAG vs Prompt 决策表

三条技术路线解决的是不同层面的问题，这句话说起来是常识。但实际项目里最常见的错误恰恰是拿错了工具：知识本该放进检索库，却花几周去微调；措辞风格问题本该改 prompt，却直接上了 LoRA。

本节给的是一个判断框架，不是精确公式。具体项目该往哪个方向走，仍然需要结合黄金集上的实测效果（第 9 章方法论）做最终决定。

**三条路线各自解决什么问题**：

- **Prompt 工程（含 §7.1 的分层结构、提示链）**：解决“模型已经会，但没有被正确引导”的问题——格式不对、语气不对、没有按预期的推理步骤走。改动成本最低，一次迭代几分钟到几小时，且可以针对不同客户/场景动态切换，不需要重新训练。
- **RAG（含 §7.3/§7.4 的全链路）**：解决“模型不知道”的问题——私有数据、时效性信息、需要频繁更新的知识。知识变化时只需要更新检索库，不需要重新训练模型，这是 RAG 相比微调最大的运维优势。
- **微调（含 LoRA/QLoRA 这类参数高效微调）**：解决“模型知道，但表现方式或推理模式需要系统性调整”的问题。典型是特定领域的术语体系、特定任务的输出模式、需要模型“内化”而非“临时被告知”的行为模式。

**LoRA/QLoRA 什么时候才值得做**：微调不是“效果不好就微调”的万能升级路径。值得做的前提通常要同时满足：

- ① prompt 工程和 RAG 已经尝试过，且有实测证据显示效果仍不达标，而不是“感觉应该微调”。
- ② 问题的性质是“行为模式”而非“知识缺失”。如果 prompt 里补充几个示例或检索库里补几篇文档就能解决，说明问题本质是知识或引导不足，不需要动权重。
- ③ 有稳定、规模足够、质量有保障的训练数据来源，且这批数据的分布在可预见的未来不会频繁大改。
- ④ 团队具备或愿意投入持续的模型版本管理能力。微调出来的权重是一个新的、需要独立测试和维护的资产，不像 prompt 和检索库那样可以“改完即生效”。

QLoRA 相比全参数微调的价值在于用量化降低显存需求，让消费级或单卡环境也能做参数高效微调。但这解决的是“训练成本”问题，不改变“什么时候该微调”这个决策本身。训练成本降低不能作为“更早启动微调”的理由，四条前提该满足几条还是几条。


**四维判据表**：

| 判据 | 偏向 Prompt | 偏向 RAG | 偏向微调 |
|---|---|---|---|
| 数据量 | 几个到几十个示例就能通过 few-shot 说清楚 | 知识库规模从几十到无上限文档，且持续增长 | 需要成百上千条高质量、覆盖目标行为分布的标注样本，样本不足时微调效果通常不稳定 |
| 领域偏移度 | 通用能力，模型预训练知识已覆盖 | 私有/时效性知识，模型预训练时不可能见过 | 领域术语体系、任务范式与通用预训练分布差异大，仅靠上下文提示难以稳定纠偏 |
| 延迟要求 | 最优，无额外调用开销 | 中等，多一次检索（§7.3 全链路每加一环都叠加延迟） | 最优，推理时无额外调用，但需要承担模型部署与版本管理的运维延迟成本 |
| 维护成本 | 最低，改 prompt 即生效，多环境可并存不同版本 | 中等，需要维护索引更新流水线（第 5 章数据管道），但不涉及模型资产管理 | 最高，每次数据分布变化可能需要重新微调，且需要独立的评估、灰度、回滚机制 |

**决策优先级**：默认从 Prompt 工程开始尝试，成本最低、迭代最快。

知识类问题优先上 RAG，而不是把知识“塞”进权重。知识会过时，微调进去的过时知识比检索库里过时的文档更难发现和纠正，因为它藏在权重里，不像检索库那样可以直接翻查内容。

只有在前两条路线都已经用评估集验证过、仍然达不到要求，且问题性质确实是“行为模式”而非“知识缺失”时，才考虑微调。

三条路线也不是互斥的终点选择。生产系统里更常见的是组合：用 RAG 解决知识时效性，用 prompt 工程控制输出格式和语气，只在两者都覆盖不到的行为模式缺陷上做小范围微调，而不是指望单一路线解决所有问题。

用一个具体场景过一遍四维判据：某医疗器械厂商的客服 Agent 经常“用词过于口语化”，客户投诉这不符合行业规范用语习惯。按四维判据过一遍：

- **数据量**：内部有过去两年的合规客服话术记录，量级足够。
- **领域偏移度**：医疗器械行业术语体系和措辞规范与通用预训练分布确实有系统性差异。
- **延迟要求**：客服场景对延迟敏感，希望零额外调用开销。
- **维护成本**：话术规范半年才更新一次，不算频繁。

四个维度里有三个偏向微调，只有“是否已经用 prompt 工程试过”这一步容易被跳过。很多团队看到“领域偏移度高”就直接跳去微调，却没有先测过“在 prompt 里给几个合规话术示例 + 明确的用词禁止清单”能不能解决大半问题。

正确顺序是先用黄金集测一版强化后的 prompt。只有实测证明 few-shot 引导不够稳定（比如超纲话术反复出现），才把这批数据整理成微调数据集。这个案例也说明四维判据要联合看，不能因为某一维“偏向微调”就跳过前面更便宜的路线。

本章讲的是系统怎么设计、Agent 怎么编排。这些设计跑到生产环境之后怎么部署、怎么设护栏、怎么被持续观测，是下一章（第 8 章 · 部署、护栏与可观测性）要接手的问题。§7.5 MCP 的容错降级、§7.6 checkpointer 的持久化、§7.7 的四类故障防御，都需要在生产可观测性层面有对应的监控信号。两章的内容是同一套系统在“设计期”和“运行期”的两个切面。

## 本章清单

- [ ] 系统提示词按四层拆：身份边界、能力工具、风格格式、任务上下文。
      **越靠前越稳定，混在一起写会让高频变化的内容稀释掉强约束**
- [ ] 给上下文窗口做预算分配。不分配的话，对话历史会随轮次增长挤占检索配额
- [ ] 主动清理上下文污染的三种来源：陈旧信息未失效、检索噪声挤占注意力、中间态污染下游。
      **不要指望模型自己甄别**
- [ ] 检索链路每一环都算一次成本。候选池很小或延迟极敏感时，多加一环反而得不偿失
- [ ] 融合算法的参数不要跨厂商照抄默认值——两个主流实现的默认值相差 30 倍
- [ ] 不同来源的评测分数不要直接比较。同一个精排模型跨论文能差 9 个点以上
- [ ] 长上下文和检索按查询路由，不是二选一。图谱检索解决的是全局归纳，不是“检索不准”
- [ ] 工具描述写清四件事：适用场景、不适用场景、参数来源、错误处理。
      **这比函数实现写得多详细更影响生产表现**
- [ ] 人在回路用动态中断，不用静态中断
- [ ] **循环拓扑必须配硬性迭代上限**，否则它就是死循环故障的直接来源
- [ ] 四类故障各设一条退出路径。目标不是消除故障，是让系统出错时能感知到自己出错了

## 自检问题

1. 一个客服 Agent 的系统 prompt 越写越长，把“不能承诺具体金额”这条硬约束和当次对话历史堆在同一段里，模型开始偶尔违反这条约束。问题出在哪，怎么改？
   **参考答案要点**：没有做分层。硬约束（身份边界层）和易变内容（任务上下文层）混在一起，随对话变长，硬约束在总长度中的相对权重被稀释。应该把硬约束单独放在最稳定的一层，且不与高频变化的对话历史交织在同一段落里。

2. 团队想用长上下文直塞替代现有的 RAG 系统，理由是“新模型上下文窗口已经能装下整个知识库”。这个理由能不能站住？
   **参考答案要点**：不能一概而论。长上下文在资源充足时质量确实有优势，但多数模型超过 64k token 后无法维持稳定准确率，且长上下文的 token 成本远高于检索窗口。正确做法是按查询路由，能用检索窗口回答的走 RAG，不能默认“能装下就该直塞”。

3. 你在两篇论文里看到同一个 rerank 模型的 BEIR 分数相差 9 个点以上，该怎么解读，能不能据此判断哪篇论文的评测“更权威”？
   **参考答案要点**：不能简单判断谁更权威。分数差异通常来自评测集、第一阶段检索器、rerank depth 等配置不同，不是评测方法本身有对错之分。正确做法是在自己的实际数据和检索管道上重新实测，不要跨论文直接比较绝对数值。

4. 一个 Agent 系统里检索到的候选池经常只有 3–5 篇文档，团队考虑加一层 rerank 精排，这个决策合理吗？
   **参考答案要点**：候选池很小时 rerank 边际收益低，问题更可能出在第一阶段召回质量不足。应该先查检索环节能不能召回更多相关候选，而不是给个位数的候选加精排。这是“什么情况下不值得上”的典型场景。

5. 用 GraphRAG 处理“这批合同里有没有第 8 条违约条款”这类具体条款查询，效果不如预期，为什么？
   **参考答案要点**：GraphRAG 解决的是全局归纳性问题，如“这批合同的主要风险类型有哪些”。具体实体/条款查询属于局部事实检索，更适合普通混合检索 RAG（或 GraphRAG 产品化库里的 Local Search）。这是用错了工具类型，不是 GraphRAG 本身的效果不行。

6. 写一份 MCP 工具描述时，只写了函数签名和一句话 docstring，模型经常调用错工具或传错参数。该往 docstring 里补什么，才能真正改善这个问题？
   **参考答案要点**：至少要补齐适用场景、不适用场景（尤其是有相似工具时的边界）、参数的来源与格式约束、返回值结构、错误情况下的处理建议。工具描述是模型能看到的全部上下文，代码实现细节对模型没有意义。

7. 一个多智能体系统里的循环节点跑了几十轮还没退出，排查后发现终止条件设计得没问题，只是任务本身确实需要这么多轮才能收敛。这种情况下“设置迭代上限”是不是在压制系统的正常能力？
   **参考答案要点**：不是。迭代上限是安全网，不是效果上限。正确做法是先用评估数据摸清任务正常收敛所需的轮次分布，把上限设在略高于正常分布的位置，而不是因为怕压制能力就完全不设上限。没有上限的循环拓扑本身就是故障隐患，与任务是否“确实需要更多轮”是两个独立的问题。

8. 团队打算用 LoRA 微调解决“模型经常引用一份三个月前就过期的价格政策”这个问题，这个决策合理吗？
   **参考答案要点**：不合理。这是知识时效性问题，属于 RAG 该解决的范畴，应该更新检索库让模型引用最新价格政策。微调会把当前的价格“内化”进权重，价格再次变化时，微调进去的过时知识比检索库里的过时文档更难被发现和纠正。原因是它不能像文档那样被直接翻查和替换。
