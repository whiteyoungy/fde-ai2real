# 第 3 章 · 规格、变更与执行纪律

> **一句话结论**：这里有三种能力——把新功能定义清楚、把改动记录清楚、
> 把 AI 干活的规矩定清楚。缺哪一块补哪一块。2026 年这三块分别有 Spec Kit、
> OpenSpec、Superpowers 可用，**但要选的是能力，不是工具**。

## 三个团队，三种卡法

第一个团队上了完整的规格流水线，两周后开始抱怨：改一行文案也要开一份规格，
20 行代码淹没在 30 个 markdown 文件里。有人直说“我宁可 review 代码，
也不想读这一堆文档”。

第二个团队反过来。规格写得很好，但那是三个月前那版功能的规格。
现在的代码早就不是那样了，规格躺在仓库里没人敢信，也没人敢删。

第三个团队规格和代码都对得上，但每次让 AI 干活，结果的质量全看运气——
有时候它先写测试，有时候它直接改代码然后说“已完成”，谁也说不清它到底验没验过。

三个团队缺的东西完全不一样。**第一个缺分档，第二个缺变更治理，第三个缺执行纪律。**
这一章要说清楚哪个工具补哪一块。

> **在骨架里的位置**：这一章本身不攒任何一类结果，它是选工具的。但三套工具各补一块：**Spec Kit 补规格产物的格式**（证据的形状）、**OpenSpec 补变更轨迹**（证据的连续性）、**Superpowers 补 AI 干活的纪律**。执行环境层三套都没覆盖，那是两本别册讲的。

## 读完这章你能做什么

1. 判断你的团队现在缺的是规格能力、变更治理，还是执行纪律——**先判断缺哪种能力，再去找工具**。
2. 说清楚三套工具各自的产物落在仓库的什么位置，以及为什么可以同时存在。
3. 定一套团队 Git 规范，让“张三写的接口”和“李四写的接口”天然对得上。
4. 把宪法抽成单一事实源，让多人、多项目、多工具指向同一份规约。

## 3.1 先选能力，再选工具

这一章原来的写法是直接比三个产品。**改成现在这样，是因为产品会过期，能力不会。**

三个团队缺的东西，抽掉产品名之后是三种能力：

| 能力 | 回答什么问题 | 产物的性质 | 不具备时的症状 |
|---|---|---|---|
| **一 · 规格能力** | 这个新功能要做成什么样 | 文件：规格、方案、任务 | 做出来和想要的不一样，而且事后说不清是谁理解错 |
| **二 · 变更治理** | 这次改动改了系统的哪些行为 | 文件：现状 + 提案，两份分开 | 规格是三个月前那版的，没人敢信也没人敢删 |
| **三 · 执行纪律** | AI 干活时按什么规矩来 | **不是文件，是流程本身** | 同一件事每次做法都不一样，说不清它验没验过 |

**这张表的最后一列就是本章开头那三个团队。** 第一个团队其实不缺规格能力，
缺的是规格能力的**分档**（§3.6 会讲）；第二个团队缺变更治理；第三个团队缺执行纪律。

三种能力的关系决定了能不能同时上：

- **一和二是同一维度的两端**，可以二选一，也可以按项目阶段切换——
  从零造新系统偏一，在已有系统上长期演进偏二。
- **三和前两者不是同一维度。** 它约束的是干活的方式，跟你用不用规格无关。
  **一个团队完全可以只上第三种能力，一份规格都不写。**

一句本章后面会反复用到的话：**方法论是工具中立的。换工具重学的是按钮，不是思维。**
所以下面几节读的时候，请按“这个工具在补哪一种能力”去读，
而不是按“哪个工具更好”去读。**后一个问题在 2028 年不成立，前一个问题一直成立。**

> **2026 年的工具快照**：三种能力在写作时分别有 Spec Kit、OpenSpec、Superpowers
> 可用，§3.3–§3.5 分别讲它们。**这三节的具体命令、目录结构和产物格式会过期**——
> 读的时候把它们当成“某一种能力的一份实现示例”，不是这一章的结论。
> **结论在 §3.1 和 §3.6，这两节不依赖任何一个产品还存不存在。**

## 3.2 三者解决的不是同一个问题

| | **Spec Kit** | **OpenSpec** | **Superpowers** |
|---|---|---|---|
| **定位** | 规格流水线 | 变更提案制 | 工程纪律层 |
| **回答什么问题** | 这个新功能要做成什么样 | 这次改动改了系统的哪些行为 | AI 干活时按什么规矩来 |
| **核心产物** | `specs/<功能>/` 下的规格、方案、任务 | `openspec/specs/`（现状）+ `openspec/changes/`（提案） | 不产出规格文件，产出的是行为约束 |
| **适合什么时候** | 从零造功能、团队要统一产物格式 | 已有系统上做增量改动、要留变更轨迹 | 想约束 AI 的干活方式，跟用不用规格无关 |
| **重量** | 重 | 轻 | 轻，但强制 |

关键差别在**产物的性质**：Spec Kit 和 OpenSpec 产出的是文件，
Superpowers 产出的是**流程本身**。前两者可以二选一，第三者和前两者不是同一维度的东西。

画成两个不同的框，就不会再被拿来互相比较：


## 3.3 Spec Kit：从零造功能的流水线

第 2 章已经把它讲完了。这里只补两句定位：

它的强项是**产物格式统一**。九条命令，每条落一份文件，团队里谁做的功能，
产物长得都一样，评审时知道该去哪儿看。多人协作、长期维护、合规审计要求高的场景，
这个价值很大。

它的弱项也是它：**没有官方的修 bug 流程**，而且流程重量不随改动大小自适应，
需要人为分档（分档表见本册 §2.6）。

## 3.4 OpenSpec：在已有系统上做增量改动

OpenSpec 的思路和 Spec Kit 不一样。它不是“给功能写规格”，
是**把“系统现在是什么样”和“这次要改成什么样”分成两个空间** [1]：

```
openspec/
├── config.yaml               ← init 只建这一个文件
├── specs/                    ← 系统当前行为的真相源（第一次归档时才出现）
└── changes/                  ← 正在进行的变更提案
    └── <变更名>/
        ├── .openspec.yaml    schema 与创建日期
        ├── proposal.md       提案：为什么改
        ├── specs/            增量规格：改了哪些行为
        ├── design.md         设计
        └── tasks.md          任务清单
```

> **`specs/` 一开始是不存在的。** `openspec init` 只创建 `config.yaml`；
> `openspec/specs/` 要等第一次归档才被建出来。**这不是 bug，是它的设计**——
> 现状规格不是手写的，是归档时从增量合并出来的。

最值得学的是**增量规格的写法**。它不重写整份规格，只标出这次改动的差集，
用三个小标题区分 [1]：

```markdown
## ADDED Requirements      新增的行为
## MODIFIED Requirements   改掉的行为（必须写出改完后的完整内容，不是只写差异）
## REMOVED Requirements    废弃的行为（必须写 Reason 与 Migration）
## RENAMED Requirements    只改名字，用 FROM:/TO: 格式
```

每条要求下面挂场景，格式是固定的：

```markdown
### Requirement: <名字>
系统 SHALL ……                       ← 用 SHALL / MUST，别用 should / may

#### Scenario: <名字>
- **WHEN** ……
- **THEN** ……
```

> ⚠️ **场景必须正好四个井号。** 用三个井号或者写成列表项，
> **它不会报错，会静默失败**——校验通过，但那条场景不算数。
> 官方文档把这一条标成 CRITICAL，本书实测确认。

这一招直接治第 2 章讲的“规格与代码漂移”。漂移的根源是**回写规格的成本太高**——
要在一份长文档里找到该改的段落、改掉、还要保证别处没矛盾。
改成写差集之后，回写成本降到几行，人才愿意做。

生命周期是三步 [1]：

| 命令 | 干什么 |
|---|---|
| `/opsx:propose <要做什么>` | 建变更目录，生成提案、增量规格、设计、任务 |
| `/opsx:apply` | 照任务清单实现 |
| `/opsx:archive` | 完成的变更归档到 `openspec/changes/archive/`，并把增量合并回 `specs/` |
| `/opsx:explore` | 先摸清现状再决定改什么 |
| `/opsx:update` | 改一个还没实施的提案 |
| `/opsx:sync` | 把规格和代码的实际状态对一遍 |

前三个是主干，后三个是补充。**装完一共给六个命令，不是三个。**

产物之间有强制顺序，工具会挡：

```text
proposal  →  specs   ┐
          →  design  ┴→  tasks
```

`openspec status --change <名字>` 会把没做完的标成 `[-] blocked by: …`。
**这不是提示，是真的做不下去**——顺序倒过来写，工具不认。

归档这一步是精髓：**变更做完之后，现状规格自动被更新。**
这是“规格永远是最新的”这件事第一次有了机械保证，而不是靠人自觉。

实测的归档输出长这样：

```text
Specs to update:
  refund-policy: create
Applying changes to openspec/specs/refund-policy/spec.md:
  + 1 added
Totals: + 1, ~ 0, - 0, → 0
Change 'add-refund-window-rule' archived as '2026-08-25-add-refund-window-rule'.
```

三件事值得留意：

**一、`Totals` 那四个数对应四种增量操作**（新增 / 修改 / 删除 / 改名）。
它是一次变更对现状规格影响面的量化摘要——**评审时看这一行比看 diff 快。**

**二、归档目录带日期前缀。** 变更名前面会加上归档日期，
所以 `changes/archive/` 天然按时间排序。

**三、增量里的 `## ADDED Requirements` 到了现状规格里变成 `## Requirements`。**
增量的标题是操作，现状的标题是状态——**这个区分是这套东西能自动合并的前提。**

安装与初始化 [1]：

```bash
npm install -g @fission-ai/openspec@latest   # 需要 Node.js 20.19.0 以上
cd your-project
openspec init
```

`init` 时用 `--tools` 指定 AI 工具（`claude`、`codex`、`cursor` 等三十多种，
或者 `all` / `none`）。以 Claude Code 为例，它会在 `.claude/` 下装 6 个命令和 6 个技能，
命令名就是上表那六个。

> **⚠️ 命令名随工具变**：`/opsx:` 是 Claude Code 下的形式，别的工具语法不同，
> 具体在 `openspec init` 时确定。**工具升级后命令名可能变化，实操前以官方文档为准。**

> **⚠️ 它默认上报匿名使用统计。** `init` 时会打印一行提示，
> 关掉的方式是环境变量 `OPENSPEC_TELEMETRY=0`，或者
> `openspec config set telemetry.enabled false`。
> **进客户内网之前先关掉，并且写进你的软件物料清单**——
> “这个工具会不会往外发数据”是安全评审必问的一条，
> 答“我没注意”和答“默认会，我们关了，关法如下”是两种结果。

> **可信度说明**：本节的目录结构、六个命令、产物依赖顺序、增量格式、
> 四个井号那条坑、归档行为，**均在 `@fission-ai/openspec@1.10.0` 上实测**
> （Node 22，2026-08-25 走完一次 `init` → `new change` → 填四件产物 →
> `validate` → `archive` 的完整流程）。**上一版本书未实跑，这一版跑过了。**

官方文档自己对两者的对比是：Spec Kit 周全但笨重，阶段闸口很硬，
markdown 很多，还要配 Python 环境；OpenSpec 更轻，允许随时更新产物，
不强制顺序推进 [1]。

**这段对比出自 OpenSpec 自己的文档，是有立场的。** 本书的判断是：
两者的差别与其说是轻重，不如说是**面向的场景不同**——
从零造和在已有系统上改，本来就该用不同的流程。

## 3.5 Superpowers：给 AI 定规矩

前两者管的是“写什么”，这一套管的是“怎么干”。

它是一个装进 AI 编程工具的技能库，把开发纪律做成**强制的工序**，
而不是写在文档里等人自觉 [2]：

| 技能 | 强制什么 |
|---|---|
| `brainstorming` | 动手之前先把设计问清楚，分段确认，不许直接开写 |
| `writing-plans` | 把工作拆成 2–5 分钟一个的任务，带确切文件路径和验证步骤 |
| `using-git-worktrees` | 在隔离的工作区和新分支上干活，先跑一遍测试建基线 |
| `subagent-driven-development` | 两阶段评审：先查是否符合规格，再查代码质量 |
| `test-driven-development` | 红 → 绿 → 重构：先写会失败的测试，再写最少的代码让它过 |
| `systematic-debugging` | 四阶段根因分析，不许“试试看这样改行不行” |
| `verification-before-completion` | 说“做完了”之前必须拿出验证过的证据 |
| `finishing-a-development-branch` | 合并还是开 PR，走固定决策流程 |

它的立场很直接：**证据优先于声称**（evidence over claims）。
这些技能是必须触发的闸口，不是可选建议 [2]。

安装（Claude Code）[2]：

```
/plugin install superpowers@claude-plugins-official
```

为什么这一层单独存在：**规格解决“做什么对”，它解决“怎么干才靠谱”。**
一份完美的规格，配上一个改完代码不跑测试就说“已完成”的 AI，
结果照样是坏的。第 2 章开头那三个翻车案例，规格能挡住一部分，
但“动生产库之前要人点头”这种事，光声明没用——它写在规格的退路块里（§2.6 第六块），
**由执行纪律层负责强制触发**。声明归规格，执行归纪律，两层都在才闸得住。

## 3.6 怎么选

按你现在最疼的那一条选：

| 症状 | 缺的是 | 上什么 |
|---|---|---|
| 需求说不清，做出来不是想要的 | 规格 | Spec Kit（或任一规格工具） |
| 规格写了，但和代码对不上，没人敢信 | 变更轨迹 | OpenSpec |
| 小改动也要写一堆文档，团队开始抵触 | 分档规矩 | 先定分档表（第 2 章 2.6），工具不用换 |
| AI 干活质量全看运气，说做完了但没验过 | 执行纪律 | Superpowers |
| 多人产出对不上，接口五花八门 | 共享宪法 | 见 3.7 |

**不要三个一起上。** 一次只解决当下最疼的那一条，
否则团队的注意力全花在学工具上，没花在交付上。

如果非要一个默认推荐：**新项目从 Spec Kit 起步，
系统跑起来之后把日常增量改成 OpenSpec 的提案制，全程叠一层 Superpowers 的执行纪律。**
宪法用 Spec Kit 立，因为它的宪法概念最成熟；日常增量用 OpenSpec，
因为回写成本低；纪律用 Superpowers 兜，因为它和前两者不冲突。

方法论是工具中立的。**换工具重学的是按钮，不是思维。**

## 3.7 Git 协作规范

规格工具解决的是“写什么”，Git 规范解决的是“怎么合”。两者缺一不可。

### 分支策略

| 分支 | 作用 | 约束 |
|---|---|---|
| `main` | 可发布主干 | 保护分支，始终干净可发布，只经 PR 合入 |
| `dev` | 集成分支 | 功能合入的目标 |
| `feature/*` | 功能分支 | 从 `dev` 切出，如 `feature/paper-check` |

### 提交信息用固定前缀

格式 `type(scope): 描述`：

```
feat(paper-check): 新增论文格式检查接口
fix: 修正行距误差判定
docs(spec): 回填澄清段
```

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档与规格 |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 杂务与配置 |

不强求描述长度，但**统一用前缀，便于检索**——三个月后想找“上次改响应体结构是哪一次”，
有前缀能搜到，没前缀只能一条条翻。

### 三条硬约束

- **提交前本地必须跑通。** 避免 commit 上去就无法运行。
- **不提交密钥、密码、`.env`。** 已经提交了就 `git rm --cached .env`、
  加进 `.gitignore`、**然后轮换密钥**——最后这一步最常被漏掉，
  而它才是真正解决问题的那一步。历史里的密钥不会因为你删了文件就消失。
- **不提交 AI 生成的未读代码。** 自己先浏览、掌握再提交。
  这条在评审时最容易被发现：提交人答不上来“这段为什么这么写”。

### 每天走的那条线

```bash
git checkout dev && git pull                 # 保持 dev 最新
git checkout -b feature/xxx                  # 从 dev 切功能分支
# …写规格 / 改代码，本地跑通…
git add .                                    # 别 add .env
git commit -m "feat(scope): 描述"
git push -u origin feature/xxx
# 开 PR 指向 dev，同事对照宪法评审后合并
```

### PR 评审对照宪法看

评审不靠个人品味，靠同一份宪法。逐条核：命名、响应体结构、
数据表的审计字段、登录与权限、界面规范。一致才合并。

**改动只进 `dev`，`main` 始终可发布。**

## 3.8 宪法是共享契约，不是某个人的偏好

“张三写的接口”和“李四写的接口”为什么天然对得上？
因为读同一份规约、走同一套产物。

要让这件事成立，宪法必须被抽到**单一共享处**：

- 一个独立的规约仓库，各项目以子模块或依赖的方式接入；
- 或者主仓库根目录下的 `constitution/` 目录。

要求是统一版本、有更新记录、**新人 clone 下来就拿到全套**。

一处维护、处处生效：命令行工具读它，IDE 的规则文件与它同源，
所有规格产物据它生成，PR 和持续集成对照它核对。

这里有一个常见误区值得点破：很多团队让每个人在自己的 IDE 里配一套规则，
然后惊讶于产出对不上。**IDE 的规则文件应该指向宪法，或者摘要宪法，
而不是各写一份。** 各写一份，就是各有各的真相。

常见故障与对策：

| 现象 | 原因 | 处理 |
|---|---|---|
| 组员产出对不上 | 各用各的宪法 | 统一一份，其余人拉取后重跑方案生成 |
| AI 超范围发挥 | 规格没写范围边界 | 补“不做什么”；用一致性核对抓超范围项 |
| 数据表少了审计字段 | 宪法里没写死 | 宪法写死四个字段，重出数据模型 |
| 接口响应五花八门 | 没统一契约 | 宪法固定响应体结构和错误码 |
| `.env` 被提交 | 没进 `.gitignore` | 移出跟踪、加忽略、**轮换密钥** |
| 命令跑不动 | 工具升级 | 以官方最新命令为准 |

## 3.9 这套东西和本书的 12 个实验是同一件事

规约驱动开发的核心主张是：**先定“做对了长什么样”，再动手做。**

本书 12 个实验里的 `verify.sh` 就是这句话在实验层面的实现。
每个实验的 README 先写验收标准，`verify.sh` 把标准变成能自动跑的检查，
全项通过且退出码为 0 才算做完。

两者是同一件事的两个层次：

| | 规约驱动开发 | 本书的实验 |
|---|---|---|
| 先定什么 | 规格里的验收标准 | README 里的验收标准 |
| 怎么自动验 | 验收剧本固化成回归测试 | `verify.sh` |
| 什么叫做完 | 门禁全绿 | 全项 OK 且退出码 0 |
| 防的是什么 | “能跑起来”被当成“做对了” | 同上 |

写这本书时反复遇到的一件事可以佐证：正文里写着一套逻辑、
同章代码却在做另一件事，这类矛盾**通读多少遍都审不出来，只有真把代码跑起来才会现形**。
规格和实现之间的漂移，最终只能靠可执行的验收来兜。

## 自检问题

**1. 团队抱怨“改一行文案也要写一堆文档”，该换工具吗？**

多半不用。这是分档规矩缺失，不是工具选错。先定一条分档规矩
（第 2 章 2.6 那张表），让每个人知道多大的改动配多重的流程。
换工具解决不了“什么都走全流程”这个习惯。

**2. 规格躺在仓库里已经和代码对不上了，最该做的第一件事是什么？**

不是重写规格，是**把回写成本降下来**。改成写差集——只标出这次改动
新增、修改、废弃了哪些行为——回写成本降到几行，人才会真的去写。
成本不降，重写多少遍都会再漂移一次。

**3. 有了规格，还需要执行纪律层吗？**

需要。规格解决“做什么对”，执行纪律解决“怎么干才靠谱”。
一份完美的规格配上一个改完不跑测试就说“已完成”的 AI，结果照样是坏的。
“动生产库之前要不要人点头”这类约束不属于规格，属于纪律。

**4. `.env` 被提交进仓库了，`git rm --cached .env` 之后就安全了吗？**

不安全。文件从当前提交里移除了，但历史里还在，任何人拉到这个仓库都能翻出来。
**必须轮换密钥。** 这一步最常被漏掉，而它才是真正解决问题的那一步。

**5. 每个人在自己的 IDE 里配一套规则，为什么产出还是对不上？**

因为各有各的真相源。IDE 的规则文件应该指向同一份宪法或摘要它，
而不是各写一份。多人、多项目、多工具必须都指向同一份规约，产出才会天然一致。

**6. 本书的 `verify.sh` 和规约驱动开发是什么关系？**

同一件事的两个层次。都是先定“做对了长什么样”，再把标准变成能自动跑的检查，
防的都是“能跑起来”被当成“做对了”。
