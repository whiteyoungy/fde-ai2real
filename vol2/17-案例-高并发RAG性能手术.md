# 第 17 章 · 案例四：300 毫秒生命线，高并发 RAG 性能手术

> **一句话结论**：延迟预算要拆到每个环节各自的毫秒数。只有拆开，才看得出哪一环还有空间、哪一环只能绕开。

> 非特定客户的真实项目。文中标注了来源的 **Notion 官方技术博客**《Two years of vector
> search at Notion: 10x scale, 1/10th cost》披露的数字（活跃工作区增长 15x、向量数据库
> 容量扩展 8x、分阶段成本与延迟改善数字）为可查证的真实信息，已注明出处，但那是 Notion
> 自己系统的真实结果，不是本章虚构客户的实测数据，两者不可混为一谈。同理，Higress-RAG
> 论文（arXiv 2602.23374）与 Elastic Search Labs 的 rerank 延迟实测数据均为**已发表的
> 第三方可查证数字**，用于校准本章合成案例里的架构决策依据，而非虚构客户自己的压测结果。

## “要更快”

压测报告出来，P95 是 1.2 秒，要求是 300 毫秒。

团队的第一反应是加机器。加了一倍，P95 变成 1.1 秒。

把链路拆开量了一遍才发现：生成那一步单独就占了 700 多毫秒，
剩下的被检索和排队分掉。**加机器改不了单次请求要走的路径长度**——
瓶颈在每一跳的预算，不在机器数。

这一章讲怎么在拆开之后做决定：先给 300 毫秒画一张分账表，再逐环手术。

## 读完这章你能做什么

1. 把一条端到端延迟预算拆解到检索、重排、生成、网络各环节，**判断每一环还有多少空间**。
2. 理解为什么“流量涨了就加机器”和“引入更精细的自纠错链路”在高并发实时场景下
   都可能是错误方向，学会**用数量级差距去否决一个方案**。
3. 掌握混合检索与融合、私有化替换、量化推理、语义缓存、冷启动消除这五件事
   在一条延迟敏感链路上各自解决什么问题、彼此怎么配合。

## 17.1 客户背景

本章客户是一家教学合成的智能客服平台提供商（以下称“音境科技”，虚构化名），核心产品是
面向电商与金融客户的实时语音客服系统：用户来电经 ASR（语音转文本）实时转写成文本片段后，
系统需要立刻理解意图、检索企业知识库（产品条款、售后政策、常见问题），生成一段可直接
交给 TTS（文本转语音）播报的应答文本。这条链路对用户的体感是“对方在正常说话”，不是
“在等一个机器人查资料”。

项目启动前，音境科技的知识问答环节走的是标准 RAG 流程：单路向量检索 top-k 后直接拼
prompt，调用一家外部闭源大模型 API 做生成，日常流量下端到端延迟能压在 500ms 左右，
业务勉强能接受。真正把问题引爆的是客户的大促活动——接入的电商客户每年双 11、618
期间呼叫量会短时间涨到日常的百倍量级，这个量级不是逐步爬坡，而是活动开始那一刻
断崖式涌入。

音境科技的客户合同里明确写了语音应答的可用性 SLA，一旦响应迟钝或干脆超时降级成
“抱歉我没有听清”，客户投诉和客户流失是当场就能看见的。这是后面所有架构决策的
第一约束条件：优化目标不是“平均更快”，而是“大促峰值下依然守得住延迟底线”。

## 17.2 真实冲突

三重压力同时压在这条链路上，任何单点优化都会撞上另外两条边界：

**端到端延迟必须压进 300ms。** 这个数字不是拍脑袋定的：语音交互研究和产品经验都指向
一个共识——应答停顿超过几百毫秒，用户会明显感觉到“卡顿”甚至开始重复自己刚才说的话。
音境科技把预算线定在 ASR 输出文本片段之后到应答文本生成完毕之间的 300ms（不含 TTS
合成本身的耗时，TTS 是下游独立环节）。这 300ms 要覆盖检索、重排、生成、网络传输的
全部开销，而旧链路日常状态下都要 500ms，大促峰值下只会更糟。

**流量洪峰是断崖式的百倍激增，不是线性爬坡。** 大促活动开始的瞬间，呼叫量在几分钟内
从日常基线冲到 100 倍量级，自动扩容（无论是加 Pod 副本还是加 GPU 实例）存在启动
延迟——新实例拉起、模型权重加载、连接池预热，这些都是秒级到分钟级的过程，而流量
洪峰是瞬时的。等扩容跟上，峰值最猛的那几分钟已经把用户体验砸了。

**外部闭源 API 的限流与 Token 成本撑不住这个量级。** 旧链路的生成环节调用的是一家
商业闭源大模型 API，日常量级下按量计费尚可接受，但把这套按次计费的成本结构乘以
100 倍瞬时并发，账单会直接失控；更麻烦的是限流——外部 API 的并发配额和 QPS 上限是
供应商侧的硬限制，不是多付钱就能瞬间解除的，大促峰值期间大概率会触发限流返回
429，而这一秒钟系统没有更好的应答可用，只能对用户露怯。

## 17.3 被否决的方案

**方案一：横向扩容 + 加大外部 API 配额**。最直接的想法是多买配额、多开几路并发请求
去扛峰值。评审阶段就被否决：外部 API 的限流是供应商侧的硬性 QPS 上限，多数商业大模型
API 的配额升级需要走商务流程，不是临时加钱就能在大促当天生效的开关；就算配额问题
能解决，P99 延迟的真正瓶颈是“一次云端网络往返 + 大模型生成耗时”本身，这个耗时不会
因为并发数增加而缩短，加并发只能让更多请求排队等着触达同一个延迟量级，解决不了
300ms 这条硬线。这条路线在方案评审阶段就出局，没有进入原型验证。

**方案二：精确匹配缓存（按查询字符串做 key 的传统 KV 缓存）**。工程团队最初考虑用
一个简单的 key-value 缓存兜底：常见问题原样命中就直接返回。原型测试后否决：真实
用户是通过语音转写出来的口语化文本，同一个意图会有大量措辞变体（“我想退货”和
“这个东西能退吗”语义相同但字符串完全不同），精确匹配的命中率低到不足以覆盖大促期间
涌入的新表述方式，而大促本身又恰恰是大量新用户、新问法集中出现的场景，精确匹配缓存
在最需要它顶住峰值的时候恰好失效。

**方案三：为提升精度引入完整的 CRAG 自纠错链路（查询分解 + 多轮检索 + 网络搜索兜底）**。
这个方案在准确率上确实有优势，Higress-RAG 论文（arXiv 2602.23374）披露的数据显示，
完整走一遍“查询分解 → 混合检索 → 重排 → CRAG 三分类质量评估 → 必要时触发网络搜索”
的深度推理链路，端到端延迟是 **11–20 秒**（该数字是论文作者单一厂商自测，测试集仅
覆盖 Higress 自身技术文档领域，样本狭窄，不构成通用基准，但用来说明数量级已经足够）。
这比 300ms 的预算高出近 40 到 70 倍，不是“优化一下就能压进去”的差距，而是路线本身
与实时语音场景的量级不兼容。团队保留了这条链路的价值，但把它挪到离线评测与异步
兜底路径（比如用户明确要求“帮我转人工核实一下”的场景），不允许出现在热路径里。

三个方案被否决后，团队才把注意力收敛到“精简但足够准的热路径 + 把重活挪到链路外”
这个方向上。

## 17.4 最终架构决策

判据只有一条：**热路径上的每一环节，都要能在自己的延迟预算内跑完，超预算的环节要么
精简、要么挪出热路径，不允许用“整体平均还行”掩盖某一环节的超支**。据此先把 300ms
拆到各环节，这张表是本章的核心产出：

| 环节 | 预算（ms） | 优化空间说明 |
|---|---|---|
| 网关接入 / 鉴权 / 限流判断 | 10 | 逻辑轻量，优化空间小，只要不引入同步远程调用即可 |
| 语义缓存查询（向量相似度比对） | （5，并行旁路） | 与后续检索并行触发，不占串行预算；命中则直接跳过下面三行 |
| 混合检索（BM25 + 向量并行 + RRF 融合） | 40 | 主要杠杆是向量库选型与两路检索并行发起，不是砍检索路数 |
| Rerank（cross-encoder 精排，候选集裁剪） | 30 | 深度（top-N）与延迟强相关，必须选轻量模型、裁剪候选规模 |
| 生成（私有化量化模型推理，短答案） | 170 | 预算里最大的一块，量化、prefix cache、批处理是优化空间最大处 |
| 结果序列化 + 网络回传 | 15 | 优化空间有限，做好即可 |
| 系统缓冲（应对抖动） | 35 | 不分配给任何具体环节，专门留给排队、GC 与偶发重试的抖动 |
| **合计** | **300（串行 265 ＋ 缓冲 35；语义缓存为并行旁路，不计入串行合计）** | |

语义缓存命中时的路径跳过检索、重排、生成三步，直接返回历史答案。Higress-RAG 论文
披露其语义缓存命中时的延迟压缩到 **50ms**（同样是单一厂商自测数字，用于校准量级，
不代表本章虚构客户的实测结果）——这个数字说明命中路径本身有充裕的余量，缓存策略
真正的工程难点不在命中路径的速度，而在阈值怎么定、命中率有多高，见下文。

**据此做出五项决策：**

1. **混合检索 + RRF 提精度**：单路向量检索遇到精确关键词（订单号、产品型号）召回
   会漏，因此改成 BM25（稀疏）与向量检索（稠密）并行执行，用 RRF（Reciprocal Rank
   Fusion）融合两路排名，公式 `RRF(d) = Σ 1/(k+r(d))`，k 取行业常见默认值 60（来源
   同上，Higress-RAG 论文正文）。**这个默认值不是普适常数**——Elasticsearch 官方
   RRF 实现默认 k=60，Qdrant 官方默认 k=2，两家相差 30 倍，k 越小头部排名权重占比
   越高；跨厂商照搬默认参数是常见错误，本章沿用 60 是因为自建融合逻辑参照的是
   Higress-RAG 的实现，不是因为 60 是普适正确答案。Higress-RAG 论文披露混合检索 +
   Metadata-Aware Boost Ranker 在其两个测试数据集上召回率（Hit Rate）均超过 90%，
   相比纯向量基线提升约 30 个百分点——同样是单一厂商自测、样本领域狭窄，不可外推
   为通用结论，但方向上支持“精确关键词场景必须上混合检索”这个判断。第 9 章 §9.3 已经完整讲过混合检索、RRF、Rerank、CRAG 各自解决 RAG 生产翻车的哪个环节，
   这里不重复原理，直接复用。
2. **私有化替换商业闭源 API**：把生成环节从外部闭源 API 换成自托管的开源模型，
   直接解决限流硬上限和按次计费失控这两个问题——自己的推理集群没有供应商配额
   天花板，边际成本从“每次调用付费”变成“摊薄到硬件与电力成本”。这一步不是没有
   代价的，量化模型的精度损失会带来新的问题，§17.6 会讲到踩的坑。
3. **量化与 vLLM**：生成服务用 vLLM 部署，当前锁定版本 0.26.0。这里要纠正一个
   容易抄错的旧说法：PagedAttention 不是 vLLM 现在的核心卖点——v0.25.0 的发布
   说明在 PR #47361 写明 “PagedAttention has been removed”，当前架构是 V1/Model
   Runner V2 统一引擎路径——第 10 章 §10.3 已经讲清楚这个变化的来龙去脉，这里不
   重写，只强调一点：如果本章还在按“PagedAttention 是 vLLM 的显存优化卖点”这个
   过时说法去介绍技术选型，就是自己打自己的脸。量化选用 AWQ/GPTQ 一类方案压缩
   模型体积、提升单卡吞吐，从而把生成环节的推理延迟压进 170ms 预算，代价是需要
   在精度和延迟之间反复测试找平衡点。
4. **语义缓存**：阈值不是抄一个数字上生产。Higress-RAG 论文披露的做法是默认
   相似度阈值 0.95，查询里出现“maybe/possibly”一类不确定性词汇时收紧到 0.98，
   TTL 默认 7 天（168 小时）；语义缓存整体带来约 40% 的 token 成本节省。这些数字
   可以作为起点参考，但第 10 章 §10.4 已经讲过阈值标定的正确方法——在自己的
   黄金集或历史真实流量上，把“相似度”和“答案是否真的可以互换”两个维度都标出来，
   先确认两组分布是否分得开：可分时把阈值定在拐点以下，不可分时（Lab-06 实测就是这种情况）
   再高的阈值也挡不住误命中，必须叠加词面护栏与显式裁判。总之不要照抄 0.95。
5. **冷启动消除**：针对大促这类可预测的流量洪峰（活动开始时间是已知的），在活动
   开始前主动预热——提前拉起足量推理实例并加载好模型权重、预热连接池和向量库
   客户端，而不是等真实流量涌入后才触发自动扩容。不可预测的突发流量（比如自然
   热点事件）无法提前预热，这类场景的冷启动问题本章没有给出通用解法，需要另外
   设计降级策略（比如短暂放宽阈值把更多请求导向缓存命中路径）。

### 这类“倍数提升”数字该怎么测

本书通篇在教读者辨别可疑数字（见上册第 2 章“四周现场冲刺解锁百万合同”的溯源示范），
如果本章自己甩一个“10 倍提升”却不说测法，就是自打嘴巴。任何声称“延迟降到原来
的几分之一”或“吞吐提升几倍”的数字，至少要交代清楚四件事：

**基线怎么定**。基线必须是“同等并发条件下的旧链路”，不能拿旧链路在日常低并发下的
表现，去对比新链路在大促高并发下的表现——那是在比较两个不同的负载条件，不是在
比较两套架构。正确做法是用同一份压测流量（最好是脱敏后的真实历史流量重放，不是
随机生成的合成文本，否则测出来的缓存命中率和检索难度都会失真）分别打旧链路和
新链路。

**并发怎么打**。用负载测试工具模拟真实大促的流量曲线——不是恒定并发的稳态测试，
而是模拟断崖式涌入的爬坡曲线，因为 §17.2 已经讲过瞬时冲高本身就是压力来源之一，
稳态压测测不出扩容跟不上的问题。

**报哪个指标**。必须同时报 P50/P95/P99，不能只报均值——均值会被大量命中缓存的
快请求拉低，掩盖没命中缓存的那部分用户的真实体验。如果只能选一个数字对外汇报，
P95 或 P99 比均值更诚实。

**冷启动和缓存命中的请求算不算**。这两类请求必须单独统计，不能混进主指标：冷启动
请求（模型刚加载、连接池未预热时的请求）耗时明显偏高，如果混入总体分布会拉高
P99 但又不代表稳态性能，应该单独报告“冷启动耗时分布”和“冷启动请求占比随时间
衰减到零的曲线”；缓存命中和未命中请求要分开报各自的 P50/P95/P99 和各自占流量
的比例，而不是把两者混合平均出一个好看的总体数字——命中率越高、混合平均数就
越好看，但这个数字对那些没命中缓存、真正走完整检索生成链路的用户毫无意义。

按这四条交代清楚之后，“优化后 P99 从 X 降到 Y”这类结论才立得住。反过来，任何
不说清楚基线口径、并发曲线、统计口径、冷启动与缓存处理方式的“N 倍提升”，都应该
按第一层可信度分层里的“笼统说法”对待，不采信。

| **3** | 语义缓存，不用精确匹配缓存 | 用户是语音转写的口语化文本，同一意图措辞变体极多 | 按查询字符串做 key 的 KV 缓存（方案二） | 要定阈值，而阈值定错会答错 | **改过**：照抄论文的 0.95 阈值直接用，出现过“能不能退货”命中“能不能换货”的错答；后来在自己的历史流量上重新标定，并把高风险问题类型排除在缓存外（§17.6） |
| **4** | 私有化量化模型替代外部 API | 供应商 QPS 是硬上限，配额升级要走商务流程，大促当天来不及 | 横向扩容 + 加配额（方案一） | 量化带来精度损失 | **认知变过**：原以为换掉 API 顺带解决精度，实际它只解决限流和成本，精度要单独验（§17.6） |
| **5** | 不上完整 CRAG 自纠错链路 | 完整深度推理链路端到端 11–20 秒，和 300ms 差两个数量级 | CRAG 三分类 + 网络搜索兜底（方案三） | 精度低于完整链路 | 未变 |
| **6** | 大促提前手动预热，自动扩容只兜底 | **新实例拉起到权重加载完、连接池预热完要秒级到分钟级，流量洪峰是瞬时的** | 全靠自动扩容规则 | 要人盯着活动时间表 | **这条是事后补的**（§17.6） |

**第 3 行是这本书反复讲的那件事在这一章的实例**：论文里的 0.95 是在论文的语义空间里
标定出来的，搬到另一个业务的语义空间里，同一个数字含义完全不同。
上册第 13 章讲“口径不同的数字不能并列比较”，第 10 章 §10.4 讲阈值要在自己的历史流量上标定——
**这条决策就是那两句话没听、然后交了学费的记录。**

**第 6 行不是性能优化，是一个关于时间的判断。** 自动扩容的响应速度和流量洪峰的
上升速度不在一个量级上，这件事和模型、框架、云厂商都没关系。
**可预知的峰值要预热，不可预知的才交给自动扩容**——两者是分工，不是替代。

**第 1 行值得单独强调，因为它是这一章唯一可以无损搬走的东西。**
表里那些具体数字（40ms 检索、170ms 生成）会随硬件和模型变化，
**但"先把总预算拆到每一环，再让每一环各自守住"这个动作不会变。**
一个只报端到端延迟的性能方案，出问题时无法定位，也无法谈判——
客户说"要更快"的时候，你能拿出来的只有一句"我们再优化一下"。

## 17.5 关键代码骨架

本章对应的可运行实现分别是 **Lab-04（混合检索 RAG，Task 39）**与 **Lab-06（vLLM
私有化 + 量化 + 语义缓存，Task 41）**，全书 Lab 清单为 Lab-01 至 Lab-12（见附录 A），
两个 Lab 均已实现；下方代码块分别标明哪些直接取自 Lab、哪些仍是场景化示意。
不要把单个 Lab 的实测结果外推为不同硬件、模型和流量分布下的生产指标。

*✓ 本段取自 Lab-04，`verify.sh` 7/7 实测通过。完整实现见 `labs/lab-04-hybrid-rag/src/retrieve.py`。*
```python
# 取自 Lab-04 src/retrieve.py，1241 篇语料 / 59 条查询实测
RRF_K = 60      # 常用默认值
TOPK  = 50      # 各路截断深度——这个参数比 k 更要命，见下方说明


def rrf(rank_lists: list[list[str]], k: int = RRF_K, topk: int = TOPK) -> list[str]:
    """Reciprocal Rank Fusion：score(d) = Σ 1 / (k + rank_i(d))。

    好处是不需要把 BM25 分数和余弦分数归一化到同一量纲——只用名次。
    """
    scores: dict[str, float] = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst[:topk], start=1):   # 截断是关键，见下
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    # 并列时按 doc_id 定序，保证多次运行结果完全一致
    return [d for d, _ in sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))]


async def hybrid_retrieve(query, dense_client, sparse_client, top_n=20):
    # 两路检索并行发起，不是先后串行，这是 §17.4 表格里 40ms 预算能守住的前提
    import asyncio
    dense_hits, sparse_hits = await asyncio.gather(
        dense_client.query_points(query),   # 注意：Qdrant client 1.16.0 起
        sparse_client.search(query),        # 已移除 search()，向量侧须用 query_points()
    )
    return rrf([dense_hits, sparse_hits], topk=50)[:top_n]
```

**`lst[:topk]` 这一刀不能省。** 实测中先按“对两路完整排序做 RRF”实现，结果混合检索永远夹在两个单路基线中间，怎么调 `k` 都超不过更强的那一路。原因是不截断时每一路的头部结果都无条件参与打分——一个 BM25 排第 1、向量排第 800 的文档，靠 BM25 那一项拿到 `1/61`，仍然能挤掉向量排第 1、BM25 排第 200 的正确答案。截断到 top-50 之后，落在 50 名之外的文档不再获得任何贡献，混合才同时超过两个基线（58/59 对纯向量 53/59、BM25 54/59）。

`k` 的取值反而没那么敏感：不同厂商实现的默认值并不统一（Elasticsearch k=60 / Qdrant k=2），自建融合逻辑时 `k` 需要结合自己的检索器排名分布单独标定，不要直接照抄——但**先把截断做对，再去调 `k`**，顺序反了会浪费很多时间在错误的旋钮上。

*⚠️ 部分未实测 —— 其中的 vLLM 私有化调用部分（OpenAI 兼容端点 + `--api-key`）已在 RTX 4090 实测通过；**语义缓存那一半仍是本节的单阈值草案**，Lab-06 实测证明它在真实语料上无法同时做到有用和安全，正确做法见 Lab-06 的三层结构。*
```python
# semantic_cache_and_serve.py —— 语义缓存 + vLLM 私有化调用骨架（示意，未实测）
import time

HIGH_SIM_THRESHOLD = 0.95   # 起点参考值；注意本段是“单阈值”方案，即 Lab-06 里的对照组
FUZZY_SIM_THRESHOLD = 0.98  # 查询含不确定性词汇（"maybe"/"大概"）时收紧
CACHE_TTL_SECONDS = 7 * 24 * 3600  # 7 天，同样是起点参考值


def pick_threshold(query: str) -> float:
    uncertainty_markers = ("maybe", "possibly", "大概", "好像")
    if any(marker in query for marker in uncertainty_markers):
        return FUZZY_SIM_THRESHOLD
    return HIGH_SIM_THRESHOLD


async def answer(query: str, cache, retriever, reranker, vllm_client):
    t0 = time.monotonic()
    threshold = pick_threshold(query)
    cache_hit = await cache.lookup(query, threshold=threshold, ttl=CACHE_TTL_SECONDS)
    if cache_hit is not None:
        return {"answer": cache_hit, "path": "cache_hit", "elapsed_ms": (time.monotonic() - t0) * 1000}

    candidates = await retriever.hybrid_retrieve(query)
    top_docs = await reranker.rerank(query, candidates, top_k=5)  # 裁剪候选集守住 30ms 预算
    # vllm_client 指向自托管的量化模型服务：vllm serve <model> --quantization awq
    completion = await vllm_client.generate(query=query, context=top_docs, max_tokens=128)
    await cache.write(query, completion)
    return {"answer": completion, "path": "cache_miss", "elapsed_ms": (time.monotonic() - t0) * 1000}
```

## 17.6 踩过的坑

- **当时以为**把两路检索改成并行发起就能守住检索环节的预算，**实际**Rerank 才是
  隐藏的延迟大户——上线一个精度更高的 cross-encoder 之后，P99 直接顶穿 300ms
  预算，排查发现候选集深度设得太大（top-100 送进重排），最后靠裁剪候选规模和换
  更轻量的重排模型才把这一环节压回预算内，精度和延迟必须一起权衡，不能只看
  Rerank 单独的准确率指标。
- **当时以为**语义缓存阈值调到论文里的 0.95 就能直接用，**实际**这个数字在自己
  的业务语义空间下含义完全不同——上线初期出现过几次“文不对题”的缓存命中，
  排查后发现是把两个语义相近但答案完全不同的问题（“能不能退货”和“能不能换货”）
  错误复用了同一个缓存答案，最后按第 10 章 §10.4 的方法在自己的历史流量上重新
  标定阈值并确认分布可分，把高风险问题类型直接排除在语义缓存之外。
- **当时以为**换成私有化量化模型就能一劳永逸解决限流和成本问题，**实际**量化
  带来的精度损失导致某些边界问题的回答质量下降，客服质检团队反馈错误率有小幅
  上升，说明“换掉外部 API”解决的是限流和成本这两个问题，不会自动解决精度问题，
  两者要分开验证，不能默认量化模型和原来的商业 API 精度对齐。
- **当时以为**压测报告里的平均延迟达标就等于生产没问题，**实际**均值达标的
  同一份报告里 P99 因为冷启动请求和缓存未命中的长尾请求被拉得很高，只看均值会
  完全掩盖这部分用户的真实体验，这正是 §17.4 强调“必须报 P95/P99”的直接原因。
- **当时以为**大促这种百倍流量峰值靠自动扩容规则就能兜住，**实际**新实例从
  拉起到模型权重加载完成、连接池预热完毕需要秒级到分钟级时间，而流量洪峰是
  瞬时涌入的，扩容速度天然跟不上——最后的解法是针对已知时间点的大促活动提前
  手动预热，自动扩容规则只用来兜底预热窗口之外的意外波动，不能指望它应对
  可预知的瞬时峰值。

## 17.7 复盘与可迁移经验

**可迁移的经验**：延迟预算分解表这个方法本身可以直接搬到任何有硬性延迟约束的
AI 系统——不只是语音客服，任何“用户在等一个实时结果”的场景都适用；用 P50/P95/P99
而不是均值衡量性能、把冷启动和缓存命中请求分开统计，这套压测方法论对所有声称
“倍数提升”的性能优化项目都适用；语义缓存阈值必须在自己的黄金集上标定、先确认分布可分、
不能照抄论文或别家的默认值，这条同样可迁移到任何引入相似度阈值判定的系统。

**不可直接迁移的部分**：300ms 这个具体预算数字、各环节的具体毫秒分配、RRF 的
k 值、量化方案的具体选择，都随场景的延迟容忍度、知识库规模、模型选型变化，换一个
客户基本要重新分配预算表，不存在“一套预算表走天下”的配置；具体的冷启动预热策略
也高度依赖于流量峰值是否可预知，本章的“提前手动预热”方案只对已知时间点的大促
成立，对不可预测的突发热点场景无效，需要另外设计。

**外部对照参考**：Notion 官方技术博客披露的向量检索系统四阶段优化历程可以作为
量级参照——活跃工作区增长 15x、向量数据库容量扩展 8x 的背景下，通过分阶段迁移
到 serverless 架构（成本较峰值下降 50%）、turbopuffer 向量数据库（搜索引擎支出
降低 60%、AWS EMR 计算成本降低 35%、p50 生产查询延迟从 70–100ms 改善到
50–70ms）、Page State 重构（数据量减少 70%）、Ray/Anyscale 计算迁移（预计基础
设施成本降低 90% 以上）四步，把系统撑住了增长曲线[1]。这是 Notion 自己系统的
真实结果，量级和本章虚构客户不同、技术栈也不同（Notion 面向的是搜索场景，不是
300ms 实时语音应答），不能把这组数字当作本章合成案例“音境科技”的效果证明，
只能作为“分阶段优化、每一步都有独立可验证的成本或延迟数字”这种做法本身值得
效仿的参照系。

这里有一条值得单独拎出来的教训：性能优化项目最容易在汇报阶段把复杂的分位数
分布简化成一个“提升了 N 倍”的标题数字，这个简化动作本身就是风险点——它可能
悄悄把冷启动请求剔除了、可能只统计了缓存命中路径、可能拿了不对等的基线做对比。
FDE 交付性能优化项目时，展示分位数分布图和统计口径，比展示一个好看的倍数标题
更重要，因为后者经不起客户技术团队的第二轮追问。

### 这个案例留下了哪一类结果

**证据，而且是一个可以直接搬走的载体：延迟预算分解表。**

这张表把“够不够快”这句没法判定的话，拆成每一环各自可测的实测耗时。
**它是证据的一种形态——不是结论，是能被复核的分解。**

要注意它的可迁移边界。**方法可以搬，数字不能搬**：
300ms 这个总预算、各环节的具体毫秒分配，全部是这个客户这套硬件下的取值。
换一个现场，表的结构照抄，格子里的数要重新测一遍。

**一张空表比一张填满别人数字的表更有用**——后者会让人以为不用测了。

## 自检问题

1. 为什么“多买配额、多加并发”这个方案在方案评审阶段就能被否决，而不需要等原型
   压测跑出来？
   参考答案要点：外部 API 的限流是供应商侧硬性 QPS 上限，商务流程不是当天能
   走完的开关；P99 延迟的瓶颈是单次网络往返加生成耗时本身，这个耗时不随并发数
   增加而缩短，靠纸面上的数量级判断就能否决，不需要浪费一轮原型开发。

2. Higress-RAG 论文里“缓存命中 50ms、缓存未命中且走完整深度推理链路 11–20 秒”
   这两个数字，为什么不能直接当成本章虚构客户的性能基准？
   参考答案要点：这是论文作者单一厂商在自己狭窄测试领域上的自测数据，样本量
   小且场景局限，只能用来校准数量级（比如判断某条链路是否与 300ms 预算兼容），
   不能当作可以照搬套用的通用基准，更不能当作本章合成案例的真实实测结果。

3. 语义缓存上线后出现“文不对题”的错误命中，第一步该查哪里？
   参考答案要点：先查阈值是不是照抄了论文或别家的默认值、没有在自己的黄金集或
   历史流量上标定阈值并确认分布可分；再查是否有高风险问题类型（语义相近但答案完全不同的问题）
   应该被排除在语义缓存之外，而不是直接调低阈值了事。

4. 一份压测报告写着“P99 延迟从 800ms 降到 200ms，提升 4 倍”，你会追问哪几件事？
   参考答案要点：基线和优化后版本是不是打的同一份流量、同等并发条件；报的是
   混合流量的 P99 还是缓存未命中路径单独的 P99；冷启动请求有没有被剔除或单独
   统计；样本量和测试时长是否足够覆盖峰值场景，而不是短时间内的小样本。

5. RRF 融合公式里的 k 值，Elasticsearch 默认 60、Qdrant 默认 2，这条信息说明
   什么更普遍的工程原则？
   参考答案要点：同一个技术概念在不同厂商实现里的默认参数可能差异巨大，直接
   跨厂商照搬默认值是常见错误；任何“行业默认值”在真正用到自己的系统里之前，
   都需要确认它来自哪个具体实现，并结合自己的排名分布重新验证是否适用。

6. 为什么“完整的 CRAG 自纠错链路”在本章场景里被否决，而在第 9 章讨论的场景里
   却是值得引入的进阶技术？
   参考答案要点：技术本身没有对错，取决于延迟预算是否兼容——CRAG 链路的
   11–20 秒延迟对追求精度优先、可以接受秒级甚至更长响应的场景（比如复杂知识
   问答）是合理代价，但和 300ms 的实时语音场景之间差着约 40–70 倍（近两个数量级），
   同一项技术在不同延迟约束下的取舍结论完全相反。
