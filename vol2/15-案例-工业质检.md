# 第 15 章 · 案例二：工业质检

> **一句话结论**：漏检和误检的代价不对称，这个不对称反过来决定阈值策略，不是准确率最大化决定。

## 准确率 96%，但产线不用

模型在测试集上的准确率是 96%，团队很满意。

上线两周，质检员基本不看它的判定，还是自己拿手电筒照。

问原因，一位老师傅说得很实在：它说这个件不合格，我看不出哪儿不合格，
我要是照它说的挑出来，出了事算谁的？

**它给的是一个分数。质检员需要的是“哪里有问题”。**

## 读完这章你能做什么

1. 理解漏检与误检代价不对称如何**反向决定**模型阈值策略。
2. 掌握边缘算力受限条件下的选型判据，以及为什么云端推理在产线场景通常直接出局。
3. 设计能建立一线质检员信任的判定输出，而不只是一个分类分数。
4. 理解与制造执行系统对接时真正的工程约束在哪里。
5. 建立对“厂商宣传峰值”和“客户侧年度均值”两类数字的分辨能力。

## 15.1 客户背景

本章的客户是一家教学合成的汽车零部件冲压件工厂（以下称“晟远精密”，虚构化名），
主营变速箱壳体与冲压结构件，三班倒运行两条冲压 + 焊接产线，节拍（cycle time）
约 4.5 秒/件。缺陷类型集中在冲压毛刺、焊点虚焊、表面划伤与孔位偏移四类。

项目启动前的质检流程是人工目视 + 抽检卡尺复核：每条产线配 2 名质检员，
每人负责约 800 件/班的抽检，抽检比例约 25%。工厂管理层的诉求很直接：
不是要把人力清零，而是要把抽检比例提到接近 100%，同时不能拖慢产线节拍——
这是后面所有技术决策的第一约束条件。

工厂已有一套 MES（制造执行系统）用于排产与工序追溯，产线设备通过 SCADA
采集运行状态，但两者此前从未与视觉系统打通，质检结果全靠质检员手工录入工单系统。

## 15.2 真实冲突

四个约束互相挤压，任何单点优化都会撞上另一条边界：

**产线节拍 vs 模型规模**。4.5 秒的节拍里，拍照、传输、推理、结果回传、
分拣执行信号下发要全部走完。留给模型推理的时间预算通常只有几百毫秒量级，
这直接把可用模型的参数规模摁在了边缘设备能实时跑动的档位，不是“选个更准的模型”
就能解决的问题——推理延迟本身就是硬约束的一部分，不是次要指标。

**光照与工况漂移**。产线上的工业相机长期暴露在车间环境里，光源存在肉眼难察觉的
渐进式衰减、冲压油雾会在镜头和工件表面形成不均匀反光、不同批次来料的表面处理
（喷砂/电镀）也会改变反射特性。训练时采集的样本分布，跑不了几周就会和产线实时
分布产生偏移（distribution shift），这是工业视觉区别于互联网视觉任务最麻烦的一点：
数据分布不是静态的，是随时间缓慢漂移的。

**误判成本严重不对称**。放走一个次品（漏检，false negative）意味着这个件可能
装到整车上，追溯成本、召回风险和品牌代价是数量级级别的；而误判一个合格品为次品
（误检，false positive）最多是多一次人工复核，成本是分钟级的。这个不对称直接决定
了阈值必须往“宁可错杀不可放过”的方向偏，代价是误检率会明显偏高，管理层要提前
接受这一点，而不是等上线后才发现“AI 太爱报警”。

**质检员的信任建立**。质检员干了多年目视检验，凭经验就能一眼判断，AI 系统如果
只甩出一个“不合格”的红灯而不给理由，质检员的第一反应是不信、绕过，或者干脆
把系统当摆设。系统必须给出“AI 为什么这么判”的可视化依据，否则再准的模型也用不起来。

## 15.3 被否决的方案

**方案一：云端大模型推理（通用视觉大模型云端调用）**。最初技术选型阶段有人提议
直接调用云端多模态大模型做缺陷识别，理由是不用自己训练模型、维护成本低。
被否决的原因有三层：一是网络延迟——工厂产线专网出口带宽有限，一次云端往返
（图片上传 + 推理 + 结果下传）实测延迟在秒级，而节拍预算只有几百毫秒，
数量级都对不上；二是产线网络本身不是全年稳定的，专网偶发抖动一次就意味着
那一件产品的质检结果缺失，产线不能因为网络问题停线等结果；三是数据出厂顾虑——
产品图像和工艺参数属于客户不愿意上云的敏感信息。这条路线在第一轮方案评审就出局，
没有进入原型验证阶段。

**方案二：传统机器视觉规则引擎（阈值分割 + 模板匹配，不引入深度学习）**。
这是工厂原本考虑的保守路线，好处是可解释、无需标注数据、部署简单。原型测试后
被否决：规则引擎对光照和工况漂移极其敏感，同一套阈值参数在早班和夜班的
误报率能差出两三倍；新增一种缺陷类型（比如某批次来料出现的新型划伤模式）
需要工程师重新调参甚至重写规则，迭代周期以周计，跟不上产线实际的缺陷谱变化速度。
规则引擎在受控光箱环境下的演示效果很好，但那不是产线的真实工况。

**方案三：边缘部署大参数量视觉模型（如未裁剪的 ResNet-152 / 大型 ViT）**。
这个方案在推理精度上确实占优，但在工控机/嵌入式 GPU 上实测推理延迟超出节拍预算
两到三倍，且长时间满载运行下功耗和散热在产线机柜的物理空间里不现实——机柜没有
额外风道扩容的余地，也不允许为了塞下这块卡去改造产线电气布局。最终判定这是一个
“实验室能跑但产线跑不动”的方案，同样出局。

三个方案被否决后，团队才把选型收敛到“轻量化边缘模型 + 分层阈值策略”这条路径上。

## 15.4 最终架构决策

判据只有一条：**在满足节拍延迟预算的前提下，把漏检率压到最低，误检率控制在
质检员可接受的复核工作量以内**。据此做出四项决策：

1. **模型侧**：选用轻量化卷积网络（MobileNet 系裁剪版本作为骨干网络）做缺陷
   分类 + 定位，在边缘工控机（不依赖云端）上实时推理，推理时间控制在节拍预算的
   三分之一以内，留出余量给拍照、传输和分拣执行信号。
2. **阈值策略**：不用单一分类阈值，而是设计双档判定——“高置信度合格”直接放行，
   “低置信度合格”与“任意置信度不合格”一律转人工复核。这是应对误判代价不对称
   的直接工程手段：宁可让复核台多接一些件，也不让漏检发生在自动放行环节。
3. **训练与漂移应对**：云端只负责模型训练、版本管理和长尾样本的回流学习，
   不参与实时推理。产线定期把复核台产生的人工标注样本回传训练集，形成模型
   迭代闭环，用来对抗光照/工况的缓慢漂移，而不是指望一个模型一次训练管一年。
4. **对接方式**：与 MES/SCADA 的集成走标准工业协议（OPC-UA 读写节点 + PLC 触发
   信号），质检结果作为工序数据写回 MES 追溯链路，不改造产线原有的 PLC 控制逻辑，
   视觉系统作为“旁路观察 + 分拣执行触发”接入，避免成为产线停机的单点故障源。

| **4** | 视觉系统作为**旁路观察 + 分拣触发**接入，不改产线 PLC 控制逻辑 | 视觉系统不能成为产线停机的单点故障源 | 让 AI 直接接管 PLC 控制 | 能做的干预有限，只能触发分拣不能改工艺 | 未变。**这是全章最该被迁走的一条** |
| **5** | 加缺陷热力图，给质检员看判定依据 | —— | 只给红绿灯结论 | 前端和推理侧都要多做一层 | **这条是事后补的**：早期版本没有可视化依据，质检员倾向于忽略红灯直接放行（§15.6） |

**第 4 行是这一章最有迁移价值的一条，而且它不是技术决策，是爆炸半径决策。**
技术上让 AI 直接控制 PLC 完全做得到，也更"彻底"。选择旁路接入，
放弃的是控制力，换来的是**这套系统出任何问题都不会让产线停**——
上册第 14 章 §14.4 那句"先问出错之后哪些后果撤不回来，再定灰度比例"，
在这里的答案是产线停机，所以爆炸半径必须压到零。

**第 5 行是全书唯一一条写进决策日志的采用率决策**，它对应本章开头那句
"准确率 96%，但产线不用"。热力图对准确率没有任何贡献，
**它贡献的是一线愿不愿意看那盏红灯**——上册第 15 章讲的第三层
"进了工作流"，工程上有时候就是这么一个不起眼的东西换来的。

**第 2 行两次"改过"值得一起看**：一次是光源老化（时间导致的漂移），
一次是来料工艺变更（上游导致的漂移）。两次都不是模型的问题，
都是环境变了而阈值没跟着变。**这类项目里"部署即终点"是最贵的假设。**

### 五层坐标

| 层 | 这个案例里长什么样 |
|---|---|
| **本体** | **空。** 对象只有「一个待检件」，MES 追溯链路的数据模型是既有的，本项目不建本体 |
| **技能** | **薄，但在长。** 复核台产生的人工标注回流训练集，是「专家方法沉淀」的一种形态——只是它沉淀成了模型权重和阈值，不是可读、可交接的技能 |
| **工具** | **主战场。** 边缘轻量模型推理 + OPC-UA 读写 + PLC 触发信号；**旁路接入不改 PLC 控制逻辑**是全章最该被迁走的一条 |
| **验收** | **主战场，而且是判据的来源。** 误判代价不对称直接决定双档阈值，不是准确率最大化决定；阈值改过两次（光源老化、来料工艺变更），最终纳入常规再校准流程 |
| **智能体** | **无。** 这个案例里没有智能体——一条固定的推理-判定-触发链路，不需要协调者 |
| **治理**（横切） | **中。** 质检结果写回 MES 追溯链路即留痕；爆炸半径压到零（不让产线停）是治理判断而非技术判断 |

**这一章的重心整个压在工具和验收两层，智能体那一栏是空的。**
值得停一下：**一个没有智能体的项目照样是一次完整的 AI 交付。**
第 8 章 §8.3 讲过智能体只是第五层，这一章是它的反面印证——
**智能体不是这套方法论的必要成分，验收集才是。**

还有一条要点出来：热力图那条决策（第 5 行）在五层里挂不上任何一层，
它是第 6 关采用的产物。**五层管建什么，六关管什么时候算成**——
一个对准确率零贡献却决定了一线愿不愿意看那盏红灯的东西，
只有从关卡那一侧才看得见。

## 15.5 关键代码骨架

以下是边缘推理服务的核心结构。**这两段是示意性骨架，用于说明架构决策如何落到代码层，
未经实测验证，不要直接用于生产**——本章没有配套 Lab（12 个 Lab 的清单见附录 A），
边缘推理的可运行实现最接近的是 Lab-06（vLLM 私有化与推理优化），但那是语言模型场景，
视觉边缘部署的工程细节与之不同。

```python
# edge_inference_service.py —— 边缘推理服务骨架（示意，未实测）
import onnxruntime as ort

class DefectInspector:
    def __init__(self, model_path: str, high_conf_thresh=0.92, low_conf_thresh=0.60):
        self.session = ort.InferenceSession(model_path, providers=["CUDAExecutionProvider"])
        self.high_conf_thresh = high_conf_thresh  # 高置信度合格 -> 放行
        self.low_conf_thresh = low_conf_thresh    # 低于此值也视为不确定 -> 人工复核

    def infer(self, image_tensor):
        score, defect_map = self.session.run(None, {"input": image_tensor})
        return self._route(score, defect_map)

    def _route(self, score, defect_map):
        # 不对称代价的核心体现：合格判定要求高置信度，其余一律转人工。
        # 两个阈值划出三段：高于 high 放行；低于 low 视为"明确可疑"，
        # 复核队列里排高优先级；中间地带是"模型拿不准"，排普通复核。
        if score >= self.high_conf_thresh:
            return {"decision": "pass", "review_required": False}
        priority = "high" if score < self.low_conf_thresh else "normal"
        return {"decision": "reject_or_review", "review_required": True,
                "review_priority": priority,
                "heatmap": defect_map}  # 供质检员前端可视化依据
```

## 15.6 踩过的坑

- **当时以为**白平衡校准一次就能长期稳定，**实际**光源存在缓慢老化衰减，
  上线两个月后误检率开始爬升，才意识到需要建立周期性基线校准的运维节奏，
  而不是“部署即终点”。
- **当时以为**提高输入图像分辨率能直接换来更高准确率，**实际**分辨率翻倍
  后推理延迟逼近节拍上限，产线出现偶发积压，最后是在分辨率和延迟之间找平衡点，
  而不是单方向堆参数。
- **当时以为**阈值调优一次定型就能长期有效，**实际**来料批次的表面处理工艺
  发生过一次调整（供应商更换喷砂工艺），旧阈值在新批次上误检率明显抬头，
  说明阈值需要纳入常规再校准流程，而不是一次性交付项。
- **当时以为**接入 MES 只是“发一条消息”的事，**实际**PLC 触发信号与拍照/推理
  的时序没对齐，早期出现过因信号时序错位导致的漏拍，排查花了不少时间才定位到
  是触发脉冲宽度不够，不是视觉系统本身的问题。
- **当时以为**质检员会因为系统“更准”就自然信任 AI 判定，**实际**在没有可视化
  依据的早期版本里，质检员倾向于忽略红灯直接放行，直到加上热力图之后，
  复核台的响应率才明显提升——技术指标达标不等于一线愿意用。

## 15.7 复盘与可迁移经验

**可迁移的经验**：不对称代价决定阈值策略这一判据，几乎适用于所有“漏检代价远高于
误检代价”的检测场景（安防、医疗初筛同理）；轻量化边缘模型 + 云端只做训练迭代
的分工模式，可以直接搬到其他产线节拍敏感的场景；给一线用户可视化判定依据这条，
本质上是任何“AI 替代人工判断”项目都要过的信任建立关卡，不是工业质检独有。

**不可直接迁移的部分**：具体的模型骨干网络选择、阈值数值、光照校准周期，
都随产线、缺陷类型、相机硬件变化，换一条产线基本要重新标定，
不存在“一套阈值走天下”的配置。

MES/SCADA 对接的协议细节同样不可迁移。本章用的是 OPC-UA，换一家工厂可能是
Modbus TCP，甚至是更老旧的私有协议。

**这里有一条值得单独拎出来的排期教训**：对接层的工程量往往比模型调优还大，
但在立项时经常被低估。客户默认“模型能跑就等于系统能上线”——实际上从
“模型输出一个判定结果”到“这个结果能安全驱动产线分拣动作”之间，
还隔着信号时序对齐、异常兜底、单点故障隔离这一整层工作。

**这部分工作量必须在立项阶段单独列项，不要合并进“模型开发”里估算。**
合并了，对接阶段就会出现工期严重超预期，而且很难向客户解释——
因为在客户眼里“模型早就做好了”。

现实中的工业质检落地效果，可以对照华为官方案例集里的具名客户数据：富士康
智能光伏控制器质检产线“月检测 6000+ 台，总体准确率＞99%”，宝德计算机
在来料检验/制程检验/包装检验环节“检测准确率超过 99%”，美的集团冰箱事业部
冷柜工厂多个检测环节“检测准确率提高了 10%”（华为官方案例页披露，未注明
统计周期，也未说明是 10 个百分点还是相对提升 10%，这个模糊度不做擅自具体化）
[1]。同一页面还有一条未具名的“某汽车制造商”案例：缺陷率下降 80%、
单件生产时间缩短 6 分钟、订单交付提速 20%（华为官方案例集披露，客户身份
匿名化处理）[2]，这条恰好和本章合成案例的行业属性接近，可作为效果量级的
参照系，但同样不能当作本章虚构客户“晟远精密”的真实结果。

**国际对照：期望管理是 FDE 的日常工作，不是意外**。OpenAI 官方案例页面披露，
John Deere 的 See & Spray 精准喷洒系统“结果是化学品使用最多减少 70%”
（“Up to 70% less chemical use”）[3]。这句话是一手来源，逐字属实，但“up to”
是关键限定词——它是最优条件下的峰值，不是平均表现。John Deere 自己在官方
新闻稿里披露的年度数据是另一回事：2024 年种植季客户平均节省除草剂 59%
[4]，2025 年扩大到 500 多万英亩后，平均减少约 50%[5]。同一套系统，
厂商宣传口径的“最多 70%”和客户侧年度均值的“59%/约 50%”之间存在明显落差，
而且落差方向是稳定的——峰值总是比均值好看。

这不是 John Deere 或 OpenAI 哪一方在说谎，“up to 70%”和“平均 59%”完全可以
同时为真，它们衡量的根本不是同一件事：前者是理想工况下单点样本的上限，
后者是覆盖各种真实田块条件后的年度平均。FDE 在客户现场天天要处理的正是这类
落差——销售/产品团队展示的是最优演示场景的峰值指标，客户真正会体验到的是
覆盖各种边缘工况后的均值表现。本章的工业质检项目同理：模型在验证集上的
准确率可以做到很漂亮，但产线交付后客户实际感受到的，是覆盖了光照漂移、
批次差异、极端工况之后的长期均值。项目立项阶段就应该主动把“最优条件峰值”
和“预期年度均值”分开讲清楚，而不是等客户自己发现两者不一致时才被动解释——
那时候项目的信任成本已经付出去了。

### 这个案例留下了哪一类结果

**接管。**

热力图这个设计常被当成“可解释性”来讲，但它在这个项目里真正起的作用是别的：
**它让质检员能自己判断这次结果该不该信。**

一个用户只能接受或拒绝系统结论的项目，交付完成之后仍然要靠你在旁边解释；
一个用户能自己看出“这次模型看的地方不对”的项目，你才走得掉。
**这就是接管，而它是在界面设计那一步就决定了的，不是在交接会上。**

## 本章清单

- [ ] 先量清楚漏检和误检各自的实际代价，**再定阈值**。不要按整体准确率最大化设计
- [ ] 拿产线节拍去否决方案，不要等原型跑出来才发现延迟不达标
- [ ] 判定输出必须能让一线看出“哪里有问题”，不能只给一个分数。
      **这是系统被真正采用而不是被绕过的必要条件**
- [ ] 光照和工况漂移做专项测试，测试集上的准确率撑不住这一项
- [ ] 引用厂商案例数字时，分清那是宣传峰值还是客户侧年度均值，项目早期就做期望管理

## 自检问题

1. 为什么“云端大模型推理”在工业质检场景通常在方案评审阶段就被否决，而不是
   等原型跑出来才发现问题？
   参考答案要点：产线节拍是硬约束（毫秒到秒级），云端往返延迟通常是秒级起步，
   数量级不匹配；专网稳定性和数据出厂顾虑进一步强化了否决理由；这些是可以在
   方案纸面阶段就用节拍预算和网络实测数据算清楚的，不需要浪费一轮原型开发。

2. 漏检和误检的代价不对称，具体是怎么落到阈值策略的工程实现里的？
   参考答案要点：不用单一阈值判定合格/不合格，而是设计“高置信度才放行、
   其余一律转人工复核”的双档策略，把误判成本从“自动放行一个次品”转移成
   “多一次人工复核”，用复核台的分钟级成本去覆盖漏检的潜在追溯/召回代价。

3. 光照与工况漂移为什么是工业视觉区别于一般图像分类任务的关键难点？
   参考答案要点：训练时采集的样本分布不是静态的，光源老化、来料批次变化、
   车间环境波动会让产线实时分布持续偏离训练分布，模型需要配合定期回流数据
   和再校准机制，而不是“训练一次终身可用”。

4. 华为官方案例页面披露的“美的集团检测准确率提高了 10%”这条数字，引用时
   需要注意什么？
   参考答案要点：原文只写“提高了 10%”，没有说明是 10 个百分点还是相对
   提升 10%，也没有注明统计周期，引用时要保留这个模糊度，不能擅自解读成
   某个具体口径。

5. John Deere 案例里“最多减少 70%”和“平均减少 59%/约 50%”这两组数字，
   为什么不是矛盾的，FDE 该怎么用这个案例做客户期望管理？
   参考答案要点：两者衡量的统计量不同，前者是最优条件下的峰值，后者是覆盖
   各类真实工况的年度均值，可以同时为真；FDE 应在项目早期主动把“演示场景
   峰值”和“预期长期均值”分开讲给客户，而不是等客户自己发现落差。

6. 本章合成案例中“提高图像分辨率反而拖累产线”这个坑，说明了什么更普遍的
   工程原则？
   参考答案要点：单一维度的指标优化（这里是准确率）如果不和其他硬约束
   （这里是节拍延迟）联合考虑，很容易做出局部最优但整体不可用的决策；
   模型选型必须在约束条件下做多目标权衡，而不是孤立地追求某一项指标。
