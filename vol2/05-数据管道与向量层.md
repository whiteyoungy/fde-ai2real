> **一句话结论**：检索答错的时候，先分清是数据缺失、检索失败、数据污染，还是模型幻觉。

## 5.0 先查数据，再怪模型

客户拿一条错误回答来找你，最省事的假设是“模型不行”。这个假设几乎总是先被提出，
而且**几乎总是最后才被证实**——因为它是唯一一个不需要你去看数据的假设。

这一章的全部内容可以收进一句话：**在说“模型不行”之前，
要能指出错误发生在哪一层。** 一条错误回答，从数据进系统到答案出系统，
中间有六层可能出错，每一层的修法完全不同：

| 层 | 问什么 | 错在这一层的样子 | 修哪儿 | 在哪一节 |
|---|---|---|---|---|
| **① 源** | 源头数据本身对不对、全不全、新不新 | 知识库里压根没有能回答这个问题的内容 | 补内容、修数据源 | §5.1 |
| **② 解析** | 文件被读成文字之后，还是不是原来那个意思 | 表格被拉成一行、页眉页脚混进正文、扫描件识别错行 | 换解析路径 | §5.3 |
| **③ 分块** | 一段完整的语义有没有被切断 | 检索到的片段只有半句话，或者上下文全丢了 | 改分块策略 | §5.4 |
| **④ 索引** | 建索引的配置和检索时的配置是不是同一套 | 换了 embedding 模型没重建索引；k 值线上线下不一致 | 重建、对齐配置 | §5.5 |
| **⑤ 检索** | 该找的东西有没有被找出来 | 内容在库里，这一次没被召回 | 修检索算法、加混合检索或重排 | §5.6 |
| **⑥ 生成** | 找对了材料，模型有没有忠实转述 | 材料是对的，回答里有材料里没有的话 | 改提示词、换模型 | §5.6、第 9 章 |

**顺序不能倒着查。** 从第六层开始怀疑模型，会一路换模型、调提示词，
而真正的原因可能在第二层——一张被解析成一行的表格。
**换十个模型也读不对一张被拉平的表。**

这张梯子最值得记的性质是：**它和用什么工具无关。**
Milvus 换成别的向量库、某个 OCR 换成另一个、某个重排模型被淘汰，
六层还是这六层，每一层要问的问题一个字都不用改。
**§5.1 到 §5.6 讲的是 2026 年每一层怎么做；这张梯子本身不会过期。**

§5.6 会把 ④⑤⑥ 三层展开成一套可执行的三步归因脚本（Lab-04 里有完整实现）。
前三层没有脚本可跑，只能人去看——**这也是它们最常被跳过的原因。**

## 5.1 防御式 ETL

企业数据管道和教程里的 ETL（Extract-Transform-Load，抽取-转换-加载）demo 最大的区别，不在技术选型，在于对“上游会给你送脏数据”这件事有没有做好心理准备。教程里的数据源是干净的 CSV，企业里的数据源是十年没人维护的 ERP 导出、字段类型说变就变的第三方 API、扫描件质量参差不齐的供应商发票。防御式 ETL 的核心命题只有一个：**管道不能假设输入干净，得假设输入随时会骗你**。

**数据契约：把假设写成能跑的断言。** 数据契约（Data Contract）不是一份 Word 文档里的字段说明，是嵌在管道里、每次运行都会真正执行的 schema 断言。契约至少包含三层：

- 结构层：字段名、类型、是否可空。
- 语义层：取值范围、枚举约束、跨字段一致性，比如“结束日期不能早于开始日期”。
- 时效层：这批数据的新鲜度 SLA，多久没更新算过期。

三层里最容易被漏掉的是语义层。很多管道只做了“这个字段是不是 string”这种结构检查，对“这个金额字段是不是变成了负数”这种语义错误毫无防备。而语义错误往往比结构错误更隐蔽，下游损失更大。

**Schema Drift 检测：漂移分三种，处理方式完全不同。** Schema Drift（模式漂移）指的是上游数据结构在没有通知的情况下发生变化。实践中分三类，判据是“新结构相对契约做了什么改变”：

- **增量漂移（Additive Drift）**：新增了字段，原有字段不变。判据：旧字段集合是新字段集合的子集。处理：不阻断管道，记录一条“发现未声明字段”的告警，交由数据团队决定是否纳入契约。默认丢弃未声明字段，不自动接纳。自动接纳看似省事，实际是把“要不要用这个新字段”的决策权交给了不受控的上游。
- **破坏性漂移（Breaking Drift）**：字段被删除、改名，或类型发生不兼容变化（如字符串变数字）。判据：契约里声明为必需（required）的字段缺失，或类型转换会抛异常。处理：立即阻断该批次，不允许污染下游，这是整套防御体系里唯一“必须硬阻断”的漂移类型。
- **语义漂移（Semantic Drift）**：结构和类型都没变，但取值分布或业务含义变了。最典型的例子是枚举字段悄悄新增了一个未声明的取值，或者某个金额字段的单位从“元”变成了“分”却没人通知。判据：新数据的取值超出契约声明的枚举集合，或统计分布相对历史基线发生显著偏移。第 9 章 §9.4 的 PSI 检测思路同样适用于 ETL 输入侧，不必等到模型输出侧才做。处理：不阻断，但强制隔离并告警——语义漂移最容易在“看起来一切正常”的情况下悄悄污染下游好几天才被发现。

**脏数据分类处理策略：四条路径，判据要写清楚，不能凭经验拍。** 一条记录校验失败之后，只有“扔进死信队列”和“硬塞进下游”两个极端选项的管道，工程上是偷懒。成熟的防御式 ETL 至少要分四条路径：

| 处理路径 | 判据 | 典型场景 |
|---|---|---|
| 丢弃（Drop） | 记录本身就是噪声，且丢弃后不影响下游统计口径完整性——例如空行、明显的测试数据、重复主键中的旧版本 | 上游导出文件末尾的空行、测试环境串进生产的探针记录 |
| 修复（Repair） | 错误模式已知且有确定性修复规则，修复后能通过契约校验——例如日期格式统一转换、全角/半角字符归一化 | 日期写成“2026/8/7”而非契约要求的 ISO 格式 |
| 隔离（Quarantine） | 无法确定性修复，但记录本身可能有价值，需要人工或下游二次处理——所有语义漂移、破坏性漂移命中的记录默认走这条路径 | 发票金额字段读出来是负数，无法判断是符号错误还是业务本身允许负数（如红冲发票） |
| 告警（Alert） | 与前三条路径叠加使用，不是并列的第四条独立路径——任何触发隔离的记录都必须同时告警，任何超过阈值比例的丢弃/修复也要告警 | 单批次隔离率超过 5%，说明上游可能发生了系统性变化，不是个别脏记录 |

注意告警不是一条独立分支，是叠加在其余三条路径之上的观测层。丢弃和修复也可能需要告警，只是阈值可以设得更宽松，隔离则几乎总是需要告警。把告警设计成独立第四分支是常见的架构错误，会导致运维只盯着告警队列，却看不到大量记录正在被静默丢弃。

**这套分类策略与 Lab-01（脏 PDF 发票摄取管道）直接对应**：

- 解析出来的字段先过 Pydantic 强类型校验，对应契约的结构层与部分语义层断言。
- 校验失败时把具体的错误信息回灌进 Agent 的上下文，让 Agent 尝试自纠错重新抽取。这是“修复”路径的一种特殊形式：用模型代替确定性规则做修复。但修复结果依然要重新过一遍契约校验，不能因为是模型输出就免检。
- 多次自纠错仍失败的记录进隔离队列，不允许污染下游。

## 5.2 Airflow 编排

**版本现状先说清楚，避免抄错代码就直接翻车。** Airflow 3.x 已是主线（3.0.0 于 2025-04-22 发布，当前稳定版 3.3.0）。2.x 系列的时间线是：2.11.2 于 **2025-10-22 进入** “Limited Maintenance”（限维护期），完全 EOL 于 **2026-04-22**。这两个日期容易读反，“进入限维护”和“EOL”中间隔了半年。写文档或做升级排期时如果把两者搞混，会导致“以为还有一年缓冲期，结果三个月后就断供安全补丁”。

TaskFlow API 当前的装饰器导入路径是 `from airflow.sdk import dag, task`，这是 Airflow 3.0+ 的公开稳定接口。不是 `airflow.decorators`——那是 2.x 惯用写法，3.x 下可能仍能通过兼容层跑通，但已非官方当前教程写法。

**TaskFlow 写法：一段可直接抄的骨架。** 以下代码逐字取自官方 TaskFlow API 教程，是当前文档站给出的标准示例：

```python
import json
import pendulum
from airflow.sdk import dag, task


@dag(
    schedule=None,
    start_date=pendulum.datetime(2021, 1, 1, tz="UTC"),
    catchup=False,
    tags=["example"],
)
def tutorial_taskflow_api():
    """
    ### TaskFlow API Tutorial Documentation
    This is a simple data pipeline example which demonstrates the use of
    the TaskFlow API using three simple tasks for Extract, Transform, and Load.
    """
    @task()
    def extract():
        data_string = '{"1001": 301.27, "1002": 433.21, "1003": 502.22}'
        order_data_dict = json.loads(data_string)
        return order_data_dict

    @task(multiple_outputs=True)
    def transform(order_data_dict: dict):
        total_order_value = 0
        for value in order_data_dict.values():
            total_order_value += value
        return {"total_order_value": total_order_value}

    @task()
    def load(total_order_value: float):
        print(f"Total order value is: {total_order_value:.2f}")

    order_data = extract()
    order_summary = transform(order_data)
    load(order_summary["total_order_value"])


tutorial_taskflow_api()
```

`@task(multiple_outputs=True)` 是这段代码里容易被忽略但很实用的细节：返回 dict 时会自动展开成多个独立的 XCom（跨任务通信对象），下游任务可以按 key 取值（如 `order_summary["total_order_value"]`），不用手动解包。

官方教程原文把 TaskFlow 定位为“a more modern and Pythonic way to write workflows”，且新版文档示例几乎全部采用 TaskFlow 写法。但官方 Best Practices 页面并没有一句明文写“TaskFlow 优先于经典 Operator”，在官方口径上两种写法是并列的有效选项。“TaskFlow 是默认推荐”更多是社区共识而非官方明文表态，行文时不要把这个共识说成官方定论。

**增量同步：靠调度周期，不靠“全量扫一遍再比对”。** 增量同步的核心是让每次 DAG 运行只处理“这个调度周期内新增或变更”的数据，而不是每次都全量拉取再自行去重比对。后者不仅浪费资源，当数据量增长后迟早会拖垮调度周期。

实现上通常依赖两种信号之一：上游系统提供的增量游标(如自增 ID、更新时间戳、变更日志表)，或者 Airflow 自身的逻辑执行时间区间(`data_interval_start`/`data_interval_end`)作为查询条件。选择哪种取决于上游能不能提供可靠的增量游标。如果上游只能整表导出、没有变更时间戳，增量同步在源头上就不成立。这种情况下该反过来考虑能不能推动上游补一个变更日志，而不是在下游硬凑增量逻辑。

**回补（Backfill）：把“过去的调度周期”当成任务重新排一遍，不是临时脚本。** 回补的场景通常是：DAG 逻辑变更后需要用新逻辑重跑历史区间，或者监控发现某几天的历史数据有质量问题。Airflow 把回补作为一等公民能力对待。本质是让调度器为过去的 `data_interval` 区间重新生成并执行 DAG Run，而不是让工程师手写一个“遍历日期循环调用某个函数”的临时脚本。

这个设计上的取舍有实际后果。如果团队图省事写了游离于 Airflow 调度体系之外的补数脚本，这些补数记录不会出现在 Airflow 的运行历史里。后续排查“这段数据是什么时候、用哪个版本的逻辑跑出来的”，会失去可追溯性。

**幂等重跑：三个必要条件，少一个都不算真幂等。** 一个 DAG 任务能不能安全重跑（无论是失败自动重试，还是回补场景下对同一区间反复触发），取决于是否满足三个条件：

1. **写入操作是幂等的**。用 `INSERT ... ON CONFLICT UPDATE`（upsert）而不是纯 `INSERT`，或者写入前先按分区/主键删除该区间的旧数据再写入(delete-then-insert)。两种模式都能保证同一区间重跑多次，最终状态和跑一次一样。纯 `INSERT` 在重跑时会产生重复记录，是最常见的“以为幂等、实际不幂等”陷阱。
2. **任务的输入完全由 `data_interval` 决定，不依赖任务实际执行的墙钟时间（wall-clock time）**。如果任务内部调用了 `datetime.now()` 而不是用 Airflow 传入的逻辑执行区间，同一个 `data_interval` 的两次重跑会因为实际执行时刻不同而拿到不同的输入，直接破坏幂等性。这是全部三个条件里最容易被忽视的一条：代码能跑、测试也能过，问题只会在补数或重试时才暴露。
3. **下游消费方能容忍同一条数据被处理多次**。即使写入端做到了幂等，只要下游是一个只能“消费一次”的队列或者按增量计数的统计口径，上游的幂等保证也会在下游被破坏。幂等设计不能只看管道内部，要看到数据流向的终点。

三个条件里，最常见的错觉是**以为**“用了 upsert 就等于幂等设计做完了”——**实际**只覆盖了第一条。任务代码里混用 `datetime.now()` 依然会在回补时产出错误数据。这是防御式 ETL 章节和本节共享的同一个教训：凡是“看起来对但没有专门测试过”的假设，都值得单独找一次回补场景验证一遍。

## 5.3 文档解析深水区

企业 RAG 项目死掉，十有八九不是死在模型选型或者 rerank 参数没调好，是死在文档解析这一层。客户甩过来的从来不是排版规整的纯文本，是十年积累下来的合同扫描件、带跨页合并单元格的财务报表、图文混排的技术手册。

这一层的成本是隐形的：demo 阶段用几份干净 PDF 就能跑通，一旦接入客户真实语料库，解析准确率骤降。团队往往第一反应是去调 embedding 模型或者 rerank 参数，查了几周才发现，问题根本不在检索链路——文档解析阶段就已经把表格拆散、把段落顺序读乱了。后面所有环节都是在一堆错误输入上做优化，方向从一开始就错了。

**四类难点，各自的本质不同，不能用同一套方案硬扛。**

- **复杂 PDF（多栏排版、图文交错、页眉页脚干扰）**：本质是“阅读顺序”问题。PDF 本身没有语义结构，只有坐标。多栏排版下按从上到下、从左到右的朴素顺序抽取文本，会把两栏内容交错拼接成语无伦次的段落。
- **嵌套表格（合并单元格、跨页表格、表中表）**：本质是“结构还原”问题。表格的语义在于行列关系，一旦拆成纯文本，合并单元格对应哪几行、跨页表格的表头要不要在下一页重复，这些结构信息全部丢失。下游即使检索命中了这段文本，模型也读不出正确的对应关系。
- **扫描件（图片型 PDF，无文本层）**：本质是“识别精度”问题。依赖 OCR（光学字符识别），识别错误率直接决定了下游能拿到多干净的文本。低质量扫描件（歪斜、模糊、印章遮挡）会把识别错误进一步放大。
- **混排版式（表格+图片+正文交叉，常见于中文技术手册与政府公文）**：本质是“版面区域检测”问题。先要正确划分出哪块是表格、哪块是图、哪块是正文。划分错了，后续不管用什么表格识别或 OCR 都是在错误的区域上做无用功。

**选型判据：先问文档质量和结构复杂度，不要先问模型好不好。** 选文档解析方案时最容易犯的错误，是先去比较不同工具的“准确率跑分”。该先做的是诊断清楚自己的文档属于上面哪一类难点、难点的严重程度如何。同一个工具在“排版规整的扫描合同”和“歪斜模糊、印章盖住关键字段的手写补充条款”上的表现可能天差地别。跑分数字脱离具体语料，谈不上参考价值。

实操中建议先抽样 20—30 份客户真实文档(不是官方 demo 文档)，人工过一遍，统计四类难点各自的占比。占比出来之后，再决定要不要为某一类难点单独选型或做定制处理。

**两个国产开源工具的机制对照(均为一手核实，可作为选型参照，但准确率数字仍需自行在客户语料上实测)：**

| 工具 | 机制 | 输出格式 | 适用难点 |
|---|---|---|---|
| PaddleOCR PP-StructureV3（百度飞桨） | 官方文档原文：支持“版面区域检测、表格识别、公式识别、图表理解以及多栏阅读顺序恢复” | Markdown + 带坐标 JSON | 复杂 PDF（多栏阅读顺序恢复）、混排版式（版面区域检测） |
| MinerU（上海 AI Lab / OpenDataLab） | 官方 README 原文：“三路后端”设计——pipeline（传统流水线）、vlm-engine（多模态大模型引擎）、hybrid-engine（混合引擎） | 结构化提取（Markdown 等） | 嵌套表格、混排版式，三路后端可按文档质量切换 |

MinerU 的“三路后端”设计值得展开说一句：

- pipeline 后端是传统的检测+识别流水线，速度快，但对复杂版式的泛化能力有限。
- vlm-engine 直接用多模态大模型理解版面语义，对复杂嵌套表格和不规则版式的鲁棒性通常更好，但推理成本更高。
- hybrid-engine 是二者的折中。

这个分层设计本身就是一个可迁移的架构思路。**不要指望一个后端啃下所有文档类型，给不同复杂度的文档路由到不同处理强度的后端，是比“死磕一个模型调到最优”更现实的工程策略**。这个思路同样适用于其他文档解析场景：简单文本用便宜快速的规则/传统流水线，复杂版式再升级到多模态模型。不要无差别地对每一份文档都上最贵的方案。

**两个已知的覆盖缺口，如实说明。**

第一，上述两个工具均未在公开检索中找到关于**竖排文本**处理能力的专项说明。竖排在中文古籍、部分传统行业文档中仍然存在。如果客户语料涉及竖排，需要在选型前专门用样本验证，不能假设主流工具默认支持。

第二，具体的解析准确率数字(如 F1、编辑距离)两个工具的官方材料均未给出可直接引用的公开基准。市面流传的准确率数字大多来自厂商自评或第三方博客的小样本测试，可信度层级低于官方文档对功能特性本身的描述。**选型报告里如果要写“准确率 XX%”，必须注明是自己在客户语料上实测出来的数字，不要直接套用别处看到的跑分**。

**扫描件质量分级处理，别用同一套流程硬闯。** 扫描件的识别质量和原始清晰度强相关。防御式 ETL 的分类处理思路（§5.1）同样适用于这里：

- 清晰扫描件直接走标准 OCR 流水线。
- 轻度模糊/倾斜的走预处理(去噪、纠偏)再识别。
- 严重降质、印章遮挡关键字段的，识别结果应该被标记为低置信度并路由到人工复核。

不要让一个置信度本身就不可靠的 OCR 结果直接流入下游向量库。把一份读错了金额的发票静默送进知识库，比拒绝处理这份发票的代价更高。这个判断标准和 §5.1“隔离优于强行通过”的原则是同一套逻辑在文档解析这一层的具体应用。

## 5.4 分块策略决策树

分块（Chunking）策略的选型顺序应该反过来做。大多数团队先纠结“用固定长度还是语义分块”，真正该先问的是“这份文档的自然结构单元是什么”。合同的自然单元是条款，代码的自然单元是函数，表格的自然单元是行或行组。

分块策略的本质是把文档切成检索粒度合适、且不破坏语义完整性的片段。选型应该服从文档类型的结构特点，而不是先选一种通用算法再削足适履。

**按文档类型给出的分块判据(工程归纳，按结构特点推导，非单篇论文的逐类型实证):**

| 文档类型 | 自然结构单元 | 推荐策略 | 判据 |
|---|---|---|---|
| 合同 | 条款/款项(有编号层级) | 层级分块，按“章-条-款”的编号结构切分 | 合同检索的核心诉求是精确定位到具体条款并可追溯编号，固定长度分块会把一个条款拦腰切断，导致检索到的片段“半句话”，无法直接引用 |
| 手册/技术文档 | 标题层级(H1/H2/H3) | 层级分块，按标题结构切分，必要时给每个 chunk 附带其所属标题路径作为元数据 | 手册的语义边界由标题划定，按标题切分能保证每个 chunk 是一个完整的主题单元；附带标题路径能弥补脱离上下文后语义不完整的问题 |
| 表格 | 行/逻辑行组 | 整表作为一个 chunk(表格不大时)，或按行组切分且每个 chunk 携带表头 | 拆散表格结构等同于丢失行列对应关系(§5.3 已展开)，分块阶段就要避免把表格当纯文本做固定长度切分 |
| 代码 | 函数/类/模块 | 语法感知分块(AST 层面按函数、类边界切分)，不用固定字符数切分 | 固定长度分块极大概率把一个函数从中间切断，产生的 chunk 既不能独立编译也不能独立理解；函数签名+文档字符串+函数体是最小语义完整单元 |
| 对话记录/工单记录 | 一轮问答或一个完整会话 | 按会话边界或滑动窗口(保留最近 N 轮作为上下文)切分，不按固定字符数切分 | 单条孤立发言经常语义不完整(如“好的，那就这么定”脱离上下文毫无意义)，需要保留紧邻的上下文轮次才能被独立检索和理解 |

**固定长度 vs 语义分块 vs 层级分块：适用条件，不是谁更先进的问题。**

- **固定长度分块**（按字符数/token 数切分，可选重叠）实现简单、速度快、成本低，适用于没有明显结构边界的纯文本(如新闻正文、非结构化说明)。
- **语义分块**（按语义相似度动态确定切分点，如检测到相邻句子主题变化时切分）在没有显式结构标记、但内容确实有主题边界的文档上有优势。
- **层级分块**（按文档自带的结构标记，如标题、条款编号切分，可以多层嵌套)在结构化文档(合同、手册)上通常是最优选择。不需要靠语义相似度去猜边界在哪，文档自己已经把边界标出来了。

**三者不是效果排名关系，是根据文档是否有显式结构、结构是否可靠这两个条件做的选择。** 文档有可靠结构标记，优先层级分块。没有结构标记但有主题边界，语义分块。两者都没有，固定长度分块兜底。


**语义分块不是碾压性优势，是权衡。** Chroma 官方研究报告对比了 `RecursiveCharacterTextSplitter`（固定长度，200 token，无重叠)与 `ClusterSemanticChunker`（语义聚类分块，200 token 上限)在同一评测集上的表现。固定长度分块召回率 88.1%、精确率 7.0%，语义分块召回率 87.3%、精确率 8.0%。**语义分块精确率略高但召回率反而略低，幅度都不到 1 个百分点，是权衡而非碾压**。

这条数据来自 Chroma 自己的研究报告，需要留意 Chroma 本身也是被测方法的提出方之一，存在自我背书倾向。但即便打了这个折扣，“语义分块显著优于固定长度分块”这个流传很广的说法依然站不住。至少在这份第三方色彩打了折扣的测试里，差距小到不足以支撑“必须上语义分块”的强结论。

**重叠比例：流传的“10%-20%”经验数字，找不到出处——但也别拿“官方默认很小”当反证。** “chunk overlap 应该设为 chunk 长度的 10%-20%”这个说法在工程博客里反复出现，本书调研没有找到任何权威一手出处把它写成建议。而工具的出厂默认值自己就互相打架：LlamaIndex 的全局常量是 `DEFAULT_CHUNK_OVERLAP = 20`（对 chunk_size=1024 约 **2%**），但它**默认使用的解析器 SentenceSplitter 用的是另一个常量 `SENTENCE_CHUNK_OVERLAP = 200`，约 20%**——同一个框架里两个默认值差十倍（本书 2026-09 直接核对源码，存档见 `docs/research/raw/bookaudit-20260901/`）。Pinecone 官方分块策略页面全文没有出现任何具体的重叠百分比建议。结论：10%-20% 这个区间找不到最初出处，工具默认值也各说各话，**它没有资格当基线，只配当实验起点之一。**

更进一步，已经有第三方论文级实证直接对“重叠有用”这个前提本身提出质疑。《A Systematic Analysis of Chunking Strategies for Reliable Question Answering》(arXiv:2601.14123,ECIR 2026)用 SPLADE 检索+生成器在 Natural Questions 上系统测试了分块方法、分块大小、重叠、上下文长度的组合，核心结论包括：

- ① **重叠不提供可测量的收益，反而增加索引成本**。
- ② 句子分块是最具成本效益的方法，在约 5k token 以内与语义分块效果相当。
- ③ 存在“上下文悬崖”(context cliff)：超过约 2.5k token 后质量下降。
- ④ 最优上下文长度取决于目标，语义质量在小上下文时达峰值，精确匹配在更大上下文时达峰值。

**可执行结论：重叠比例怎么定，分三步走，不要直接抄一个百分比数字。**

- **第一步，先看文档类型有没有可靠的结构边界。** 层级分块场景下(合同、手册)重叠的必要性本身就大幅降低。切分点是文档自带的语义边界，不太存在“关键信息正好卡在切分点两侧被拦腰截断”的问题。
- **第二步，固定长度分块场景下，把重叠当成待实测的超参，不是默认福利。** 拿三档在评估集上跑对照：0（无重叠——上文实证连“重叠有用”都测不出收益）、约 2%（LlamaIndex 全局常量）、约 20%（其默认解析器的出厂值）。指标说了算，不要预设一个百分比就固定下来。
- **第三步，同时关注“上下文悬崖”。** 分块大小往上加不是没有上限的，超过某个量级质量反而下降(实证研究给出的参考值约 2.5k token，具体拐点因模型和场景而异)。分块策略调优不能只调重叠比例，分块大小本身同样需要在评估集上找拐点，而不是选一个“看起来够大”的数字就不再回头验证。

## 5.5 Embedding 选型

Embedding（嵌入）模型选型经常被简化成“看一眼榜单分数，选第一名”。这个做法在企业场景里至少漏掉三个维度：

- 榜单跑分的评测领域和客户的实际业务领域往往不是一回事。
- 高分模型的向量维度可能带来不成比例的存储和检索成本。
- 换模型意味着全量重新计算向量并重建索引，不是一个能轻易反悔的决策。

选型应该从四个维度系统评估，而不是单看一个分数。

**四维选型框架：维度、语言、领域、成本，缺一不可。**

| 维度 | 关键问题 | 判据 |
|---|---|---|
| 向量维度 | 维度越高检索效果越好，但存储和计算成本同步上升，值不值得 | 向量数据库的存储成本与索引构建/查询延迟大致随维度线性增长；业务对召回率的边际收益要和这部分增量成本对比，不是维度越高越好 |
| 语言支持 | 是纯中文场景，还是中英混排，还是需要支持更多语种 | 单语模型在其目标语言上通常有精度优势，多语言模型在跨语言检索场景不可替代；纯中文业务场景下，中文专项模型不一定比多语言模型差，需要实测，不能默认“多语言=更强” |
| 领域适配 | 通用语料训练的模型，能不能覆盖客户的专业术语(法律条款、医疗术语、内部产品代号) | 通用 embedding 模型对垂直领域黑话、缩写、内部代号的向量表征质量通常不如领域内容——这类问题很难靠榜单分数预判，只能拿客户真实语料做检索命中率抽测 |
| 成本 | API 调用计费 vs 自托管部署，延迟要求，向量重算的一次性成本 | 自托管需要评估显存/算力门槛(参考第 8 章私有化部署);API 调用要看单位 token 计价与调用量估算；换模型意味着全量语料重新计算向量，这个一次性成本要在选型阶段就估算进决策，而不是等换完才发现代价超预期 |

**中文 embedding 模型现状：一手核实的两个选项，以及一个明确的核实缺口。**

| 模型 | 发布时间 | License | 向量维度 | 最大序列长度 | 已核实的评测数字 |
|---|---|---|---|---|---|
| BAAI/bge-large-zh-v1.5 | 2023 | MIT | 1024 | 512 | 官方模型卡自称 C-MTEB 均分 **64.53**（发布时点的自我声明，非实时榜单快照） |
| Qwen3-Embedding（0.6B/4B/8B 三档） | 较新一代 | Apache 2.0 | 1024 / 2560 / 4096（按档位；官方博客 Model Overview 表逐字核对，且支持 MRL 自定义降维） | 32K（三档一致，同表核对） | 8B 档在 **MTEB 多语言榜单**排名第一（截至 2025-06-05，分数 **70.58**）——官方博客原文逐字核对 |

这张表格里最需要读者注意的，是两条明确的核实缺口，而不是表格本身呈现出的“数字对比”:

- **bge-large-zh-v1.5 的最大序列长度只有 512**。这是 2023 年发布的较早模型，512 的上限对长文档场景(如合同、长篇技术手册)是明显短板。如果客户文档普遍较长，选型前要先确认这个限制会不会成为瓶颈，而不是等接入后才发现长文档被截断。
- **Qwen3-Embedding 系列没有单独公布 C-MTEB(中文子榜)的分数**。官方博客通篇搜索，“CMTEB”字样只出现在 reranking 模型的 CMTEB-R 子指标表格里，embedding 模型本身没有列出中文子榜总分。已核实的“MTEB 多语言榜单第一、70.58 分”是多语言综合榜单，不能直接当成“中文效果榜单第一”来引用。这是两个不同的榜单口径。写选型报告时如果需要中文专项效果数据，必须自己在客户中文语料上实测，不能拿多语言榜单分数替代。

**一个更普遍的提醒：实时榜单排名不代表“永远第一”。** MTEB/C-MTEB 官方排行榜(`huggingface.co/spaces/mteb/leaderboard`)是持续更新的。本书引用的所有排名数字都标注了发布时点(如“截至 2025-06-05”)，不代表读者阅读本书时刻的现状。**选型前务必自己去官方榜单页面核对当前排名，新模型发布速度很快，书面材料里的排名数字有天然的时效衰减**。这条提醒对任何一本印刷成书的技术资料都成立，不止是本书。

**一个方向可信、数字无源的常见说法：中文分词对 BM25 的影响。** 网上反复流传“中文没有天然分词边界，BM25(稀疏检索算法)必须先用 jieba/HanLP 等工具分词，否则召回率骤降”这类论断。方向本身有依据——Lucene/Elasticsearch 官方专门提供 CJK 分析器，词边界处理被引擎当真；上一节那张自测表也测出了同向差异。缺的是“骤降多少”这类具体数字的可靠出处：本书没有找到给出量化验证的一手文档或论文，只有大量自媒体反复转抄同一个未溯源的结论。

这类“方向可信、数字无源”的说法，处理原则和 §5.4“重叠比例 10%-20%”是同一套。方向上可能是对的：中文分词确实会影响基于词频的检索效果，这是语言学常识层面的合理推测。但没有实证支撑的具体数字不能拿来当选型依据。如果 BM25 混合检索链路涉及中文，建议自己动手对比“分词后 BM25”与“不分词直接按字符 n-gram 检索”在客户语料上的效果差异。不要直接采信网上流传的说法。

**这个对比本书自己做了一遍。** Lab-04 的语料（1241 篇中文企业文档、59 条查询）上，只换分词方式、其余全部固定，BM25 的 Recall@5 是：

| 分词方式 | 总分 | 语义改写类 | 埋编号类 |
|---|---|---|---|
| 不分词（按空格切） | **10/59** | 0/8 | 0/40 |
| 单字 unigram | 47/59 | 7/8 | 29/40 |
| **字符 bigram** | **57/59** | 6/8 | 40/40 |
| jieba 分词 | 54/59 | 3/8 | 40/40 |

两个结论，一个印证了流传的说法，一个推翻了它：

**“不分词召回骤降”是真的，而且比想象的更极端**——54 掉到 10。原因不难理解：中文文本按空格切几乎切不出任何词元，整段话成了一两个巨型 token，词频统计完全失效。剩下那 10 条命中全部来自 `lexical` 类，靠的是 `BX-70` 这种本来就带连字符和空格的编号。

**但“必须用 jieba”是假的**——字符 bigram（57）反而比 jieba（54）更好。差距集中在语义改写类（6/8 对 3/8）：jieba 把“核销”“时限”切成完整词之后，用户问的“多久”“到账”一个都对不上；bigram 切出的碎片反而有更多机会撞上。

所以正确的说法不是“中文 BM25 必须分词”，而是**“必须切成足够细的粒度，具体用哪种切法要在你自己的语料上量”**。这也正是上一段说的处理原则——方向上的合理推测（分词影响检索）成立，但顺着它推出的那个具体做法（所以要用 jieba）并不成立。这个区别很重要：把方向当成做法，是这类“听起来有道理”的说法最常见的害人方式。

需要说明这组数字的边界：**它只在这一份语料上成立。** 换一份文档特征不同的语料，排序完全可能反过来——比如专业术语密集、复合词多的语料，jieba 的词边界信息会更有价值。这张表的用法是“照着做一遍这个对比”，不是“照抄这个结论”。

## 5.6 检索质量三分法诊断

客户拿着一条错误回答来找你，第一反应往往是“模型不行，换个更贵的模型试试”。这是全章最容易被跳过、但最该先做的一步诊断。章首说四种根因，这里先摘掉一种：**数据缺失**在 Step 1 的存在性检查里单独处理——语料里根本没有这份材料，谈不上检索对不对。剩下三种才进入三分法，它们互不相同、要用不同的手段修复：

- **检索失败**：该找的文档没被找到，修检索算法或索引配置。
- **数据污染**：文档被找到了，但文档内容本身是错的、过时的或自相矛盾的，修数据源头。
- **模型幻觉**：文档被找到了、内容也是对的，模型却没有忠实转述，修 prompt 或换模型。

三条根因对应完全不同的修复动作，分不清就去调整，大概率是在错误的地方花钱花时间。

**三步归因流程，每一步都对应一个可独立验证的判断。**

```{=latex}
\fdfig{\fdragtriage}
```

**Step 1：知识库里到底有没有这份支持材料。** 这一步和后面三分法的判断是分开的。如果知识库里压根没有能回答这个问题的内容，那不是检索算法的问题，是内容缺失(对应第 9 章 IBM 案例里“missing content”这类失败点)。补内容是唯一解法，不需要往下走三分法。

判断方法：用问题涉及的关键实体、编号直接在知识库源头做精确匹配查找，而不是经过向量检索。例如直接对 Qdrant 底层做 `scroll` 扫描过滤，不走向量相似度检索。这一步刻意绕开检索算法，只确认“内容存在与否”这个更底层的事实。

**Step 2：该文档有没有被这次检索命中，命中的内容是否正确。** 如果知识库里确实有支持材料，下一步检查这次检索实际返回的 context 里有没有包含它。

用 Qdrant 时这里有个必须注意的 API 细节：**`search()`/`recommend()` 方法在 client 1.16.0 起已被移除**(不是“弃用”、调用会直接报错)，必须改用 `query_points()`。而且 `scroll()` 的过滤参数叫 `scroll_filter`,`query_points()` 的过滤参数叫 `query_filter`，两者拼写不统一，是容易写错的坑。

如果目标文档没有出现在检索结果里→**检索失败**。如果出现了，但文档内容本身有问题(过时、被后续文档否定、原始录入错误)→**数据污染**。这一步的判断依据是拿检索到的内容去和知识库的权威版本或最新版本比对，而不是看模型怎么转述它。

**Step 3：如果检索到的内容是对的，模型有没有忠实转述。** 走到这一步说明知识库有材料、检索也命中了正确材料。如果回答依然是错的，问题出在生成环节：模型没有忠实使用检索到的 context。这正是第 9 章 RAGAS Faithfulness 指标要衡量的：把回答拆解成若干 claim，逐条检查能否从检索到的 context 中推出。拆解后发现有 claim 在 context 里找不到支持依据，这条 claim 就是幻觉的具体位置，对应**模型幻觉**这个根因。

```python
"""检索质量三分法诊断脚本（骨架。完整可运行实现见 Lab-04，其 verify.sh 用 5 条注入故障覆盖全部根因）。

三步对应关系：
- diagnose_step1_content_exists  → 底层精确查找，判断"内容存不存在"
- diagnose_step2_retrieval_and_pollution → 判断"检索到没到、内容对不对"
- diagnose_step3_faithfulness    → 判断"模型有没有忠实转述"

Qdrant 相关注意（v1.19.0 client 实测约束，逐字核实自官方文档/源码）：
- search()/recommend() 已在 1.16.0 移除，一律用 query_points()
- scroll() 的过滤参数叫 scroll_filter，query_points() 叫 query_filter，不统一，容易写错
"""
from dataclasses import dataclass
from typing import Callable, Literal

from qdrant_client import QdrantClient, models

RootCause = Literal["missing_content", "retrieval_failure", "data_pollution", "hallucination", "answer_actually_correct"]


@dataclass
class DiagnosisResult:
    root_cause: RootCause
    detail: str


def diagnose_step1_content_exists(
    client: QdrantClient,
    collection_name: str,
    entity_key: str,
    entity_value: str,
) -> list[dict]:
    """Step 1：绕开向量检索，直接用精确过滤在知识库底层查找支持材料。

    用 scroll() 而非 query_points()：这里不做相似度排序，只确认"存不存在"。
    注意参数名是 scroll_filter，不是 query_filter。
    """
    points, _ = client.scroll(
        collection_name=collection_name,
        scroll_filter=models.Filter(
            must=[models.FieldCondition(key=entity_key, match=models.MatchValue(value=entity_value))]
        ),
        limit=10,
    )
    return [p.payload for p in points if p.payload]


def diagnose_step2_retrieval_and_pollution(
    client: QdrantClient,
    collection_name: str,
    query_vector: list[float],
    target_doc_id: str,
    authoritative_content: str,
    top_k: int = 5,
) -> DiagnosisResult | None:
    """Step 2：用当前生产检索配置跑一次真实查询，检查目标文档是否命中、内容是否正确。

    API 约束见文件头注释（query_points / query_filter）。
    """
    result = client.query_points(
        collection_name=collection_name,
        query=query_vector,
        query_filter=None,  # 如需按元数据过滤，这里传 models.Filter(...)
        limit=top_k,
    )
    hit_ids = [str(point.id) for point in result.points]
    if target_doc_id not in hit_ids:
        return DiagnosisResult("retrieval_failure", f"目标文档 {target_doc_id} 未出现在 top-{top_k} 检索结果中")

    hit_payload = next(p.payload for p in result.points if str(p.id) == target_doc_id)
    retrieved_content = (hit_payload or {}).get("content", "")
    if retrieved_content.strip() != authoritative_content.strip():
        return DiagnosisResult("data_pollution", "命中了目标文档，但其内容与权威版本不一致，疑似过期或录入错误")
    return None  # 通过 Step 2，交给 Step 3 判断


def diagnose_step3_faithfulness(
    model_output: str,
    retrieved_context: list[str],
    judge_fn: Callable[[str, list[str]], float],
    threshold: float = 0.8,
) -> DiagnosisResult:
    """Step 3：知识库有材料、检索也命中了，回答依然错，检查是不是模型没忠实转述。

    judge_fn 对齐 RAGAS Faithfulness 的计算方式（claim 拆解 -> 逐条判断是否被 context 支持）。
    """
    score = judge_fn(model_output, retrieved_context)
    if score < threshold:
        return DiagnosisResult("hallucination", f"faithfulness={score:.2f}，低于阈值 {threshold}，模型未忠实转述检索内容")
    return DiagnosisResult("answer_actually_correct", f"faithfulness={score:.2f}，检索与生成均正常，建议复查评估集标注")
```

**三分法诊断给出的根因，直接决定下一步动作，不能三种都用同一个“再调一下参数”应付过去：**

| 根因 | 典型信号 | 对应修复动作 |
|---|---|---|
| 数据缺失 | 直接精确查找也找不到支持材料 | 补充知识库内容，这不是检索或生成层面能解决的问题 |
| 检索失败 | 材料存在，精确查找能找到，但向量检索的 top-k 里没有 | 检查 embedding 模型是否适配该领域（§5.5）、分块策略是否切碎了关键信息（§5.4）、是否需要混合检索/rerank |
| 数据污染 | 检索命中了目标文档，但内容与权威版本不一致 | 回到 §5.1 的防御式 ETL：该文档的摄取环节可能存在脏数据未被拦截，需要补数据契约或触发人工复核 |
| 模型幻觉 | 命中的内容正确，但生成回答的 claim 无法从 context 推出 | 调整 prompt 强调“仅基于给定材料回答”、换更强的模型、或在 CI 门禁中加 Faithfulness 阈值（第 9 章） |

这套三分法和第 9 章的评估体系不是两套并行的东西，是同一套评估基础设施的两种用法。第 9 章讲的是“怎么系统性地测”，这里讲的是“测出问题之后怎么一步步定位到底是哪个环节坏的”。黄金集里那些“命中但检索指标不好看”的失败用例，正好可以拿来跑一遍这个三步诊断，反过来验证评估集本身的分类是否准确。

## 本章清单

- [ ] 把数据假设写成契约里能真正执行的断言，**不是写在文档里**
- [ ] 脏数据分四条路径：丢弃、修复、隔离、告警。告警是叠加层，不是并列的第四条
- [ ] 模式漂移分三种：增量、破坏性、语义。**只有破坏性需要硬阻断**
- [ ] 专门盯语义漂移——它不改结构不改类型，只改取值分布或业务含义，最容易漏
- [ ] 幂等重跑要同时满足三条：写入幂等、输入不依赖墙钟时间、下游能容忍重复消费
- [ ] 选解析方案前，**先抽样统计客户真实文档里四类难点各自的占比**
- [ ] 分块服从文档的自然结构单元：合同的条款、代码的函数、表格的行组
- [ ] 别照抄“重叠 10%–20%”这个数字——它找不到出处、工具默认值互相打架（2% vs 20%），已有论文实证质疑重叠本身的收益；拿 0/2%/20% 三档实测
- [ ] 向量模型选型看四维：维度、语言、领域、成本。**榜单分数会随时间衰减**
- [ ] 中文子榜分数缺失时，不要拿多语言综合榜单的分数替代
- [ ] 回答错误时先跑三步诊断定位根因，再决定修复动作

## 自检问题

1. 你发现某个 ETL 批次的隔离队列突然从平时的 0.5% 涨到 8%，这应该归为哪类 Schema Drift？下一步该做什么？
   **参考答案要点**：隔离率骤增通常对应语义漂移或早期未被结构校验拦住的破坏性漂移。不要先去扩大隔离阈值让告警消失。应该先抽样看隔离记录的共同特征，确认是不是上游做了未通知的变更。

2. 一个团队的 Airflow 任务用了 `INSERT ... ON CONFLICT UPDATE` 做 upsert，团队认为这样就实现了幂等重跑，这个判断哪里不完整？
   **参考答案要点**:upsert 只满足“写入幂等”这一个条件，还需要检查任务输入是否依赖 `datetime.now()` 等墙钟时间、下游消费方能否容忍重复处理，三个条件缺一不可。

3. 客户给的文档大多是扫描版的历史合同，部分页面有印章遮挡关键金额字段，你会怎么设计这部分文档的处理路径？
   **参考答案要点**：不能让低置信度的 OCR 结果直接进知识库。应该用置信度分级：清晰扫描件走标准流程，印章遮挡等严重降质页面应路由到人工复核。答案要体现“隔离优于强行通过”的原则。

4. 有同事提议“不管什么文档统一用固定长度分块，重叠设 15%，简单省事”，你怎么评估这个提议？
   **参考答案要点**：固定长度分块对合同、代码这类有清晰结构边界的文档并不合适，会切断语义单元。15% 这个重叠比例缺乏权威依据——工具默认值本身在 2% 与 20% 之间打架，正确做法是拿 0/2%/20% 几档在评估集上实测再定，而不是直接采纳一个流传的经验数字。

5. 一份中文选型报告写道“Qwen3-Embedding 8B 在 C-MTEB 排名第一”，这句话哪里有问题？
   **参考答案要点**：已核实的数据是“MTEB 多语言榜单第一，截至 2025-06-05”，不是 C-MTEB(中文子榜)的分数；官方材料没有单独公布中文子榜分数，两个榜单口径不同不能混用。

6. 客户投诉一次回答“张冠李戴”，你打开 trace 发现检索到的 context 里确实包含了正确的价格信息，但模型输出的价格是错的，这属于三分法里的哪一类？第一步该做什么？
   **参考答案要点**：属于模型幻觉(检索命中且内容正确，生成环节没有忠实转述)。第一步是跑一遍 Faithfulness 类的评分，把回答拆解成 claim 逐条核对能否从 context 推出，而不是直接假设“模型不行”就换模型。

7. 为什么“检索失败”和“数据缺失”要分开判断，合并成一类会有什么后果？
   **参考答案要点**：数据缺失的解法是补内容，检索失败的解法是调检索算法/分块/embedding。合并判断可能导致把本该补内容的问题错误地归因为“检索没调好”，反复调参数却始终无法修复——问题根本不在检索环节。

8. Qdrant 代码里出现了 `client.search(...)`，在当前锁定的 1.19.0 client 上会发生什么？该怎么改？
   **参考答案要点**:`search()`/`recommend()` 在 1.16.0 起已被移除(不是弃用警告)，直接调用会报错；应改写为 `client.query_points(...)`，并注意其过滤参数名是 `query_filter`，与 `scroll()` 的 `scroll_filter` 不同名。
