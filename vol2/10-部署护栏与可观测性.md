## 10.0 上生产要满足的三条，K8s 只是其中一条的实现

这一章的七节里，有一半内容任何一本讲云原生运维的书都有，而且讲得更细。
所以先说清这一章真正在守的是什么。

上册骨架第三层里的**控制**，落到这一层就是三个词。**三个都成立，才算进入生产**：

| | 意思 | 不成立时的样子 | 在哪几节 |
|---|---|---|---|
| **可观测** | 发生了什么看得见 | 客户报障之后你才知道出了事；成本超支到月底账单才发现 | §10.5、§10.6 |
| **可控制** | 系统不能做什么，是被代码挡住的 | 边界写在提示词里，模型“通常”会遵守 | §10.1、§10.7，加第 9 章 §9.6 的闸门 |
| **可撤销** | 出问题能停、能退、能隔离 | 只能等它跑完，或者拔电源 | §10.1（回滚脚本与预检），加上册 §14.4 |

**中间那一行是这一章存在的主要理由，值得说重一点。**
一个约束写进提示词，等于**请求**模型不要那样做；写进代码、写进网络策略、
写进数据库账号的权限，才是**挡住**它。上册第 14 章 §14.2 那句“写进提示词不算挡住”，
工程上就落在这一节：**能用确定性代码挡的，不要交给模型自觉。**

这条判断有一个很实际的推论，也是这一章和普通运维材料的分界：

> **控制面比模型聪明更重要。** 一个模型能力一般但边界清楚、出事能停能退的系统，
> 可以上生产；一个模型很强但只能靠提示词约束、出事只能拔电源的系统，不能。

K8s、镜像构建、缓存策略这些是实现手段，会换。三个词不会换——
换到信创栈上（第 13 章）、换到物理隔离环境里（上册第 19 章），
问的还是这三个问题，只是答案的技术形态不一样。

## 10.1 容器化与 K8s 交付

FDE 现场交付的容器镜像，和互联网公司内部微服务镜像的约束条件不一样：

- 现场客户不一定有 CI/CD 流水线替你代下载依赖。
- 不一定有内部镜像仓库缓存基础镜像。
- 客户安全团队也真的会打开 Dockerfile 逐行看你装了什么。

多阶段构建（multi-stage build）不是锦上添花，是把“能跑的镜像”和“客户能接受进内网的镜像”分开的那道分界线。

多阶段构建的核心思路是把“编译/安装依赖”和“运行”拆成两个 stage。只把运行所需的产物拷进最终镜像，编译工具链、源码、中间产物都留在 builder stage 里，不进最终镜像：

```dockerfile
# 示意骨架，未经实测验证，不要直接用于生产
# ---- Stage 1: builder，装编译依赖，产出可复制的依赖目录 ----
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/build/deps -r requirements.txt

# ---- Stage 2: runtime，只拷贝运行时需要的产物 ----
FROM python:3.12-slim AS runtime
WORKDIR /app
COPY --from=builder /build/deps /app/deps
COPY src/ /app/src/
ENV PYTHONPATH=/app/deps
USER 10001:10001
ENTRYPOINT ["python", "-m", "src.server"]
```

几个容易被忽略的细节：

- builder stage 里的 `gcc`、`build-essential` 一类编译工具链不会出现在 runtime stage。现场安全审计常见的第一个问题就是“这个生产镜像里为什么装着 gcc”，多阶段构建从根上避免这个问题，而不是事后用 `apt remove` 补救。`apt remove` 不会清理已经写入镜像层的文件，镜像体积不会因此变小。
- `USER 10001:10001` 让容器以非 root 用户运行。很多客户的安全基线会强制要求容器不能以 root 身份跑，尤其是有物理隔离/国防背景的客户（见上册第 19 章）。这条规则最好在写 Dockerfile 时就满足，而不是等客户扫描工具报错才回头改。
- 用 `pip install --target=` 而不是装进系统 site-packages，方便 `COPY --from=builder` 精确控制拷贝范围，避免把 pip 缓存、构建工具的残留一起带进最终镜像。
- 基础镜像要锁定到具体 tag（如 `python:3.12-slim`，避免用 `latest`）。这条在 §10.2 的离线打包场景里尤其关键——两次分别拉取的 `latest` 可能指向不同的底层镜像摘要，离线环境里出了问题很难排查是不是这个原因。

Helm Chart 交付时，目录结构决定了这个 Chart 能不能被客户团队接手维护。一个最小但完整的结构：

| 文件 | 作用 |
|---|---|
| `Chart.yaml` | Chart 元数据：名称、版本号、依赖声明 |
| `values.yaml` | 默认参数：镜像 tag、副本数、资源 request/limit、探针配置 |
| `templates/deployment.yaml` | Pod 模板：容器定义、探针、环境变量注入 |
| `templates/service.yaml` | 暴露服务：ClusterIP（集群内）或 NodePort（需要外部访问时）|
| `templates/configmap.yaml` | 非敏感配置注入，避免把配置硬编码进镜像 |
| `templates/secret.yaml` | 敏感配置（API Key、数据库密码），交付前要确认客户的 Secret 管理规范（自建 Vault 还是原生 Secret）|
| `templates/hpa.yaml` | 水平自动扩缩容（HorizontalPodAutoscaler）规则 |

资源 request 与 limit 不是拍脑袋填的数字，判据是压测数据，不是“感觉给 2 核应该够”：

- CPU request 应该基于压测下的 p50 实际占用来定，limit 通常设为 request 的 1.5—2 倍，留出应对突发流量的余量。这个倍数没有统一标准，需要结合自己的压测数据和成本预算标定，不是行业公认的固定值。
- 内存 limit 设得过低会触发 OOMKill；有 GC 的运行时（Python、Java）内存曲线是锯齿状的，压测要看峰值而不是均值，否则线上偶发的 GC 前峰值会把容器直接打挂。
- 涉及 GPU 的推理服务是特例，“留余量”这个思路在 GPU 资源上不成立。K8s 把 GPU 当扩展资源调度：**不可超卖，request 必须等于 limit**；默认语义按整卡分配，要做卡内切分得靠设备插件层的机制（NVIDIA MIG、time-slicing、MPS），那是集群管理员的事，不在默认调度语义里。真正的显存精细化管理，是在容器内部由 vLLM 自己的 `--gpu-memory-utilization` 参数负责——“分几张卡”“卡怎么切”“卡内显存怎么用”是三层，不要混为一谈。
- 探针配置对 LLM 推理服务要特殊处理。模型加载可能耗时数十秒到数分钟，尤其是量化模型的反量化、首次编译 CUDA kernel。`livenessProbe`/`readinessProbe` 如果沿用 Web 服务惯用的短超时，会在模型还没加载完时就被 K8s 判定为不健康并反复重启。生产实践通常会额外加一个宽松超时的 `startupProbe`，等模型真正加载完成后再切换到正常的存活/就绪探测节奏。

### 命令不由你来敲的时候

上面这些配置有一个隐含前提：你能对客户的集群执行命令。不少现场不给这个前提。

- 你的操作要经过堡垒机，会话有审计和录屏。
- 你没有集群凭据，命令由客户运维代你执行，你只能在旁边看着念。
- 生产变更只在固定窗口内做，错过等下一轮（§6.4 那张表里的“等下个变更窗口”）。

这三条改变的不是部署方式，是**交付物的形态**。执行的人不是你的时候，
交付物得从“我知道怎么装”变成“另一个人照着能装”。具体是四件东西：

1. **按顺序编号的执行脚本**，每一步能单独重跑，重跑不产生副作用。
   代执行的人中途卡住时，第一反应是从头再来一遍，脚本得扛得住这个动作。
2. **每一步配一条验证命令和期望输出**，让敲命令的人当场知道这步成没成，
   而不是全跑完了回来问你“这样对吗”。
3. **回滚脚本，和安装脚本同时交付。** 窗口里出问题，你只有回滚的时间，没有排查的时间。
4. **预检脚本，在窗口开始之前跑。** 磁盘不够、端口被占、镜像没导入、
   证书还没批下来——这类问题要挡在窗口外面。

**窗口的价值密度很高，别拿它当发现问题的时间。** 预检和回滚这两件东西存在的意义，
就是把窗口里的不确定性压到最低。

还有一条容易忘：堡垒机会把你敲的每一条命令留档。别在命令行参数里带密钥，
也别用 `echo` 把配置文件打到屏幕上。这件事和 §10.5 的日志脱敏是同一个问题，
只是发生在另一个地方——而且这个地方的记录，删不掉。

## 10.2 自包含离线部署包

上册第 19 章要讲的物理隔离/主权 AI 场景，前提条件是“现场没有外网、不能 `pip install`、不能 `docker pull`”。这一节讲的自包含离线部署包，就是让上册第 19 章那个场景成立的技术前提。这里的清单和构建脚本对应本书 Lab-07（Task 42），该 Lab 已实现并通过验收；下面凡标注“取自 Lab-07”的命令均实测跑通，个别标注“示意骨架”的除外。

一个能在断网环境里独立起服务的部署包，需要打包五类东西，缺一类都会在客户现场卡住：

```{=latex}
\fdfig{\fdofflinepack}
```

**第一步：镜像导出与多架构构建。** 客户现场的 CPU 架构不一定和你的开发机一致（尤其是国产化信创环境常见 ARM64/龙芯）。交付前要用 `docker buildx` 构建多架构镜像并合并成一个 manifest list，再用 `docker save` 导出成 tar 包供离线传输：

```bash
# 示意骨架，未经实测验证
# 注意：--push 直接推 registry，镜像不落本地 daemon，docker save 会报 image not found。
# 离线场景要导出文件，用 --output 直接产出 OCI 布局（或用 skopeo 从 registry 拉成 tar）：
docker buildx build --platform linux/amd64,linux/arm64 -t myimage:1.0 \
  --output type=oci,dest=myimage-1.0.tar .
```

**第二步：cosign 签名。** cosign（当前版本 v3.1.3）默认推荐 keyless 签名——把临时密钥绑定到 OIDC 身份，签名验证依赖 Sigstore 的 Fulcio/Rekor 在线服务。但离线部署包的定义前提就是“目标环境没有外网”，keyless 在这个场景直接不可用，必须改用 key-based 签名：

*✓ 本段取自 Lab-07，`verify.sh` 7/7 实测通过（含 `unshare -rn` 断网验签）。*
```bash
cosign generate-key-pair
# 注意：cosign sign / verify 作用于**镜像引用**，要去 registry 推拉签名，
# 离线场景不成立。对着导出的 tar 文件签，用 sign-blob / verify-blob，见下方实测流程。
```

`cosign generate-key-pair` 会生成 `cosign.key`（私钥，签名时需要密码，可用 `COSIGN_PASSWORD` 环境变量跳过交互）和 `cosign.pub`（公钥）。

**上面那三行命令在 cosign v3.1.3 上跑不通**——这是写作时实测的结果，也纠正了本书初稿留下的一个待查项。初稿当时写的是“未查到官方 air-gapped signing 指南，不能想当然认为 key-based 签名在断网环境都畅通无阻”。现在查了，情况比“key-based 就够了”复杂得多：

- **`--tlog-upload=false` 已被弃用并直接报错。** cosign v3 默认走 signing config，报错原文要求改用“一份不含透明日志服务的 signing config”，通过 `cosign signing-config create` 生成。
- **签名能离线，验签默认不能。** 实测 `cosign sign-blob --key ... --new-bundle-format --bundle` 在断网下可以签出来；但用同一份公钥去 `verify-blob` 时，cosign 会先去 `tuf-repo-cdn.sigstore.dev` 拉 TUF 信任根，断网直接失败——**失败发生在验签之前**，连“签名对不对”都还没开始算。这一条最反直觉：既然用的是自己的密钥对，凭什么还要联网？
- 所以完整的离线链路需要**一份额外产物**：一个本地 trusted root。用 `cosign trusted-root create --out trusted-root.json` 生成，实测只有 73 字节，作用是让 cosign 不去联网拉 TUF。

实测跑通的完整离线流程是这样（cosign v3.1.3）：

```bash
# 签名端（可联网也可不联网）
cosign generate-key-pair                       # 产出 cosign.key / cosign.pub
cosign sign-blob --key cosign.key --yes \
  --new-bundle-format --bundle myimage.bundle myimage-1.0.tar

# 随包一起交付给客户的额外一件：本地信任根
cosign trusted-root create --out trusted-root.json

# 客户现场（完全断网）
cosign verify-blob --key cosign.pub \
  --bundle myimage.bundle --new-bundle-format \
  --trusted-root trusted-root.json --insecure-ignore-tlog \
  myimage-1.0.tar
```

这条链路在 `unshare -rn` 的无网络命名空间里实测通过，且两个反例都会失败：篡改 tar 文件报 `invalid signature`，换一把错的公钥同样报 `invalid signature`。**验签确实在验，不是走过场。**

但要说清楚代价：`--insecure-ignore-tlog` 会让 cosign 打出一行醒目的 WARNING，提示跳过透明日志验证“缺少透明性与可审计性”。这不是可以忽略的噪声——**你是拿透明日志的可审计性，换来了断网可验的能力**。透明日志的价值在于“这个签名什么时候被谁登记过”是公开可查的，跳过它之后，一份被私钥泄露者伪造的签名，你在现场无从察觉。物理隔离场景通常认为这个交换划算（网络本来就不通，公开日志也查不了），但它是一个需要向客户安全团队讲明白的取舍，不是一个技术细节。

这件事的一般教训比 cosign 本身重要：**“这个工具支持离线”这句话要拆成“签能不能离线”和“验能不能离线”两问分别验证。** 交付现场断网的是客户那一侧，也就是验签那一侧——恰恰是更容易出问题的那一半。真到现场才发现验不了签，那时候补救的余地非常小。

验证方法也值得记：不要靠读文档判断，用 `unshare -rn`（或 `docker run --network none`）把命令扔进一个没有任何网络的命名空间里跑一遍。上面这些结论都是这么测出来的。

**第三步：syft 生成 SBOM（Software Bill of Materials，软件物料清单）。** syft（当前版本 v1.50.0）支持多种输出格式，物理隔离场景客户通常要求同时留存两种主流格式方便不同审计工具消费：

*✓ 本段取自 Lab-07，`verify.sh` 7/7 实测通过。*
```bash
syft myimage:1.0 -o spdx-json=./sbom-spdx.json -o cyclonedx-json=./sbom-cyclonedx.json
```

**第四步：离线依赖打包。** 除了镜像本身，安装脚本、Helm Chart、以及任何在安装时才会去外网拉取的依赖（Python wheel、Helm 依赖 Chart、apt 包）都要提前下载好，和镜像一起打进离线介质（这一步本身要联网——它是在**打包侧**把外网内容拉全，让**现场侧**可以断网）：

*✓ 本段取自 Lab-07，`verify.sh` 7/7 实测通过。*
```bash
pip download -r requirements.txt -d ./offline-deps/wheels
helm dependency update ./chart && helm package ./chart -d ./offline-deps/charts
```

**第五步：离线安装脚本。** 客户现场执行的入口脚本要把“导入镜像 → 验证签名 → 校验 SBOM 存在性 → 安装 Chart”串成一条不依赖外网的流程：

*✓ 本段取自 Lab-07，`verify.sh` 7/7 实测通过（含 `unshare -rn` 断网验签）。*
```bash
#!/usr/bin/env bash
set -euo pipefail
# 顺序不能改：先验签，再加载。反过来等于把一个还没验证的镜像先塞进 daemon，
# 验签失败时它已经躺在本地了。Lab-07 的安装脚本就是按这个顺序写的。
cosign verify-blob --key cosign.pub \
  --bundle image.bundle --new-bundle-format \
  --trusted-root trusted-root.json --insecure-ignore-tlog \
  myimage-1.0.tar
test -f sbom-spdx.json && test -f sbom-cyclonedx.json
docker load -i myimage-1.0.tar
helm install myrelease ./offline-deps/charts/mychart-1.0.tgz \
  --set image.pullPolicy=Never \
  -f offline-values.yaml
```

上面用的是 `verify-blob` 而不是 `verify`，因为**`cosign verify` 作用于镜像引用，需要连 registry**——在断网现场直接失败。这条和本节前面讲的 TUF 那一条是同一类问题的两个面：判断一个命令能不能离线用，要看它到底在跟谁说话。

`image.pullPolicy=Never` 是断网场景的关键一行。默认的 `IfNotPresent`/`Always` 在某些 K8s 发行版配置下仍会尝试联网检查镜像摘要。`Never` 强制只用本地已加载的镜像，避免安装脚本卡在一次不会成功的网络请求上。

这份清单对应 Lab-07 的验收标准：在断网容器中执行离线安装脚本能成功起服务，SBOM 与签名校验通过——五个步骤任何一步遗漏，这条验收标准都无法达成。

## 10.3 推理性能优化

先纠正一个流传很广、但已经过时的说法：**PagedAttention 不是 vLLM 现在的核心卖点。**（这条已实测：在装好 vLLM 0.26.0 的机器上 `import vllm.attention.ops.paged_attn` 直接 `ModuleNotFoundError`，模块确实不在了。） vLLM v0.25.0 的官方发布说明在 PR #47361 里写明 “PagedAttention has been removed”——随着 V1/Model Runner V2 成为唯一的引擎路径，早期那套独立的 PagedAttention 实现已经被删除。这不是说“分页管理 KV cache”这个思路被放弃了，而是它作为一套独立、遗留的实现被整合进了新引擎架构。市面上大量还在把 PagedAttention 当作 vLLM 卖点介绍的资料，说的是 vLLM 早期版本的架构。本书写作时的当前稳定版本是 v0.26.0，这块内容已经过时，不要照抄。

vLLM 0.26.0 对外暴露的关键调优参数拼写没有变化，含义值得重新过一遍：

- `--max-model-len`：模型上下文长度上限，未指定时从模型配置自动推导，现在支持人类可读单位（如 `1k` 表示 1000，`1K` 表示 1024）。
- `--gpu-memory-utilization`：GPU 显存**预留比例**，默认值 **0.92**——这条已在 RTX 4090（vLLM 0.26.0）上实测确认，帮助原文是“If unspecified, will use the default value of 0.92”。初稿曾把它标为存疑（不确定是否从 0.9 改来），现在至少可以确定 0.26.0 上就是 0.92；具体哪个版本改的仍未逐版本核实。

  **要紧的是“预留”这两个字，它和直觉相反。** 实测把 `gpu_memory_utilization` 设成 0.85 去加载一个 **0.5B** 的小模型，nvidia-smi 显示占用 **21.2GB / 24.5GB**——vLLM 按比例把显存整块划走，模型权重用不完的部分全部转成 KV Cache。这不是浪费，是设计：KV Cache 越大能并发的请求越多。但它意味着两件事——**你没法靠调小模型来省显存**，以及**同一张卡上起第二个 vLLM 实例会直接失败**，因为第一个已经把 85% 划走了。帮助文本里那句“This is a per-instance limit”说的就是这个。

```{=latex}
\fdfig{\fdgpumem}
```
- `--quantization`（短写 `-q`）：量化方式，未指定时会先检查模型配置文件里的 `quantization_config` 字段。

**查参数默认值时注意**：vLLM 0.26.0 的 `vllm serve --help` 只列出配置分组（ModelConfig、CacheConfig 等十几个），**不列具体参数**——想看到带默认值的完整列表要用 `vllm serve --help=all`（实测输出 1831 行）。照着老教程直接 `--help | grep` 会一无所获，误以为参数不存在。

**量化方案要按硬件代际选，不能笼统写“仅 GPU”。** 不同量化方案对 GPU 代际、CPU 架构的支持差异很大，选错了会出现“装是装上了、跑起来直接报错”的情况：

| 量化方案 | 硬件支持范围 | 适用场景 |
|---|---|---|
| AWQ | x86 CPU 支持，ARM CPU 不支持；GPU 侧 Volta 代不支持 | 需要在 x86 CPU 上跑量化模型的场景 |
| GPTQ | x86 CPU 支持，ARM CPU 不支持；GPU 侧全代际支持 | 通用性最好的量化方案之一 |
| Marlin（GPTQ/AWQ/FP8/FP4 的加速内核） | 仅 Turing–Hopper 代 NVIDIA GPU；AMD/Intel GPU、Volta 代 NVIDIA GPU 均不支持；CPU 不支持 | 在受支持的 GPU 上榨取量化推理的额外吞吐 |
| llm-compressor INT8（W8A8） | x86/Arm CPU 均支持 | CPU 部署下相对通用的量化选项 |
| llm-compressor FP8（W8A8） | 仅 Ada/Hopper/AMD GPU；CPU 不支持 | 追求高吞吐、显存换算成本的新一代 GPU |
| bitsandbytes | 仅 Volta–Hopper 代 NVIDIA GPU；AMD/Intel GPU 均不支持；CPU 不支持 | 快速原型、显存紧张的中小模型 |
| GGUF | 仅 GPU（Volta–Hopper 代）+ AMD GPU；CPU 侧在 vLLM 上不支持 | GGUF + CPU 是 llama.cpp 的地盘，不是 vLLM CPU 后端的选项 |

对 CPU 部署场景的直接结论：vLLM CPU 后端只能选 AWQ、GPTQ（限 x86）或 llm-compressor INT8（x86/Arm 均可），GGUF 和 bitsandbytes 在 vLLM CPU 上都用不了。这条经常被忽视：很多团队照着 GPU 教程抄了一个 GGUF 或 bitsandbytes 的例子放到 CPU 环境，跑起来才发现根本装不上。

**连续批处理（continuous batching）与并发调优。** vLLM 的调度器把多个并发请求的生成步骤交织执行，而不是等一个请求完全结束再处理下一个。这仍然是当前引擎架构的核心机制。`--gpu-memory-utilization` 和调度相关参数（如控制并发序列数的参数）共同决定了单张卡能承载多少并发请求。调优思路是先用固定负载压测吞吐/延迟曲线，找到延迟开始明显劣化的并发拐点，然后把线上并发上限设在拐点以下留出余量。不要直接拉满显存利用率去测理论峰值吞吐。

**KV cache 管理在 GPU 和 CPU 路径上的操作方式不同。** GPU 路径下，KV cache 空间由 `--gpu-memory-utilization` 间接控制，vLLM 自己在这个预算内做管理。CPU 路径下要显式设置 `VLLM_CPU_KVCACHE_SPACE`，单位 GiB，默认值是 `0`，必须手动设置，否则服务无法正常提供 KV cache 空间。另外 `VLLM_CPU_OMP_THREADS_BIND` 控制 OpenMP 线程绑核，默认 `auto`。

**CPU 无 GPU 环境的三档降级方案——这是本节对 Lab-06 最关键的结论。** vLLM CPU 后端是真实可用、持续在开发的功能，v0.23—v0.26 连续四个版本都有 CPU 相关的实质性提交。但门槛比“pip install 然后 vllm serve”高得多：

- 只支持 Linux 原生，不支持 Windows 原生。macOS 仅 Apple Silicon 分支、需源码构建的实验性支持，IBM Z/s390x 同样是实验性源码构建。
- 预编译 wheel 装完之后，必须手动把 TCMalloc 和 Intel OpenMP 加入 `LD_PRELOAD` 才能正常跑。这一步很容易被新手漏掉，表现为“装完了但跑不起来”。

不能把这条路径当成对所有读者都“开箱即跑”的唯一选项，实际交付时按硬件条件分三档：

*✓ 档位①的 `vllm serve` 与 OpenAI 兼容调用已在 RTX 4090（vLLM 0.26.0）实测：`--api-key` 确实生效（不带 key 返回 401，带 key 返回 200），响应体是标准 OpenAI 格式含 `usage`。**代跑的模型是 0.5B 而非示例里的 8B**，故延迟数字不具参考性。档位②③（无 GPU / 纯 CPU）由 Lab-06 以 Ollama 实测。*

## 10.4 缓存策略

**语义缓存的阈值不能拍脑袋定。** 语义缓存的做法是把历史请求的 embedding 存起来，新请求进来时算余弦相似度，超过阈值就直接返回历史答案、跳过一次真实推理。

很多团队直接抄一个 0.95 之类的数字上生产。问题是这个数字对不同业务语义空间的含义完全不同。标定方法应该和第 8 章讲的评估集方法论一致。在黄金集或历史真实流量上，把“语义相似度”和“答案是否真的可以互换”两个维度都标出来，画一张相似度分布图。

**但画完图之后要先问一个问题：这两组分布分得开吗？** 本书初稿在这里给的建议是“找到错误复用比例明显上升的拐点，把阈值定在拐点以下留安全边际”。Lab-06 实测下来，这个建议预设了一个不一定成立的前提。

Lab-06 用 22 对中文问题（10 对同义改写、12 对似而不同）在 `bge-small-zh-v1.5` 上量到：**应当命中的最低相似度 0.651，不该命中的最高相似度 0.954**。两组完全重叠，中间没有任何空隙：

| 阈值 | 命中率 | 误命中 |
|---|---|---|
| 0.85 | 7/10 | 4/12 |
| 0.90 | 5/10 | 2/12 |
| 0.94 | 1/10 | **1/12** |

调到 0.94 时缓存已经基本不工作了——10 条同义改写只认出 1 条——**却仍然有一次误命中**。相似度最高的那对反例是“合同盖公章找谁”与“合同盖合同章找谁”（0.954）：在向量空间里几乎重合，在审批流程里是两条路。

所以更准确的说法是：**先验证分布可不可分。可分时，拐点是有意义的安全阀；不可分时，阈值只是召回率的旋钮，往上调只会让缓存失效，不会让它变安全。** 遇到不可分的情况，安全必须由阈值之外的机制提供。Lab-06 用的是“标识符必须完全一致”的词面护栏加上一层模型裁判。词面护栏免费，把误命中从 4 压到 2 而命中率不变；模型裁判判断两问能否共用同一答案，把误命中压到 0。这和 §9.3 混合检索是同一个二元性：稠密相似度负责找回，词面与显式判断负责分辨。

顺带一提，那层裁判有模型尺寸下限。Lab-06 实测 `qwen2.5:0.5b` 对六条测试全部回答“是”——它不是判错，是根本没在判，这种“恒定输出”式的失效比判错更难发现，因为指标上看它一直在工作。

防错命中要在两个层面做兜底，只靠相似度分数是不够的：

- **业务上下文必须成为缓存 key 的一部分，不能只用 embedding 相似度做匹配。** 缓存 key 里要带上租户 ID、模型版本、prompt 模板版本这些维度。两个语义上非常接近的问题，如果来自不同租户或者命中了不同版本的 prompt 模板，答案未必能互换。缺了这层隔离，语义缓存会变成跨租户串答案的安全事故。
- **高风险操作直接跳过语义缓存，走精确匹配或不缓存。** 涉及金额计算、合同条款解读、法务口径这类场景，语义相似不等于业务等价。“退款政策是否适用于第 8 天”和“退款政策是否适用于第 15 天”在向量空间里可能非常接近，但答案可能完全相反。这类场景应该被显式排除在语义缓存之外，或者退化为只做精确字符串匹配的缓存。
- **命中之后再做一次轻量一致性检查，不要无条件信任相似度分数。** 比如对命中结果做一次关键字段抽取（金额、日期、条款编号），和当前请求的对应字段做比对，不一致就放弃缓存结果转真实推理。这一步的额外开销远小于一次完整推理，但能拦住相似度分数打分虚高导致的错误复用。

**模型权重缓存要解决的是“重复下载”和“首次加载竞态”两个问题。** 权重文件通常是几十 GB 级别，如果每个 Pod 各自维护自己的本地缓存目录，每次扩容都要重新下载一遍，既浪费带宽也拖慢扩容速度。做法是把 HuggingFace 缓存目录（`~/.cache/huggingface`）挂载为共享的持久卷（PVC），多个副本共用同一份权重缓存。多副本同时冷启动时会有竞态。如果没有预热机制，第一次扩容时多个 Pod 可能同时触发下载，既浪费带宽也可能把同一份缓存文件写坏。生产实践通常用 InitContainer 预热或者提前把权重打进只读挂载卷来规避这个问题。

**多级缓存架构把“精确复用”和“语义复用”分层处理，各自解决不同粒度的重复计算。**

```{=latex}
\fdfig{\fdcachetiers}
```

（注意这里的 L1/L2/L3 与 Lab-06 README 里说的“三层缓存”不是一回事。那三层是 L2 语义缓存**内部**的防错命中结构：稠密相似度、词面护栏、模型裁判，正是下面说的“需要前面讲的防错命中机制兜底”的具体做法。两者是正交的，可以叠加使用。）

三层缓存的分工：

- L1 处理完全相同的重复请求（比如前端重试导致的重复提交），命中成本最低。
- L2 处理语义相近但字面不同的请求，命中收益最大但风险也最高，需要前面讲的防错命中机制兜底。
- L3（vLLM 内部的前缀缓存/KV cache 复用）处理的是同一次会话内、共享前缀的多轮对话场景，这一层由推理引擎自己管理，不需要业务层介入。

三层各自命中率和错误率的监控指标应该分开统计，混在一起看会掩盖“语义缓存到底有没有在错误复用”这个关键问题。

**什么情况下语义缓存不该上。** 两类场景不适合引入 L2 语义缓存：

- 请求本身高度个性化、几乎不存在真正的语义重复，比如带着用户专属上下文的长对话推理。这种场景引入语义缓存的命中率会低到不值得承担错误复用的风险。
- 团队没有能力维护“相似度阈值标定—回放错误案例—调整阈值”这一整套持续运营流程。语义缓存不是配置一个阈值就能一劳永逸的静态系统。投入不了持续运营精力的团队，宁可只做 L1 精确匹配缓存，也不要上一套自己看不住的语义缓存。

## 10.5 可观测性

企业客户问“这次输出为什么是这样”时，答不上来是护栏体系最容易露怯的地方——没有完整调用链路（trace），出了问题只能靠猜。这一节对应本书 Lab-08（Task 43），Lab-08 已实现并双档验收通过（`verify.sh` 7/7），本节涉及 SDK 接入的代码已按实测结果回填。

**Langfuse trace 接入。** 当前 Langfuse Python SDK 版本是 4.14.3，平台（自托管 Web+Worker）版本是 v4.6.0，v4 起 SDK 基于 OpenTelemetry 重写。官方文档给出的埋点方式里，装饰器最省事：

```python
from langfuse import observe

@observe()
def my_data_processing_function(data, parameter):
    return {"processed_data": data, "status": "ok"}

@observe(name="llm-call", as_type="generation")
async def my_async_llm_call(prompt_text):
    return "LLM response"
```

需要更细粒度控制时用上下文管理器，可以在一个 span 内嵌套多个 generation：

```python
from langfuse import get_client

langfuse = get_client()

with langfuse.start_as_current_observation(as_type="span", name="process-request") as span:
    span.update(output="Processing complete")

    with langfuse.start_as_current_observation(
        as_type="generation", name="llm-response", model="gpt-3.5-turbo"
    ) as generation:
        generation.update(output="Generated response")

langfuse.flush()
```

自托管 Langfuse 依赖四个有状态服务：Postgres（元数据）、ClickHouse（trace/分析数据）、Redis（队列/缓存）、MinIO（S3 兼容对象存储），官方最低建议配置是 4 vCPU / 16GiB RAM / 100GiB 存储。

这个部署量级不轻。如果 Lab 或早期 POC 只是想验证“埋点能不能跑通”，直接用 Langfuse Cloud 或者本地 mock 更划算，没必要为了演示自建一套 ClickHouse 集群。只有确定要长期自托管（通常是数据合规要求不能出境时）才值得投入这份基础设施成本。

```python
# 取自 Lab-08，langfuse SDK 4.14.3 实测
from langfuse import get_client, observe

langfuse = get_client()

# 关掉自动捕获——见下方说明，这两个参数不写就等于漏了脱敏
@observe(name="chat-completion", as_type="generation",
         capture_input=False, capture_output=False)
def call_model(prompt: str, model: str) -> str:
    # 传进来的 prompt 必须已经脱敏过；原文不应出现在这个函数的调用栈里
    response = "..."          # 真实推理调用（如 vLLM OpenAI 兼容端点）
    langfuse.update_current_generation(       # 注意方法名，见下
        input=prompt, output=response, model=model,
    )
    return response
```

这段骨架有三处是实测中改出来的，每一处都值得单独说：

**方法名按 `as_type` 分。** SDK 4.14.3 里**没有** `update_current_observation()` 这个方法，调用会直接 `AttributeError`。实际提供的是 `update_current_generation()` 与 `update_current_span()`，按被装饰函数的 `as_type` 选对应的那个。

**`capture_input` / `capture_output` 必须显式关掉。** `@observe` 默认会自动把函数的入参和返回值写进 span。这意味着**只要原文作为参数传进被装饰的函数，它就绕过了你所有的脱敏逻辑，直接进了 span 属性**。这个默认行为很容易漏——脱敏中间件写得再仔细，装饰器在你背后又抄了一份原文送出去。

**闸门要收敛到少数几个函数。** Lab-08 的做法是让 `_span_io()` / `_generation_io()` 成为整个模块唯一写 span 属性的地方，脱敏就挂在这两处。原文只存在于最外层的局部变量里，任何跨出进程的路径都得先过脱敏：进 span 属性、进检索索引、发给模型厂商 API、以及**异常信息**。最后这条最容易漏，异常消息里带的原文照样会被 SDK 上报上去。

要审计“脱敏是不是真在上报之前”，只需要看那两个函数。闸门散在几十处调用点上，是审不动的。

**日志脱敏（PII 掩码）必须在写入日志/trace 之前完成，不是在展示层或下游消费端才做。** 如果原始 PII（身份证号、手机号、邮箱、姓名）已经落进日志文件或 trace 存储，事后再“脱敏展示”解决不了合规问题——底层数据已经带着敏感信息落盘了。两类脱敏手段各有覆盖范围，通常需要组合使用：

| 脱敏方式 | 覆盖范围 | 局限 |
|---|---|---|
| 正则规则 | 结构化、格式固定的 PII：身份证号、手机号、邮箱、银行卡号 | 对格式不固定的信息（人名、地址、公司名）基本无效 |
| NER（命名实体识别）模型 | 非结构化 PII：人名、地址、机构名 | 需要额外的模型推理开销，存在误判（漏掉变体写法或过度脱敏正常文本）|

工程落地建议是在日志/trace 写入的最外层加一道脱敏中间件。正则规则打头阵处理格式固定的字段，NER 模型兜底处理自由文本里的人名地址。脱敏后的日志才允许写入持久化存储或转发给 Langfuse，这一步顺序不能反。

**审计留痕的合规要求因行业而异，本篇不逐条列具体法条**（没有针对特定行业法规原文做过核查，不在这里编造具体条款）。但可以给出一套通用的设计原则：

- **留存期限要有明确策略。** 不同行业的最低留存年限差异很大，需要按客户所在行业的官方法规确认，不能凭经验估一个数字。
- **审计记录本身要防篡改。** 常见做法是只追加写入、或者用哈希链固化历史记录的完整性，避免“审计日志被事后修改”这个更严重的问题。
- **访问控制要有独立的授权层级。** 谁能查看审计记录本身也是一项需要被审计的操作，不能所有工程师默认都有权限。

这三条原则是通用工程设计考量，具体合规红线以客户所在行业的官方法规文本为准。

## 10.6 成本治理

**单位经济模型要算两层，只算第一层会低估真实成本。** 第一层是“每次调用成本”：按 token 计价，输入 token 和输出 token 通常单价不同，把两者按当次用量加权求和就是这次调用的直接成本。第二层是“每个业务动作成本”。一个业务动作往往不是一次调用就能完成，比如“处理一张发票”或“回答一次客服工单”。它可能包含检索、多轮推理、失败重试、甚至触发人工复核前的多次候选生成。把这个业务动作背后所有相关调用的成本汇总起来，才是这个业务动作的真实成本。

只报第一层的数字会系统性低估真实成本，接了第 8 章讲的 HITL 门槛之后尤其如此。一部分业务动作会因为触发人工复核而产生比“看起来简单”的调用记录高得多的实际成本（多轮生成候选答案供人工挑选、或者失败重试）。

成本看板至少要覆盖这几类指标，任何一类缺失都会让“这套系统到底贵不贵”变成一笔糊涂账：

- **按模型/租户/业务功能拆分的成本**——不拆分只看总成本，出问题时无法定位是哪个模型选型不合理还是哪个租户异常放量。
- **缓存节省的成本**——§10.4 讲的多级缓存，命中率提升带来的成本节省应该单独算一条线。被总成本曲线的自然下降“悄悄吸收掉”，就看不出缓存策略本身的贡献。
- **P50/P95 延迟与 token 用量分布**——延迟和成本经常是一对需要权衡的指标，量化程度越激进吞吐越高但可能损失一些效果。看板要能把这个权衡摆出来，而不是只看成本一个维度就下调整决策。
- **业务动作粒度的单位成本趋势**——按业务动作而不是按调用汇总的成本，看它随时间的变化趋势。这是判断“这套系统的经济性能不能撑住规模化”的核心信号。

**容量规划与压测方法，直接复用第 8 章的评估体系，不需要另起一套。** 压测输入应该用黄金集覆盖典型场景、对抗集覆盖边缘和高负载场景，而不是随手写几条测试 prompt。这样测出来的延迟和吞吐数字，才能和评估侧的质量指标放在同一份报告里对照着看。

压测要覆盖真实的峰值并发场景，不能只测平均负载下的表现。很多系统在平均负载下 P95 延迟完全达标，一旦遇到促销、月末结算这类业务高峰触发的并发尖峰，排队和超时会集中爆发。

压测报告应该同时给出“P95 延迟是否达标”和“缓存命中率与错误命中率”两组数字并列展示。这是本书 Lab-06 的验收标准之一：压测报告显示 P95 延迟达标，缓存命中率与错误命中率同时打印。无 GPU 环境降级为 CPU 小模型时验收阈值相应放宽，并在 README 里写清楚放宽了多少、为什么。

本章讲的七块是容器化交付、离线部署包、推理性能优化、缓存、可观测性、成本治理，以及生成内容的标识义务。前六块合起来，是让一套 AI 系统从“能在自己电脑上跑”变成“能在客户环境里稳定运行”的完整工程闭环；第七块决定它被不被允许对外提供服务。

上册第 19 章的物理隔离主权 AI 部署案例，直接站在 §10.2 的自包含离线部署包之上：客户现场没有外网、镜像必须扫描过审、模型权重传输需要审批。§10.2 给出的五步清单会被逐条摆到真实的现场约束里检验，包括它在什么条件下会不够用、需要额外补什么。

## 10.7 生成内容的标识义务

前面六节讲的是系统怎么跑起来、跑得稳、跑得便宜。这一节讲的是它被允许上线的一个前提条件：
生成出来的东西，要能被认出来是生成的。

《人工智能生成合成内容标识办法》由国家网信办、工业和信息化部、公安部、国家广播电视总局联合发布，
2025 年 9 月 1 日起施行；配套的强制性国家标准 GB 45438-2025《网络安全技术 人工智能生成合成内容标识方法》同日实施。
它要求两类标识并存：

- **显式标识**：用户能直接看到或听到的提示，要同时带上“人工智能”或“AI”，以及“生成”或“合成”。
  位置按内容类型定——文本在起始、末尾或中间的适当位置，图片在边角的显著位置，
  音视频在内容相关位置，交互场景在界面顶部、底部或背景。
- **隐式标识**：写进文件元数据，包含生成合成标签、服务提供者、内容制作编号这几类要素。
  内容本身没有文件元数据、技术上做不了隐式标识的，可以只做显式标识。

先说一个容易走错的判断。很多企业内部系统的第一反应是“我们不对公众开放，这条不适用”。
**这个结论可能是对的，但不能靠直觉得出。** 适用范围写在办法原文里，
判断依据是服务形态和适用条款，不是“感觉我们是内部系统”。这个判断要留下书面记录，
和上册第 18 章讲的备案适用性判断放在同一次对话里一起过。

判断下来确实适用的话，工程上的落点有四处，每一处都有对应的常见漏法：

| 落点 | 要做的事 | 常见漏法 |
|---|---|---|
| 输出渲染层 | 显式标识跟着内容一起产生 | 只在 Web 界面加了角标，API 返回和导出的文件没有 |
| 文件产出链路 | 写元数据这一步放在生成之后、分发之前 | 中间经过一次转码或压缩，元数据被剥掉了 |
| 缓存与批处理 | §10.4 的缓存命中路径也要经过标识 | 缓存直接回吐历史结果，绕开了标识那一步 |
| 用户协议与说明 | 写清楚标识方法 | 改了代码没改协议 |

第三行最值得单独看一眼。语义缓存的设计目标就是绕开生成这一步，
而标识动作如果挂在生成链路上，缓存命中时它自然就被绕过去了。
**这类缺陷不会在功能测试里暴露**——命中和未命中返回的内容看起来是一样的，
差别只在元数据里。要专门写一条用例去测缓存命中路径的标识。

最后一句关于时机：**这不是上线前补一补就能加上的东西。**
显式标识改的是产品形态，客户未必愿意在自己的界面上写“AI 生成”；
隐式标识改的是产出链路，元数据在哪一步写、经过几次转手会不会掉，都得在架构里安排。
两件事都要在第 2 关定界时摆到桌面上，写进验收单，而不是等验收会上被问。

> **可信度说明**：办法名称、四家发布部门、施行日期与强制性国标编号，是可公开核对的一手信息。
> 显式标识的位置要求与隐式标识的元数据要素，本书转述自公开的合规解读文章，
> 未逐条比对办法条文与国标原文。系统是否落入适用范围、具体要标到什么程度，
> 写进方案或验收条款前应查办法与 GB 45438-2025 原文，必要时问法务。**本书不提供法律意见。**

## 本章清单

- [ ] 用多阶段构建把编译工具链和运行时产物分开。**这直接回应现场审计**
- [ ] GPU 资源的申请值和上限设成相等。“留余量”这个思路在 GPU 上不成立
- [ ] 离线部署包四件套齐全：镜像、签名、物料清单、离线依赖
- [ ] 纯离线环境只能用带密钥的签名方式。**无密钥签名的默认路径依赖在线服务，离线不成立**
- [ ] 核对推理框架的当前版本特性，不要照抄两年前的技术卖点
- [ ] 无 GPU 环境准备三档降级路径，不要只准备一条
- [ ] 定语义缓存阈值前，**先验证两组分布分不分得开**。不可分时阈值只是召回旋钮，不是安全阀
- [ ] 缓存安全靠阈值之外的机制：词面护栏、显式裁判、高风险场景直接排除
- [ ] 命中后加一道二次一致性检查，比信任一个相似度分数可靠
- [ ] 成本算到“业务动作”这一层，不要停在“单次调用”。
      人工介入触发的多轮生成和失败重试，会让真实成本明显高于最简路径
- [ ] 命令由客户运维代执行时，交付四件套齐全：编号脚本、每步验证命令、回滚脚本、预检脚本
- [ ] 预检在变更窗口开始之前跑完。**窗口是执行时间，不是排查时间**
- [ ] 标识义务的适用性判断留下书面记录，不靠“我们是内部系统”这句直觉结论
- [ ] 缓存命中路径单独写一条用例测标识。**功能测试看不出这个缺陷，差别只在元数据里**

## 自检问题

1. 客户现场审计你交付的镜像，发现里面有一份完整的 GCC 工具链，你会怎么改？
   **判断标准**：能不能准确指出问题出在没用多阶段构建（或者多阶段构建写错了，把 builder stage 的产物整个 COPY 进了 runtime stage）。能不能说清楚为什么“事后 apt remove”解决不了体积和审计问题（不会清理已写入的镜像层）。

2. 一个团队给 GPU 推理 Pod 设置了 `requests.nvidia.com/gpu: 1`、`limits.nvidia.com/gpu: 2`，想留一点弹性余量，这个配置有什么问题？
   **判断标准**：能不能指出 GPU 作为 K8s 扩展资源**不可超卖**，这种“预留低于上限”的写法不合法，request 与 limit 必须相等；能不能说清楚“显存利用率的弹性”应该在哪一层解决（vLLM 自己的参数，不是 K8s 资源声明），而卡内切分（MIG/time-slicing）属于设备插件层，是集群管理员的决定。

3. 一个物理隔离项目的技术负责人坚持用 cosign 的默认 keyless 签名流程，理由是“官方推荐”，你怎么判断这个决定对不对？
   **判断标准**：能不能指出官方推荐 keyless 的前提是能访问 Fulcio/Rekor 在线服务，物理隔离场景的定义就是没有外网，这个前提不成立。能不能说出正确的替代方案（key-based 签名）以及需要额外确认的风险点（air-gapped 场景下 key-based 流程本身是否完全不触网，本章标注为未完全核实）。

4. 有人说“我们用了 vLLM 就等于用上了 PagedAttention 的显存优化”，这句话现在还成立吗？
   **判断标准**：能不能准确说出 v0.25.0 起 PagedAttention 已作为独立实现被移除，当前架构是 V1/Model Runner V2。能不能区分“某个具体实现被删除”和“分页管理显存这个思路被放弃”是两回事。不能简单地说 vLLM 现在完全没有类似机制，但也不能继续用旧说法去介绍当前版本。

5. 一个 Windows 笔记本上的销售演示环境，团队打算装 vLLM CPU 后端来跑本地推理，你会给什么建议？
   **判断标准**：能不能指出 vLLM CPU 后端不支持 Windows 原生；能不能直接给出正确的替代方案（llama.cpp 或 Ollama）并说明理由（都提供 OpenAI 兼容端点，客户端代码不用改）。

6. 语义缓存上线一个月后，客户反馈“偶尔会有答案文不对题”，你会先查哪里？
   **判断标准**：能不能想到先查缓存 key 有没有正确隔离租户/模型版本/prompt 模板版本。能不能想到查有没有对高风险场景做排除。能不能提出“回放这些错误案例，看它们的相似度分数落在哪个区间”这类可执行的排查动作，而不是直接调低阈值了事。

7. 成本看板显示“上个月平均每次调用成本下降了 15%”，业务方很满意，你觉得这个结论完整吗？
   **判断标准**：能不能指出“每次调用成本”下降不等于“每个业务动作成本”下降。如果同期因为质量下滑导致重试次数、人工复核比例上升，业务动作层面的真实成本可能不降反升。能不能提出应该同时看哪个指标才能验证这个结论（业务动作粒度的单位成本趋势）。

8. 审计日志的合规留存年限，你会怎么确定这个数字？
   **判断标准**：能不能拒绝“凭经验估一个数字”这种做法。能不能说出正确路径（按客户所在行业的官方法规文本确认，不同行业差异很大，本章没有给出可以直接照抄的统一数字）。

9. 一套对外提供的文案生成系统按要求加了显式标识，Web 界面上每段生成内容下方都有“AI 生成”字样，功能测试全部通过。上线两周后仍被指出有未标识的内容流出。最可能是哪两处漏了？
   **判断标准**：一是 API 直接返回和文件导出这两条路径没有经过 Web 渲染层，标识没跟上；二是语义缓存命中时直接回吐历史结果，绕开了挂在生成链路上的标识动作。这两条在功能测试里都不暴露——返回的内容看起来完全正常，差别在元数据和分发路径上。
