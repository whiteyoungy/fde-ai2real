# 第 11 章 · 国产模型与平台栈

> **一句话结论**：同一个系列、相邻两个档位的模型，可能用的是两份完全不同的许可证。
> **凭记忆下结论，会在合规审查时翻车。**

## 同一个系列，两份不同的许可证

方案里选了某系列的 3B 模型，理由是同系列的 72B 明确写着可以商用。

合规审查时法务打开了这个 3B 模型的 `LICENSE` 文件：**仅限研究与评估，不可商用。**

档位相邻，不代表授权条款相邻。这不是特例，这一章会用这个真实反例贯穿始终。

> **在骨架里的位置**：模型可替换这件事，工程上靠的不是选型选得好，是**验收集**——上册第 2 章骨架第四层那一样。有它才敢换，没它每次换模型都是重新赌一次。这一章讲怎么选，第 9 章讲那个让你敢选的东西怎么建。

## 读完这章你能做什么

1. 拿到任何一个国产开源模型的仓库，**先读 `LICENSE` 原文再决定能不能商用**，
   而不是凭“某某系列都是某某协议”这种记忆下结论。
2. 走完“商用授权 → 显存预算 → 上下文需求 → 函数调用 → 中文能力”五步，
   选出具体档位，而不是直接抄榜单第一名。
3. 区分“官方给出的显存数字”和“按参数量估算的理论值”，
   知道哪些场景下这两者的差距会直接导致部署翻车。
4. 说清三个主流平台各自的能力边界，**并分清哪些条款是核实过的、哪些需要你自己二次核对**。
5. 处理中文检索时说出选型的口径陷阱，以及中文混排文档该用哪类工具解析。

## 11.0 这一章哪些会过期，哪些不会

这一章更新周期不是按年，是按月。模型会发新版、License 条款会改、
显存需求会因为量化方案变化、平台会上线新功能——**写在纸上的那一刻就开始过期。**

所以先把这一章切成两半，读的时候分开对待：

| | 内容 | 保质期 | 怎么用 |
|---|---|---|---|
| **会过期的** | 具体型号、License 条款、显存数字、推荐卡型、平台计费细则 | 按月 | **已经迁到配套手册 C1**，那一页每季度复核。正文只留三行缩减快照。真要选型时按 §11.2 的五步自己重跑一遍，去官方仓库看当天的 `LICENSE` 原文 |
| **不会过期的** | §11.2 那五步判据、§11.1 里“同系列不同档位 License 可能完全不同”这个教训、§11.4 中文评测口径的问题 | 长期 | 这才是这一章要教的东西 |

**五步判据是这一章的结论**，它不依赖任何一个模型还存不存在：
商用授权能不能接受 → 显存预算够不够 → 上下文长度够不够 → 要不要函数调用 →
中文能力达不达标。**顺序体现的是“先排除硬约束，再比软指标”，
这个顺序在 2030 年同样成立，哪怕今天表里的档位一个都不剩。**

> **这一章的取舍**：完整八档位表与三家托管平台的计费条款已迁往**配套手册 C1**，
> 正文保留缩减快照与全部判据。这么切的理由写在配套手册的 README 里，一句话是：
> **数字过期的那天，跟它印在同一页上的判断会一起失去可信度。**

## 11.1 模型私有化选型表

选国产模型做私有化部署，最容易踩的坑不是“选错了参数规模”，是“想当然地认为同系列所有档位用的是同一份 License”。下面这三行取自完整选型表（**配套手册 C1**，覆盖 DeepSeek、Qwen、GLM、Kimi 四个系列共八个档位）。License 一栏全部核对过 Hugging Face 仓库根目录的 `LICENSE` 文件原文，不是转述第三方博客。

**先说这张表里最容易让人栽跟头的一条：Qwen2.5-3B-Instruct 用的是 Qwen RESEARCH LICENSE AGREEMENT，条款原文写明“Non-Commercial” shall mean for research or evaluation purposes only——仅限研究与评估，不可商用。** 这和同系列 72B 档位那个允许商用（超 1 亿月活需申请授权）的 Qwen License，是两份完全不同的法律文本。档位相邻不代表授权条款相邻。

3B 恰恰是最容易被选中做演示、做实验室环境的档位：参数小，单卡随便一张消费级显卡就能跑起来，下载快。这意味着它也是最容易被人在没读 License 的情况下就悄悄用进商用 Demo 甚至生产环境的档位。

如果你的项目预算或客户合同里出现了“用 Qwen2.5-3B 做原型，验证通过后直接上生产”这种计划，先停下来。换成 7B 或以上档位，或者确认最终交付形态里根本不含 3B 的推理权重。

| 模型 | 参数档位 | License（商用限制） | 显存需求（推理） |
|---|---|---|---|
| Qwen2.5-3B-Instruct | 3B（稠密） | **Qwen RESEARCH LICENSE AGREEMENT——仅限研究与评估，不可商用**，与同系列其他档位不是同一份协议 | *笔者估算*：BF16 权重 ≈6GB（未计 KV Cache） |
| Qwen2.5-7B-Instruct | 7B（稠密） | **Apache 2.0**，可商用无月活门槛 | *笔者估算*：BF16 权重 ≈14GB（未计 KV Cache） |
| Qwen2.5-72B-Instruct | 72B（稠密） | **Qwen License**（非 Apache）——超 1 亿月活需申请授权 | *笔者估算*：BF16 权重 ≈145GB |

> **这是缩减快照，只有三行，检索日期 2026-08。**
> 完整的八档位表（另含 DeepSeek-V3、DeepSeek-R1-Distill-Qwen-32B、GLM-4-9B、
> Kimi-K2-Instruct 四档，以及上下文长度、推荐卡型、函数调用支持三列）
> 在**配套手册 C1**，那一页每季度复核一次。
>
> **正文只留这三行，是因为这一节要教的东西只需要三行就够了**——
> 同一个系列里，3B 不可商用、7B 无条件可商用、72B 有月活门槛，三份不同的法律文本。
> 其余五档位的具体数字对这个判断没有增量，而它们过期得比这三行还快。

显存一列刻意区分了两种口径，**上面三行全是第一种**：

- **标「笔者估算」的，是按 FP16/BF16=2 字节/参数推算的理论值**。只算权重本身，不含 KV Cache 与实际 batch 占用。
- 标「官方来源」的才是厂商给的数字（完整表里 DeepSeek-R1-Distill-Qwen-32B 那一行取自 NVIDIA 官方 System Card，含 Minimum/Recommended 两档；GLM-4-9B 取自 Hugging Face 自动化 model-sizer）。

这两类数字不能混着用。估算值天然偏乐观：真实部署时 KV Cache、并发请求、框架自身开销都会往上叠加。尤其上下文拉长或并发数上升时，这部分开销可能远超权重本身。

**任何拿这张表做硬件采购预算的场景，都应该以官方数字为准。只有估算值时，要按至少 20%—30% 的余量往上留，并且用真实压测数据校正。不能把估算值当成能贴着上限部署的安全线。**

## 11.2 怎么选

面对一张选型表（正文这三行，或配套手册 C1 那八档位），正确的顺序不是“看哪个跑分高”，而是先过滤掉不可行的选项，再在剩下的可行集合里挑性价比。**这五步是这一章的结论，它不依赖表里有哪些档位**：

**第一步，商用授权能不能接受。** 这一步先把整张表劈成两半：

- DeepSeek-R1-Distill-Qwen-32B（MIT）、Qwen2.5-7B/32B（Apache 2.0）：无条件可商用。
- Qwen2.5-72B、DeepSeek-V3、Kimi-K2：可商用但带条件（月活门槛、使用限制条款、来源标注要求）。
- GLM-4-9B：需要先完成注册流程。
- **Qwen2.5-3B 直接出局**。如果最终交付物要商用，这个档位从选型集合里删掉，不进入后续任何一步比较。

如果客户是政务/国企场景，License 条款里的“军事用途”“伤害未成年人”等使用限制条款要额外让法务过一遍，不能假设“开源=随便用”。

**第二步，显存预算能不能满足。** 用第一步筛剩的档位对照表里的显存需求列（完整口径见配套手册 C1.1），先看客户现场实际能批到的 GPU 型号与数量，再倒推能装下哪些档位。这一步要严格执行上一节的口径区分：手里只有估算值的档位，预算要按估算值上浮留余量；DeepSeek-R1-Distill 系有官方数字，可以按官方 Recommended 档直接对照现场硬件清单。671B/1T 级别的 DeepSeek-V3 与 Kimi-K2 在这一步基本会被淘汰出“本地私有化部署”候选集。它们的存在意义是作为云 API 调用对象或效果对比基准，不是拿来在客户机房里从零搭建的目标。

**第三步，上下文长度是否够用。** 长文档问答、多轮长对话场景要看“官方声明上下文”这一列（正文缩减表未含此列，见配套手册 C1.1）。但要留意：config.json 默认值和“官方声明的最大值”经常不是一回事。比如 Qwen2.5 系官方声明 128K 是 YaRN（一种把上下文窗口外推到训练长度之外的方法，词条见附录 C）扩展后的数字，config.json 默认是 32,768。直接按默认配置部署拿到的不是文档写的那个上限，需要显式改配置并验证扩展后的效果是否稳定。不能默认“文档写了 128K 就等于开箱可用”。

**第四步，是否需要函数调用（function calling）。** 完整表里除 DeepSeek-V3/Kimi-K2 这两个不适合本地部署的档位外，其余都支持某种形式的工具调用。但成熟度不一样：

- Qwen2.5 系的 Hermes 风格 `<tool_call>` 格式在 vLLM 生态里文档最完整，`--tool-call-parser hermes` 直接可用。
- DeepSeek-R1-Distill 系以推理见长，工具调用能力相对弱。Agent 场景需要额外测试，而不是假设它和原生 Qwen2.5-Instruct 一样稳。

如果要交付的是 Agent 编排场景（对应第 7 章），这一步的权重应该拉高，不能只看参数规模和跑分。

**第五步，中文能力是否达标。** 这一步没有一张能直接照抄的权威打分表可用，详见 §11.4 关于中文评测口径的问题。实操做法是拿客户真实中文语料（不是通用测试集）跑一遍候选档位的抽样评估。用第 9 章讲的评估框架量化对比，而不是凭“国产模型中文肯定更好”这种直觉下结论。这个直觉方向可能是对的，但具体到某个客户的专业术语、行业黑话上是否成立，只有实测才知道。

五步走完，如果剩下的可行集合是空的，说明约束条件本身有冲突。比如客户既要求 100% 免费商用，又只有一张 16GB 显卡，还要 128K 上下文。需要回到客户那里谈判放松哪一个维度，而不是硬凑一个不满足约束的方案上线。

这五步的顺序体现的是“先排除硬约束、再比软指标”的原则，画成决策路径是这样：

**边界条件：这五步不是每次都要机械地从头走到尾。**

如果客户已经明确“预算充足、硬件是双 A100、只做内部知识库不涉及 Agent”，第二、第四步几乎不会成为瓶颈。可以把重心提前放到第一步（License）和第五步（中文能力）上，用更多时间做实测评估。

反过来，如果客户只给了一张 16GB 卡且预算极紧张，第二步显存约束会先把选型集合压缩到 Qwen2.5-7B、GLM-4-9B 这两三个档位。后面几步只需要在这个小集合里比较，不必对全部档位重新走一遍五步判据。

**判据顺序不变，但每一步该花多少精力，取决于哪个约束在这次交付里最紧。**

## 11.3 平台层

火山方舟、阿里云百炼、腾讯元器/大模型知识引擎是国内三个主流的托管大模型平台。
**选型逻辑和上一节完全不同：这里买的是服务，不是权重。**
核心问题从「显存够不够」变成「锁定风险有多大、迁移成本有多高」。

三家都以「聚合多模型 + OpenAI API 兼容层」作为卖点，表面上降低了应用层代码的锁定风险。
**但真正决定迁移成本的通常不在这一层**，而在三个更深的地方：

| # | 要问的 | 为什么它比 API 兼容更决定成本 |
|---|---|---|
| **①** | **能不能导出微调后的模型权重** | 导不出，意味着你在这家平台上积累的所有训练投入都带不走 |
| **②** | **Prompt / Agent 编排层是不是平台专有 DSL** | 只调基础对话 API 迁移很便宜；一旦深度用了编排能力，迁移成本是重写 |
| **③** | **私有化部署报价相对公有云 API 的价差** | 它决定了客户将来想退出公有云时，那条成本曲线长什么样 |

**这三条要直接向厂商销售或已落地案例求证，不要凭搜索结论下断言。**
它们也是这一节唯一不会过期的部分——**哪怕三家平台将来一家都不剩，
换成另外三家，要问的还是这三个问题。**

> **三家平台各自的计费细则、私有化条款与可信度标注，在配套手册 C1.2。**
> 那一节整节放在配套手册而不是书里，理由是：本书没能拿到三家可逐字核对的官方原文，
> 现有表述大量停留在「摘要级、未核实」——**这种状态可以存在于一份带复核日期的活文档里，
> 不该以确定语气印在书上。** 报价或写进合同前，按那一页给的 URL 自己核当天的数。

**一个决定「要不要选托管平台」本身的边界条件：涉密 / 物理隔离场景从架构原点就排除了这三个平台。**

涉密网络的通行原则是「涉密计算机不得直接或间接接入非涉密计算机信息系统及国际互联网，
涉密计算机和非涉密计算机信息系统之间必须实行物理隔离」。

> **出处**：《计算机信息系统国际联网保密管理规定》（国家保密局，2000-01-01 施行）第六条原文：
> “涉及国家秘密的计算机信息系统，不得直接或间接地与国际互联网或其它公共信息网络相联接，
> 必须实行物理隔离。”（全文经中国信息安全测评中心法规库页逐字核对，
> 存档 `docs/research/raw/bookaudit-20260901/guolianwang-baomi-guiding.txt`；
> 各行业保密管理规定的同类表述均由此而来。）

## 11.4 中文 RAG 特有问题

第 5 章 §5.5 讲过 Embedding 选型的通用四维框架（维度、语言、领域、成本），第 8 章讲过推理部署的通用方法论。这两处的结论在中文场景下依然成立，本节不重复展开。只补三个中文语境特有、英文材料完全不覆盖或覆盖不足的问题。

**中文分词对 BM25 的影响：一个流传很广但查无实据的说法。** 网上反复出现“中文没有天然分词边界，BM25（一种基于词频的稀疏检索算法）必须先用 jieba/HanLP 等工具分词，否则召回率骤降”这类论断。这条说法方向上有一定语言学合理性：中文书写确实不像英文那样用空格天然分词。但**没有任何一手技术文档或论文给出过量化验证**，能看到的都是自媒体反复转抄同一个未溯源的结论。处理原则和第 5 章对“分块重叠比例 10%–20%”这类流传数字的处理方式一致：**不采信具体数字，不当作可以直接引用的结论写进选型报告**。如果项目的混合检索链路涉及中文 BM25，正确做法是自己动手对比“jieba 分词后跑 BM25”与“不分词、直接按字符 n-gram 检索”在客户真实语料上的召回率差异。用实测数据说话，而不是复述网上的说法。

**中文 Embedding 选型：注意两个不同榜单口径不能混用。** 两个经核实的选项：

- **BAAI/bge-large-zh-v1.5**：2023 年发布，License 为 MIT，向量维度 1024。官方模型卡自称 C-MTEB（中文 MTEB 子榜）均分 **64.53**，这是发布时点的自我声明，不是实时榜单快照。**最大序列长度只有 512**，这是较早一代模型的明显短板。客户文档如果是长合同、长篇技术手册，这个上限会成为瓶颈，选型前必须先确认。
- **Qwen3-Embedding 系列**（0.6B/4B/8B 三档）：更新一代，Apache 2.0，8B 档在 **MTEB 多语言榜单**排名第一（截至 2025-06-05，分数 70.58，已直抓官方博客原文逐字核对）。**关键提醒：官方博客通篇没有单独公布这一档在 C-MTEB（中文子榜）的分数**——“CMTEB”字样只出现在 reranking 模型的 CMTEB-R 子指标表格里，embedding 模型本身没有列出中文子榜总分。“MTEB 多语言榜单第一”和“C-MTEB 中文榜单第一”是两个不同的评测口径，前者衡量的是跨多语言的综合表现，不能直接当成后者的替代证据来引用。如果选型报告需要中文专项效果数据，必须自己在客户中文语料上实测，不能拿多语言榜单分数冒充中文效果证明。

另外要提醒一点：MTEB/C-MTEB 官方排行榜页面是前端渲染的 Hugging Face Space，常规抓取工具只能拿到骨架 HTML，拿不到实时快照。本章给出的所有排名数字都标注了具体发布时点，不代表读者阅读本书时的现状。选型前应该自己去官方榜单页面人工核对当前排名。

**边界条件：榜单分数不适用的两种情况。**

**第一种是客户语料严重偏离通用领域。** 法律条款、医疗术语、内部产品代号这类内容，榜单分数再高的通用 embedding 模型也可能在专业术语上表现不佳。这一点和第 5 章 §5.5 讲的“领域适配”维度是同一个问题在中文场景下的具体化。解法同样是拿客户真实语料实测，不是换一个分数更高的模型。

**第二种是需要配合 Reranker（重排序模型）使用的两阶段检索架构。** Qwen3 系列除 Embedding 外也发布了配套的 reranking 模型，同样是 Apache 2.0（已核对官方博客原文：“we... published the reranking models under the Apache 2.0 license”）。选型时两者的 License、版本兼容性需要放在一起考虑，不能只选好 Embedding 就结束。漏掉 Reranker 这一环会让“选型完成”的判断不完整。

**中文混排文档（表格 + 图 + 竖排）的解析工具。** 第 5 章讲过文档解析的通用四类难点（阅读顺序、结构还原、识别精度、版面区域检测），中文场景下有两个专门针对这类问题的开源工具值得关注：

- **PaddleOCR PP-StructureV3**（百度飞桨）：官方文档原文称支持“版面区域检测、表格识别、公式识别、图表理解以及多栏阅读顺序恢复”，已核对 GitHub 原文，为逐字引文。输出格式为 Markdown + 带坐标 JSON，适合需要把解析结果直接喂进分块管道的场景。
- **MinerU**（上海 AI Lab / OpenDataLab）：开源 PDF 结构化提取工具，官方 README 采用“三路后端”设计——pipeline / vlm-engine / hybrid-engine（已核对 GitHub 中文 README 原文，“hybrid”是简称）。

这两个工具的**竖排文本处理能力本书没有核实过**。中文历史文档、部分古籍与法律文书是竖排的，这是英文技术材料完全不涉及的问题。客户文档里有竖排内容的话，单独做一次小样本实测，别假设工具默认支持。具体识别准确率数字同样待补。选型前建议先用客户真实的一批混排样本跑一遍两个工具的输出，对比结构还原的完整度，而不是直接看 GitHub star 数或宣传页面下结论。

## 11.5 Lab-09 任务书：国产栈演练

Lab-09（对应 Task 44）已实现并通过验收，材料包与 `verify.sh` 都在 `labs/lab-09-china-stack/`；这里给任务书。

**场景**：客户要求把一套内部知识问答系统从云端 API 迁移到私有化部署，理由是数据不能出内网。现场硬件条件不确定，任务书要求同时规划“有 GPU”与“无 GPU、只有昇腾 NPU 或纯 CPU”两条路径。因为这是国产化交付里极其常见的现实：客户机房拿到手的硬件清单和最初谈的经常对不上。

**任务要求**：

① 依据 §11.1 的选型表，为“数据不出内网 + 单机部署 + 需要 Agent 工具调用”这个约束组合选出具体模型档位。写清楚选型走完了五步判据里的哪几步、结果分别是什么。**注意许可证这一步**：本约束组合是要上生产的，因此不可商用的档位一律出局，`verify.sh` 对此零容忍。但这条判据是**条件性**的，不是“3B 永远不能选”。Lab-09 的夹具里专门放了一对只差“是否商用”一个条件的场景：商用那个正确答案是 7B，纯研究评估那个正确答案就是 3B。把条件性判据记成绝对禁令，会在客户明确说“只做内部研究”时白白多花几倍硬件钱。

② 为选定档位写出 GPU 路径（vLLM 部署）与降级路径（昇腾 NPU 或纯 CPU）各一份最小可运行配置骨架。两条路径的性能预期要分别写清楚，不能用同一套延迟/吞吐指标应付两种硬件。

③ 用第 8 章 §8.3 讲过的 CPU 三档降级方法论，把本章选定的国产模型档位套进那个框架里，写出对应的降级判断逻辑。

④ 产出一份显存预算表，明确标注每一项数字是“官方给出”还是“按参数量估算”。估算值必须按不低于 20% 的比例上浮，并说明这个上浮比例的依据（压测数据或 §11.1 的口径提醒）。

*✓ 本段的 API 形态已在 RTX 4090（24GB，vLLM 0.26.0）上实测跑通——但**模型换成了 Qwen2.5-0.5B-Instruct**，不是骨架里写的 7B（临时租用的机器带宽只够拉 1GB 权重）。也就是说：这段代码能不能跑、参数名对不对、`LLM(...)` 构造是否合法，已经验过；**7B 在 24GB 卡上的实际显存占用与吞吐没有验过**。*
```python
# labs/lab-09-china-stack/deploy_gpu.py（7B 配置仍需在目标硬件实测）
# 目标：Qwen2.5-7B-Instruct 单卡 GPU 部署骨架；API 形态已用 0.5B 代跑验证

from vllm import LLM, SamplingParams

# 显存预算：估算 BF16 权重 ≈14GB，未计 KV Cache，
# 实际部署时应按压测数据留出 20%-30% 余量，不能贴着估算值上限配置
llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    tensor_parallel_size=1,
    gpu_memory_utilization=0.85,  # 由 vLLM 自己管理显存切分，不是 K8s 层的资源分配
    max_model_len=32768,           # config.json 默认值；128K 需显式开启 YaRN 扩展，另行验证稳定性
)

sampling_params = SamplingParams(temperature=0.2, max_tokens=1024)

# 工具调用需在 serve 命令中显式启用 hermes 解析器：
# vllm serve Qwen/Qwen2.5-7B-Instruct --enable-auto-tool-choice --tool-call-parser hermes
```

实测记录（RTX 4090 / vLLM 0.26.0 / Qwen2.5-0.5B-Instruct 代跑）：

| 项 | 实测结果 |
|---|---|
| `LLM(model=..., tensor_parallel_size=1, gpu_memory_utilization=0.85, max_model_len=32768)` | 构造成功，模型加载 130.3 秒（含 CUDA graph 捕获 86 个） |
| `SamplingParams` + `generate()` | 成功，64 token 耗时 0.19 秒，中文输出通顺 |
| `--enable-auto-tool-choice` | 存在 |
| `--tool-call-parser` 的可选值 | 共 44 个，**含 `hermes`** |

加载耗时 130 秒这个数字值得单独说一句：它对 §8.1 讲的探针配置是直接的输入——`livenessProbe` 沿用 Web 服务惯用的几秒超时，会在模型还没加载完时就把 Pod 判死并反复重启。**这就是那里为什么要额外配 `startupProbe`。** 0.5B 尚且要两分钟，7B 只会更久。

### 把模型和依赖弄到机器上，往往比选型更耗时间

本书为了实测这一节的 GPU 路径，临时租了一台 RTX 4090。**一小时的机时里，超过四十分钟花在“让机器能下载东西”上**，真正跑模型只用了几分钟。四个坑按踩到的顺序记在这里，都是国内 GPU 机器上的高频问题：

**一、DNS 解析到 IPv6，但 IPv6 出口不通。** 表现是所有 `curl` 静默卡住直到超时，看着像“网络全断了”，而 `apt` 却是通的——因为 apt 源解析到了 IPv4。判据是 `getent hosts <域名>`，返回 `2402:...` 这类地址就是它。改法是在 `/etc/gai.conf` 里放开那行 `precedence ::ffff:0:0/96  100`，让系统优先 IPv4。**这一条最坑，因为它伪装成“网络不好”，而不是“配置不对”。**

**二、量带宽要量对目标。** 我最初拿默认 pypi 量出 36 KB/s，据此判定“这机器装不了 vLLM，需要 27 小时”，差点把机器退了。换成清华镜像和 hf-mirror 之后实测 **2.9 MB/s，快八十倍**，vLLM 全套依赖二十分钟装完。**测量本身没错，错在没检查测量条件**——这和上册第 6 章讲的“用 mock 数据测出来的结论不算数”是同一类错误。

**三、`huggingface-cli` 已更名为 `hf`。** 老命令会打印一段迁移提示然后退出，脚本里 `set -e` 的话直接中断。

**四、`huggingface_hub` 的 Python API 会走 Xet 后端，国内镜像不代理它。** `snapshot_download()` 报 `401 Unauthorized`，域名是 `cas-server.xethub.hf.co`——注意它**不是** `hf-mirror.com`，所以设了 `HF_ENDPOINT` 也没用。绕法是直接 `curl` 拉 `https://hf-mirror.com/<org>/<model>/resolve/main/<文件>`，实测稳定在 2.9 MB/s。

这四条没有一条和模型能力、显存、许可证有关，但它们决定了你今天能不能开始干活。**给客户做交付排期时，“把东西弄进去”这一段要单独留时间**，它不属于“环境准备”这种一笔带过的项。

**验收标准（草案）**：`verify.sh` 检查：

① 选型结果是否规避了 3B 研究许可档位。

② 两条硬件路径的配置骨架是否都能在对应环境里完成模型加载。不要求达到生产级吞吐指标，昇腾/CPU 降级路径允许放宽延迟阈值，但必须在文档里写清楚放宽了多少、依据是什么。

③ 显存预算表是否明确标注了每个数字的官方/估算来源。

内容质量（选型判断是否站得住）需要人工或参考答案比对。

本章的选型表和决策路径，是上册第 12 章讲国企/银行/政务客户交付时“为什么很多现场只能选国产模型而不是调用境外 API”这个前提条件的技术落地。反过来，上册第 11 章讲的招投标与预算结构，也决定了客户能不能接受 72B 或以上档位这种需要更大硬件投入的方案。

国产模型栈的选型从来不是一个纯技术决策。本章给出的判据要和上册第 11、12 章的商务约束合在一起看，才是完整的选型逻辑。

## 自检问题

1. 同事提议“Qwen2.5 系列都是 Apache 2.0，直接拿 3B 做客户 Demo 之后原样上生产”，这句话哪里有问题？
   **参考答案要点**：3B 档位是 Qwen RESEARCH LICENSE AGREEMENT，仅限研究与评估，不是 Apache 2.0。即使 Demo 阶段可以用，“原样上生产”是商用行为，必须在正式交付前换成 Apache 2.0 的 7B/32B 档位或有商用条款的其他档位。不能因为 Demo 阶段跑通了就假设授权也没问题。

2. 一份选型报告写道“DeepSeek-V3 直到 V3.1 才支持 128K 上下文，之前版本更短”，这句话的问题出在哪？
   **参考答案要点**：这混淆了“在线聊天产品 chat.deepseek.com 的上下文窗口升级”和“开源权重模型的规格”两件事。开源版 DeepSeek-V3 从初版 README 就声明 128K（config.json 的 `max_position_embeddings` 为 163840、原生 4096 加 YaRN 扩展——两个口径都比“更短”的说法高），不存在“之前版本更短”的情况。写选型报告时要分清引用的信源到底描述的是哪个产品形态、引的是哪个口径。

3. 一张显存预算表上写着“Qwen2.5-32B-Instruct 显存需求 64GB”，没有任何其他说明，你会追问什么？
   **参考答案要点**：先问这个数字是官方给出的还是按参数量估算的。如果是估算值（本章与配套手册 C1 表里都是笔者按 BF16=2 字节/参数估算的），意味着没有计入 KV Cache 和实际 batch 占用，真实部署需要的显存会更高。采购硬件前应该要求提供压测数据或按估算值上浮 20%-30% 留余量，不能直接按这个数字去配等大小的显卡。

4. 客户只能提供一张 16GB 显卡，同时要求商用授权无门槛、128K 上下文、成熟的函数调用支持，这四个条件能同时满足吗？
   **判断标准**：能不能指出显存约束（16GB）在选型表里基本排除了 32B 以上的稠密模型。剩下的可行档位是否同时满足 License 无门槛与函数调用成熟这两个条件。能不能给出结论是“可行但需要明确哪个候选档位”而不是笼统地说“肯定能满足”。也能不能识别出如果确实无解，应该回头和客户谈判放松某个维度而不是硬凑。

5. 一份报告引用“Qwen3-Embedding 8B 在 C-MTEB 排名第一”，这句话可信吗？
   **判断标准**：能不能指出已核实的数据是“MTEB 多语言榜单第一，截至 2025-06-05，分数 70.58”，官方材料没有单独公布 C-MTEB（中文子榜）分数。能不能说明这是两个不同的评测口径，不能混用。

6. 你在网上看到“中文 BM25 检索不分词召回率会骤降 40%”这样一个具体数字，会怎么处理？
   **参考答案要点**：先追问这个数字的一手来源是哪篇论文或官方基准测试。如果只能找到自媒体反复转抄、没有可溯源的原始出处，这个具体数字不能采信，只能承认“中文分词可能影响 BM25 效果”这个方向性判断。精确数字需要自己在客户语料上实测得出。

7. 客户方 IT 负责人说“我们已经和某平台谈好了私有化部署报价，条款都定了”，作为交付方你该做什么？
   **判断标准**：能不能指出本章对三个平台私有化条款的核实程度普遍只到摘要级。即便客户方声称“条款都定了”，也应该要求拿到书面条款原文，而不是假设客户谈判的结果一定准确、完整。自己核对一遍导出模型权重、Prompt/Agent 编排层锁定、私有化报价与公有云价差这三点。

8. 你负责的项目决定用国产模型做私有化部署，但客户现场实际到货的硬件是昇腾 NPU 而不是最初谈的 GPU，这时候第一步该做什么？
   **参考答案要点**：不能直接假设 GPU 路径的部署配置和性能预期可以照搬。应该先回到 §11.1 的选型表和第 8 章的降级方法论重新走一遍决策路径。确认所选模型档位在昇腾/CPU 路径下能否找到对应的推理框架支持，并重新设定一套单独的性能预期。不能用 GPU 路径的指标要求降级后的环境。
