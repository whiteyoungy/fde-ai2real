# 第 6 章 · 本体的工程实现

> **一句话结论**：本体属于客户，平台只是它的一种运行方式——这句话落到工程上，就是每一层都得能换掉。

## 七要素定完了，落到什么上

上册第 7 章那七个要素——对象、状态、关系、动作、判据、权限、证据——
在会议室里都填完了，客户方业务专家签了字。

回到工位，第一个问题就卡住：**这七样各自落到什么技术上？**

架构师给的方案是一套图数据库加一个规则引擎，理由是“本体天然是图”。
听起来对。但你想起上册那句话——**本体属于客户**——于是多问了一句：

> 五年后我们不在了，客户能把这个本体导出来、看得懂、接着用吗？

这个问题一问，方案就得重来。因为它决定的不是选型，是**这套东西归谁**。

> **在骨架里的位置**：**这一章决定另外三类结果的形状。** 本体里的“证据”要素定义了第 4 关能攒到什么字段，“判据 + 权限”决定第 5 关的控制有多细，“对象 + 动作”决定第 6 关客户要接管的到底是什么。**本体没定，外面那三关攒的东西都会缺一块形状。**

## 读完这章你能做什么

1. 把七个要素落到具体技术层上，并说清每一层为什么可替换。
2. 判断一个“有关系就上图数据库”的方案是不是过度设计，并给出改期条件。
3. 把“动作必须写回”从一句原则变成幂等、事务边界和补偿三件具体的工程约束。
4. 把判据的例外分支做成系统里的一条路径，并说清为什么“不给出路”会让证据链整段消失。
5. 评估一个开源本体平台**覆盖了七要素里的哪几样、缺了哪几样**，而不是看它的宣传页。

## 6.1 七要素对应哪几层

原则只有一条：**可替换优先。** 具体落法：

| 要素 | 落在哪一层 | 优先选 |
|---|---|---|
| **对象** | 数据模型 | 开放 Schema——JSON Schema、OpenAPI，或干脆就是数据库表结构 |
| **状态** | 数据模型 + 状态机 | 状态与迁移条件显式建表，不要散在业务代码的 if 里 |
| **关系** | 存储层 | **关系数据库优先**，确有复杂关系需求再上图数据库 |
| **动作** | 执行层 | 工作流引擎、规则引擎、服务 API |
| **判据** | 执行层 | 规则引擎或策略引擎，与动作分离 |
| **权限** | 授权层 | IAM、RBAC/ABAC、策略引擎 |
| **证据** | 事件层 | 消息队列 + 事件日志 + 审计存储 |

```{=latex}
\fdfig{\fdontolayers}
```

再加两条跨层的：

- **Agent 通过工具接口调动作，不直接写底层数据库。** 这条和下册第 8 章讲的护栏是同一件事——
  **Agent 能做的动作集合，必须等于人能做的动作集合**，不能多出一条旁路。
- **元数据要能导出、能版本控制、能做差异审查。** 这条是“本体属于客户”的工程落点。

### 为什么这一章插在数据管道之后、Agent 编排之前

因为**本体是 Agent 动作的作用对象**。

上一章（第 5 章）解决的是数据怎么进来、怎么切、怎么向量化——那是**原料**。
下一章讲 Agent 怎么编排——那是**执行**。
中间必须先有一层回答“这些原料构成哪些对象、对它们能做什么、谁批准”，
**否则 Agent 编排出来的是一串对着裸数据的操作，没有业务语义，也没有授权边界。**

顺序倒过来的典型症状：Agent 能查任何表、能改任何字段，
每加一个新场景就要在提示词里补一段“不要动 XX 表”。**那不是本体，那是口头约定。**

### 关系层：先别上图数据库

这是这类项目最常见的过度设计，值得单独说。

“本体天然是图”这句话本身没错，但它推不出“所以要用图数据库”。
一个最小可执行业务模型里的**关系类型**通常只有几十条——
设备属于产线、工单关联设备、审批人属于部门。这个量级关系数据库装得下，
而且客户的 DBA 已经会维护它。

**判据是查询形态，不是关系数量。** 该上图数据库的信号只有一个：

> **你的核心查询是变长路径遍历，而且深度不定。**

“找出这台设备三跳以内所有受影响的下游工位”——这是图查询。
“找出这个工单关联的设备和它所在的产线”——这是两个 JOIN。
**后者用图数据库，你付出的是一整套新的运维、备份、监控和人员技能，换回来的是零。**

上册第 7 章说的“平台只是本体的一种运行方式”，在这一层的含义是：
**先用客户已经在运维的东西实现，等它真的不够用了再换。**
换的时候有对象模型和关系定义在手，换的是存储不是本体。

## 6.2 硬规矩落到工程上

上册第 7 章给了三条硬规矩，外加一条增补的第四条。这一节讲它们各自的工程形态。

### 一、动作必须写回：幂等、事务边界、补偿

“写回”在工程上是三件事，缺一件都会在生产上咬人：

**幂等。** 动作会被重试——网络超时、消息重投、用户手抖点两次。
每个写回动作要有幂等键，重复执行不产生第二条工单。
下册第 4 章讲企业集成时那套幂等设计，在这里是同一套东西，
**只是这次的调用方可能是 Agent 而不是人。**

**事务边界。** 一个业务动作经常要写多个系统——建工单、扣库存、发通知。
这三件不在一个事务里。要显式决定：哪些必须同时成功，哪些可以最终一致，
**哪一步失败了算整个动作失败。** 不决定的后果是出现“工单建了但库存没扣”这类
既不算成功也不算失败的中间态，而这种状态在审计时最难解释。

**补偿。** 承认会失败，然后写清楚失败之后怎么退回去。
**没有补偿路径的动作，本质上是一个不能回滚的写操作**——
它可以存在，但必须在设计时被标出来，让人知道这一步过了就没法退。

### 二、权限进模型：和 API 鉴权不是一层

这条最容易被工程师误解成“我们有鉴权啊”。

区别在**粒度和归属**：

| | API 鉴权 | 本体里的权限 |
|---|---|---|
| 管什么 | 这个调用方能不能调这个接口 | **这个人能不能对这个对象执行这个动作** |
| 谁定义 | 后端或网关团队 | **业务方**，照抄现有审批制度 |
| 变更频率 | 低 | 跟着组织和制度变 |
| 出错的表现 | 401/403 | **动作执行了，但执行的人本不该有这个权限** |

最后一行是要害。API 鉴权拦得住“没登录的人”，拦不住“登录了但不该批这一单的人”。
上册第 7 章那个例子里，申请停机在车间主任手上——**这条约束不在网关里，在业务模型里。**

工程落法：把权限作为动作的前置条件之一求值，和判据同一个位置，
**而不是在动作执行完之后再去查一次谁执行的。**

### 三、证据落到字段，不是落到日志

“我们记了日志”和“这个动作留下了可审计的证据”是两回事。

区别在**结构化程度和完整性**：日志是给人排障看的，字段随开发心情变；
证据是给审计看的，字段固定、必填、可查询。

一条动作证据至少要有五样：

```text
谁          执行主体（人或 Agent 的身份，不是"system"）
什么时候     时间戳
对哪个对象   对象 id 与版本
基于什么     触发它的上游事实（哪条告警、哪份申请）
判据取值     ★ 执行那一刻，每个前置判据分别是什么值
```

**第五样是最容易漏的，也是唯一能区分“判据放行了”和“有人绕过了判据”的。**
上册第 7 章那个停机例子里说过一次，这里给它的工程形态：
判据求值的结果要和动作记录一起落库，**不能只落一个布尔的最终结论。**

### 四、例外分支要是系统里的一条路径，不是绕过系统的一条路

上册第 7 章在三条硬规矩后面补了第四条：**判据必须带例外分支。**
这一条的工程形态最容易做错，而且做错的方式只有一种——**做成了“不做”。**

现实里判据经常不满足：三个条件满足两个，而设备已经在冒烟了。
这时候业务必须往下走。系统如果没给出路，出路自然会长在系统外面：
有人打电话、有人直接改数据库、有人拿别人的账号点一下。
**这三种做法的共同点是，它们全都不留证据。**
上一小节辛辛苦苦建起来的那五个字段，在这些路径上一个都没有。

所以例外分支的工程判据只有一条：

> **例外必须比正常路径更难走，但必须走得通；
> 而且例外路径产生的记录，要比正常路径更详细，不是更少。**

落到实现上是三样：

**一、例外是一个显式状态，不是判据被跳过。**
动作记录里要能区分“判据全部满足后执行”和“判据未满足，由某人升级放行后执行”。
做法是给动作加一个放行方式字段，取值至少三种——正常、升级放行、降级执行——
**默认值不能是空。**

**二、放行权限本身是本体里的一条权限，不是一个开关。**
“谁能在判据不满足时放行”和“谁能在判据满足时执行”是两条不同的权限，
经常也不是同一个人。把它做成一个配置开关或者一个管理员后门，
等于把这条权限从业务模型里拿掉了——上一小节讲的“权限进模型”在这里被自己破了例。

**三、例外记录要多存两样东西：放行理由，以及放行那一刻每条判据的实际取值。**
第二样是关键。只记“车间主任批了”，事后无法回答“他批的时候到底差哪一条”；
记了取值，这些记录就自动成为一份素材——**如果某条判据被绕过的比例长期偏高，
那说明这条判据本身定错了，该回到上册第 2 关重谈，而不是继续每次都批。**

**这第三样是例外分支唯一的正面价值。** 前两样是为了合规和可追溯，
第三样让例外记录变成改进判据的输入。一套只允许正常路径的系统，
业务会绕开它；一套允许例外但不记录的系统，你永远不知道判据定得对不对。

> **和第 8 章的关系**：例外放行是一个典型的人工闸门，
> 它的审批实现、留痕要求和阻断策略在第 8 章那套护栏里，本节只定义它在本体中的形状。

## 6.3 参照实现：Semantica

有一个开源项目值得当参照看：`semantica-agi/semantica`，MIT 许可证，
Python 写的，自称“面向 AI Agent 的开源 Palantir” [1]。

> **可信度说明**：本节所述均取自仓库 `c7d60857`（2026-08-25，`v0.6.6`）
> 及其自带文档。**本册读了它的代码与文档，没有运行它。**
> 它处于 0.6.x 阶段，接口会变；**下面每一条覆盖度判断都是对这个提交的判断。**

### 它是什么形状

一条从数据源到知识图谱、再到“智能层”的管线 [2]：

```text
接入 → 解析 → 归一 → 切分 → 抽取（实体/关系/事件）
   → 冲突检测 → 去重 → 知识图谱构建
   → [本体 · 推理 · 溯源 · 决策]
   → 向量库 + 图存储 → 导出（RDF/OWL/SHACL/Parquet/Cypher…）
```

对 FDE 有意义的是“智能层”那四块和它们的两条性质。

**第一条性质：确定性。** 官方明说——**推理引擎、知识图谱构建与溯源层是完全确定性的，
使用它们不需要 LLM** [1]。

这一条在中国现场的分量比在别处大。**一个不需要调用模型就能跑的审计层，
意味着它不产生跨境传输、不需要为了合规去论证模型部署位置、
断网也能跑。** 上册第 13 章讲合规排期时那三个问题，这一层能绕开其中两个。

**第二条性质：可替换的存储。** RDF 与属性图两类后端都支持，
向量库也是多后端，官方的说法是“全都可换，不用改你的代码” [1]。
这正好对上 6.1 那条可替换优先。

### 决策是一等公民

它最值得学的设计是把**决策做成图里的一等节点**，而不是一行日志 [1][3]：

```python
decision_id = graph.record_decision(
    category="credit_application",
    scenario="个人贷款，年收入 8.5 万，负债收入比 31%，在职 3 年",
    reasoning="收入达标；在职稳定；无不良信用记录",
    outcome="proceed_to_underwriting",
    confidence=0.88,
)
```

然后可以把决策之间连成因果链、按先例检索、追溯完整祖先、
过一遍策略门禁，最后**导出成 W3C PROV-O**——这是多数合规框架接受的溯源格式 [1][3]。

**对照 6.2 第三条看**：`scenario`、`reasoning`、`outcome`、`confidence`
正好是“谁、基于什么、结果、把握有多大”的结构化版本。
**这就是“证据落到字段”的一个现成实现。**

## 6.4 它覆盖了什么，缺了什么

这一节是本章的核心判断。把七要素逐条对一遍：

| 要素 | 覆盖 | 依据 |
|---|---|---|
| **对象** | 有 | 知识图谱构建、实体消解 |
| **关系** | 有 | 同上，RDF 与属性图双后端 |
| **状态** | 有 | 双时态事实与时点快照（可以查“某天的图长什么样”） |
| **判据** | 有 | 策略引擎（约一千行）＋ SHACL 约束 |
| **证据** | **强** | **W3C PROV-O 溯源，六个文件近五千行——溯源层在整个代码库里的分量罕见地重** |
| **动作** | **无** | **仓库里搜不到写回或动作类型这类概念** |
| **权限** | **无** | 只有 API 与存储层的访问控制，**没有对象级、动作级的业务授权** |

**结论要说准确**：它覆盖了七要素里的五样，缺的两样正好是最难的两样——
**而按上册第 7 章 §7.3 的三条硬规矩，缺了动作就不算业务本体。**

所以“开源版 Palantir”这个说法要打折扣。上册第 7 章 §7.1 说过，
Palantir 本体论和知识图谱的分界正是“**谁能基于这种关系执行什么动作、
动作如何写回生产系统**”——而这恰好是它没做的那一半。

**但这不算批评，因为它自己没这么承诺。** 官方的定位是
“补充你现有的技术栈，而不是替换它” [1]——这个说法是准确的。

所以正确的用法是：

> **把它当本体的知识层与证据层，动作层和权限层你自己在它外面接。**

这个定位下它很值钱：你省掉的是溯源、冲突检测、去重、多后端存储、
审计导出这一整摊——这摊活自己写要几个月，而且**写不好在审计时是致命的**。

### 三条要一起记住的限制

**一、`evals` 模块是空的。** 目录存在，但 `__init__.py` 全文就是
`"""Coming Soon"""`，状态字段写着 `coming_soon`，导出列表是空的。
**别因为看到目录名就把评估这一块算进方案。** 下册第 9 章那套评估仍然要你自己建。

**二、推理引擎的匹配器是简化版，官方自己说了。** README 里有一条限制说明：
Rete 引擎的条件匹配在这个版本里“刻意简化”，
**接进生产合规门禁之前，请先用你自己的规则集验证它的输出** [1]。

主动写下这种话的项目不多。**照它说的做**——把这句话当成一条必须执行的动作，
不是一条免责声明。

**三、0.6.x。** 接口会变。要写进合同就锁版本，理由和本册第 8 章锁镜像、锁依赖那套一样。

## 6.5 什么时候不该用它

| 情况 | 判断 | 怎么办 |
|---|---|---|
| 你缺的是完整业务本体（含动作与权限） | **不对症** | 它只给知识与证据层，另外两层自己接 |
| 你缺的是可审计的溯源与决策记录 | **对症** | 就是它最强的地方 |
| 客户的软件清单要求组件有商业支持 | **不能用** | MIT 开源件通常过不了这一关 |
| 客户要求断网运行、数据不出域 | **可以用** | 推理、图构建、溯源不需要 LLM |
| 你只有几十个对象、几十条关系 | **过重** | 先用关系数据库加审计表，别为了架构好看引入一整套 |
| 合同运维期长、交付后你就撤场 | **谨慎** | 锁版本，并在合同里写明升级不在服务范围 |

倒数第二行要认真读。**这一章讲的所有东西，都可以用一张业务表加一张审计表实现。**
引入一整套本体平台的门槛不是“我们有本体”，而是——

> **你的对象和关系是否已经多到，用表维护它们本身成了一件出错的事。**

答不上来这个问题，就先用表。上册第 7 章那句“不要叫它企业统一本体”，
防的就是这一步的过度设计。

## 这一章的来路：源 · 理 · 证 · 界

**源 · 从哪来。** 上游判据是**上册第 7 章**那七个要素。
这一章讲的是它们落到工程上分别对应什么。参照实现的部分来自对一个开源项目
某一次提交的代码检索 [1][2][3]——**§6.4 那张覆盖度表是本书对那次提交的判断，
不是该项目的官方说明** [4]，而且它会随版本过期，所以章末标了检索日期。

**理 · AI 改变了哪个前提。** 传统信息系统里，这几样东西**分处三个地方**：
对象和关系在数据库表结构里，判据在应用代码里，权限在审批制度和岗位职责里。
它们对不对得上，**靠人在中间兜着**——需求评审、联调、上线前对一遍。
AI 系统要自己给结论、自己调工具、自己执行动作，**中间没有那个兜着的人了**。
于是判据、权限、证据必须和对象、动作在同一个模型里、能被程序读取，
否则每一次决策都得现场拼一遍，而拼错了没人知道。

**证 · 现实里能看到什么。** 章首那句“七要素定完了，落到什么上”。
定完了没有承载物，那份七要素就退回成一份文档——
**而文档不会拒绝一次越权的动作。**

**界 · 什么时候不适用。** §6.5 已经写了一整节。这里补两条：
第一，**这一章绑的是一个具体实现的某一次提交**，工具会变、判断会过期，
它的作用是给一个可对照的参照系，不是推荐选型；
第二，也是更硬的一条——**上册 §7.2 那句“技术平台可以表达授权，
不能代替组织授予授权”在工程上同样成立。** 组织责任没解决的时候，
这一整套东西建得再完整，也只能读不能写。

## 本章清单

- [ ] 七个要素逐条落到具体技术层，每一层写清为什么这么选、什么条件下换掉
- [ ] 关系层默认关系数据库；要上图数据库，先写出那个变长路径遍历的查询
- [ ] 每个写回动作确认三件事：幂等键、事务边界、补偿路径
- [ ] **没有补偿路径的动作单独标出来**，让人知道过了就退不回去
- [ ] 权限求值放在动作的前置条件里，不放在执行之后的审计查询里
- [ ] 动作证据落五个字段，**包括判据在执行那一刻的取值**，不只落最终布尔结论
- [ ] Agent 能执行的动作集合，和人能执行的对一遍，不能多出旁路
- [ ] 若选用开源本体平台，**逐条对七要素填覆盖度表**，缺的那几样写进方案
- [ ] 本体元数据能导出成文本、能进版本库、能做差异审查

## 自检问题

**1. 客户的架构师说“本体天然是图，所以要上图数据库”，这个推理哪里断了？**

参考答案要点：前提成立，结论不跟随。该不该上图数据库看的是**查询形态**——
有没有深度不定的变长路径遍历，不是看关系多不多。
两个 JOIN 能解决的事用图数据库，付出的是一整套新的运维和人员技能，换回来的是零。

**2. “我们有 API 鉴权”和“权限进了本体模型”，差在哪？举一个前者拦不住的例子。**

参考答案要点：差在粒度和归属。API 鉴权管“这个调用方能不能调这个接口”，
本体权限管“这个人能不能对这个对象执行这个动作”。
前者拦不住“登录了但不该批这一单的人”——**动作执行成功，执行的人本不该有这个权限。**

**3. 动作证据里“判据在执行那一刻的取值”这一项，不记会怎样？**

参考答案要点：事后无法区分“判据放行了”和“有人绕过了判据”。
只记最终布尔结论，等于只记录了系统的自我声明，
**而审计要的恰恰是这个声明的依据。**

**4. 一个开源项目的仓库里有 `evals` 目录，你能不能在方案里写“评估能力由该组件提供”？**

参考答案要点：不能，要先看内容。本章那个例子里 `__init__.py` 全文是
“Coming Soon”。**目录名不是能力**——这条对任何依赖的第三方组件都成立。

**5. 官方文档主动写了“这个匹配器是简化版，接进生产合规门禁前请自行验证”。
你在方案里怎么处理这句话？**

参考答案要点：把它转成一条必须执行的验证动作，写进上线检查清单，
并留下验证记录。**主动披露的限制被当成免责声明读过去，是这类风险最常见的漏法。**
